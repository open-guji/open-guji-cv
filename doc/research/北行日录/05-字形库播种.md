# 字形库播种：字流证人对齐 × 字体模板，两路零同源互证

- **状态**：2026-09-16 打通链路，**小样本验证中**（7 页 OCR → 1,680 个标签）。
- **为什么要有这一步**：Step5-a `glyph_match` 的库是空的，54 页 2,515 格全判 `diff`；
  而 `seed_admit` 最强的几条通道都要「库里已有字形」或「整理本对齐字」，是个冷启动死结。
- **正本**：本卡。相关：`04-step4字框塌缩.md`（塌缩的字位会被 Step4 旗标挡在库外）。

---

## 一、冷启动死结怎么解开

`seeding.py` 开头那条纪律：**「库里的字是对的」是 100% 目标，不是统计目标**。
所以自动进库必须**两路零同源互证**，单路再准也不行。本书手上正好有两路：

| 路 | 来源 | 独立性 |
|---|---|---|
| **文本** | 校對本（同书现代排印本）→ 字流对齐给每个字位一个候选字 | 与图像无关 |
| **形状** | I.Ming 字体模板检索 top-1 | 与文本无关 |

两路一致才进库。证人错的字位，字体 top-1 几乎不可能恰好错成同一个字。

## 二、新写的一段：字流对齐 `witness_align_stream.py`

现成的 `witness_align` 是**列级**的（证人一行 = 刻本一列，项数相等就一一对应），
**同书异版对不上这个结构**——刻本 9 列 × 21 字无标点，校對本 17 列 × 14~16 字带标点，
换行完全不同。README 早就写了「不能套 `guji witness-align`」。

所以新写一条把两边都拉成**一维字流**：

- 刻本侧：Step3 的 `char` 格按阅读序（页 → 列右→左 → 格上→下），跳过版心与非 body 列；
- 证人侧：去页码行/脚注行/标点，只留汉字；
- **OCR top-1 当锚**，`difflib.SequenceMatcher` 求匹配块，**只收 `equal` 块且块长 ≥ 8**。

**OCR 只当锚，不当标签**——标签一律取证人字。`replace` 块里 OCR 与证人不一致，
可能是 OCR 错、也可能是两版异文（刻本「曾」作「會」、「遊」作「游」），
这一层分辨不了，**不猜，整块跳过**。

CLI：`guji witness-align-stream <book> [--min-block 8]`

### 实测（7 页 OCR，p3-8 + p30）

| 项 | 值 |
|---|---|
| 刻本字位 | 18,162（全书） |
| 证人汉字 | 18,306 |
| OCR 覆盖 | 1,977 个字位（7 页） |
| `equal` 块覆盖 | 2,039 |
| **给出标签** | **1,680**（块长 ≥8 那部分） |
| **标签处 OCR 与证人一致** | **1,680 / 1,680 = 100%** |
| 最长块 | 55 字 |
| 标签覆盖字头 | **655 个**（其中 353 个只有 1 例） |

最长那个 55 字块横跨 p30 col17-19，文本是
「十二日癸卯晴四更車行七十里飯新樂縣尤繁庶古鮮虞國也又四十五里宿中山府靖康之禍真定中山皆固守不下中山城外猶有敗城」
——与原图逐字核对相符。

## 三、踩到并修掉的一个坑：`source_kind` 写死 `'print'`

`seed_witness.py` 是给**现代排印本**写的，进库最后一句写死
`UPDATE sources SET kind='print'`。而 `candidates.GlyphKnnProposer` 默认
**只查 `kinds=("woodblock",)`**——刻本的书要是被记成 `print`，
**播进去的字形在候选检索里静默查不到**（不报错，只是永远没有候选）。

已改成参数 `source_kind`（默认仍是 `print`，现代链行为不变），
CLI 加 `--source-kind woodblock`，刻本必须显式传。

## 四、`norm_stroke=3` 是必须的，不是可选

`seed_witness` 的注释里就有这本书 2026-09-15 的实锤：不做笔宽归一时
「书块 4.6px vs 字体 2.7px，cov 0.6~0.8 量的是粗细」，字→宇、旦→且、宣→宜/直
每个实例都反，**字/旦/宣 一个都没进库**。

本轮独立复量（归一到 64×64 之后）：

| | 笔宽 p50 |
|---|---|
| 刻本字块 | **4.65px** |
| I.Ming 模板 | **5.73px** |

两边差 1.1px，`cov` 会把「粗细差」当成「形状差」。所以播种与 Step5-a
**必须用同一把尺子** `--norm-stroke 3`（两边都骨架化再细到 3px）。

⚠️ 但 `glyph_match` 的 `norm_stroke` 默认是 `None`（"刻本链保持 None"），
**播种用了 3、Step5-a 用 None 就是两把尺子**，库里的字配不上。
这一条要在跑 Step5-a 时显式对齐，见下。

## 五、第二个坑：字体库把半个 Unicode 扩展区也装进来了

第一轮播种：**1,625 个字位只进库 830，字体不认 795（49%）**——而 `seed_witness`
的注释说这个数应该在 8% 左右。查拒绝样本立刻看出问题：

```
witness=十  font_top1=𬂛  cov=0.972
witness=二  font_top1=𠄠  cov=0.955
witness=壬  font_top1=𡈼  cov=0.966
witness=卯  font_top1=𭅵  cov=0.937
```

字体 top-1 是**扩展区里的生僻异体**，跟常用字形几乎一模一样、码位不同。
40 个拒绝样本里 **25 个（62%）是这一类**。

**根因**：`charset.ranges.tsv` 是按语料扫出来的合法字表，包含大量扩展区字；
I.Ming 渲染出 **56,778 个字头，其中 29,991 个（53%）在 BMP 之外**。
这半个库对本书**只可能产生假 top-1**，不可能贡献正确答案：

| | |
|---|---|
| 校對本用到的不同汉字 | **2,074**，**全部在 BMP 内**（0 个扩展区） |
| BMP-only 字体库对它的覆盖 | **2,074 / 2,074 = 100%** |
| 丢掉扩展区损失的字 | **0** |

所以把本工作区字体库里的扩展区字头删掉（26,787 留存）。**这不是删数据**——
`kind='font'` 的字形本来就不进 Git、由字体档 + 字表确定性重建，
重新 `import-font` 随时能恢复。

⚠️ **这条对所有书都成立**：拿字体模板当形状证人时，库的字表应当收敛到
「这本书可能用到的字」，而不是整张合法字表。否则扩展区的生僻异体会持续顶掉
正确答案，而且**表现为「字体不认」而不是「字体认错」**——不看拒绝样本根本
不会发现，只会以为是图块质量差。

剩下那 15 个 BMP 内的拒绝是**真·形近字**（書/晝、未/末、酉/西、侍/待、仲/伸），
字体不认是**对的**——这正是互证该拦下来的东西，不要去放松它。

**效果**（同样 1,625 个字位、同样 `--norm-stroke 3`）：

| | 全量字表 | BMP-only |
|---|---|---|
| 字体认可 | 830 | **1,001** |
| 字体不认 | 795（49%） | **624（38%）** |

⚠️ **操作提醒**：`seed-witness` 是「先检索后写库」两阶段，写库阶段独占 SQLite。
我在它跑的时候去清库里的孤儿行，直接把写阶段撞成 `database is locked`（检索白跑十几分钟）。
**播种期间别碰 `glyph.db`**——控制台也开着连接，必要时先停。

⚠️ **`glyph-db drop-edition` 不清 `admissions` 台账**（踩了一轮）：
它删 `glyphs` / `instances`，但准入审计行留着。而 `admit_instance` 靠台账判重，
于是**重播时 1001 个字位全被当成 duplicate 跳过**，只补进新出现的那 114 个字头——
库看着「播过了」，其实少了一大半，而且**不报错**。
重播前要连台账一起清：`delete from admissions where instance_id like '<book>:%'`。

## 六、二值化重做（2026-09-16 晚，用户裁定）

用户定的口径：**最后进字形库的一定是二值的，灰度值会干扰；review 时看二值的也更好**。
此前两条进库路径存的都是缓存里的**灰度**裁片（189~203 个灰阶）。已全部重做。

### 6.1 三处共用同一把尺子

| 路径 | 改法 |
|---|---|
| 整页副本 | `guji binarize <book>` → `binarized/<book>/<page>.png`（Sauvola 31/0.2） |
| 播种进库 | `seed_witness(binarize=True)`（`--keep-gray` 可退回旧行为） |
| 人裁进库 | `consumers.glyphdb_admit(binarize=True)` |

**库里那张 = 人裁看的那张 = 播种进去那张**，不再是「各二值各的」。

### 6.2 🔴 修一个会**静默裁错字**的 bug

`?src=bin` 按 `bbox_page` 去二值页上裁，但 `bbox_page` 是**右上原点规范空间**
（x 向左递增），磁盘图是左上原点。必须 `x_img = (W-1) − x_canon` 且左右边界互换。

不翻的后果是**裁到另一个字**——y 一点不差、尺寸也对，看着像「图没对齐」，
不像「坐标系错了」。实测 `p3 c11 s11「鳳」`：bbox_page x=1467，真实位置 x=1243，
模板匹配一量就现形（score 0.973）。对照图里二值那一行原本是空白或别的字（雨/驛）。

⚠️ **这是我上一轮的疏漏**：当时在浏览器里只验了「URL 变了、图不裂」，
**没验裁出来的是不是那个字**。图像类改动必须比对像素内容，不能只看请求成功。
两条回归测试守着（含一条反面证据：不翻会裁到左边那个记号）。

27 个字头，全部严格 2 灰阶，字头与裁决逐字相符（鳳棲餞途周甫别閣晚…）。

### 6.4 浏览器逐类卡片验收（无头 Chrome，独立端口/profile）

- **定字裁决**：30 张卡、30/30 图加载、**全部走 `src=bin`**、切换按钮在
- **切分裁决**：4 张卡、13 条候选线、**4 种描边色**、整理本期望有值
- **无报错、无 4xx/5xx**
- 逐像素核对：乾道五年己丑 六个字，灰度与二值**同字**、与证人一致

⚠️ 量图片健康**必须先把 lazy 图滚进视口**（或临时改 `eager`）——无头模式不滚动时
`loading=lazy` 根本不发请求，看着是 0×0，会被误当成坏图。

### 6.5 复用组件

`BinaryToggleImage`（`components/common/`）：Step7 定字卡、异体组视图、夹注卡三处共用。
缩略图网格传 `showToggle={false}` 只吃缺省二值、不占地方。
各写一份的结果就是有的地方看二值有的看灰度，人对不上号。
