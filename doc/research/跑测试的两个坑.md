# 跑测试的两个坑（全仓通用）

- **状态**：告警，已复现；根因未定位
- **来源**：Step0-闸0 道 2026-09-09 报回，协调者复现证实

## 一、`pytest --collect-only` **会弄脏工作区**

全仓跑 `pytest --collect-only -s -q -p no:cacheprovider`（**只收集、不执行测试**）之后：

```
 M data/book2/profile.json
 M data/book3/profile.json
 ...
 M data/book8/profile.json      ← 七个都被改写
```

**协调者独立复现过**：跑之前 `git status data/` 干净，跑完就是上面这样。

- **单独收集 `tests/recognize-profile/test_recognize_profile.py` 不复现**（弄脏 0 个），
  所以不是那一个文件模块级代码那么简单——**只有全仓收集才触发**，
  疑似 conftest 或某个 import 链的连带作用。**根因未定位。**
- 后果：任何人跑一次全量收集，仓就脏了；**如果没注意，这七个文件可能被顺手 commit 进去**。

**处置（在根因查清之前）**：

1. **跑完全仓收集／全量测试，一律 `git status` 查一遍**，脏了就 `git checkout -- <路径>`。
2. 子会话的 `done` 单里若报「跑了全量测试」，**协调者复核时要顺带查工作区干不干净**。
3. 谁有空定位根因，就在这里补上。

## 二、`pytest` 不带 `-s` 会崩——**连 `--collect-only` 都要带**

`ValueError: I/O operation on closed file`（capture 收尾）。

**云端与本地都复现**，不是某台机器的毛病。此前只知道「跑测试要带 `-s`」，
Step0-闸0 道补了一条：**只收集也要带**。

## 三、顺带一处文档与实际不符

`precleaned/vol02/{151,152,153}.png` **已经在 git 里被跟踪**，
而模块文档说的是「是产物不是缓存，不会被 git 追踪」。
`--force` 重生成后与仓里版本逐字节一致，没有引入差异，
但**措辞要么改文档、要么改状态**，别让下一个人照文档推断错。
