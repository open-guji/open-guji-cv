## 一、先分清：哪些是真源，哪些可以重算

| 东西 | 在哪 | 真源？ | 现在怎么过机器 |
|---|---|---|---|
| 刻例（图块 + 定的字 + 来路） | guji-workspace `output/glyph_store/`（git） | **是** | git |
| 字形 db `output/glyph.db` | 各机本地 | 否，由 store `glyph-db rebuild` 重建，字体域再 `import-font` | 不传 |
| 人裁事件 `feedback/events/*.jsonl` | guji-workspace（git） | **是**（只追加） | git |
| 模型 `models/<名>/best.pt` | cv 仓（git，r5 18.8 MB） | **是**（重训要 GPU 数小时） | git |
| 训练 / 评测基准 `cache/glyph_bench` 等 | 各机本地 | 否，`build_glyph_bench.py` 从字形库确定性重建（固定种子） | 目前靠 `_shared/train_bundle.zip` 手工打包 |
| 产物 products、缓存 cache、emb 缓存 | 各机本地 | 否 | 不传；靠指纹判过期（checkpoint、库指纹都已在指纹里） |

所以两台机器之间真正要保持一致的只有三样东西：**刻例真源、事件、模型**，三样都已经在 git 里。
难点不在「怎么传」，而在下面三个现在会出问题的地方。

## 二、现在会出问题的三个地方（都实际撞见过）

1. **db 领先 store**：人裁进库只写 db，store 要有人记得跑 `snapshot_glyph_store.py` 才会导出。
   09-25 实测四庫有 820 条人裁只在 db 里，北行整本从没导出过。另一台机器 pull 下来，看到的是旧库，而且**不会报错**。
2. **两台机器都写库**：GPU 机上用新模型重跑管线，自动准入会往它本地的 db 里写。
   这些写入回不到服务器；反过来服务器上的新人裁，GPU 机也看不到。store 是整表导出，两边都导出再合并，git 冲突是按行的，会出现静默丢行。
3. **模型和它的训练数据、阈值脱节**：
   - 训出来的 checkpoint 不记是在哪个库快照上训的。
   - 换 checkpoint 要连着重标三个阈值（`models/README.md`），不重标，闸会**静默关死**：r4→r5 实测放行率 76% → 0.6%。
   - 这些现在全靠人记得。

## 三、方案：每样东西只有一台机器能写

| 东西 | 唯一写入机 | 另一台怎么拿 |
|---|---|---|
| 字形库（store / db） | **云服务器**（人裁、控制台都在这） | GPU 机 `git pull` → `glyph-db rebuild` → 只读用 |
| 人裁 / 机器判定事件 | 两台都可追加 | 事件是只追加的 jsonl、按批次分文件，git 合并天然安全；**库的改动一律由服务器消费事件产生** |
| 模型 | **GPU 机**（训练） | 服务器 `git pull` cv 仓；换现役是一次「模型发布」提交 |

要点：
- **GPU 机不直接写库**。它若要往库里加东西（比如新模型下重跑后的自动准入），就产出**事件**推回，由服务器消费进库。
  这和现在控制台裁决的路子一样：事件 → 路由 → 消费者。于是库永远只有一个写入口。
- **每次训练都记下吃的是哪个库快照**：
  - store 目录的内容哈希；
  - guji-workspace 的 commit；
  - bench 哈希；
  - cv 代码的 commit。
  这四样写进 `models/<名>/meta.json`。之后任何产物、任何数字都能追到「哪个模型 × 哪个库」。
- **服务器上训练期间的新人裁不会丢**，只是没进这一版模型；下次训练自然吃到新快照。
  「一致」的意思是可追溯，不是时时相等。

## 四、要做的三件事（等点头）

1. **store 自动导出**（治第一个问题）
   - 服务器上加 systemd 定时器（和控制台同一套托管），每 30 分钟跑一次：`snapshot_glyph_store.py --force`（对两本书）→ 有变化就 commit、push guji-workspace。
   - 同时在 `glyph-db stats` 和控制台总账页亮「store 落后 db N 条」。现在已经有这条告警，只是要人去看。
2. **GPU 机只读保护 + 同步检查**（治第二个问题）
   - 环境变量 `GUJI_GLYPH_READONLY=1` 时，`GlyphDB` 的一切写操作直接报错。GPU 机上默认设它。
   - 新命令 `guji sync-check`，逐项核对：
     - 本机 db 与 store 行数、内容哈希一致；
     - 工作区仓、cv 仓没有未推的提交；
     - 现役 checkpoint 与 cv 仓 `models/` 一致；
     - 本机 bench 的来源快照等于当前 store。
   - 训练前、换模型后各跑一次，不一致就拒绝开跑。
3. **模型发布流程**（治第三个问题）
   - `scripts/release_model.py`，一次做完：
     - 写 `meta.json`（库快照 / 代码 commit / bench 哈希 / 关键指标）；
     - 用新 checkpoint 把要重标的三个阈值扫一遍，出建议值；
     - 提交 `best.pt`、meta、阈值改动。
   - 服务器 pull 之后，产物因 checkpoint 指纹自动过期、重跑，再重跑一次字形库体检。
   - 单个模型文件超过 100 MB（GitHub 上限）时改走 GitHub Release 附件，`models/manifest.json` 记下载地址与 sha256。
     现在 r5 只有 18.8 MB，用不着。

## 五、不做的

- **不同步 db 文件本身**：1 GB 的二进制，git 存不了；rsync 两边都写还会互相覆盖。db 永远从 store 重建。
- **不同步 products / cache**：各机重算；指纹会判定过期。
  GPU 机要省时间，可以单向 rsync 服务器的 cache 过去当加速，但那不是真源，丢了照样重算。
- **不上数据库服务器 / 对象存储**：现在的量（store 两本合计 67 MB、增量小）git 完全扛得住，也符合「机器产物存免费本地」的约定。
