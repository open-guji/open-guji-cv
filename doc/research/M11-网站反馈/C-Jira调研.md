## 0. 三句话结论

1. M8 把流程定成「平台粗校 → 0.1.0 → 平台精校 → 1.0.0 → 网站持续反馈（1.x…2.0）」，第三段就是 M11。M8 里真正做出来的「公众回路（工作包 5，子对话 E）」服务的是**第二段精校**（`/proofing` 精校页、`/api/cellreview`、AI 落裁决）。第三段只做了入口（阅读页「改字」`/api/charfix`、专名意见），**还没有后台处理**。
2. 网站上现在有**三条互不相通的反馈通道**：①M6 旧通道 `/api/feedback`，选中文字报错，带 `/feedback` 公开页、管理页「标记已改」，并有 feedback-route 转成 GitHub issue；②`/api/cellreview`，精校页的六档意见；③`/api/charfix`，1.0 之后阅读页改字和专名意见。只有②接进了中心库（proofing-sync Action 加 `web_opinions.py --from-db`）；①走 GitHub issue，③只存在 KV 里，没人消费。
3. 「机器上报」和「字形库深度自检」在 M8 里只做到 1.0.0 的出口闸，不是持续流程。字形库体检（glyph_selfcheck）有「结果过期、不带库指纹」的已知缺陷（GUJI-623 评论）。「重跑后旧裁决按格位继续生效」也没修（GUJI-623）。重跑对比只做过一次性的「第一册重跑对比定字」页（GUJI-624 末条评论）。

## 1. M8 定下的整体流程

### 1.1 阶段划分（GUJI-543 用户原文，10-16 12:25 PDT 建卡）

> 1. 平台粗校：完全由脚本 cv 完成，跑完全部流程，少许 AI 参与。希望达到须人审<1% 或更低。……
> 2. 平台精校：由人来反馈平台粗校阶段，脚本无法确定的部分。……我觉得这一部分要加到我们的开源古籍网站上，让任何人都可以帮助反馈。这一部分完成之后，guji-workspace 这个 book 就可以归档或者删除了。
> 3. **网站反馈：经过 1-2 两步，能够快速判断的都已经判断过了。剩下的是一个长期挑错、修改的过程。可能是之前自动放行的有错误，可能是之前人的判断有错误。剩下的就走一个独立的流程。不再写到 guji-workspace。文字判定、以及标点、专名识别都在这个流程里。也在网站上操作。**

> 标准 3：**网站持续反馈。从这里文本可以从 v1.0.0 逐渐增加版本号，不断提高。注意文本、标点、专名号有分开的版本号。v2 应该是达到出版级。**

> 网站设计 2：**精校完成之后。一个 book 的校对页面变成了不太一样的。首先分成文字、标点、专名三个部分。文字部分应该是对置信度不够高的文字，提示用户可以重新判断，或者是用户可以在阅读过程中主动提出修改意见，这里可以变成一个讨论区。** 标点、专名如何反馈我们之后再说，先集中在文字上。

> override：……平台粗校或精校有的时候会发现一些问题，如正文识别成小注，或反之，有字格识别成无字或反之，甚至整列切分错误。……要允许平台粗校或精校过程中，强行 override 一些 cv 流程中的决定……这些决定后续应该作为训练的标注。

设计 v0.8（ai-team `team/整理/设计/文本整理三阶段流程.md` §0）一句话：
> **平台粗校（脚本＋CV，出文本 0.1.0）→ 平台精校（人逐格过疑难字，出文本 1.0.0，之后归档工作区）→ 网站持续反馈（文字、标点、专名各自升版本，2.0.0＝出版级）。** 前两段的数据在 guji-workspace；第三段不再写 guji-workspace，只在 book-text 与网站上走。

§1 三段总表里第三段的写法：谁做是「公众＋团队长期挑错、讨论」；数据在 `book-text（char／decision／punct／entity）＋网站反馈库`；在网站上操作；出口「文本 1.x；标点、专名各自 1.x；2.0＝出版级（另有流程，现在不管）」；完成标准写的是「不收口，持续」。

**10-19 的改动**：「公众卡片改进」线程按用户 10-19 的意见（设计 `待审单与公众意见走中心库.md`）改了做法：
> 待审单、公众意见、由意见落成的裁决都只在中心库……book-text 只在出版本时变。……1.0 之后读者反馈也不写 book-text，攒批出版本即可。

这和 §6.3 原写的「走 G 块提交→初审→终审→批次合入 book-text」不一致。设计 F 节写了「回改三阶段文档 §6.3」，**还没回改**。

### 1.2 版本号规则（用户 10-16 16:2x PDT 当面批准，GUJI-543 评论 13137；规范 book-text#148、guji-format#18/#19）

| 版本 | 含义 |
|---|---|
| 0.1.0 | 粗校完成，可以并 main 上网站（带 banner，`proofing: true`） |
| 0.x.0 | 精校进行中，每合一批人裁升一次 minor |
| 1.0.0 | 精校完成（F1–F5） |
| 1.x | 第三段：文本、标点、专名三条线各自升版 |
| 2.0.0 | 出版级（另有流程，现在不管） |

- 标点、专名在文本 1.0.0 之后才正式开工。0.x 阶段允许「试跑、不入库」。
- `text_version` 的同步：由改文本的那个 PR 把伴生层 `text_version` 跟上，伴生层自己的版本不升（Tristan，评论 13163）。
- `proofing`（布尔）：放在 book-text `index.json` 的 `chapters[]` 里。0.x 时必须为 true，1.x 也可以写 true。写入工具 `bump_original.py --proofing on|off`。
- vol02、vol03：保留按旧定义定的 1.0.0，以后补走精校，合入算 minor。
- 每本书固定一个 CV 版本（§2a）：册配置写 `cv_version`，cv tag 为 `vX.Y.Z`（10-17 用户定去掉 `cv-` 前缀）。冻结基线规矩见 GUJI-601（用户 10-18 定）：到了 0.1.0 或 1.0.0 的册登记冻结基线，不随 cv 升版重跑。
- 第三段改字属类型 A（格号不变）：走「合入 PR 的 CI」自动核（F-OV-02 扩到 entity，book-text#149），PR 里报「标点 pre_char 对不上 N 条、实体失效待看 N 条」，N>0 才要人看。重切或补页属类型 C／D，走 GUJI-541 的对照表流程。

### 1.3「公众回路 E」是什么

M8 拆分（GUJI-567 评论 13729，Jira 10-17 17:17 PDT）：33 张任务 GUJI-568～600，编号 M8·1.1～7.4，7 个工作包；后来又加了工作包 8 中心库（602–611），合计「7+1」。执行按「子对话」分线：B＝CV 统一窗口，C＝重跑，**D＝精校检查／1.0.0 验收**，**E＝公众回路**，F＝补精校，G＝归档，另有中心库线程。

- **公众回路（E）＝工作包 5（M8·5.1–5.5，GUJI-589～593）**，内容是：网站精校页收公众意见 → 每日导入 → H 道（AI）逐条看图，自动落正式裁决 → 有问题的列给用户 → 单页重跑 → 导出 0.1.x → 网站可见。它接手了 P0 的 GUJI-551／552／553 和 P1 的 GUJI-561。
- GUJI-567 评论 13954（10-18 19:47 PDT）：「vol01：……下一步是**待审格走公众回路（E）**和 **1.0.0 验收（D，GUJI-597）**」。
- 设计 §6.2 原文（v0.4，用户 10-16 晚定）：
  > **H 道（AI）逐条过一遍公众意见，自动落正式裁决**，不设「几人一致」的投票门槛；**AI 觉得有问题的（看图不支持、意见互相冲突、疑似刷票、规则说不清的个案）列清单给用户看**，将来再定要不要加团队一级。
- 公众页六档选项 → 正式裁决（Eliot 13141，Mila 13141 同意）：`char`→confirm；`none`→not_a_char；`unsure`→不写，只计数；`cut`→seg_defect（不自动）；`jiazhu`／`main`→seg_defect＋reason（不自动）。公众不给 `damaged`。页面提交 `shown`（机器当时读的字），和 rev 产物对不上的意见丢弃。

## 5. 流程断点、用户偏好与定论

### 5.1 流程断点（读卡和评论得出）

1. **三条反馈通道互不相通**（`/api/feedback`、`/api/cellreview`、`/api/charfix`）。旧通道选中文字报错后走 GitHub issue，由文本块人工改，再用 `resolvedRef` 回写，没有 AI 判断；charfix 只进 KV，没有消费者；只有 cellreview 接进了中心库。用户说的「报错页面让用户讨论」就是 M6 的 `/feedback` 列表，只有回复（reply），没有讨论串（GUJI-561 Mason 的对比结论是暂不做）。
2. **1.0 之后改字怎么落地，前后口径不一致**：设计 §6.3 写的是「批次合入 book-text、文本线 patch、CI 核」；10-19 新设计写的是「读者反馈不写 book-text、攒批出版本」，裁决事件在中心库。但已冻结、已归档的册（vol01 的 freeze）怎样从事件生成新的 1.x 文本，没有写明：直接改 char.json，还是恢复工作区重导？M10 又说「1.0 之后不再重跑 pipeline」。
3. **裁决锚定的是 rev 快照工作区**（设计 §5.2 第 1 条）。1.0 之后工作区要归档或删除，AI 落裁决要先 `guji archive fetch` 恢复。书影落点未定（GUJI-598），恢复链条不完整。
4. **重切后旧裁决按格位继续生效**（GUJI-623），这正好是「部分重跑、旧数据不能全丢」的反面：旧数据错误地压住新结果。绑定表的 valid／rebound／stale 机制只对带锚事件有效，vol01 有 682 条早期老裁决没有锚（GUJI-543 Eliot 13134）。
