# cv 仓版本号规矩

> 来源：GUJI-491b 第 6 步。Mila 2026-10-16 审定，据 ai-team `team/CV/版本号规矩-初稿.md` 定稿；同日据 Owen 提醒改 tag 名（见第一节）。
> 时间一律洛杉矶时间。

## 一、格式

- 版本号采用 `MAJOR.MINOR.PATCH`（语义化版本的子集），文中写作 `vMAJOR.MINOR.PATCH`，如 `v1.0.0`。
- **基线 `v1.0.0` = 重写后 main `26657f84`**（2026-10-16 分 7 段重写后的历史）。重写前的历史不再编号。
- **git tag 名一律加 `cv-` 前缀**：`cv-v1.0.0`、`cv-v1.1.0-rc.1`。原因：`.github/workflows/release.yml` 对 `v*` 的 tag 推送会自动打包并**公开发布 GitHub Release**；以 `cv-` 开头的 tag 不触发它。要不要真的公开发版是另一件事，由用户定，定了再改 release.yml 或另行打 `v*` tag。
- 只用 **annotated tag**；tag 一经推送不改、不删、不挪。要修正就发新 PATCH。
- 预发布（窗口候选）用 `cv-vX.Y.Z-rc.N`，如 `cv-v1.1.0-rc.1`。rc 只用于窗口候选验收，正式版本不得以 rc 为依据。

## 二、怎么升版

| 变化 | 升哪一位 | 例子 |
|---|---|---|
| 默认输出会变（admit、verdict、字形库落点、放行结果等已发布产物的结论会变） | MAJOR | 改 seed_admit 默认规则，已放行格的结论会变 |
| 破坏性改动：manifest／产物格式、目录结构、CLI 参数不兼容 | MAJOR | manifest 字段语义改变、旧产物不能被新代码读 |
| `code_hash` 变，但默认输出不变（新功能、开关默认关） | MINOR | 新增 S8 看图脚本、新开关 `variant_tie_margin`（默认关） |
| 新增工具、评测、脚本、文档（不影响任何 Step 的 `code_hash`） | MINOR | 新 `freeze_check.py`、新 research 目录 |
| 修 bug 且默认输出不变，或仅修测试、文档、注释 | PATCH | 修 `zl.py` 的边界错误，结果不变 |

- **`code_hash` 变但默认输出不变＝MINOR**。这会让各书已有产物判为过期，因此 PR 描述**必须写明哪几个 Step 的 `code_hash` 变了**。
- **默认输出变＝MAJOR**。
- 拿不准时往大的升，并在 PR 描述里写明理由。
- 同一个 PR 含多类改动时，按最大的一类升。

## 三、谁打 tag

- 只在 **main** 上打 tag；分支上不打。
- 打 tag 前：CI 绿、PR 已合并、`code_hash` 已按窗口规矩核过（如有窗口在跑）。
- **正式 tag 由 Owen 打**，经理（Mila）批准后做，写入任务卡。冻结期内不打正式 tag，除非 Mila 明确说明。
- **rc tag 由窗口负责人打，Mila 复核。** rc 只用于窗口候选。
- 推任何以 `v` 开头的 tag 之前，先确认 release.yml 的触发条件；会触发公开发版的名字，必须用户本人点头。

## 四、产物如何记录版本（manifest，窗口甲后再加）

- manifest 新增两个字段（**窗口甲后再加，本次不改**）：
  - `cv_version`：生成产物的代码所对应的最近一个 tag 的版本号（去掉 `cv-v` 前缀），如 `"1.0.0"`。
  - `cv_commit`：生成产物时的完整 commit sha。
- 非 tag 版本生成的产物，`cv_version` 写 **`最近 tag+N`** 形式，如 `"1.0.0+12"`，表示在 v1.0.0 之后 12 个提交。
- 有 `cv_version` 的产物，才能被视为可对比、可复现。
