# cv 仓版本号规矩

> 来源：GUJI-491b 第 6 步；Mila 2026-10-16 初定。2026-10-17 据用户意见定稿（去 `cv-` 前缀、MINOR／PATCH 口径、滚动发版；同日再据用户更正，Step `code_hash` 变化本身不算 MINOR）；2026-10-18 用户定待发分支流程、MINOR 收紧为「值得多数册重跑」，依据 ai-team `team/CV/Mila决定-10-14.md` 末节「版本规矩定稿」。
> 时间一律洛杉矶时间。

## 一、格式

- 版本号 `MAJOR.MINOR.PATCH`（语义化版本的子集），git tag 写作 `vX.Y.Z`，如 `v0.2.0`。
- 基线 `cv-v0.1.0` = 重写后 main `26657f84`（2026-10-16），**旧 tag 保留作历史，不动**；此后的版本一律不带 `cv-` 前缀。重写前的历史不再编号。
- 只用 **annotated tag**；tag 一经推送不改、不删、不挪。要修正就发新 PATCH。
- 预发布用 `vX.Y.Z-rc.N`；rc 只用于验收，正式版本不得以 rc 为依据。
- 改动先合进待发分支 `rc/vX.Y.Z`，发版时再合进 main（第三节）；**rc tag 打在待发分支上，不打在 main 上**（第六节）。
- 旧的 `release.yml`（exe 打包／自动公开发布）已停用，移至 `doc/archive/release.yml.legacy`，推 tag 不再触发构建。GitHub Release 页由 Owen 手动建（目前无发布物）。

## 二、怎么升版（0.x 阶段；用户 2026-10-18 收紧）

| 档 | 条件 |
|---|---|
| **MINOR**（0.X.0） | **只有一类：对大部分册来说值得重跑一遍的升级**——核心算法改进、重大性能提升、改了多数册的缺省输出。升 MINOR 前先问用户 |
| **PATCH**（0.x.Y） | 其余一切：bug 修复、调参、重构、测试、文档、依赖／打包；**新增 CLI 命令、参数或入口**；缺省关的新功能和新开关；Step 的 `code_hash` 变了但缺省输出不变的改动 |
| **MAJOR** | 近期不升；到格式与流程稳定、定 1.0 再议 |

- 尽量少升 MINOR。拿不准就按 PATCH，在 PR 描述里写明理由。
- `code_hash` 变化**不决定档位**，但**必须登记**：它会让各册已有产物判为过期，PR 描述和 CHANGELOG 要写明哪几个 Step 的 `code_hash` 变了（合前实算，对比合并前的待发分支），便于判断是否重算。

## 三、待发分支与发版节奏（用户 2026-10-18 定）

1. **任何时候都有一条待发分支** `rc/vX.Y.Z`：版本号缺省是上一个正式版的 PATCH 加一（`v0.3.0` 发了，待发就是 `rc/v0.3.1`）。它从 main 开出，所有改动都合进它，**不直接合 main**。
2. **每个功能在自己的分支上做**（`feat/<名>`、`claude/<名>` 均可），从待发分支开出，PR 目标是待发分支。待发分支的 CHANGELOG 顶上有一节 `## [X.Y.Z] - 待发`，PR 只在这一节下加一行、写明档位，不另起版本节，也不改 `pyproject.toml` 的版本。
3. **合进待发分支的门槛：不破坏现有流程。** 默认每个合进来的 PR 随时都可能被发出去，所以：
   - 新行为缺省关（册 yaml 或参数开关控制），关着时输出逐字节不变；
   - 全量测试过；改了哪几步的 `code_hash` 写清楚；
   - 不用管和别人的改动相不相关；**做了一半也可以合**，只要关着不影响流程。
4. **谁都可以发 PATCH**：觉得一波东西做完了，就把 `## [X.Y.Z] - 待发` 的「待发」改成发版日期，待发分支合进 main，在 main 的合并提交上打 `vX.Y.Z`（第 6 条）；然后从 main 开下一条待发分支 `rc/vX.Y.(Z+1)`（CHANGELOG 顶上加 `## [X.Y.(Z+1)] - 待发`），把还开着的 PR 改目标到新分支。发 PATCH 不用再问用户，打完在项目里说一声。
5. **要升 MINOR 时**：先尽快把当前待发分支按 PATCH 发出去，再从 main 开 `rc/vX.(Y+1).0` 作为新的待发分支。MINOR 发版前做组合验收（第六节）并出 L1 影响报告（GUJI-576 评论）。
6. **谁来打 tag**：云端会话没有推 tag 的权限（HTTP 403），tag 统一经总管请 Owen 在服务器上打；消息写清仓、提交全 sha、tag 名和命令，他打完用 `git ls-remote origin 'refs/tags/<tag>*'` 核对。只用 annotated tag，打了不改不删。

## 四、记录分工：CHANGELOG、Release note、内部跟踪（用户 2026-10-17 定）

- **`CHANGELOG.md`（仓根）＝完整记录，含 PATCH**：Keep a Changelog 风格，每个版本一节（PATCH 也有）。动代码的 PR 在待发分支的 `## [X.Y.Z] - 待发` 下加一行；发版时把「待发」改成日期（第三节）。
- **`RELEASES.md` 小节＋GitHub Release＝仅 MINOR**：release note 按 **Added／Changed／Fixed／Removed** 分条，每条一行，不写内部票号长文，影响清单写明哪几步 `code_hash` 变了。

| 档 | 打 tag | `CHANGELOG.md` | `RELEASES.md` 小节 | GitHub Release | 内部跟踪 |
|---|---|---|---|---|---|
| **MINOR** | 打 | 写 | 写一节 | 建（Owen 手建，正文即 release note） | 登记 |
| **PATCH** | 打（版本号照升） | 写 | **不写** | **不建** | 登记 |

- **内部跟踪**登记在 ai-team `team/CV/各册产物cv版本登记.md` 和台账：版本、sha、`code_hash` 是否变、哪些步指纹变、产物是否过期。

## 五、产物如何记录版本（manifest，窗口甲后再加）

- manifest 新增两个字段（**窗口甲后再加，本次不改**）：
  - `cv_version`：生成产物的代码所对应的最近一个 tag 的版本号（去掉 `v`／`cv-v` 前缀），如 `"0.2.0"`。
  - `cv_commit`：生成产物时的完整 commit sha。
- 非 tag 版本生成的产物，`cv_version` 写 **`最近 tag+N`** 形式，如 `"0.2.0+12"`。
- 有 `cv_version` 的产物，才能被视为可对比、可复现。

## 六、MINOR 的组合验收（用户 2026-10-17 定，10-18 并入第三节的待发分支）

MINOR 分支里常常装着好几个改同一 Step 的功能，单项过不等于合起来没事：

1. **单项验收**：每个改缺省输出的功能自己跑一次 A/B（`guji exp`，A＝开关全关、B＝开），上游用同一份快照，只重跑受影响的步。报告写清：目标对象变了多少、放对放错多少；目标之外的格是否逐格不变；改了哪几步的 `code_hash`。
2. **组合验收**：都合进 `rc/vX.Y.0` 之后，再做一次全关对全开的 A/B，受影响的步只重算一遍。
3. **打 rc**：`vX.Y.0-rc.N` 表示待发分支在这个点上通过了组合验收；不过就在分支上修，出 `rc.N+1`。rc tag 打在待发分支上，不打在 main 上。
4. **正式版**：组合验收通过后待发分支合进 main，在 main 的合并提交上打 `vX.Y.0`；含 rc 以外的改动要再验。
