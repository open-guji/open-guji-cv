# cv 仓版本号规矩

> 来源：GUJI-491b 第 6 步；Mila 2026-10-16 初定。2026-10-17 据用户意见定稿（去 `cv-` 前缀、MINOR／PATCH 口径、滚动发版；同日再据用户更正，Step `code_hash` 变化本身不算 MINOR）；2026-10-18 用户定待发分支流程、MINOR 收紧为「值得多数册重跑」；2026-10-20 用户改为 dev 集成分支＋发版时切 rc（第三节），依据 ai-team `team/CV/Mila决定-10-14.md` 末节「版本规矩定稿」。
> 时间一律洛杉矶时间。

## 一、格式

- 版本号 `MAJOR.MINOR.PATCH`（语义化版本的子集），git tag 写作 `vX.Y.Z`，如 `v0.2.0`。
- 基线 `cv-v0.1.0` = 重写后 main `26657f84`（2026-10-16），**旧 tag 保留作历史，不动**；此后的版本一律不带 `cv-` 前缀。重写前的历史不再编号。
- 只用 **annotated tag**；tag 一经推送不改、不删、不挪。要修正就发新 PATCH。
- 预发布用 `vX.Y.Z-rc.N`；rc 只用于验收，正式版本不得以 rc 为依据。
- 三种分支（第三节）：**`dev`** 是日常集成分支，所有 PR 都投它；**`rc/vX.Y.Z`** 是准备发版时从 dev 切出来的测试分支；**`main`** 只接发版（rc 合进来）。tag 打在 main 的发版合并提交上。
- 旧的 `release.yml`（exe 打包／自动公开发布）已停用，移至 `doc/archive/release.yml.legacy`。**新的 `.github/workflows/release.yml`（用户 2026-10-23 定）**：推 `vX.Y.Z`／`vX.Y.Z-rc.N` tag 时自动构建执行包（wheel ＋ 资源包 ＋ `install_release.py` ＋ `SHA256SUMS`）挂到该 tag 的 GitHub Release，没有 Release 就建（rc 标 prerelease）。装法见 README「用发版附件安装」，设计见 `doc/design/发版附带Python执行包.md`。

## 二、怎么升版（0.x 阶段；用户 2026-10-18 收紧）

| 档 | 条件 |
|---|---|
| **MINOR**（0.X.0） | **只有一类：对大部分册来说值得重跑一遍的升级**——核心算法改进、重大性能提升、改了多数册的缺省输出。升 MINOR 前先问用户 |
| **PATCH**（0.x.Y） | 其余一切：bug 修复、调参、重构、测试、文档、依赖／打包；**新增 CLI 命令、参数或入口**；缺省关的新功能和新开关；Step 的 `code_hash` 变了但缺省输出不变的改动 |
| **MAJOR** | 近期不升；到格式与流程稳定、定 1.0 再议 |

- 尽量少升 MINOR。拿不准就按 PATCH，在 PR 描述里写明理由。
- `code_hash` 变化**不决定档位**，但**必须登记**：它会让各册已有产物判为过期，PR 描述和 CHANGELOG 要写明哪几个 Step 的 `code_hash` 变了（合前实算，对比合并前的 dev），便于判断是否重算。

## 三、分支与发版流程（用户 2026-10-20 定：dev 集成、发版切 rc；取代 10-18 的「待发分支」）

```
 feat/…、claude/… ──PR──▶ dev ──（准备发版时切出）──▶ rc/vX.Y.Z ──（测完，merge commit）──▶ main ＋ tag vX.Y.Z
                          ▲                               │
                          └────── rc 上的修复合回 dev ──────┘
```

1. **`dev` 是默认的集成分支。** 每个功能在自己的分支上做（`feat/<名>`、`claude/<名>` 均可），从 dev 开出，**PR 目标是 dev**。不直接合 main，也不往 rc 合新功能。
2. **合进 dev 的门槛不变：不破坏现有流程。** dev 随时可能被切出去发版，所以：
   - 新行为缺省关（册 yaml 或参数开关控制），关着时输出逐字节不变；
   - 全量测试过；改了哪几步的 `code_hash` 写清楚（对比合并前的 dev）；
   - **做了一半也可以合**，只要关着不影响流程。
   - CHANGELOG：dev 顶上有一节 `## [未发版]`，PR 只在这一节下加一行、写明档位；不改 `pyproject.toml` 的版本。
3. **准备发版时从 dev 切 rc。** 谁觉得一波东西可以发了，就：
   - 在 dev 上提交一次：把 `## [未发版]` 改成 `## [X.Y.Z] - 测试中`，顶上再加一节空的 `## [未发版]`；
   - 从这个提交开 `rc/vX.Y.Z`（版本号按第二节定档；PATCH 不用问用户，MINOR 先问）；
   - 在项目里说一声「vX.Y.Z 已切，rc/vX.Y.Z 只收本版修复」。**切出之后大家照常往 dev 交 PR**，那些改动进下一版。
4. **在 rc 上测试。** 全量测试；要验的册跑一遍（MINOR 做第六节的组合验收）。发现问题：
   - 修复的 PR 投 `rc/vX.Y.Z`，合进去之后**同一个修复再合回 dev**（把 rc 合进 dev，或同一改动另开 PR 投 dev），不能只修 rc；
   - rc 上**只收本版的修复**，不收新功能。
5. **发版。** 测完没问题：
   - 在 rc 上把 `## [X.Y.Z] - 测试中` 改成发版日期，`pyproject.toml` 版本改成 `X.Y.Z`；
   - 开 PR 把 `rc/vX.Y.Z` 合进 main，**用 merge commit（不要 squash）**，这样 main 的历史里有 rc 的提交，下一次 rc 合进 main 时不会冲突；
   - **在 main 的这个合并提交上打 `vX.Y.Z`（第 7 条）。打了 tag 才算发完**：rc 合进 main 之后没打 tag 的，这一版不算发出，不宣布、不钉册；
   - 打完跑 `python scripts/check_release_tags.py`（第 9 条），返回 0 再往下；
   - **把 main 合回 dev**（带回日期和版本号的改动），之后 rc 分支不再收改动。rc 分支暂时保留不删（用户 2026-10-20 定），删不删以后再定；删了也不影响查版本，版本一律以 main 上的 tag 为准。
6. **main 只接发版。** 平时不直接往 main 合 PR（10-20 之前 hanzi 库几个 PR 直接合了 main，发 v0.4.8 时补并进来，以后不再这样）。
7. **谁来打 tag**：云端会话推 tag 是 403，用中转站：ai-team 仓 `python3 process/tag.py open-guji/open-guji-cv <main 上合并提交的 40 位 sha> vX.Y.Z "<说明>"`（见 ai-team `通用/协调者通讯.md`「打 git tag」）。中转站只给默认分支上的提交打 tag，所以 rc tag（`vX.Y.Z-rc.N`）要打的话找 Ops。只用 annotated tag，打了不改不删。
8. **合 PR 之前先跑** `python scripts/check_rc_target.py <目标分支>`：目标是 `dev` 返回 0；目标是 rc 时，该版已发（远端有 `vX.Y.Z`）返回 1，不是最新一条 rc 返回 2，还能收修复返回 0 并提醒「rc 只收本版修复，记得合回 dev」；目标是 `main` 返回 4（只有发版 PR 才投 main）。M8 有两批 PR 因合进已发的 rc 丢了（靠 #206、#265 补回），这条检查就是防这个。
9. **发版后核对 tag**（用户 2026-10-20 定：每个 rc 发进 main 后，main 上都要有对应的 tag，以后按版本号就能找到是 main 的哪个提交）：`python scripts/check_release_tags.py`（加 `--list` 列出每个版本对应的 main 提交）。它把 main 主线上标题提到 `rc/vX.Y.Z` 的提交认作该版的发版提交：已发却没 tag 的、tag 不在 main 主线上的返回 1；还在测试中的 rc 不算缺。发版 PR 的标题因此**必须写 `rc/vX.Y.Z`**（照现在的「发 vX.Y.Z：rc/vX.Y.Z 合进 main」写）。经理巡检时也跑一次，查出缺的就按第 7 条补打。
10. **按版本找代码**：
    - 某版在 main 的哪个提交：`git fetch --tags origin && git rev-list -n1 vX.Y.Z`（或 `git show vX.Y.Z`）；
    - 某个提交最早进了哪一版：`git describe --contains <sha>`，或 `git tag --contains <sha> 'v*'`；
    - 产物是哪版代码出的：看 manifest 的 `cv_version`（第五节）。

## 四、记录分工：CHANGELOG、Release note、内部跟踪（用户 2026-10-17 定）

- **`CHANGELOG.md`（仓根）＝完整记录，含 PATCH**：Keep a Changelog 风格，每个版本一节（PATCH 也有）。动代码的 PR 在 dev 的 `## [未发版]` 下加一行；切 rc 时改成 `## [X.Y.Z] - 测试中`，发版时改成日期（第三节）。
- **`RELEASES.md` 小节＋GitHub Release＝仅 MINOR**：release note 按 **Added／Changed／Fixed／Removed** 分条，每条一行，不写内部票号长文，影响清单写明哪几步 `code_hash` 变了。

| 档 | 打 tag | `CHANGELOG.md` | `RELEASES.md` 小节 | GitHub Release | 内部跟踪 |
|---|---|---|---|---|---|
| **MINOR** | 打 | 写 | 写一节 | 建（附件由 workflow 自动挂；Owen 在该 Release 上补写正文即 release note） | 登记 |
| **PATCH** | 打（版本号照升） | 写 | **不写** | 自动建，**只有附件和一行说明**，不写 release note | 登记 |

- **内部跟踪**登记在 ai-team `team/CV/各册产物cv版本登记.md` 和台账：版本、sha、`code_hash` 是否变、哪些步指纹变、产物是否过期。

## 五、产物如何记录版本（manifest）

- manifest 每条记录有两个字段（GUJI-577 起写入；之前的老条目没有，读成空）：
  - `cv_version`：生成产物的代码所对应的最近一个 tag 的版本号（去掉 `v`／`cv-v` 前缀），如 `"0.2.0"`。
  - `cv_commit`：生成产物时的完整 commit sha。
- 非 tag 版本（dev、rc 分支、任意提交）生成的产物，`cv_version` 写 **`下一个 PATCH.devN+g<12 位 hash>`**（PEP 440），如最近 tag 是 v0.5.9、往后第 12 个提交 → `"0.5.10.dev12+g1a2b3c4d5e6f"`（2026-10-23 起；之前写 `0.5.9+12`，不带 hash，老产物照旧）。`open_guji_cv/` 下有没提交的改动时本地段再加 `dirty`：`"0.5.9+dirty"`、`"0.5.10.dev12+g1a2b3c4d5e6f.dirty"`。浅克隆或没拉 tag、算不出离 tag 多远时写 `"dev+g<12 位 hash>"`。
- **正式版**＝三段数字（`0.5.9`）。只有正式版产物在 `guji status`／收口检查里「只因代码升版过期也算新鲜」（`core/engine.py` `_FORMAL_CV`），也只有正式版产物包能标 main（下面护栏第 3 条）。
- 有 `cv_version` 的产物，才能被视为可对比、可复现；dev 产物靠 hash 精确对回提交。
- 实现：`open_guji_cv/core/cv_version.py`（按 `git describe` 取最近的正式 tag，rc 不算；不是 git 检出时用安装包版本、commit 为空）。不进指纹，19 步 `code_hash` 不受影响。
- **护栏**（2026-10-23 起改成三条）：
  1. 册配置 `books/<册>.yaml` 写 `cv_version: "0.3.0"`（不带 `v`）或有 `freeze:` 后，`guji step`／`pipeline`／`rerun` 发现装的版本不同就拒跑（退出码 2）；`guji status`／`progress` 只提醒。没写 `cv_version` 的册不设防。防的是：dev 代码覆盖正式产物、一波里各册数字不可比；冻结基线被改；本地改动冒充版本。
  2. **在未发布版本上做实验、重跑：上中心库实验分支跑**（`export GUJI_DATA_BRANCH=exp/GUJI-<卡号>-<说明>`，见 ai-team `通用/中心库实验分支.md`）。产物、glyph.db 落该分支自己的数据目录，护栏自动放行、只提醒，每条 manifest 记 `cv_version`（带 hash）和 `cv_override: "exp-branch:<分支>"`。设了 `GUJI_PRODUCTS_DIR` 或工作区没迁中心库时产物不随分支换目录，不自动放行。
     不开分支、确要在正式产物目录上用当前代码跑：`--allow-cv-mismatch --why "<理由>"`，不写理由不放行，理由记进 manifest `cv_override`。
  3. 正式库的产物包只有正式版 cv 出的能标 main（`pack push --main`／`pack promote`），否则拒；确要标加 `--why`，记进 main 指针。实验桶不查。dev 上跑出的结果要转正：发正式 tag，在 tag 上重跑再存包标 main。

## 六、MINOR 的组合验收（用户 2026-10-17 定；10-20 起在切出的 rc 上做）

MINOR 分支里常常装着好几个改同一 Step 的功能，单项过不等于合起来没事：

1. **单项验收**：每个改缺省输出的功能自己跑一次 A/B（`guji exp`，A＝开关全关、B＝开），上游用同一份快照，只重跑受影响的步。报告写清：目标对象变了多少、放对放错多少；目标之外的格是否逐格不变；改了哪几步的 `code_hash`。
2. **组合验收**：从 dev 切出 `rc/vX.Y.0` 之后，在 rc 上做一次全关对全开的 A/B，受影响的步只重算一遍。
3. **打 rc**：`vX.Y.0-rc.N` 表示 rc 分支在这个点上通过了组合验收；不过就在 rc 上修（修复合回 dev），出 `rc.N+1`。rc tag 打在 rc 分支上，不打在 main 上。
4. **正式版**：组合验收通过后按第三节第 5 条合进 main、打 `vX.Y.0`。

## 七、整册跑批钉什么版本（M9 波次，用户 2026-10-20 定，GUJI-656）

粗校按「一波约 10 册」推进（`doc/design/M9-平台粗校-调研与总设计.md` 第八节）。为了让一波里每册的数字可比、可追溯：

1. **每波开工前发一个正式 tag**（PATCH 或 MINOR 都行），这一波的每册都钉它：册 yaml 写 `cv_version: "X.Y.Z"`，装的 cv 与它不同就拒跑（`core/cv_version.py`）。不用 rc 分支、不用 `+N` 版本跑正式册。
2. **同时钉语料和字形库**：册 yaml 写 `corpus: N`（语料库版本）和 `glyph_pin: N`（字形库版本，见 `core/glyph_pin.py`）。不钉字形库时，任何会话推一条人裁都会让本册 seed_admit 过期（10-19 夜 vol04–10 全部过期即此）。
   **字形库按版本钉**（GUJI-727，2026-10-21 起）：`guji glyph-db snapshot -w <工作区>` 把本书字形库定成只读快照 g<N>（清单随 `config/` 进中心库，一个号只写一次），钉了有快照的号，本册读字形库的步用 `output/glyph-g<N>.db`、指纹取快照内容哈希——平时重跑、升级 cv 或语料库时字形库不动，跟它有关的都不用重算。只有开新册、或有意让旧册吃新人裁时才出新号、改钉，按受控重跑出差异单（`doc/runbook/整理一册书.md` S6 第 4 条）。钉了号却没有那一版快照的（旧做法）只钉指纹、跑时读当前库，`guji status` 会提示。
3. **波内的修复进 dev，随下一次发版在下一波生效**。波内确需换版本的册，按 `doc/受控重跑.md` 只重跑受影响的步，出差异单，并在台账里记新版本。
4. **已出 0.1.x 的册不追新版本**：只有新版本在粗校基准上能让该册人审率降 20% 以上，才只重跑待审格所在的页；其余交精校人审。
5. 出口报告（`scripts/zhengli/collect_exit.py`）在总判前单列一行「钉版」，没钉的项标 ⚠（只提示，不挡出口）。
