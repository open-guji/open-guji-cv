# 册配置分层与运行覆盖（设计 + 实现说明）

> A31，2026-10-26（洛杉矶），Sheldon 已同意（四个待定点全按推荐）。实现在 `core/book_config.py`，测试 `tests/test_book_config.py`。第一版只讲了「拆成基础配置＋册配置」，Sheldon 指出不够完整：哪些能覆盖、任务参数怎么生效、yaml 什么时候进库、管线支持哪些覆盖。本版先把**现状逐层查清**（cv dev 34cdc8d），再给统一方案。

---

## 一、结论（一句话版）

**配置分五层，从低到高：代码默认 → 管线 yaml → 工作区基础配置（新）→ 册 yaml → 本次运行覆盖。** 上层能覆盖下层的任何字段（少数「只能写在册里」的字段除外）；正式配置只存在中心库，不进 git；实验和任务的覆盖**只在运行时叠在内存里**，不改任何 yaml 文件、不推库，生效值记进每条产物的 manifest。

## 二、现状：今天的配置是怎么生效的

### 2.1 一册书的参数来自哪几层（代码实查）

| 层 | 在哪 | 管什么 | 代码 |
|---|---|---|---|
| ① Step 默认 | cv 代码里各 Step 的 Params 类 | 所有参数的缺省值 | `steps/*` |
| ② 管线 yaml | cv 仓 `pipelines/keben_body_v2.yaml` 的 `params:` | 这条链的默认（**殿本这条目前没配任何参数**） | `core/engine.py:290` |
| ③ 册 yaml | 中心库 `books/<册>.yaml` | 图源、版式先验、证人、码位、钉版（cv/语料/字形库）、`params:`（任意 Step 的参数） | `core/book.py::load_book` |
| ③′ 工作区级 | 中心库 `config/codepoints.yaml` | 码位归一，册 yaml 逐条覆盖（10-24 起，**已有的先例**） | `book.py::_ws_codepoints` |
| ④ 运行覆盖 | `guji pipeline --params '<JSON>'`、控制台表单、`guji exp` 变体 | 只能改 Step 参数 | `engine.py:293` |

### 2.2 任务库的单子今天怎么覆盖（`jobs/runner.py`、`scripts/rerun_prep.sh`）

| 任务字段 | 实际做法 | 问题 |
|---|---|---|
| `--cv` | 切到那个提交；**用 sed 改本机数据目录里那份册 yaml** 的 `cv_version` 跟着走 | 改文件 |
| `--corpus`、`--glyph-pin`（`book_overrides`，**只收这两个**） | 同上，sed 改本机册 yaml；下一张单先 `db pull --force` 还原 | 改文件；其他册级字段（证人、group_flow 以外的册字段）一律不能覆盖 |
| `--params` | 原样传给 `guji pipeline --params` | 见 2.3 的坑 |
| `--env` | 只收 GUJI_ 开头 | Step 本身几乎不读环境变量（只读工作区、字形库、缓存路径），**特性开关不靠环境变量** |
| `--from/--to/--pages/--force` | 传给 `guji pipeline` | 无 |

本机改过的册 yaml **不推库**，跑完即弃。所以「任务改配置」今天是：**在执行机上改一份临时 yaml**，不是改正式配置。

### 2.3 现有的两个坑

1. **`--params` 关不掉册 yaml 打开的开关。** 书级覆盖 `_with_book_params`（`core/step.py:105`）的规则是「只替换**仍等于默认值**的字段」。所以册 yaml 写了 `shadow_veto: true`，命令行传 `--params '{"seed_admit":{"shadow_veto":false}}'`（false 恰好是默认值）→ 被册 yaml 改回 true，**命令行静默不生效**。代码注释和 `doc/exp_framework.md` 都承认这一点；`guji exp` 为此自己先合并好再清空书级参数，绕开了它，但**任务库和 `guji pipeline --params` 没绕开**。
2. **同一份内容存 99 遍。** vol51–99 与 vol50 只差 3～4 行；升一次版本要改 49～99 个文件（10-25 A22、A24、A31 各改一轮）。

### 2.4 册 yaml 现在存在哪

- **只在中心库**（Neon，`books` 表）。10-19 迁库后 guji-workspace 的 git 里已经**没有** `books/`（实查目录只剩 data_full、experiments、feedback 等）。
- 本机副本在 `$GUJI_DATA_HOME/main/<工作区>/books/`，`guji db pull` 落、`guji db push/sync` 推。

## 三、方案

### 3.1 五层，优先级从低到高

| 层 | 位置 | 谁改 | 进中心库？ |
|---|---|---|---|
| ① 代码默认 | cv Params 类 | cv 开发（PR） | 否（在 cv 仓） |
| ② 管线 yaml | cv `pipelines/*.yaml` | cv 开发（PR） | 否（在 cv 仓） |
| ③ **工作区基础配置（新）** | 中心库 `config/book_defaults.yaml` | A31（定版本）、A22/A24（定开关），**改即推库** | 是 |
| ④ 册 yaml（瘦身） | 中心库 `books/<册>.yaml` | 立档人；册特有的调参 | 是 |
| ⑤ 运行覆盖 | 命令行／任务单／`guji exp` 变体 | 跑的人 | **否**，只记进产物 manifest |

- 放 `config/` 而不放 `books/_base/`：照 `config/codepoints.yaml` 的先例，中心库已经按 `files` 表收 `config/**`，不用改 `books` 表的归类，`book list`、批量脚本也不会把它当成一册。
- 一个工作区＝一部书（殿本 99 册都在 `siku-zongmu`），所以「工作区基础配置」就是「殿本共用配置」。北行日錄等别的书在各自工作区，互不影响。

### 3.2 合并规则（统一一个函数，所有层都用它）

- **映射按键深合并**：`params`（到 Step、到字段）、`codepoints`、`font`、`jiazhu` 等。
- **标量、列表整体替换**：如 `group_flow`、`references`、`dev_set`。（不做「列表追加」语法，规则越少越不容易出错；`group_flow` 本来就该整份放基础配置里统一管。）
- **删除**：上层写 `字段: null` 表示「去掉下层的值，回到代码默认」。
- **按「写没写」判断，不按「等不等于默认值」判断**（修 2.3 的坑）：合并在**字典层面**一次做完，再构造 Params，`_with_book_params` 那套「仍是默认值才替换」退役。
- 以后 `codepoints.yaml` 也可以并进这一套（行为不变，只是少一个特例）。

### 3.3 哪些字段能写在哪一层

| 类别 | 字段 | 基础配置 ③ | 册 yaml ④ | 运行覆盖 ⑤ |
|---|---|---|---|---|
| 身份与图源 | `id`、`title`、`raw_dir`、`raw_pattern`、`pages`、`sets` | **禁止**（写了直接报错） | 必填／可写 | 禁止 |
| 实测版式先验 | `bottom_gap`、`period_prior`、`frame_height`、`col_pitch`、`outer_shift`、`outer_gap`、`preclean`、`page_split` | **禁止**（代码注释明写「换书必须重标，别抄」） | 可写 | 可写（实验用） |
| 冻结 | `freeze` | 禁止 | 可写 | 禁止 |
| 钉版 | `cv_version`、`corpus`、`glyph_pin` | **推荐写这里** | 可写（个别册钉旧版） | 可写 |
| 书级共性 | `expected_cols`、`chars_per_line`、`edition`、`references`、`codepoints`、`font`、`iron_gate`、`frame` 等 | 推荐写这里 | 可写（覆盖） | 可写 |
| Step 参数 | `params:`（含 `group_flow`、`page_map`、`layout_prior` 等） | 推荐写这里 | 可写（覆盖） | 可写 |

**回答「册里是不是所有参数都能覆盖基础设置」：是。** 基础配置里能出现的字段，册 yaml 全都能覆盖；反过来，身份、图源、实测先验、冻结这几类只能写在册里。

### 3.4 运行覆盖：一个入口，不再改文件

**新增 `guji pipeline --override <JSON 或 @文件>`**，内容就是一段「册配置片段」，任何 ⑤ 列允许的字段都能写：
```bash
guji pipeline keben_body_v2 vol51 -w $WS --override '{"corpus":23,"params":{"seed_admit":{"shadow_veto":false}}}'
```
- 在内存里叠在册 yaml 之上，**不改任何文件**；`--params` 保留，等价于 `--override '{"params":…}'`。
- 每条产物 manifest 记 `config_overrides`（原文）和覆盖后的生效值，`guji status` 报过期原因时能说出「是这次覆盖改的」。
- 和今天一样：覆盖改了参与指纹的值 → 对应步骤判过期、重算；没改就不重算。
- 新命令 **`guji book show <册> --effective`**：打印合并后的完整配置，每个字段标出来自哪一层（代码默认／管线／基础／册／覆盖）。查「为什么这个开关没生效」就靠它。

**任务库对应改：**
- `book_overrides` 放开成任意 ⑤ 列允许的字段（照样校验字段名，写错直接拒单）；执行方改成传 `--override`，**不再 sed 本机 yaml**，也就不用每张单先 `db pull --force` 还原（准备更快、不会串单）。
- `--cv` 不变：切代码，`cv_version` 护栏用覆盖层放行（记进 manifest），同样不改文件。
- `--params` 不变，走同一层。

### 3.5 什么时候进中心库、什么时候进 git

| 情况 | 动作 |
|---|---|
| 新立一册 | 写 ④ 册 yaml（几行），**推中心库** |
| 全书升版本／换语料／换字形库／开关转正 | 改 ③ 基础配置一处，**推中心库**；之后提交整批任务 |
| 某一册单独调参，结论要留下 | 改该册 ④，推中心库 |
| 做实验、A/B、试新参数 | **只用 ⑤ 运行覆盖**，不推库、不改文件 |
| 实验还要写库（人裁、字形库、字组配置、码位表、语料） | 开中心库实验分支 `exp/GUJI-卡号-说明`，用完删；要留的显式导回 main |
| 改 Step 默认值、管线结构 | cv 仓 PR（git） |
| 册 yaml / 基础配置 | **永远不进 git**（10-19 起只在中心库） |

推库照旧用 `guji db sync/push`（有版本号 rev、可回溯）；`guji db diff` 能看到 `config/book_defaults.yaml` 的变化。

### 3.6 指纹与重跑

- 指纹看的是**生效值**（Step 参数合并后、`book_deps` 列出的册字段现值），不看值来自哪一层。所以只要合并结果不变，**拆分不会让任何册判过期**。
- `cv_version` 只是护栏，不进指纹；`corpus`、`glyph_pin` 进指纹（换号即重算对应步，符合预期）。
- 修 2.3 的坑会不会改现有产物：只有「命令行传了一个等于默认值、又和册 yaml 冲突的参数」才会变；正式产物都不是这样跑出来的（任务库至今只用过 corpus/glyph_pin），**现有册不受影响**，上线前用 2.4 节的全册对账确认。

## 五、风险

| 风险 | 对策 |
|---|---|
| 合并出来少一个字段，指纹变，整册判过期 | 迁移工具强校验；上线前全册 `guji status` 对账 |
| 还有代码绕过 `load_book` 直接读册 yaml（实查：`corpus_pin.py:382` 读 `corpus_dev`、`datastore/pull.py:13` 取 id、`datastore/scope.py:330`） | 统一改走合并出口；加守卫测试禁止直接 `safe_load` 册 yaml（参照 `tests/test_central_paths.py`） |
| 改一次基础配置影响全部册 | 改基础配置走推库记录（有 rev 可回退）；`guji db diff` 列出受影响册；冻结册的比对走快照，不受影响 |
| 运行覆盖太自由，正式产物来源说不清 | manifest 记覆盖原文与生效值；`pack push --main`（标 main）时有覆盖就提示，需明确确认 |

## 六、实现说明（与上文的细化）

- **运行覆盖怎么传**：`--override JSON` 设环境变量 `GUJI_BOOK_OVERRIDE`，`load_book` 读它；`--isolate-steps` 的每步子进程自动继承，不用逐个透传。`--override` 里的 `params` 另外交给引擎当「调用方显式参数」。
- **null 的含义**：普通字段写 `null` 就是 null（`expected_cols: null` 等本来有意义）；只有 `params:` 里的字段写 `null` 表示去掉下层的值、回到 Step 默认。
- **修坑的做法**：`_with_book_params` 改成按 `model_fields_set`（调用方有没有显式传）判断，不再比「是否等于默认值」。没显式传的字段仍取册 yaml 的值，行为同以前。
- **字段分层校验**：基础配置不许写 `id/title/raw_dir/raw_pattern/pages/sets/freeze` 和实测先验 `bottom_gap/period_prior/frame_height/col_pitch/outer_shift/outer_gap/preclean/page_split/dev_set`；运行覆盖不许写前一类（身份与图源）。
- **看生效值**：`guji book show <册> -w … --effective` 打印合并后的配置，每个字段标出来自哪一层。
- **决定**：基础配置放 `config/book_defaults.yaml`；列表整体替换；先迁 vol51–99，稳定后迁 vol21–50，vol01–20 不迁。
