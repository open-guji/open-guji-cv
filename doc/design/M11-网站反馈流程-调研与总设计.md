## 〇、一页结论

1. **网站上现在有四条读者意见通道，彼此不通**：通用反馈 `/api/feedback`、阅读页改字 `/api/charfix`、讨论 `/api/thread`、精校页 `/api/cellreview`。数据都只存 EdgeOne KV（60 天或 180 天过期）。真正接到 CV 的只有精校页这一条，而且靠人手跑 ai-team 里的一次性脚本 `web_opinions.py`。
2. **1.0 之后最主要的入口「改字」后面没有接任何东西**：每日 Action 把它拷进了中心库 `fixes.jsonl`，但没有程序读。原规格写的去向是「直接改 book-text」，这样会绕过 CV 人裁事件，和「已放行格只增不改、改动走人裁事件」的规矩冲突。阅读器右栏的「报告错字」和非对读章的选字报错走的是通用反馈，不带格号、不带文本版本，只能在管理页手工回一句话。
3. **定位会漂**：意见只按格号（`页:列:格`）和 `text_version` 记。book-text 里已有多次人手拆格、删格、补格（#177、#179、#184、#205），这些格在 CV 产物里根本不存在。文本版本和 CV 快照之间也没有程序能读的对应表：中心库为此建的三张表没人写，修订对照表的目录也不存在。
4. **没有判断和闭环**：意见进来后没有 AI 初判；`fs:` 采纳状态没有写入界面，也不进中心库；反馈者收不到任何回音。用户 10-16、10-18 两次定过「AI 先过、存疑才给我」，第三段还没实现。
5. **机器报错没有通道**：重跑差异、字形库体检、模型看图、放行错穷举各出各的报表文件，没有统一的待处理池。冻结册吸收新算法的 L2「只合并待审→可放行」还没实现；只有一次手工实操（vol01「重跑对比定字」，139 条）。
6. **字形库自检有盲区**：查不出「标成异体 A、其实更像异体 B」，因为体检把异体当作同一个字。它只查库里的刻例，不查文本里数万个机器放行格。结果不带库指纹，出过 9 张错位卡。裁决账不在中心库，换机器就丢。
7. **真实流量很小**：线上能看到的读者文字意见只有 1 条（vol002 3:1:9「卷」→「卷一」，读者自己也说图上没有字）。精校页真实意见 2 条，另有用户自己投的 3 条。所以 M11 **先把流程和规矩做对、做成全自动**，不先追求规模和性能。

**建议立项的方向**：建一个**意见池**作为单一真源，读者意见和机器意见都进同一个池。所有入口共用一个数据契约，按「格号＋版本＋稳定定位」锚定。**AI 初判**后分三路：自动结案、交用户、公开讨论。采纳的意见先写成**中心库人裁事件**，再由工具按「1.x 修订通道」批量生成新版文本，book-text 不再手改。在这条主干上，再接机器报错和字形库深度自检。

## 一、项目范围

### 1.1 做什么

| # | 范围 | 说明 |
|---|---|---|
| S1 | 网站上关于**文字**的所有读者入口 | 选字报错、点字改字、右栏报告错字、通用反馈里的「内容有误·错字」、讨论；1.0 之后的「待再判」文字栏（decision `open`） |
| S2 | 意见的收集、存储、去重、定位与跨版本迁移 | KV 只当收件箱，中心库为真源 |
| S3 | AI 初判与人审（交用户的那一小撮） | 和 M10 共用一套引擎（见 1.3） |
| S4 | 采纳后落到文本：1.x 修订、发版、CHANGES 回链意见 | 只针对已到 1.0.0 的冻结册；0.x 册的意见交 M10 |
| S5 | 机器报错：算法升级后对冻结册做差异检查（L1），把差异当意见入池；局部合并（L2） | 「旧数据不能全丢，部分重跑」 |
| S6 | 字形库深度自检：异体贴合度、放行格全扫、体检结果的新鲜度与回流 | 结论作为机器意见入池 |
| S7 | 闭环：反馈者能看到处理结果；站方有看板与提醒；端到端演练 | |

### 1.2 不做什么

- 标点、专名号意见（`kind=entity`、span 的 `punct/para/heading/entity` 类）：接口保留，M11 只做**分流**（转给负责人的队列），不处理。
- 0.x 册的精校页（`/proofing`）本身：归 M10。M11 只复用它的数据形状和 AI 引擎。
- 异体分组算法本身（字组、IDS 路、上下文路）：归 M7（GUJI-563）。M11 只负责把 M7 的结论落成已发布文本的修订。
- 2.0 出版级流程、抽检规则。
- 登录和用户信誉体系（先匿名，见第八节 Q6）。
- 切分大缺口（整列重切、补删并格 override，GUJI-579，约 44–62 小时）：M11 只**依赖**它，不在本项目里做；没有它之前，C／D 类修订照旧走人工加对照表。

### 1.3 与 M7、M9、M10 的边界（建议，需用户点头）

| 交叉点 | 建议归属 |
|---|---|
| AI 判「公众意见→裁决」的引擎 | **只做一套**。M11 建通用的「意见→裁决」引擎（意见池＋AI 初判＋人审台）；M10 的 cellreview 改为它的一个来源。理由：1.0 之后的意见类型更杂，引擎按难的那头设计更稳。如果 M10 已经先动手，就反过来由 M11 接管扩展。 |
| 网站校对页「第三段形态」（文字栏、讨论区） | M11（M8 设计 §4.4 写了这个出口动作，但没人做） |
| 字形库「出口前交叉检查」 | M10（出口闸）；M11 做 1.0 之后的**持续**自检，结论入意见池 |
| 重跑 | M9 管 0.1 之前；M11 只管冻结册上的 L1 差异和 L2 合并 |
| ws 归档与恢复 | M10 负责；M11 提需求：归档后要能 `guji archive fetch` 回到 rev 产物并取到书影（GUJI-598、599） |

### 2.3 CV 侧能接什么

- 人裁事件信封只有一种（`feedback/events.py:136`），按格号写。**定位锚由控制台在写入那一刻按当时产物现算**，所以网站意见必须在「对应 rev 的快照工作区」里写，才带得上锚。
- 采纳改字的正确形状是 `kind=confirm, v=confirm, shape=<字>`。「图上无字」是 `not_a_char`，切坏是 `seg_defect`。
- 补格、删格、整列重切**没有事件种类**（`recrop` 无出口），所以读者报「漏字、多字」时 CV 表达不了，只能人手改 book-text。

### 3.1 国内访问实测（10-20，Globalping 国内节点，电信、联通、移动、阿里云、腾讯云混合）

谁会从国内碰中心库：读者不会，网站只读 COS、只写 EdgeOne KV，由 GitHub Action 在美国同步；会碰的是**在国内机器上整理书的人**。其中 `guji db pull` 走 Worker 查表签名，再到 blob 公开域名取图；`guji db push/sync` 直连 Neon Postgres（443 上的 wss 桥或 5432），上传图经 Worker。

| 目标 | 测法 | 结果 |
|---|---|---|
| Neon 端点（AWS us-west-2） | DNS / TCP 443 / TCP 5432 / HTTPS，各 22 节点 | DNS 全部正常无污染；443、5432 **22/22 通、丢包 0**，RTT 中位约 **200 ms**；HTTPS 握手中位约 200 ms |
| `console.neon.tech`（`db branch` 用） | HTTPS 22 节点 | 22/22，总耗时中位约 0.9 s |
| Worker `data.open-guji.com`（Cloudflare） | HTTPS `/v1/health` 22＋39 节点；TCP 443 22 节点 | TCP 22/22、RTT 中位约 240 ms；**HTTPS 只有约 85% 成功**（19/22、33/39），失败的都是 TLS 握手超时或等首字节超时；成功的总耗时中位约 0.9–1.1 s，p90 约 2.3–2.7 s |
| blob `blob.open-guji.com`（R2 公开域名） | HTTPS 22＋39 节点 | 约 97% 成功（21/22、38/39），首字节中位约 0.45–0.55 s；吞吐量测不了（探测只收 10 KB） |
| 对照：腾讯 COS `data.kaiyuanguji.com` | HTTPS 22 节点 | 22/22，总耗时中位约 0.2 s |
| 网站 `www.openguji.com`（规范域名，EdgeOne） | 读 `/api/fixes` 22 节点；`/api/charfix`、`/api/cellreview` 的 OPTIONS 预检 22 节点 | 读 22/22，中位约 0.74 s；提交预检 22/22（204）。连续第 4、5 次测时有 7–9 个节点被 ECONNRESET，**疑似 EdgeOne 对测速节点限流**，要请国内真人复核 |
| 旧域名 `www.kaiyuanguji.com` | 同上 | 国内访问页面 301 到 `www.openguji.com`，**`/api/*` 一律 404**。凡是写死旧域名的接口调用，在国内都会失败 |

**结论**：①Neon 本身国内可达、稳定，瓶颈是约 200 ms 的往返，push/sync 一次要多少轮 SQL 往返没量过，轮数多就会慢，但能用。②真正不稳的是 Cloudflare 上的 Worker，约 15% 的请求握手超时。客户端已有退避重试（`datastore/client.py:94-113`），但一次超时要等满 `timeout`，最长 120 秒，体验会很差。③整库拉取的吞吐、端到端 `guji db sync` 耗时没测；要一台国内真机跑一次，团队那台服务器 43.162.109.111 在美国 Santa Clara，不算。④网站国内通道（GUJI-610）能读能提交，但旧域名的 API 在国内不可用。

**由数字得出的判断**：量小，所以 M11 的价值在于「每条都走对、全自动、可追溯」。目前最大的意见来源反而会是**机器**：重跑差异、体检、异体复核，一次就是上百格。所以意见池从第一天起就要把机器意见当作一等公民。

## 五、解决思路与方向

### 5.1 六条设计原则

1. **单一真源**：一切意见，包括读者的和机器的，都进中心库的**意见池**。KV 只当 24 小时的收件箱。采纳后的改动一律先成为**中心库人裁事件**。
2. **book-text 只由工具写**：1.x 文本由「冻结基线＋已采纳修订」用工具生成，人不再手改 char/cord。手改过的存量先补回事件，补不回的登记为「人工格」。
3. **定位三件套**：每条意见带「格号＋文本版本＋校验字」；入池时由**版本登记表**补齐 rev、CV 快照和 cord 框 id。文本每次升版产出**修订对照表**，旧意见自动迁移，迁移不了的进人工清单。
4. **AI 先判，人只看存疑**（用户 10-16、10-18 两次定论）：AI 的结论要带证据（裁图、字形库前几名、整理本对位字、上下文），可以复核。
5. **机器意见和读者意见同形**：机器报错就是 `source=machine:<检查名>` 的意见，走同一条初判、讨论、采纳流程。冻结册上的机器意见**只提议，不直接改字**。
6. **先跑通再优化**：先把 vol01–03 走通一条最小闭环（第七节阶段一），再接机器报错和深度自检，最后打磨体验。

### 5.2 目标数据流

```
         读者入口（统一的「报错」弹窗，按选区自动定格号）        机器检查（L1 差异 / 体检 / 异体贴合 / 看图 / 放行错）
                     │ KV 收件箱                                          │
                     ▼                                                      ▼
            ┌──────────────── 中心库「意见池」opinions（单一真源）────────────────┐
            │ 定位：书/册/格号/文本版本/校验字 + 版本登记表补 rev、快照、框 id     │
            │ 状态：new → triaged → (auto_accepted | auto_rejected | to_user | discussing) → accepted/rejected → applied(vX) │
            └──────────────────────────────┬──────────────────────────────────────┘
                                           ▼
                           AI 初判（证据包：裁图、库前五、整理本、上下文、同字例）
                         ┌─────────────┼───────────────┐
                    自动结案（回复理由）  交用户（人审台）   公开讨论（/feedback/text）
                                           ▼
                         采纳 → 中心库人裁事件（confirm / not_a_char / seg_defect …）
                                           ▼
            修订生成器：冻结基线 char/cord + 已采纳修订（A/B 类直接套；C/D 类走 CV 局部重跑 + 对照表）
                                           ▼
                book-text PR（CHANGES 每行列出意见 id）→ 网站新版本 → 意见状态 applied(v1.0.x) → 通知反馈者
```

### 5.3 几个关键做法

- **意见池放在哪**：中心库新表 `opinions`，外加 `opinion_events` 状态流水，由 Worker 加接口，网站 Action 和 cv 客户端共用。不放 KV，因为 KV 不能排序、不能计数、会过期。也不放 book-text，因为 10-19 已定意见不进 book-text。
- **四个入口合成一个**：阅读页所有「报错」都进同一个弹窗，选区落在对读章就自动带格号。右栏「报告错字」也改走 charfix。`/api/feedback` 只留给非文字类意见（条目、网站、合作）。
- **通用反馈里的文字类意见先由 AI 规整再入池**（用户 10-20 定）：通用反馈和「这段有问题」里的自由文字，由 AI 引擎第一步「规整」处理，定位到格号、拆成一条条、标好类别和建议字后再写进意见池；定位不到的标「待定位」交人。原始记录保留，入池记录回链原始 id。
- **改字弹窗补证据和输入法**：弹窗里显示该格书影裁图，附候选字（字形库前五、相似字，复用精校页的 `lib_top/alt`），提供「图上没有字」「切坏了」「漏了字」「多了字」几档按钮，生僻字可以用部件检索（hanzi 库）。
- **AI 初判**：把 `web_opinions.py` 并进 cv，做成 `guji opinions triage`。输入是一条意见加证据包，输出是 `{verdict, confidence, rationale, evidence_refs}`。分流规则如下：
  - 自动采纳：AI 判「对」，并且至少两路证据一致（字形库前一名、整理本、上下文）。
  - 自动不采纳：AI 判「不对」且证据充分，必须带一句公开理由。
  - 交用户：其余情况，加上所有「按文意改字」类意见（以图为准还是按文意补，这是原则问题，见 Q7）。
  - 门槛用金标集标定：先拿已有人裁加造数做一个 50–100 条的评测集。
- **冻结册怎么出 1.x**：
  - A 类（同格改字）、B 类（□↔字）：修订生成器直接改冻结基线 char，同时写 confirm 事件，字形库也就学到了。不需要恢复工作区，不需要重跑。
  - C 类（切分变）、D 类（补页）：`guji archive fetch` 恢复 rev 产物，写带锚事件，局部重跑，产出对照表，再迁移意见、标点和专名锚点。依赖 GUJI-579、598。
  - 出版节奏先不定（用户 10-20：先手动测试）：头几批由人手触发 `revise apply`，patch 升版，CHANGES 列意见 id；跑顺了再定频率。
- **录文以图为准；图上无字、但按文意和他本应有字的，录成阙文并带推测字**（用户 10-20 定，首例 vol002 `3:1:9` 后一格）：
  - 显示为 □，鼠标移上去显示「推测为『一』」，按磨损缺字处理。
  - 现行格式表达不了：char 的 `guess` 是布尔值，表示 `c` 是推测的残字，显示为灰字加点线；`lacuna` 时 `c` 只能写 □。所以要做三件事：
    - guji-format spec 02 扩一个写法，例如 lacuna 格允许 `guess` 取字符串；
    - 阅读器在 lacuna 格上显示推测字的悬停提示；
    - CV 的 `damaged` 裁决把 `guess` 导出到 char。CV 侧 `feedback/consumers.py:85-91` 已把 guess 当「最像的那个字」收进名单。
  - 首例那一格在 CV 里落在排除名单上（cord marks `excluded`，「排除名单·非字（墨污/切坏）」），要先移出名单，再写 `confirm v=damaged guess=一`。这是插格，属 C 类修订。
- **机器报错**：cv 每发一个新 tag，就对每个冻结册跑一次 L1（`guji exp run` 以快照为上游），并把「放行字变」「待审→可放行」「可放行→待审」三类差异落成机器意见：
  - 「待审→可放行」且 AI 复核一致的：自动采纳，这就是 L2 只合并改进。
  - 「放行字变」：一律交 AI 初判，存疑的给用户。冻结册不整册重跑。
- **字形库深度自检**：
  - 加「异体贴合度」一路：在异体组内，把刻例和各异体的字体渲染、本书各异体刻例分别比距离，出「标的是 A、更像 B」的意见。用 hanzi 库给异体关系和字形向量（hanzi B2）。
  - 加「放行格扫描」一路：把文本里机器放行、不在库里的格按批跟库比对，出离群意见。
  - 每份体检结果都带库指纹，出卡前比对，过期就不出。
  - 裁决账改为从 `glyph_audit` 事件重建。撤库时连带给事件侧人裁打 `human_stale` 标记。

### 5.4 AI 引擎：负责什么、输入输出、M10 与 M11 的区别（回答 Q4）

**一句话**：AI 引擎是意见进来之后、人裁事件写出之前的那一段。它把一条意见变成「规整的意见＋带证据的结论＋去向＋可执行的草稿」。它不写 book-text，不发版，不改切分。

**负责的五件事**

| # | 职责 | 做什么 | 现在谁在做 |
|---|---|---|---|
| ① | 规整 | 自由文字（通用反馈、「这段有问题」的说明、读者长评）→ 一条或多条结构化意见：定到格号、类别（错字、缺字、多字、次序、切坏、阙文、标点或专名转出）、建议字、读者理由摘要；定位不到的标「待定位」 | 没有（M6 靠人读） |
| ② | 配证据 | 按意见的格号和版本，从对应的冻结基线或 rev 产物取：该格裁图、字形库前五（`lib_top`）、本书同字刻例、整理本对位字（`ref`）、上下文、这一格的历史裁决，以及同一格的其他意见 | `web_opinions.py`（手工，只有裁图拼图） |
| ③ | 判 | 给出结论 `verdict`：原文对；建议对；图无字（按文意应有的，录阙文带推测字，见 Q7）；切分问题；超出范围（标点、专名转出）；看不清。附 `confidence`、一句公开理由、内部理由、引用了哪些证据 | H 道会话人工看图 |
| ④ | 分流 | 按规则表定去向：自动结案（采纳或不采纳，附公开回复）；交用户（人审台）；公开讨论；转给别的线 | 没有 |
| ⑤ | 起草 | 对要采纳的意见，起草人裁事件（`confirm v=confirm shape=…`／`not_a_char`／`damaged guess=…`／`seg_defect`）、修订分类（A/B/C/D）、公开回复文字 | `web_opinions.py write`（只有精校页的六档） |

**输入**：一条意见（`guji-opinion/0.1`：来源、书、册、格号或格号区间、文本版本或 rev、校验字、建议、读者说明、原始记录 id）＋证据包（第②步取到的东西）＋规则表（门槛、阶段口径）。

**输出**：一条判定记录 `triage`。字段：

| 字段 | 内容 |
|---|---|
| `opinion_id` | 判的是哪条意见 |
| `normalized` | 规整后的意见，可以拆成多条 |
| `verdict` | 结论 |
| `confidence` | 置信度 |
| `rationale_public`／`rationale_internal` | 公开理由、内部理由 |
| `evidence_refs` | 引用了哪些证据 |
| `route` | 去向：`auto_accept`／`auto_reject`／`to_user`／`discuss`／`forward` |
| `draft_event` | 起草的人裁事件 |
| `revision_class` | 修订分类：A/B/C/D |
| `reply_draft` | 公开回复草稿 |
| `engine_version`／`model`／`prompt_hash` | 引擎版本、模型、提示词哈希，方便复核和重判 |

人审台收的是 `to_user` 的记录。用户一键裁决后，由引擎把草稿事件落进中心库。

**M10 与 M11 的区别**：引擎只做一套，按「阶段口径」切换参数。

| 维度 | M10 精校（文本 0.x，出 1.0.0 之前） | M11 网站反馈（文本 ≥1.0，冻结册） |
|---|---|---|
| 对象 | 机器自己说不准的**待审格**（pending 清单里的） | **任意格**，包括已放行、已人裁的 |
| 意见形状 | 精校页六档按钮，天然结构化，一格常有多票 | 自由形状：改字、一段话、通用文本，再加机器意见；**多半先要「规整」** |
| 先验 | 机器没把握，读者给出的字和机器候选一致时可以直接定 | 已发布文本默认是对的，**举证责任在意见一方**，自动采纳的门槛更高 |
| 和旧裁决冲突 | 少见 | 常见：这一格已有人裁（用户亲裁）的，一律交用户，不自动改 |
| 证据来源 | rev 快照工作区（活的） | 冻结基线（快照或产物包）；工作区可能已归档，要 `archive fetch` |
| 产出落到哪 | 人裁事件 → 局部重跑 → 0.x minor | 人裁事件 → 修订工具直接改冻结 char（A/B 类）→ 1.x patch；C/D 类才走 CV |
| 要不要公开回复 | 不必（精校页不显示结果） | **必须**（读者在 /feedback/text 看结果） |
| 特有结论 | `unsure` 只计数 | 阙文带推测字（Q7）、超出范围转出、「已在 vX 改过」 |
| 机器意见 | 没有 | 有（L1 差异、体检、异体贴合），同一个入口进来 |

共用的部分：证据装配、模型调用、判定记录 schema、人审台、事件写出。不同的部分只是一个配置文件（门槛、先验、允许的结论、要不要回复）。这也是建议「只做一套、由 M11 建」的理由：M11 的口径是 M10 的超集。

| 估时 | 约 8–12 小时，另有机器时间（模型调用，量小可忽略） |
| 依赖 | A；与 M10 协调（1.3） |
| 不做 | 训练新模型；投票门槛 |

## 七、阶段与顺序

| 阶段 | 内容 | 涉及块 | 估时 | 阶段验收 |
|---|---|---|---|---|
| 0 决定与清账 | 用户回答第八节；Jira 清账；契约草稿评审 | A（设计）、G⑤ | 约 2 小时 | 契约评审过，卡状态一致 |
| 1 最小闭环 | 池＋迁移；统一入口（最简版）；AI 初判＋人审台；A/B 类修订发版 | A、B（最简）、C、D（A/B 类） | 约 25–30 小时 | 线上那条「卷→卷一」走完全程：回复读者，结论可见；staging 造数 3 条进 vol01 1.0.x |
| 2 机器意见 | L1/L2；GUJI-623；体检新鲜度与回流；异体贴合度、放行格扫描 | E、F | 约 18–24 小时（另有机器时间） | vol01 一轮 L1 和一轮深度自检全部入池、分流完 |
| 3 体验与运维 | 弹窗打磨、跨设备「我的」、看板、提醒、e2e、文档 | B、G | 约 10–14 小时 | 项目验收全过 |

**项目验收标准（收口时逐条核）**：

1. 网站上任何文字类意见 24 小时内进意见池；KV 对池的对账差为 0（命令 `guji opinions reconcile`）。
2. 每条意见 48 小时内有 AI 初判；自动结案的抽检错判 ≤2%；交用户的 ≤40%。
3. 采纳的意见 7 天内进入新版本文本；CHANGES 引意见 id；读者在 /feedback/text 看到「已进 vX」。
4. book-text 中 char/cord 只由工具改：最近 30 天的 PR 里人工改动为 0。存量人工格全部登记。
5. vol01–03 各完成一轮 L1 机器报错和一轮深度自检，全部入池并分流完。
6. staging 端到端演练脚本通过；e2e 覆盖四种入口。
7. 文档：本设计定稿；三阶段设计 §6.3 回改；architecture、runbook、skill 更新；经验写回 ai-team `domain/网站与运维`、`domain/CV`。
