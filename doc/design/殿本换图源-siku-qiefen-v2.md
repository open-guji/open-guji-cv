## 三、格级对照表（v4 新增，所有按格寻址数据的唯一来源）

页级对照表只管页号。行、格号在新图上会有 0.1–1% 变动，凡是按 `册:页:列:格` 存的东西都要一张格级表才能机械地迁。

- **文件**：ai-team `domain/CV/图源迁移/siku-qiefen-v2/results/old_new_cells/<册>.tsv`，列为 `旧格 新格 旧字 新字 类别 IoU 说明`。
- **类别**：`同格`（编号未变）、`改号`（对上了但编号变了）、`删`（旧格在新图上没有对应）、`新增`（新格在旧图上没有，含新补页）。
- **配法**：旧格框经页变换 A 变到新图，与新格框按 IoU 一对一配对（不按同编号）。IoU 低于门槛的、落在没对上 14 页与可疑 45 页上的，一律不配，类别记 `删`、说明写原因。
- **新格从哪来**：准备阶段在实验分支上用正式 tag 跑出新切分，据此出表；正式重跑后再用新 main 包重出一遍，两版逐行比对，有差就以新 main 为准、重做下游。
- **旧格从哪来**：缺省是旧 main 包。迁票时旧格必须取**出该单那一版**的 cord／产物包（A32：册004 r3/r5 就曾因拿现行 cord 核旧票错落一格），由同一工具 `--old-cord <版本>` 另出一张。
- **同一张表供给**：迁票（A32）、标点实体重挂（A33）、字形库改键与 L2 答案表、回放集改键（A24）、dataset 金标里按格寻址的部分。两线用同一张表，才不会互相打架。

## 四、防混图：册 yaml 钉页表 rev、新页表以 staged 登记（cv 改动 1，PR #633）

- **新页表一律用 `guji source register --staged` 登记。** `read_table` 不带 rev 时跳过 staged 的 rev；某册只剩 staged 时报错，要求写 `source_rev`。新页表发出去以后，没切的殿本册做 pull 或任务库 prep，拿到的仍是旧图，不必先把 99 册 yaml 都钉一遍。新页表一直保持 staged。
- **册 yaml 加 `source_rev: <N>`。** `guji source pull` 与任务库 prep 都按它取页表。切换时由 A31 写，**切过的册必填**，没切的册不写。
- 新页表的 `raw_dir` 是 `data_full/qiefen/<册>`，不和旧图混在一个目录。

## 六、旧事件失效（cv 改动 2）

只对 yaml 写了 `source_rev` 的册（切过的册）生效，没切的册行为不变。

- **判据**：事件锚里的 `anchor.source_rev` 等于本册 yaml 的 `source_rev` 才采信；没有这个字段的一律不采信，不看 ts。迁移事件锚里写了新 rev，照常采信。
- **锚 rev 取产物自己的来历，不取册 yaml**（A32）：`cell_anchor`／`_product_anchor` 按算锚时读的那份产物的 `_raw_index.json` 里的 `source_rev` 写（§五）。否则用 `--pack` 取旧图包落旧票时，旧坐标会被盖上新 rev 的章，读口放行，静默钉错格。
- **写事件的入口加护栏**：`guji cellvotes write` 与控制台写事件时，切过的册若所依产物的 `source_rev` ≠ 册 yaml 的，**拒写并提示**先走迁移工具；`cellvotes draft` 的 meta 记 `source_rev`。网站不写事件，不用改锚；待审单 `pending.json` 顶层加 `source_rev` 只作标注。
- **`guji db push` 对切过的册拒收无 rev 或旧 rev 的事件**，提示先迁移；`guji db status`／落票命令打印「N 条因页表 rev 不符不采信」，不静默丢。
- **读口收拢**（A24）：现有不少地方直接 glob `feedback/events/*.jsonl`、不经 `EventLog`（含 `groups/freq.py`、`clustering/glyph_ledger.py`、`ops/glyphlib.py`、`eval/round_check.py`、`scripts/zhengli/pending_route.py` 等）。开关打开前，涉及人裁读取的全部改走一个读口，并在 `feedback/lint` 加一条禁止直接 glob。
- **开关次序**：先落票、先推各方待推的事件包 → 再迁移 → 再打开读口判据。开关一开，旧事件（含刚落的）全部失效，只有迁移批次存活。上线前先在 vol04 干跑（只读，对比有效事件数）。
- 实现方：A30、A24。

## 七、迁票（vol04–10，A32 定流程）

1. **盘点**（只读）：线上待审单 rev 与格数、该 rev 的票数、已有人裁事件数、冻结状态；**每张在途单的出单版旧格表（`--old-cord`）在这一步就出好**，免得窗口里才发现对不上。盘点表贴 GUJI-748，作计数核对的左端。
2. **停写→落票**：旧单只读（`/api/cellreview` 对旧 rev 返回只读）。每张在途单按**出单那一版**的 cord 或产物包跑 `cellvotes draft`；ready 的落成人裁，held 的（无字、分歧、推翻、格位对不上）单独存清单。
3. **迁**：用该单出单版的格级表（§三 `--old-cord`）迁。IoU 低或落在没对上／可疑页上的票，和 held 清单一起进新待审单（带旧新格截图），不丢、不自动裁。
4. **核对**：人裁数＝迁入＋退役页＋补不出锚，差额逐条列。新图重跑后变了的字一律进待审，人裁优先，不写回文本。
5. **发新单**：从新 main 包出新 rev（延续编号，如 `004-r8`），旧单作废。新单上复审格的 `prior.id` 按 `id_map.tsv` 改成迁移后的事件 id，否则 `web_votes.triage` 会把迁过去的复审格一律挂起。不在新旧两套图上各出一轮单。

## 八、顺序与单册步骤

**册序**：vol11（无票，试流程）→ vol04（有票，验迁票与重挂）→ vol06、vol07 → vol05（视冻结状态）→ 其余。vol06 用户 10-26 定跟其他册一起换，放弃 0.5.7 对照基线（推翻 10-25「留在 0.5.7」）。vol08–10 未定接手方前不动票。

每册步骤（每步的输入与验收）：

1. **准备（本机与实验分支，可撤）**
   - 产出：新页集、`map.json`、页级表、实验分支上正式 tag 跑出的新切分、格级表、新册 yaml、新版式先验行、迁移脚本试跑的事件 jsonl。
   - 验收：页级表覆盖全部旧页；格级表 `删` 类占比 ≤ 1%（超了逐页看）。
2. **发页表与书库号（不影响在跑的册）**
   - 新页表 staged 登记；版式先验、字形库各出新版本号，钉子账只改要切的册。
   - 验收：`guji source show --rev N` 是新图；不带 rev 的 `guji source pull` 仍取旧图。
3. **切换前清场**
   - A24、A32、A33 各自待推的事件包推掉（推前请用户亲口说「推」），使其进迁移批次。
   - book-text：该册 dev 上的改动经每日合并进 main，改字清单 sync 清空；之后该册 dev 冻结，A32、A33 都不推。
   - 任务库撤单（§五）。
4. **切换窗口**
   - 旧单只读、落票（§七 第 2 步）。
   - 严格按这个先后（A24）：① 各方待推包（含 `glyph_audit`）推完，glyph 消费者跑完；② 按格级表改字形库键，出新版本；③ 从中心库最新事件**重跑迁移**，推迁移事件（跳过进库）；④ 打开 §六 读口判据。② 必须在 ③ 之前，否则迁移事件的 key 会先撞上旧实例。
   - 计数核对，对不上不切。
   - **推册 yaml 前请用户确认**。册 yaml 的 `source_rev`、`raw_dir`、`cv_version`、像素参数，钉子账的新书库号与 `glyph_pin`，改键后的字形库，迁移事件，同一次推送生效（否则 corpus verify 报 StaleBase）。
   - 验收：`guji db status` 无残留改动；计数核对表贴 GUJI-748。
5. **重跑、标 main**
   - 用正式 tag 在任务库重跑：不铺底包、单上不写 `human_chars` 自检。
   - 验收：整册失败 0 页；重绑定 valid＋rebound ≥ 97%，其余进待审单；新 main 的切分与格级表一致。
   - 标 main 后算新基线人裁数，写进册 yaml 说明。
