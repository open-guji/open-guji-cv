## 一、要解决什么

人审时手输的字，下一次遇到 5-b 还是给不出来。四书 26,044 例人裁刻例里，445 例（112 字）不在本书 5-b 基集里：

- 扩 B 的字要靠升级档，升级档只在基集首位余弦低于 `escalate_threshold`（0.85）时才查，r5 模型下这 445 例没有一例触发；
- 扩 C 以后的字不在升级档里；
- 内、无、遥、温、宫 这类刻本真这么刻的字形被简体否决（`allow: no-simplified`）挡掉；
- 𠎝、𦫵 这类字体模板和刻形差得远，放开字表也排不到前面。

这些字很集中（𠋫、内、𥳑、𠮓、𨽾、𠎝 六个字占一半），手输过一次之后，库里就有它的刻例。

已有的 `font.real_proto`（真刻例原型）单独开没有用：原型只落在检索字表以内的字上，字不在基集，刻例再多也进不了候选。
而且它对基集内的字也生效，全唐文 010 册上让 127 格首位变动，对整理本看改对 25、改错 96（己已巳、日曰 互换占 64）。

## 二、做法

```yaml
font:
  charset:
    lib_chars: true      # 缺省 false
  real_proto:
    stores: [...]        # 可不写；库的位置与真刻例原型同一个来源，缺省本书 output/glyph_store
```

开着时，`rare_for_batch` 在基集检索（和可能的升级档）之后多查一档：

1. **库字档字表**（`rare_panel.lib_tier`）＝本书字形库里人裁过的单字（`label_status == human`，与真刻例原型同一口径）中，
   基集里没有的，加上在基集里但会被白名单否决挡掉的。
2. **每格都查这一档**，不看分数门槛。这一档通常只有几十到一百多个字，一次小矩阵乘法。
3. **刻例原型在这一档总是开着**，且只作用在这一档的字上（`font.real_proto.enabled` 管的是基集那次，互不影响）。
   所以基集那次检索的结果不变，基集内的字彼此的先后不变，只会被库字档的字按分数插队。
4. 与基集候选**按余弦分归并**（同升级档的办法，不能拼在后面，见 `charset_spec` 模块头）。
5. 库字档的字**不受白名单否决**：它们是人在这本书上定过的刻形，和语料用字一样无条件放行。

指纹：开着的册，`rare_candidates` 的指纹多一个键 `lib_chars`＝库 `instances/*.jsonl` 的内容指纹，库里新裁了字产物就过期。
关着的册指纹逐位不变。`font` 在 5-b 的 `book_deps` 里，改开关只让该册 5-b 过期。

没有改的：单查路径 `rare_for`（控制台生僻字面板）不走库字档；库字档只读人裁例，机器回库的例不算。

## 三、全唐文 010 册对照

010 册 182 页、26,928 格，人裁 338 格（对上 336 格），其中 5-b 给不出来的 29 格。字形库去掉了 010 册自己的全部刻例
（模拟这册还没人裁），库字档字表来自其余各册的人裁字。上游用 c1 包，两组都从 5-b 重跑到第 7 步。

| | 关 | 开 |
|---|---|---|
| 给不出来的 29 格：首位／前三／前十 | 0／0／0 | 10／25／26 |
| 基集内人裁 307 格：首位／前三／前十 | 281／300／306 | 281／300／306 |
| 全册首位变动 | — | 62 格 |
| 第 7 步放行／待审 | 26,926／2 | 26,926／2，逐格零差异 |

- 首位变动的 62 格里，60 格变成了现行放行的那个字（茲→兹 32、蘊→藴 5、溫→温 5、官→宫 5、𠎝 5、𦫵 3 等，
  都是刻形与整理本不同、现在靠 5a 库例放行的格），2 格不合（佀→侣 而放行 侶；升→𦫵 而放行 升）。
- 没找回的 4 格：𠴲、𤱶、𨽾 是别的册没出现过的字，库里没有；𠋫 一格排第 4。
- 𠋫、𥳑 进候选后多数排第 2，排在 候、簡 后面。要上首位得靠字对判别（5a.3），不是这个开关的事。
- 关着时与 origin/dev 5c276aa 全册 182 页产物逐字节相同。
- 耗时：5-b 整册，关 156 秒（先跑，缓存较冷）、开 81–88 秒，没有看到变慢（两次缓存状态不同，不能当提速看）。

第 7 步零差异要这样读：这些格在现行库里已有人裁或库例，第 7 步本来就按库放行。这个开关的收益在**还没人裁的册**上，
是人审卡片上直接出现正确字，以及 5-b 首位更接近刻形；010 册的对照量不到下游放行的变化。
