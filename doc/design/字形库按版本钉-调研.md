# 字形库按版本钉：现状调研与设计方向（2026-10-21）

> 状态：**已出细设计并实现**（`字形库按版本钉-细设计.md`，GUJI-727）。下面是 10-21 的调研原文。
> 原状态：**调研完，待设计**。这里写的是事实和方向，不是定稿。细设计、评审、实现交给新开的会话，跟踪卡见 Jira（GUJI，标题「字形库按版本钉」）。
> 起因：用户 10-21 提出，重跑旧册时**轻易不要改字形库**。字形库固定在某一版，只有开新册、或者明确要让旧册吃到新人裁时才换版本。
> 这样升级 CV 或语料库时，凡是只跟字形库有关的部分都可以跳过。

## 一、要的效果（用户原话归纳）

1. 云端的每一版字形库都有**版本号或内容指纹**。出了新版也不覆盖旧版，旧版随时能按号取回。
2. 册配置写明用哪一版；跑的时候**用的就是那一版的内容**，而不是「当前最新」。
3. 规矩：
   - 平时重跑、升级 CV 或语料库时，字形库不动，跟字形库有关的东西都不用重算；
   - 开新册、或者有意让旧册吃新人裁时，出新版本、把册上的号加一，受控地重跑一次，并出差异单。

## 二、现状（逐条核实过）

### 2.1 库指纹怎么进产物指纹

| 步 | 字段 | 现在的口径 |
|---|---|---|
| glyph_match（5a） | `db_fingerprint` | **软参数**（2026-09-25 用户定，`steps/glyph_match.py` 模块头「库指纹：记录，不判过期」）。库变了不判过期，只在 `status` 的「漂移」一列报页数；要吃新库得点名 `guji recheck`。格级复用（`core/reuse.py`）照常生效。 |
| glyph_match | `borrow_fingerprint` | 硬参数：借的库换了版本，这一步判过期。 |
| seed_admit | `human_fingerprint`、`approx_fingerprint` | 硬参数：整个工作区的人裁一变就整册过期。`glyph_pin` 就是为它加的（见 2.2）。 |
| rare_candidates | `db_font_fingerprint` | 硬参数：字体域在不在是实实在在的差别，不能钉。 |

结论：**5a 重跑慢并不是库变造成的**（实测：改一个切分参数后从 row_segment 重跑到 glyph_match，150 页里 133 页判新鲜跳过，
真正变了的那一页 171 格里复用了 164 格）。库变化影响的是 seed_admit 判过期，以及 5a「用的是不是同一份库」能不能复现。

### 2.2 `glyph_pin` 现在是什么

- `core/glyph_pin.py`：册 yaml 写 `glyph_pin: N`，`params_for` 把 `PIN_FIELDS`（`human_fingerprint`、`approx_fingerprint`）换成 `glyph-gN`。
- **只钉指纹，不钉内容**：跑的时候读的仍然是当前库（模块头原话：「钉的是指纹，不是库内容」）。所以同一册里各页用到的人裁新旧不一，号加一时也说不清「第 N 版」到底是什么内容。
- runbook S2「钉版三项」与 `doc/版本号规矩.md` 第七节要求每册钉 `glyph_pin`，但 **10-21 查殿本 10 册的 yaml（中心库 rev 34313），一册都没写**。`corpus: 11` 各册都钉了。

### 2.3 能不能取回旧版

| 途径 | 能不能当「按号取回」 |
|---|---|
| 中心库全局 `rev` | 每次写入加一（10-21 约 34,300）。只是一个序号，库里没有「某个 rev 时字形库长什么样」的现成读法。 |
| `guji db branch create … --from-rev N` | Neon 写时复制分支，可以从某个 rev 开出来再 `db pull`。但只能在 Neon 的历史保留期内往回开（保留期多长**未核实**，免费档一般很短），不能当长期版本库用，而且整个项目最多 10 个分支。 |
| 每日备份（GUJI-611） | 整库导出，保留 30 天，恢复要开新分支、用户点头。不是按版本取的。 |
| 共享刻例库 `glyphlib-<族>-v<N>` | **正是想要的形状**：每版一个只读工作区，同一个名字只能写一次，出新版就开新名字，借用方按名字拉（`ops/glyphlib.py`、`doc/datastore.md`「共享刻例库」）。但只用于借给别的书，本书自己的库没有这一套。 |
| 刻例图 | R2 里按 sha256 存（`BlobCache`、`fetch_blobs`），不会被覆盖。所以一份快照只要存文本加图的 sha，不用再存一遍图。 |

### 2.4 同一工作区多册

殿本 vol01–10 同在 `siku-zongmu` 一个工作区，共用一个 `glyph.db`（`core.workspace.glyph_db_path`）。要是不同册钉不同版本，就得各用各的库文件。

## 三、设计方向（供新会话细化、评审）

1. **出版本**：`guji glyph-db snapshot -w <工作区>` 把本书字形库真源（`output/glyph_store/` 的文本加图 sha 清单，必要时连 `feedback` 的水位线）
   定成只读快照 `g<N>`，同一个号只能写一次。存法二选一，评审时定：
   - 照 `glyphlib` 的写法，开中心库只读工作区 `<ws>-glyph-g<N>`；
   - 存成 R2 派生件 `derived/glyphstore/<ws>-g<N>.tar.gz`，加一份清单（内容 sha）。
   另可顺带存一份**建好的 glyph.db**（含派生表示，键 = 快照内容 sha + 建库代码指纹），新容器直接取，省掉重建（殿本约 55 s）。
   字体域已有预建件（`clustering/font_pack.py`），可以拼上去。
2. **册钉版本**：`glyph_pin: N` 的含义从「只换指纹」改成「用第 N 版的内容」：
   - 跑这册时用 `glyph-g<N>.db`（按版本分文件，各册互不干扰），没有就从快照建；
   - 跟字形库有关的指纹一律换成版本号，结果可以复现。这时 `db_fingerprint` 能不能重新改回硬参数，评审时定。
   - 没钉的册保持现行行为（读当前库），指纹逐位不变。
3. **人裁照常写当前库**：控制台裁决、`db sync` 都不变；只有出新版本时才进快照。旧册要吃新人裁，就出新版、改号、受控重跑、出差异单。
4. **要一起想清楚的点**：
   - 人裁「进库即生效」的通道（seed_admit 读人裁形状 `_human_shapes`、铁证匹配器 `iron_evidence.human_matcher`）钉版以后读快照，那刚审完的格在本册里什么时候算数？目前的想法：钉版时人裁事件仍按事件流生效，但需要确认；
   - `guji recheck` 的「库变了要点名重查」是否改为「换版本才重查」；
   - `exp` 框架、`close-check` 的钉版检查项、出口报告怎么报版本；
   - 跟 `corpus_pin`（语料库钉子，有版本清单、会校验内容）统一写法，字形库这次也要有清单、做校验。
5. **迁移**：殿本 10 册先出 `g1`（取当前库），各册写 `glyph_pin: 1`。这一步的指纹变化需要和 M9 的波次窗口对齐。
