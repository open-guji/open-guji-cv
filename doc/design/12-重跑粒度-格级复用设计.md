# 重跑粒度：从「页」到「格」——只对变了的字格跑 Step4–8（设计，2026-09-20）

- **触发**：用户「重跑能否更有效率？裁过之后如果字框位置没变化就不用重跑 Step5–8；指纹能否更精确；
  希望重跑后只对 131 个 seg_defect 格跑 Step4–8，而不是所有字格」
- **状态**：**已实现**（2026-09-20 当天，用户「先做 1 和 2」）。落地与设计的差别见 §六。

## 一、现状：指纹已经是「内容寻址」的，但粒度是页

`core/engine.py::fingerprint` = sha256(step.version, params, 代码哈希, **上游产物的 sha256**)。
注意最后一项是上游**产物文件**的内容哈希，不是上游的指纹——所以理论上 Step3 重跑后
只要某页 `cells` 文件**逐字节相同**，Step4 那页的指纹就不变、照报新鲜、不重跑。

实际做不到，两个原因：

1. **粒度是页**：`cells` 是一页一个 JSON，54 页里任何一页有一格的 `kind`/`x0`/`quad_page`
   小数点后变了，整页 Step4–8 全部重来。Step1 版框动 1px → Step2 列窗动 1px → 列图变
   → Step3 全页 boundaries 变 → 全书 Step4–8 全过期。这就是现在 `status` 的样子。
2. **`upstream_stale` 是传递的**：`_page_status_row` 里上游任一页过期，下游那页即使指纹
   对得上也标过期——设计如此（上游一改下游整链过期），但它把"上游改了、结果没变"
   也算成过期。

bxgb 实测每步耗时（54 页，manifest `elapsed` 中位）：

| 步 | 每页 | 合计 | 占比 |
|---|---|---|---|
| border_detect | 6.9s | 5.8 min | 13% |
| column_warp / column_gate / row_segment | 0.6 / 0.2 / 1.8s | 2.5 min | 6% |
| cell_shrink | 1.7s | 1.6 min | 4% |
| **glyph_match** | **12.7s** | **17.2 min** | **38%** |
| **ocr_candidates** | **17.0s** | **15.4 min** | **34%** |
| rare_candidates | 2.3s | 2.1 min | 5% |
| align_ref / context_decide / seed_admit | 0.1s ×3 | 0.3 min | <1% |

**72% 的钱花在 Step5-a/5-b 逐格的 CNN 匹配与 OCR 上**，而这两步是纯逐格的
（`for cc in columns: for r in chars: ctx.image("char_patch", r.patch_key)`），没有页级状态。
Step6/7 是页级算法（n-gram 上下文、整页 8-gram 锚定、段级词表）但只要 0.3 分钟，**照旧全跑**即可。
所以目标不是"所有步都格级"，而是**Step4/5-a/5-b 三步格级复用，其余不动**。

## 二、方案：格级几何键 + 步内复用，指纹层不动

### 1. 格的身份与几何键

- 身份：`id = book:page:col:slot[a|b]`，已是全管线主键，跨重跑稳定（只要该列格数不变）。
- 几何键：`geom = (kind, round(quad_page 四角, 1px), seam_top/seam_bottom 有无)`——
  `quad_page` 是**原图规范空间**的坐标（`cells.py` 头），与 Step2 列窗怎么动无关，
  正是"字框位置没变化"的定义。**不用列图坐标 `x0/y0`**，那随列窗漂。
- 容差：四角各 ≤1px 视为同一格。要不要放到 2px 得量一次（§三·1）。

### 2. 步内复用（Step4 / 5-a / 5-b 各加一段，共用一个 helper）

引擎给 `RunContext` 加两样：`ctx.prev_product(kind, page)`（上一版产物，manifest 里那份，
没有就 None）与 `ctx.cells_geom(page)`（本页每格几何键）。Step 基类加一个 helper：

```
reuse = ctx.reusable_ids(page)   # {id} ：上一版 cells 里存在、几何键相同、且上一版该步产物里有记录
```

三步的 `run_page` 逐格循环开头加一句：`if r.id in reuse: recs.append(prev_rec[r.id]); continue`。
Step4 还要把复用格的 `char_patch` 从旧缓存原样保留（缓存键就是 id，本来就不会动）。

判断"上一版存在"不能只看 `cells` 文件——要看**上一版 `cells` 的几何**，所以引擎在重跑
Step3 写新产物前把旧产物的几何键表存进 manifest 条目（`geom_sha` 一列 + `_geom/` 小文件），
或者直接留一份旧 `cells` 副本。前者干净。

### 3. 指纹与 stale 怎么算

不改。Step4 的指纹仍是 sha(版本, 参数, 代码, 新 `cells` sha)，重跑后产物文件是新写的
（复用的记录 + 重算的记录），manifest 记新指纹，`status` 报新鲜。复用只发生在 `run_page`
内部，**引擎眼里这一页就是重跑过了**。这样：

- 不引入"容差指纹"这种模糊概念——指纹仍是精确的；
- 复用的记录其输入（格几何 ±1px + 同一张原图）确实没变，结果可信；
- 参数/代码/库指纹一变，`reuse` 自动为空（helper 先比 Step 自己的 params/code 哈希，
  不同就不复用）——**换 checkpoint、改阈值仍是全量**，与 cv-pipeline-ops §2.2 的纪律一致。

### 4. 对 131 个 seg_defect 的效果

重跑 Step1–3 后（≈10 min），bxgb 18,153 格里几何键变了的预计只有：Step1/2 修了首行顶边
（cv-segmentation §十五）的页首格、Step4 端格截断（§十四）涉及的末格、人裁切点改过的列。
131 条 seg_defect 88 条在列端，正是这批。其余 ~17,000 格 Step4/5 直接复用，
Step5 两步从 32 min 降到按变动格数比例——**变动 5% 就是 1.6 min**。

⚠️ 但**名单不会自己退**：`crop_exclusions.jsonl` 按 id 排除，图块修好了名单还在，
Step7 照样把它当排除格。重跑后要一道"名单复核"：对名单上每个 id，比较新旧几何键，
变了的出卡让人看一眼（`review-artifact`），能进库的撤名单。这一步不做，格级复用省下的
时间等于白省——文本里还是 131 个 `[[]]`。

## 三、动手前要量的两件事

1. **容差**：用另一会话改完 Step1 后的 bxgb 重跑 Step1–3（本来就要跑），对比新旧 `cells`
   的 `quad_page`，看四角位移分布——1px 内的占多少、哪些格 >1px、是不是就是端格。
   这个数决定容差取 1 还是 2，也验证"变动只有 5%"是不是真的。
2. **Step5 对 1px 位移的敏感度**：抽 50 格，原图块与平移 1px 的图块各跑一次 glyph_match，
   看 top1/cov 变不变。不变就放心复用；变了说明连 1px 都不该复用，方案要改成
   "只复用几何键**完全相同**的格"（那样端格之外的格也大多相同，收益不会差太多）。

## 四、要用户定的

- 复用的记录**不带"这是复用的"标记**（产物里看不出来）还是带一个 `reused_from` 字段？
  带了可审计，但产物 sha 会因这个字段变动——建议不带，复用记录逐字节等于旧记录。
- 容差 1px（严）还是 2px（松），等 §三·1 的数。
- 名单复核那道卡谁裁、什么时候裁——建议跟这次重跑一起做，131 条一小时内能过完。

## 五、不做的

- 不改指纹算法本身、不引入容差指纹；
- Step6/7/8 不做格级（页级算法，且只占 <1% 时间）；
- Step1–3 不做格级（几何链必须整页跑）。

## 六、落地记录（2026-09-20）

与 §二 的设计比，三处改动：

1. **Step4 不复用，只 Step5-a/5-b/5-c 复用**。Step4 只占 4% 时间，而它产的 `char_patch`
   缓存在重跑前会被引擎按页清掉——复用 Step4 记录等于留下一堆没有图块的记录，得靠惰性
   `render` 补，得不偿失。Step4 全算（重切图块），Step5 三步拿新旧 `char_index` 逐格比
   `bbox_page`（±1px）+ cell_type/step3_kind/flags/patch_key，同则搬旧记录。
2. **"当时那份上游"靠 manifest 记的 sha 认**，不靠时间。`ProductStore.write` 覆盖前把旧文件
   挪到 `_prev/`（只留一代）；复用时要求 manifest 上一条 `upstream[char_index]` 的 sha 等于
   `_prev` 那份或盘上现在这份，否则不认（中间多跑过一次上游就对不上，见单测）。
3. **`self_hash` 进 manifest**（`engine.self_hash`，= 指纹去掉上游），复用第一道闸。老条目没有
   → 第一轮不复用。为了让 bxgb 这一轮就吃到，写了 `scripts/backfill_self_hash.py`：
   只对「参数哈希相同 + 盘上文件 sha 相符」的条目按现在的代码补——**这等于宣称插桩前后
   代码等价**，对 09-20 这次成立（三步各插 6 行搬记录的代码，判决逻辑没动，且 git 证实
   这两步及其 code_deps 自产物写出后没有别的提交）。**别拿它掩盖真算法改动。**
   实测：`ocr_candidates`/`rare_candidates` 54 页可补；`glyph_match` 只有 3 页——其余 51 页
   参数哈希不同，是字形库指纹变了（人裁进库），**库变了识别就该重算**，这是设计，不补。

落点：`core/reuse.py`（判据）、`core/engine.py::self_hash`、`products/store.py::_prev`、
`products/manifest.py::self_hash`、三个 Step 各 6 行、`GUJI_NO_REUSE=1` 关开关。
单测 `tests/test_cell_reuse.py` 7 条（含"中间又跑过一次上游不认"）。指纹值逐位与改前相同
（bxgb 4 步实测）。

**§三 的两个待量项还没量**：容差 1px 是拍的；Step5 对 1px 位移的敏感度没测。
这一轮重跑的日志里「复用 n/m 格」就是第一份数据。

## 八、第二轮实测：算法改了照样便宜（2026-09-20 15:5x）

用户问「算法确实会变，很难永久定稿——如果 Step1 变了但 Step4 结果不变，是不是 Step5–8
就不用重跑？」**是，实测如此。** 3 页先验（p6–8，Step1 起全链）：

```
glyph_match    135.0s  每页 [134.77, 0.12, 0.07]  复用 958/958
ocr_candidates   6.6s  每页 [  6.51, 0.03, 0.02]  复用 958/958
```

一格没重算。那 135s 是**首页的库冷加载**（一次 run 只付一次），不是匹配——第二、三页
0.12s / 0.07s 就是证据。OCR 的 6.51s 同理是引擎初始化。

全书（48 页重跑 + 6 页新鲜跳过，含另一会话当天提交的 Step1 清账与未提交的「列 x 在版框
中高处取」修复）：

| 步 | 耗时 | 复用 |
|---|---|---|
| border_detect | 6.14 min | — |
| 其余 Step1–4 | 2.57 min | — |
| **glyph_match** | **2.30 min** | **16313/16381 = 99.6%** |
| ocr_candidates | 0.25 min | 99.6% |
| rare_candidates | 0.07 min | 99.6% |
| Step6–8 | 0.13 min | — |
| **合计** | **11.4 min**（首轮 25.9、复用前 ≈45） | 0 失败 |

结论：**几何链改动不再需要"定稿"才敢重跑**。Step1 每改一次就全书重跑一次，代价是
Step1 自己那 6 min + 真动了的格。仍然全量的只有三种：换 checkpoint、改阈值、人裁进库
让库指纹变（`self_hash` 变 → reuse 为空），那是设计。

重跑后核对：`status` 13 步 54 页**全新鲜**（过期 702 → 0）；`progress` 待审 79 → 73、
切线 8 → 2、21 页无待办；9.1 零 stale、單行注 78 格；对勘一致 17,669 → **17,674**；
