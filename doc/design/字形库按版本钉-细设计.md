# 字形库按版本钉：细设计（GUJI-727，2026-10-21）

> 前文：`字形库按版本钉-调研.md`（事实与方向）。本文是细设计，贴在 GUJI-727 上评审；「待拍板」一节的推荐项先按推荐实现，
> 用户改主意再改。

## 一、一句话

`guji glyph-db snapshot` 把本书字形库真源定成**只读快照 g<N>**：清单（每个文件的路径加 sha256）随 `config/` 进中心库，
文本按 sha 进 R2，刻例图本来就在 R2 按 sha 存。册 yaml 的 `glyph_pin: N` 从「只换指纹」改成「**用第 N 版的内容**」：
跑这一册时，读字形库的步改读 `output/glyph-g<N>.db`（从快照建，按版本分文件），跟字形库有关的指纹换成快照的内容哈希。
没钉的册一字不变；钉了号却没有快照的册（旧做法）也一字不变，只多一行提示。

## 二、快照（g<N>）长什么样

数据目录 `config/glyph-pack/g<N>/manifest.json`（同语料库清单 `config/corpus-pack/v<N>/`，随 `config/` 进中心库 `files` 表）：

```json
{"version": 1, "ws": "siku-zongmu", "rev": 34313, "created": "2026-10-21T…", "note": "殿本首版",
 "digest": "glyph-1a2b3c4d5e6f7a8b",
 "borrow": ["glyphlib-qkp-v1"],
 "fingerprints": {"borrow_fingerprint": "", "approx": true, "n_human": 4374, "n_instances": 18512},
 "build": {"rebuild_code": "<glyph_db 代码指纹>", "algo": {…}},
 "items": [{"root": "gs", "path": "instances/vol01.jsonl", "sha256": "…", "size": 123, "type": "txt"},
           {"root": "gs", "path": "patches/v2_vol01_10_9_18.png", "sha256": "…", "size": 456, "type": "png"},
           {"root": "borrow:glyphlib-qkp-v1", "path": "exemplars.jsonl", "sha256": "…", "type": "txt"}, …]}
```

- `items`：`output/glyph_store/` 下全部文件（文本与刻例图），加借来的字形库（`root = borrow:<名字>`）。
- `digest`：items 的 (root, path, sha256) 排序后哈希，即快照的**内容指纹**，进产物指纹用它，不带版本号（同语料库 10-21 口径）。
- `rev`：出快照时数据目录对应的中心库 rev（要求数据目录没有未推的改动，所以快照就是中心库那一刻的字形库）。
- 一个号只写一次：中心库里已有的 `config/glyph-pack/g*/manifest.json` 再推、内容不同就拒绝（照搬语料库清单的守卫）。
- 不空升：内容与最新一版相同（digest 相同）拒绝出新号。

文本按 sha 存 R2（`sha256/xx/<sha>.txt`，与整理本同一套 `upload_files`／`BlobCache`），同 sha 不另存：
按册分的 `instances/<册>.jsonl` 没变就不占新空间。刻例图 db push 时已按 sha 进 R2，不重传。
**传的时机**：`guji db push` 推到一份基准里没有的 g<N> 清单时，清单登记的文本随这次 push 一起传（本机文件已与清单不同就拒推：
那一版谁都拼不出来，删号重出）。`snapshot-upload --execute` 留作补传。

## 三、按版本建库

`output/glyph-g<N>.db`（与 `glyph.db` 同目录，工作区本地，不进中心库）：

1. 拼快照目录 `cache/glyph-pin/g<N>/`：每个条目先找本机当前字形库里同 sha 的文件（通常全中），找不到从 R2 取（`BlobCache`）。
   任一条目 sha 不符或取不到 → 报错，不建半个库。
2. `rebuild_from_store(快照, 库, extra_stores=借库)`，同 `db pull` 的重建，不 replay。
3. 字体域：从当前 `glyph.db` 拷（`font_pack.export_pack`／`import_pack`，按 `font_manifests` 里的 edition），与当前库逐列相同。
   当前库没导字体就不拷，status 里提示。
4. 库的 `meta` 写 `glyph_pin = {n, digest, build}`。`build` = 建库代码指纹（`clustering.glyph_db` 源码哈希 + `ALGO_VERSIONS`）。
   下次用时 digest、build 都对得上就直接用；build 变了（派生算法改了）重建。

谁来建：`guji glyph-db pin-build -w <工作区> [--pin N]`（缺省：工作区里各册 yaml 写到的全部号）；`guji db pull`／`sync`
拉完后也顺手建缺的；`guji pipeline`／`step` 起跑前建（缺的、过时的）。引擎（第 1 层，不能 import 建库代码）只核对：
读钉版库的步（`glyph_match`、`seed_admit`、开了 `roster_glyph_refine` 的 `row_segment`）起跑前库文件不是那一版建的就拒跑。

复用条件还有一条：当前库的字体域指纹。新机器常是先拉库（顺手建了钉版库）、后导字体，导完下次起跑时重建一次把字体域带上。
出快照时登记的文件同时按 sha 存进本机图缓存（`BlobCache`），之后当前库再变，本机重建旧版也不用连网。

## 四、指纹与参数（`core/glyph_pin.py::with_glyph_pin`）

| 册的状态 | 读哪个库 | 指纹 |
|---|---|---|
| 没钉 | 当前 `glyph.db` | **逐位不变** |
| 钉了 N、没有 g<N> 清单（旧做法） | 当前 `glyph.db` | 不变（`human_fingerprint`／`approx_fingerprint` → `glyph-gN`），status 提示「只钉指纹，没快照」 |
| 钉了 N、有 g<N> 清单 | `glyph-g<N>.db` | 见下 |

有快照时，在 `params_for` 里（不改 Step 模块）：

- `glyph_match`：`db_path` → `glyph-g<N>.db`；`db_fingerprint`（软参数）→ 快照 digest；`borrow_fingerprint`（硬）→ 清单里记的值。
- `seed_admit`：`db_path` → `glyph-g<N>.db`；`human_fingerprint` → digest（开了人裁通道时）；`approx_fingerprint` → digest（快照有近似字时，否则空）。
  人裁形状、铁证匹配器、近似字表、共识升档都读 `db_path`，于是都读快照。
- `row_segment`（只在 `roster_glyph_refine` 开时）：`roster_glyph_db` → `glyph-g<N>.db`，`roster_glyph_fingerprint`（软）→ digest。
- `rare_candidates.db_font_fingerprint` 不动：字体域与快照无关，照旧读当前库（字体域在快照库里是同一份）。
- 只换「按工作区解析」的缺省库路径；书 yaml `params:` 显式写了别的库的，原样不动。

参数只读清单、不开库，`guji status` 不会因为库文件缺而算错指纹。`db_path`、`roster_glyph_db` 本来就是 `path_params`，不进指纹。

**17 步 code_hash**：改动只在 `core/`、`ops/`、`cli_glyph_db.py`、`datastore/`，都不在任何 Step 的 `code_deps` 里；
PR 里附改前改后 17 步 code_hash 对照（应全部相同）。

## 五、人裁怎么生效（钉版以后）

- 人裁照常写当前库（控制台、消费者、`db sync` 都不变），快照只在出新号时才收进去。
- **本格的裁决立即生效**：`seed_admit` 的事件通道 `feedback.lookup.human_chars`（读事件流，不读字形库）照旧实时，审完的格本册马上采信。
- **经字形库传播到别的格的部分**（库通道 `_human_shapes`、铁证、近似字、共识升档、5a 匹配）要等出新号、改钉才进本册。
- 让旧册吃新人裁：`guji glyph-db snapshot` 出 g<N+1> → 册 yaml `glyph_pin: N+1` → seed_admit 整册判过期 →
  `guji recheck <册> --glyph-diff N` 只点名换库后判决可能变的格（kNN 邻域差分，`ops/glyph_diff.py`；2026-10-24 起，原来用 `--verdicts unsure,diff --dead`，约半价） → `guji pipeline --from glyph_match` → `guji products diff` 出差异单。

## 六、其它接口

- `guji status`：册名下一行「字形库钉在 g<N>（glyph-xxxx，rev R，库文件 有/缺）」；旧做法提示「只钉指纹，没有快照」。
  5a 的「漂移」列：记录里的库指纹 ≠ 快照 digest 的页（钉版前对活库跑的页都会算漂移，这是实情）。
- `guji glyph-db pin-list -w`：列出各版本（号、digest、rev、条目数、本机库文件在不在、哪些册钉了它）。
- `guji glyph-db pin-verify -w --pin N`：对 R2 核对每个文本 blob 都在（推之前跑）。
- `guji glyph-db snapshot-upload -w --pin N [--execute]`：把文本 blob 传 R2（正式令牌，缺省演练）。
- `exp`、出口报告：已经记 `glyph_pin`，不改；产物包 `versions` 多记 `glyph_digest`。
- `recheck`：不改。`close-check`：不加项（出口报告的钉版行已有）。

## 八、待拍板

1. **快照存哪**（推荐 C）：
   - A. 照 glyphlib 开中心库只读工作区 `<ws>-glyph-g<N>`：现成；但每版把全部字形库行（殿本几万行）在 Postgres 复制一遍，Neon 存储额度有限。
   - B. R2 派生件 `derived/glyphstore/<ws>-g<N>.tar.gz` 加清单：便宜；每版整包存，没变的文件也重存。
   - **C. 清单进中心库（随 `config/`，几 MB），文本按 sha 进 R2、图本来就在 R2**：与语料库清单同一套写法与守卫；没变的文件不重存；不涨 Postgres 行数。
2. **指纹串**（推荐内容哈希）：`glyph-<digest>`（同语料库 10-21 口径，号变内容不变时不过期）还是 `glyph-gN`。
3. **5a 库指纹钉版后改不改硬参数**（推荐不改，仍软）：改硬则每次升号全册 5a 重跑（殿本一册约 1.5 小时，格级复用第一道闸失效）；
   不改则升号后用 `guji recheck --verdicts unsure,diff --dead` 点名重查（约半价）。改硬要动 `glyph_match` 的 `StepSpec`，17 步里它的 code_hash 会变。
4. **旧做法（钉了号、没快照）**（推荐照旧跑、只提示）：还是直接拒跑、逼着出快照。
5. **人裁生效口径**（推荐第五节）：本格立即生效（事件通道），传播等升号。
6. **建好的 `glyph-g<N>.db` 要不要存 R2**（推荐本期不做）：殿本建库约 1 分钟加字体拷表，先本地建；新容器多了再加。
7. **迁移时机**：殿本 g1 与 10 册写 `glyph_pin: 1` 何时推（各册 seed_admit 及其下游过期一次），对齐 M9 哪一波。
