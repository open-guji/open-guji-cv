# 分块设计：M11 网站反馈 ／ 第一阶段最小闭环（块 A 意见池＋块 C AI 初判＋块 D1 修订工具）

> 项目主力：M11 会话　｜　状态：执行中（用户 10-20：「你自己审完、觉得和计划相符就可以合；剩下的任务先往前推进」）
> 总设计：[M11-网站反馈流程-调研与总设计.md](M11-网站反馈流程-调研与总设计.md) 第五、六、七节。Jira：GUJI-712（A）、GUJI-713（C）、GUJI-715（D1）。
> 时间一律洛杉矶时间。

## 一、目标与边界

**目标**：一条读者文字意见，从网站进来，到 AI 初判、交用户或自动结案，再到冻结册出 1.x 新版本，全程走工具，不靠人手拼；每一步都留在中心库里，可以追溯。

**第一阶段做什么**
- **A 意见池**：先用中心库的**文件**（`feedback/lists/opinions/<书>/…`），不建新表、不改 Worker。现在量小（线上文字意见 1 条），文件够用，`guji db sync` 照常同步。等量上来或网站要实时读状态时，再迁成表（第二阶段）。
- **C AI 初判**：确定性的部分（规整、配证据、规则分流）写成命令。「判」这一步第一阶段由**会话本身**做：会话看证据包，写判定记录。这和 H 道现在的做法一致，用户 10-20 也定了「先手动测」。接口留好，以后可以换成 API 自动判。
- **D1 修订工具**：直接对 book-text 的冻结 char 应用已采纳的 A/B 类修订，外加 B′ 类，生成 PR，并在 CHANGES 里引意见 id。

**不做**
- 改网站：状态回显、统一入口都归 B2（GUJI-714）。
- 写 CV 人裁事件：要恢复 rev 快照工作区才带得上锚。第一阶段只把「该写的事件」列进待办清单，第二阶段在恢复的工作区里补写（GUJI-718）。
- C 类切分修订（拆格、并格、整列）：依赖 GUJI-579。
- 机器意见（E）、深度自检（F2）。

### 2.2 `guji-opinion/0.1`（opinions.jsonl 一行）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | str | `op_<渠道>_<来源 id 的 sha1 前 10 位>[_<序号>]`；同一来源拆成多条时加序号 |
| `book` | str | book-text 书 id |
| `vol` | str | 章号 `NNN` |
| `channel` | str | `charfix`／`span`／`cellreview`／`feedback`／`machine:<名>` |
| `raw_id` | str | 原始记录 id：KV key 去掉 voter、`fb_…`、机器检查号 |
| `voter` | str? | 来源哈希，用来去重计数；`fb_` 没有 |
| `ts` | str | 原始提交时间（ISO，UTC） |
| `target` | obj | `{start, end}` 格号（单格时两者相同）；`text_version` 或 `rev`；`check`：读者看到的原文（取自 char） |
| `category` | str | `wrong`／`missing`／`extra`／`order`／`seg`／`lacuna`／`unclear`／`punct`／`entity`／`other` |
| `proposal` | obj? | `{text}` 建议文字，或 `{choice}` 精校档 |
| `note` | str? | 读者原话，按网站规则脱敏后的 |
| `normalized_by` | str? | 由自由文字规整来的，记规整者（会话名或 `rule`） |
| `created_at` | str | 入池时间 |

### 2.3 log.jsonl 事件

`{ts, opinion, kind, by, data}`，`kind` 取值如下：

| kind | 何时记 | data |
|---|---|---|
| `ingested` | 入池 | — |
| `superseded` | 被新 id 取代 | `{by}` |
| `dup` | 判为重复 | `{of}` |
| `forwarded` | 转给别的线（标点、专名） | `{to}` |
| `triaged` | 判定完成 | 判定记录，见 2.4 |
| `decided` | 用户裁决 | `{decision: accept／reject／discuss, by}` |
| `applied` | 已进文本 | `{text_version, pr}` |
| `replied` | 已回复读者 | `{text}` |
| `cv_written` | 已补写成 CV 事件 | `{batch}` |

意见的**状态**由 log 推出来，不另存：

```
new → triaged →（auto_accepted｜auto_rejected｜to_user｜discussing｜forwarded｜dup）→ accepted／rejected → applied
```

### 2.4 判定记录（log `triaged` 的 data，总设计 §5.4）

| 字段 | 内容 |
|---|---|
| `verdict` | `text_ok`（原文对）／`accept`（建议对）／`lacuna_guess`（图无字，录阙文带推测字，Q7）／`seg_issue`／`out_of_scope`／`unclear` |
| `confidence` | 0–1 |
| `rationale_public` | 公开理由，一句话 |
| `rationale_internal` | 内部理由 |
| `evidence` | 证据包路径或摘要：裁图 sha、上下文 |
| `route` | `auto_accept`／`auto_reject`／`to_user`／`discuss`／`forward` |
| `revision` | `{class: A／B／B′／C, cells: [{a, from, to, lacuna?, guess?}]}` |
| `reply_draft` | 公开回复草稿 |
| `judge` | 判定者：会话名或模型名 |
| `profile` | `published` 或 `proofing` |
| `engine` | 引擎版本 |

### 2.5 text_versions.json

```
{"<章>": [{"text_version", "date", "pr", "rev", "cv_version", "cv_commit", "snapshot", "kind": "cv_export"|"manual"|"revise"}]}
```

由 book-text `default/CHANGES.md` 解析得出。人写的散文解析不出的字段留空，`locate` 报「缺」。

## 三、程序架构（open-guji-cv）

新包 `open_guji_cv/opinions/`，只依赖标准库、Pillow、`datastore`，不碰任何 Step，`code_hash` 不变：

| 模块 | 内容 |
|---|---|
| `schema.py` | dataclass 加校验，JSON Schema 导出 |
| `store.py` | 读写上面五个文件；本地路径在数据目录 `feedback/lists/opinions/<书>/`；`--remote` 时经 Worker `/v1/files` 读写，带 `base_sha` 乐观锁 |
| `ingest.py` | 三个来源的适配器：`fixes.jsonl`（cf/cs/ce；ce 直接 `forwarded`）、`<rev>.jsonl`（cr）、`/api/feedback` 公开读（文字类，`category=typo` 或页面在 `/read/`）。`fb_` 进来时状态是「待规整」 |
| `textsrc.py` | 取 book-text 的 char/cord/CHANGES：本地 book-text 检出，或 GitHub raw |
| `evidence.py` | 证据包：IIIF manifest 找原图档，下载整页（按 sha 缓存）后按 cord 框裁该格，外加前后各 3 格的条带；上下文 ±12 字；同格其他意见；排除名单、marks（如那格是 `excluded`） |
| `rules.py` | 确定性规则：超出范围 → `forward`；同格同建议 → `dup`；`check` 与当前 char 不同 → 「已改」或版本漂移；`published` 档的门槛；用户亲裁过的格 → `to_user` |
| `revise.py` | 修订：A（改 `c`）、B（□↔字）、B′（cord 里 `excluded`／`blank` 的 mark 变成 lacuna 格，带推测字）；写 char/cord，调 book-text 的 `bump_original.py`，CHANGES 引意见 id |
| `cli.py` | `guji opinions …` 子命令 |

子命令：

| 命令 | 作用 |
|---|---|
| `ingest [--book] [--dry-run]` | 三源入池，幂等 |
| `list [--status] [--vol]`／`show <id>` | 看意见和状态 |
| `locate <id>` | 格号加版本 → 当前格号、text_version、rev、快照 |
| `normalize <fb_id> --into <json>` | 会话把自由文字规整成一条或多条 |
| `pack <id…> --out <dir>` | 出证据包，外加一页拼图 `sheet.png` 和 `sheet.md`，给会话看 |
| `triage <id> --verdict … --confidence … --public … [--revision …]` | 写判定，规则表决定 route；也可 `--from <tsv>` 批量写 |
| `to-user --out <dir>` | 交用户的意见出成审阅页数据（用 review-artifact skill 发页）；`decide --from <收回的裁决>` 记 `decided` |
| `revise --book --vol [--dry-run] --book-text <检出>` | 对已采纳的意见改 char/cord，升 patch，写 CHANGES；打印 PR 正文 |
| `reply-drafts` | 列出已结案、待回复读者的意见和回复文字（回写网站归 B2） |

## 七、风险与未决
- **最可能出错的一处**：B′ 把 mark 变成格时的格号和读序。mark 的 `slot` 与 char 格号口径不一定相同（002 第 3 页第 1 列：mark slot 9 的框在「卷」字 `3:1:9` 之下）。新格号按「同列最后一个字的格号＋1」取，插在该字之后；单测要覆盖夹注列、抬头列。
- 中心库 `/v1/files` 正式令牌能否写 `feedback/lists/opinions/**`：A4 前实测，不能就走 `guji db push`。
- book-text CHANGES 的散文解析不全，`text_versions` 会有缺字段；`locate` 报缺，不阻塞第一阶段。
- 读者回复要写网站 `fs:` 状态，得有网站管理令牌，本会话没有。第一阶段只出回复草稿。

## 九、设计变更记录

| 日期 | 改了什么 | 为什么 |
|---|---|---|
| 10-20 | **id 的来源键规范化**：`op_<渠道>_<sha1(来源键)>`，来源键 = 渠道前缀＋书＋三位章号＋版本＋格位（＋类别）＋来源哈希前 6 位；`raw_id` 仍照各来源原样（KV key 去 voter；公开读 `kind~首格~末格~类别~who`） | 线上那条改字还没同步进中心库 `fixes.jsonl`，只能从公开实时读 `/api/fixes` 取，那里 voter 只给 6 位。来源键不规范化的话，日后 Action 同步进 `fixes.jsonl` 会再入池一次 |
| 10-20 | **一票一条**：同一格不同来源各是一条意见（id 含来源哈希），同格同建议的后来者入池时就记 `dup`（不等 `rules`）；同一来源改了意见（网站同 key 覆盖）追加 `<id>_2`、旧条 `superseded` | 「voter 用来去重计数」要求每票可数；A2 验收要求入池即出 dup |
| 10-20 | schema 补字段：意见 `extra`（渠道特有原始字段，如精校票的 shown、pick_src）；`target.entity_version`（专名意见没有 text_version）；判定记录加 `rule`（规则给的去向理由）、`draft_event`（总设计 §5.4 的起草事件）、`evidence_agree`（自动采纳门槛用）；B′ 的修订格加 `after`、`mark` | 落地时缺的信息；都是可选字段，不改已有字段的意思 |
| 10-20 | B′ 新格号：取**读序上紧挨 mark 之前那个字格**的格号＋1（mark 按上沿插进 char 读序）；算出的格号已有字就拒绝（要改格号，归 C 类）。抬头列 `-1` 之后是 `1` | 原写法「同列最后一个字＋1」只对列末成立；mark 夹在列中时会插错位置。真书 002 `3:1:9` 是列末，两种算法结果相同（`3:1:10`） |
| 10-20 | 阙文带推测字的写法做成开关 `--guess-style`：`lacuna`（缺省，现行 v0.1：`□`＋`lacuna`，推测字只进 CHANGES 与意见池）／`guess-char`（现行残字写法 `c=一`＋`guess: true`）／`guess-str`（D4 扩展，`guess: "一"`，GUJI-717 合了才能用） | D4 还没合，D1b 先用哪种写法要用户定 |
| 10-20（合并前，项目主力） | `--guess-style` 去掉 `guess-str`，改为 `guess-c` 并设为缺省：`{"c":"□","lacuna":true,"guess_c":"一"}`，用到它的章 `$schema` 写 char v0.2 | D4 已合（guji-format#21、open-guji-cv#280），实际格式是新键 `guess_c`，不是让 `guess` 取字符串；这正是用户 10-20 定的显示方式 |
| 10-20 | 伴生层跟随：插格后标点 `char_offset`、实体 `span` 全部按锚点重算；锚在前一格、`pos: after` 的点号与分段符挪到新格；改过的标点、实体线各升 patch | 字下标是字流下标（guji-format 00 §四·2），插一格后面全部要挪。代价：002 首例 PR 里 punct／entity 是机械的大 diff（本地演练 7379／3057 处），char 只多 1 格、cord 只挪 1 个框 |
| 10-20 | 意见池本地后端加 `--root`（不进数据目录、`guji db sync` 不会推）；会话的试判、演练都写在 `--root` 下 | 用户要求首例判定先不落库 |
| 10-20 | 包放在 L4（与 `review`、`ops` 同层），命令行 `cli_opinions` 在 L6 | 只依赖 `core`、`datastore`，不被下层引用 |
