## 〇、一页摘要

**范围**：从「选定一册书」到「这一册在 book-text 是 0.1.x、待审单和字块图在网站上、所有该留的数据在中心库／R2」为止。之后的人审精校归 M10，网站长期反馈归 M11。

**现状**：四庫總目 vol04–10 已按这条线跑过两轮。M8 新基线的人审率在 0.78%–1.68%（7 册合计 1,775／189,776 格，约 0.94%），流程能走通，有三点不足：
1. **能跑，但离不开熟手。** runbook 有 20 步，其中约 10 步要人或会话看图、手配。关键脚本散在 ai-team 工单目录里，没有版本，也没有测试。编排脚本 `zl.py` 从没整册实跑过，而且还在读中心库切换前的路径。
2. **数字不可信。** 人审率至少有三套口径，同一册先后报过 466、437、303、280、279、273 好几个数。新鲜度也有两套判据（R1 严、1a 宽）。派生结果不带上游指纹：重切或重排号之后，旧裁决、旧体检结果会悄悄错位（GUJI-623 的两例）。
3. **数据去向没定死。** 产物有三套存法（snap 分支、R2 数据快照、R2 产物包）。冻结基线记在三处，三处对不上。雪碧图只有 vol01 有，vol04–10 的精校页没有字块图。book-text 和中心库里的待审单还是 10-19 那一轮的，不是 M8 新基线。原图有一部分只在某台本机上。

**这次人审率下降，主要靠人裁回流，不是算法改进**（例如 vol09 有 110 格是新读到的人裁）。要让人审率持续下降，得先把成因分清，交给对口专家修，再用固定评测集验证收益。这个回路现在还没有。

**方案**：把粗校做成一条**有闸门、有台账、按波次推进的生产线**。分 8 个领域（第五节），每个领域写好输入、输出和验收（第六节），节奏按「一波 N 册 → 归因 → 专家改 → 验收发版 → 下一波」走（第八节）。性能单独写成需求书交给专家（第九节）。

**要你定的 7 件事**见第十一节；不答就按各条写的默认做。

## 一、范围与边界

### 1.1 M9 管什么

```
 选书立档 ─▶ 原图入库 ─▶ 环境/数据就绪 ─▶ Step0–4 切分 ─▶ 切分闸(R2/R6) ─▶ Step5–7 识别定字
   ─▶ 定版自检(AI 看图、异常表) ─▶ 落盘(中心库/R2) ─▶ 导出 char/cord/norm ─▶ book-text 0.1.x
   ─▶ 待审单 pending.json + 字块雪碧图 ─▶ 网站精校页可见  ══▶ 交给 M10
```

### 1.2 不做什么

- **人审本身**：网站精校页的交互、公众意见、AI 落裁决、升到 1.0.0、归档，归 M10（GUJI-637）。M9 只保证交出去的待审单准确、齐全、可追溯。
- **定稿后的长期反馈**：归 M11（GUJI-638）。
- **标点、专名**：不管。
- **具体算法改进**：形近字、异体归 M7（GUJI-563）。切分算法、性能各有专家。M9 负责**归因、派单、验收收益**，不替专家写算法。
- **非正文页**（目录、职名、序跋、牌记）：照旧只报数，不优化（cv CLAUDE.md）。
- **不重跑已冻结的册**：vol01（1.0.0）、vol02–03（1.0.x）。它们只在 M10／M11 里做局部修。

### 1.3 与 M10 的交接线（契约）

M9 把一册交给 M10，同时交出下面四样东西，四样都以同一个中心库 `rev` 为准：
1. book-text main 上 `NNN.{char,cord,norm}.json`，文本线 0.1.x，`proofing: true`；
2. 中心库 `feedback/lists/proofing/<书>/<章>.pending.json`（guji-proof 0.2），每格带 `img`（雪碧图坐标）；
3. R2 上本册的产物包，标成 `main`（正式基线），记 cv 版本、语料号、字形库号；
4. 本册台账一行（第七节 7.3）：人审数、人审率、成因分布、重切清单数、放行错抽检结果。

M10 回给 M9 的东西：人裁事件（进中心库）、成因标注（「其实是切分错」这类）。这些进入第六节 D6 的归因回路。

## 四、发现的问题（按环节）

每条标了出处（A／B／C／D 指底稿），以及归到第五节的哪个领域。

### P1 入口：开一本新书没有现行流程 → D1
- 唯一的开书文档是 overview `项目进展/新书整理/开书手册.md`（09-28），里面服务器导入那一套已经过时，而 overview 本身已淘汰（C）。
- 没有书单。路线图只写了「全唐文、四庫全书排在四庫總目之后」。四庫總目只下了 vol01–10 的原图，全书还剩多少册没人核过（C）。
- 原图落点不一致：四庫、北行的原图在 guji-workspace git 里；**全唐文的原图被 `.gitignore` 拦住，只在某台本机上**（B）。GUJI-598（落原图还是 WebP）还没定论。
- 全唐文借四庫的字形库，人审率约 26.7%，09-27 暂停扩量（C）。换书时冷启动怎么做，没有方案。

### P2 环境与拉数据：每开一个新容器，要付 30–45 分钟的固定成本 → D2
- 依次是 `db pull` 4.5–8 分、字体域 12–15 分、rare index 10–19 分、LM 现训约 28 秒（A）。
- 云容器大约每小时回收一次，后台任务 30 分钟会被杀，靠指纹续跑（C、D）。磁盘约 4 GB，低于导入门槛 10 GB（D）。
- GUJI-627（R2 缺 121 张锚图、语料钉选漂移）数据已经补上，cv#258 也加了缺图跳过，但**没人在新容器上验收，卡也没关**（B、D）。

### P3 版本、指纹、新鲜度：同一套规则有好几种说法 → D3
- 开工钉什么，设计稿和实践不一致。设计 §2a 要求钉正式 tag，不跟 cv 升级；实际上 vol04–10 跑在 rc 分支未打 tag 的提交上，一册里混了好几个提交（C）。10-19 用户改为「在当时的 cv 下新鲜即可」，设计稿没有跟着改。
- 出口有两套新鲜判据：R1 用 `guji status` 严口径，close-check 1a 用宽口径，vol09 已经踩过（A）。
- **人裁指纹是 seed_admit 的硬参数**：任何人 `db sync` 推一次人裁，没钉 glyph_pin 的册就全部判过期（10-19 夜 vol04–10 全过期）。glyph_pin 又不在标准配置里（A、C）。
- PR 合进已发版的 rc 分支，改动就丢了（先后靠 #206、#265 补回）；`--params` 加 `--jobs>1` 时参数被丢，指纹照记；`bindings.py` 不在 code_deps 里，改它不判过期；没装 torch 时产物照样「新鲜」（C）。
- 跨项目改共用配置没人协调：M7 改了 `config/groups`，导致语料钉选漂移（D，推测）。

### P4 派生结果不带上游指纹，上游一变就悄悄错位 → D3
- GUJI-623：重切之后，旧的「切坏」裁决仍按格位挡住新切结果，vol01 因此出了 75 个 □。
- 同类：字形库体检结果停在 09-26，vol01 刻例 09-27 重排了编号，结果控制台出卡全错一格。GUJI-586 挡出口的 23 个离群也来自这份过期结果（D）。
- vol02 重跑后有 27 格人裁被补锚逻辑顶掉（D）。
- 这三例根因相同：**裁决、体检、绑定这类派生结果，没有记录它是基于哪一版切分或字形库算出来的。**

### P5 切分缺陷：拦不住，也改不了 → D4
- A 类 373 格的根因在切分或对位。整页、整列丢字（R6）没有落仓的检查工具，`colgap.py`、`widthscan.py` 在哪个仓都找不到。三道闸和 2c、2d 都拦不住整列问题（C）。
- 切分侧已有的盘点见 `doc/research/切分现状梳理与新方向-2026-10-19.md`，D4 开工先读。
- 实例：四联叶拆页裁偏（GUJI-625）、vol04 p80/p217 窄切占待审 22%（cv#101 缺省关）、职名页夹注被当正文切（GUJI-536、624）、vol03 57:1 整列没切出。
- **人工 override 通道一个都没有**（GUJI-579 及子卡 618–621：整列重切、逐页页型、补格删格、版框列框，估 44–62 小时）。现在切分错了只能等改代码，或者手改文本，结果产物和文本分叉，vol01 就是这样。

### P6 人审率：口径不一，没有台账，归因不全 → D6
- 至少三套口径：close-check 队列、pending.json、人审率分析（去标题槽）。vol04 同一册有 0.78%、0.88%、1.27%、1.35% 四个数（A）。
- 每册的「当前数」没有单一真源，各处数字前后打架。例如 vol04 new-glyphs 的记录，结论写 279→273，表里写 279→279；vol09 正文说「遮挡 272 格」，同一份报告的分类计数里只有 43（C）。
- 「其他」类占 35–45%，没有分类器，归因只做了一次（vol04–09），不能每波复算（A）。
- 下降来自人裁回流，不是算法（D）。缺一道「放行字变了必须看图」的闸：每次换基线都留下几格没核（07 有 4 格、09 有 13 格、10 有 3 格），会越积越多（D）。

### P7 工具散落，编排脚本过时 → D2
- 关键脚本 `pending_list`、`alt_build`、`sprite_build`、`decision_build`、`exit_report`、`collect_exit`、异常表模板都在 ai-team 工单目录里，没有版本、没有测试；而 cv 的 runbook 直接引用它们（A、C）。这和 10-20「长期东西进资源仓」的规矩相左。
- `zl.py` 从未整册实跑，还从 `ws/books/` 读册 yaml，没有 db sync 一步，快照仍走旧的 snap pack（A）。
- runbook 的 S8、S20、close-check `--notes`、修图记录仍写到已淘汰的 overview；S19 写推 `wip/siku`，实际是每册开 PR 并入 main（A、B）。
- runbook 第五节「交付标准 14 项」把粗校出口和精校出口混在一起（第 2 项「待审清零」是 M10 的事）。

### P8 数据去向：一份数据存在几处，或只在某台机器上 → D7
- 产物有三套存法：git 孤儿分支 `snap/*`、R2 数据目录快照 `snapshot/`、R2 产物包 `pack/products/`。哪份是正式的，靠人记（A、B）。
- 冻结基线记在三处，没对齐：vol01 的 `freeze.snapshot` 指向 git snap 分支，R2 有同名产物包，中心库 `freeze_baselines`、`snapshots`、`cv_versions` 三张表都是空的（B）。
- `packs._ws_name()` 拿不到 `.central.json` 时回退成 `"ws"`，vol01–03 的包落在 `products/ws/` 下，用 `-w siku` 取不到（B）。
- 雪碧图设计上要进 R2，实际走的是 dataset Release 加指针，而且**只有 001 有**。中心库里 004–010 的 pending 都没有 `img` 字段（B）。
- 只在本地、丢了就没了的东西：全唐文原图；北行、全唐文的产物（R2 没有包）；`reports/`（请审单、cards.alt、Step9、体检结果）；导出目录里的 lines.md、pages.json；runs（B）。
- 备份只剩一份。设计里「git 每日导出作第二份备份」没有落实，现在只有 R2 `backup/`，和图在同一个云上（B）。
- workspace.yaml 在中心库和 git 里各一份。`PROOF_WS` 只配了 siku-zongmu，新书要手工加（B）。

## 六、各领域的输入、输出与验收

格式按 `ai-team/process/项目驱动与计划优先.md`：每个领域写目标、输入标准、输出、步骤要点和验收。验收写成「命令＋数字」。这里只写领域一级，分块设计由各块负责人在评审通过后按 `templates/part-design.md` 细化。估时单位是小时，机器时间另列。

### D1 选书立档与原图入库

- **目标**：任何一本新书（四庫總目后续册，或别的书），按一份现行文档加一条命令，就能到「Step0 预检通过、可以开跑」。
- **输入标准**：book-index 里已有 Book 条目（10 位 id）；影像源已确定（IA、CADAL 等），有可下载的清单；已选好整理本或证人（可以没有，但要写明）。
- **输出**：
  1. cv `doc/runbook/开一本新书.md`：替代 overview 的开书手册。
  2. `guji book init <book-index-id> --source <IA清单>`：在中心库 `workspaces`、`books` 登记，写 workspace.yaml；**原图按 sha 进 R2**（guji-workspace git 不再增长），生成原图 manifest。
  3. 冷启动档位表：借哪个字形库、要不要先做 10–20 页测试集、预期人审率区间。
  4. 书单：`config` 或中心库里一张表，列出候选书、册数、原图状态、优先级。
- **步骤要点**：先补全唐文原图入 R2（P1 的丢失风险）→ 核四庫總目全书册数和原图来源 → 写 init 命令 → 用四庫 vol11 实走一遍。
- **验收**：
  - 新容器上 `guji book init` 加 `guji db pull` 后，`guji pipeline … --to page_survey` 不报错；
  - R2 原图 manifest 的 sha 数等于页数，`git -C guji-workspace status` 无新增大文件；
  - 全唐文原图 R2 manifest 齐全，和本地文件 sha 全对上。
- **估时**：约 6–10 小时（含下载机器时间另计）。

### D2 跑批平台与编排

- **目标**：在一个空的云容器里，一条命令从拉数据跑到出口报告。只在定义好的闸门停下等人，停下时写清做什么。
- **输入标准**：D3 的钉版规则已定；D7 的落盘规则已定；第九节的预建件（字体域库、rare index）已在 R2，或者先接受冷建。
- **输出**：
  1. `zl.py` 改成 `guji rough`（或升级 zl.py）：读中心库、带 db sync，产物包走 `products pack push`，删掉旧 snap pack 路径；首次整册实跑留下度量。
  2. ai-team 里的粗校脚本迁进 cv `scripts/zhengli/`（或成为 `guji` 子命令），配单元测试：`pending_list`、`alt_build`、`sprite_build`、`decision_build`、`exit_report`、`collect_exit`、异常表模板。
  3. 云容器标准环境：setup script，`[torch]` 必装且自检失败即停；长任务一律 `setsid nohup`。
  4. 介入记录：每次停下记哪一步、为什么、等了多久、人花了几分钟（runbook 第六节「介入次数」落成数据）。
  5. runbook 改写：去掉 overview 落点；S19 改成「并 main」；第五节拆成「粗校出口（M9）」和「精校出口（M10）」两张表。
- **验收**：
  - 用 vol06（150 页）在新容器上 `guji rough run --book vol06` 到出口，**介入 ≤ 3 次**（版面先验、S8 看图、异常表结论），机器墙钟 ≤ 2 小时（性能专家合入后再压，见第九节）；
  - ai-team `team/整理/` 下不再有被 cv runbook 引用的脚本，可用 `grep -r "ai-team" doc/runbook` 核对为 0；
  - 迁过去的脚本有测试，跑全量测试全绿。
- **估时**：约 12–18 小时，另加机器时间约 2 小时／次实跑。

### D3 版本、指纹与新鲜度

- **目标**：任何一个产物、裁决、体检结果、台账数字，都能说清它基于哪版 cv、语料、字形库、切分。上游一变，下游要么自动重算，要么明确标过期，不允许静默错位。
- **输入标准**：第十一节第 2 条（钉版策略）用户已定。
- **输出**：
  1. **钉版规则**写进 `doc/版本号规矩.md` 和设计 §2a：每波开工发一个正式 tag，波内的册都钉这个 tag 加语料号加 glyph_pin；波内修复进 rc，下一波生效。确需中途换版的，按「受控重跑」出差异单。
  2. glyph_pin 进标准册配置（粗校期钉字形库，别人推人裁不会让本册过期）。
  3. 新鲜度只留一套判据：R1 和 close-check 1a 合一，`--strict-cv` 作可选项。
  4. 派生结果带上游指纹：裁决记锚点（bbox、content_sha），体检结果记字形库指纹，绑定记 Step3 sha。读的时候比对，不一致就标 `stale`，**放回闸门重判**，不再沿用（GUJI-623 的通用修法）。
  5. 小坑一次清完：`bindings.py` 进 code_deps；`--params` 加 `--jobs>1` 丢参的修复核验；合 PR 前查 rc 是否已发版，做成本地检查脚本。
- **验收**：
  - 新测试：①重切一格后，旧 seg_defect 裁决不再排除该格；②字形库重排号后，体检结果标过期、控制台不出卡；③推一条人裁后，钉了 glyph_pin 的册 `guji status` 仍新鲜；④改 `bindings.py` 后 seed_admit 判过期；
  - vol02–04 扫一遍「裁决锚点和当前切图不一致」的排除格，列出清单（GUJI-623 要求）；
  - 全量测试全绿；19 步 code_hash 变化在 PR 里列明，并写清各册是否要重算。
- **估时**：约 10–14 小时。

### D4 切分质量闸与人工 override

- **目标**：整页、整列丢字或错位，机器在 Step4 后就能拦住（R6 有工具）。拦住的问题，人能用 override 事件当场改，改动走事件、可重放，**不再手改文本**。
- **输入标准**：D3 第 4 项（派生结果带锚点）已合，否则 override 之后旧裁决会挡住新切图。
- **输出**：
  1. R6 检查进 cv：整页字数异常、列宽异常、列格数与版式先验或整理本列长不符、列间隙漏切（把散在外面的 colgap、widthscan 思路正式实现），产出**重切清单**（机器维护，进中心库）。
  2. override 四类事件（GUJI-579 的 618–621）：`column_recut`、`page_type`、`slot_edit`（补、删、并格）、`border_offset`。经控制台或 `guji events add` 写入，Step 重放时生效，进 code_deps 和指纹。
  3. 「重切清单清零」做成机器判的闸：粗校出口时，清单里每格要么已修，要么在待审单里标 `seg_bad` 交 M10。
- **验收**：
  - R6 在 vol01–10 上对已知案例召回 100%：vol01 p196 整页、vol03 57:1 整列、vol04 p80/p217 窄切、四联叶裁偏页；同时报出误报数，以 ≤ 每册 10 列为目标；
  - 四类 override 各有一条端到端测试：写事件 → 重跑 → 产物变 → 导出变 → 再跑一次结果不变；
  - 用 override 修 vol03 57:1（与 vol01–03 线协调），char.json 出字，不手改。
- **估时**：R6 约 8–12 小时；override 44–62 小时（沿用 579 的估算，可只先做 `column_recut` 与 `page_type`）。
- **与 M10 的关系**：M10 的人审页也要发 override。事件格式由 D4 定，M10 只做前端入口。

### D6 人审成因与专家反馈回路（M9 的核心）

- **目标**：把各册、各波的待审格统一归因，按成因派给对口专家；专家的改动在固定评测集上验证收益，确认有用才进下一波。用户的说法是「帮大家把结果整理到一起，哪些结果给谁反馈」，落到这里。
- **输入标准**：D3 已合（数字可追溯）；有至少一册的完整待审单。
- **输出**：
  1. **统一口径**（第十一节第 3 条请用户定）。默认：人审率 ＝ 正文页送 M10 的待审格数 ÷ 正文页字格总数（不含标题槽、非字格）；重切清单数、非正文页另报。
  2. **成因分类器**（cv `guji rough reasons --book X`）：每个待审格打一个主成因码，写进 pending.json 的 `cls`。码表用人审率分析的 A–I，再加「切分可修」「字形库缺例」「整理本异文」等细分。目标是「其他」< 10%。
  3. **台账表**（中心库新表 `rough_ledger`，或 `files` 下的 JSONL）：每册每次出口一行，记 cv 版本、语料号、glyph_pin、rev、总格数、待审数、人审率、成因分布、重切清单数、S8 结果、墙钟、介入次数。**这是每册「当前数」的唯一真源**。网站和 Jira 只引用它。
  4. **派单表**（谁收什么）：

     | 成因 | 交给 | 交付形式 | 回收什么 |
     |---|---|---|---|
     | A 切分／对位、重切清单 | 切分专家（D4） | 格清单＋原图裁图＋所在页 | 新 cv 版本＋R6 召回 |
     | B 码位异体、C 形近 | M7（GUJI-563） | 按字组分的格清单、上下文 20 字 | 字组解法＋册配置更新 |
     | I 库 unsure、字形库缺例 | 字形库（glyphdb-audit） | 缺例字表＋候选刻例 | 新刻例入库（人裁） |
     | G 对齐改字、整理本异文 | 语料／整理本 | 冲突列表 | 语料新版本号 |
     | D 遮挡、真不可读 | 不修，直接交 M10 | — | — |
     | 慢、OOM、冷启动 | 性能专家（第九节） | 度量表 | 新版本＋基准数 |
     | M10 回来的「其实是 X 错」 | 按上面路由 | M10 的成因标注 | — |

  5. **固定评测集**（金丝雀）：从 vol04–10 各抽若干页，加上已知难例，冻结成「粗校基准」，放进 open-guji-dataset，用 `guji eval run` 跑。专家的改动先在 `guji exp` 旁路沙箱上跑基准，报两个数：人审率变化、错放数（必须为 0）。确认有收益才进 rc。
  6. **每波一份归因报告**：成因分布、各专家上一波改动的实际收益、下一波目标。由 M9 协调会话生成，贴到 Jira。

  - 台账覆盖 vol04–10，每行可由一条命令重算，重算结果相同；

## 七、存放原则：中心库、Cloudflare、本地、git 各放什么

### 7.1 四条原则（建议）

1. **人产出的、不可重算的** → 中心库。文本行进 Neon，二进制按 sha256 进 R2（只增不改）。包括人裁事件、台账、锚、册配置、字形库账本、语料、待审单、异常表结论。
2. **可重算但贵的** → R2 包（带 manifest，只增不改）：产物包、字体域 glyph.db、rare index、数据目录快照、原图。
3. **便宜可重算的** → 只留本地：cache、glyph.db（不带字体域时）、runs。
4. **git** 只放代码、文档、规范和公开成品：book-text 放文本，dataset 放评测和归档。**guji-workspace git 冻结，不再进新书的原图。**

**国内发布副本**（COS／EdgeOne）只是从中心库或 R2 单向导出的缓存，任何人不往里写真源。

## 八、节奏：在哪跑、什么顺序、跑一段提一段

### 8.1 在哪跑（建议）

| 场所 | 用来干什么 | 不用来干什么 |
|---|---|---|
| **云会话**（4 核，会被回收） | 跑批主力：一个线程负责一册，从拉库到 0.1.x | 训练、长于 1 小时又不能续跑的任务 |
| **本机 GPU** | 模型训练（U-Net、小分类器）、大规模重算 | 写正式库（照常走 db push） |
| **美国服务器**（2 核 7.5 G，已搁置） | 控制台、H 道、中转站 | 整册跑批（内存不够） |

规则：**一册由一个线程持跑批位，一直做到 0.1.x**，不中途交接。同时在跑的册数 ≤ 线程数，云上建议 3–4 册并行（性能合入后再看）。

### 8.2 波次（跑一段、提一段）

```
 第0波：vol04–10 换新基线、补齐出口（D8-3）               ← 先把已有的做对
 第1波：vol11–N（N 视原图和 D1 结果，建议 10 册）         ← 用当时的正式 tag 跑
   └▶ 归因报告 ─▶ 专家改（限时）─▶ 粗校基准验证 ─▶ 发新 tag
 第2波：下 10 册（用新 tag），已出 0.1.x 的册不追新版
   └▶ 同上
 第3波起：人审率和错放稳定后，扩大并行或换书（全唐文等）
```

- **进入下一波的条件**：上一波每册出口过；归因报告已出；至少一项专家改动在基准上验证有收益并进了 tag；错放 = 0。
- **专家改进窗口**：每波之间留固定窗口（建议 1–2 天墙钟）。窗口内只合进 rc，到点发 tag，没赶上的进下下波。这样跑批永远钉一个版本，不会在波中途换版。
- **已出 0.1.x 的册不追新版本**：只有当新版本在基准上能让这册的人审率降 ≥ 20%（建议阈值）时，才用受控重跑**只重跑待审格所在页**，出差异单。其余的交 M10 人审。
- **各波人审率目标（建议，待定）**：第 1 波 ≤ 0.8%，第 2 波 ≤ 0.6%，第 3 波 ≤ 0.5%；错放始终为 0（S8 抽检）。

### 8.3 每册的顺序（单册内）

`立档/拉库 → Step0–4 → R6 切分闸（有问题先 override 或进重切清单）→ Step5–7 → 定版自检（放行变化看图、S8、异常表）→ 落盘 → publish → 台账`。本册 Step5–7 跑的时候，同线程可以先拉下一册做 Step0–4（实测从 2.5 小时降到 1.5 小时）。
