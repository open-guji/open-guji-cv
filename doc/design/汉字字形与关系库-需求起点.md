## 0. 一页话

1. **要的不是「字典」，是「以字找字」的底座。** 定字时有三步：
   - ① 人或模型先给出一个近似字 p，比如整理本字、5-b 前几名；
   - ② 展开 p 的异体、形近、同部件邻居；
   - ③ 按刻本字块图排序。

   字统网只帮了第 ② 步，而且不排序。离线实验（414 条）里：
   - 族按图排序后，top-3 是 413/414；
   - 同一个族不排序，top-5 只有 353；族扩到 22 字时只剩 122。

   **关系表决定能不能找到，图像排序决定排第几**，两样都要。
2. **关系表是命根子，图像近邻代替不了。** 只用 p 的 30 个字形近邻、不查异体表，只找回 25%：异体形和正字往往长得不像，如 歴/歷、𨕖/選。
   我们的表也比字统网小得多：「互」我们一跳 3–4 字，字统网 76 个已编码字加 69 个未编码形。
3. **库要有四样东西**：
   - 字（码位与属性）；
   - 关系边（有向、有类型、有来源、有许可）；
   - 字形（多套图，加 CNN 向量）；
   - 部件索引。

   还要能离线打包、按版本钉住（会进产物指纹），每条数据都能按许可过滤。
4. ~~**最大的风险是许可，不是工程。**~~（10-19 晚用户已定：关系是事实，许可不挡导入，见文首补充。下面这段留作背景。） 字统网的族多出自《汉语大字典》《汉字海》、台湾《异体字字典》，没有数据许可，**不能整站爬来建库**（10-19 已定）。
   能合法用的开放源不少（§6）：Unihan、IDS、GlyphWiki、部件檢索（非商业）、cjkvi（无 LICENSE）、康熙公版扫描自切。缺口要靠我们自己的人裁回流补。

## 1. 现在怎么用字统网，慢在哪

### 1.1 调用点

| 调用点 | 代码 | 怎么用 |
|---|---|---|
| 出待审单 `guji audit alt <册> [--fetch-zi]` | `review/alt_cands.py` → `clustering/variant_sources.py:ZiCache` | 每格的近似字查一跳族，并进候选池，按图排出 ≤30 个，挂在卡上的 `alt` |
| 控制台「以字找字」 | `GET /api/rare/alt/...`，`AltPanel` | 人键入近似字；缓存里没有的现取一次 |
| 卡片修饰 | `rare_panel._decorate` | 只放字统网外链 |
| 研究脚本 | `research/pivot_family/coverage_sources.py:zi_family` | 覆盖对比 |

- 取法：`GET https://zi.tools/api/zi/<字>`，解析 `yi.nodes`＋`yi.edges`，走一跳，只收已编码单字（`zi_parse`）。
- 缓存：`$GUJI_DATA_HOME/_shared/zitools/U+XXXX.json`，只存 `{q, fam, ts}`，不进 git。
- 族不对称（查 𫎇 得 蒙，查 蒙 不得 𫎇），所以缓存同时记反向边。

### 1.2 慢和不稳

- 单字约 2.5 秒、约 400 KB（大半是 SVG 和 base64 图），礼貌间隔 ≥3 秒。
- 10-19 取 236 字用了约 25 分钟。
- **10-20 本会话实测**：vol04 待审 283 格，`--fetch-zi` 新取 501 字。光礼貌间隔就要 25 分钟以上（501×3 秒），算力那部分只要两三分钟。
- 新机器缓存是空的：每台机器、每个会话都要重新取。
- 依赖外站：站点改版或断网时 `ZiCache` 静默当没有，候选池悄悄变小。
- **它的族噪声大**：族按「字典义项」连，混着通假、同音、构件关系（歷 的族里有 勒栗壢），只能当池子、必须按图排。

### 1.3 字统网一条主条目里有什么（10-20 实测「互」）

这一节是为了看清**要替代的是哪些字段**。

| 块 | 内容 | 我们要不要 |
|---|---|---|
| `yi.nodes`（183 个） | 每个节点＝「某部字典的某义项」，17 个字段，含：节点 id、来源前缀、条目号、字形（已编码字或 IDS 串）、释义（如「同=䇘」「同「牙」」）、读音（`G:hu4`）、正字、出处（如《敦煌俗字典》p.914）、标签 `互(氐)` | **要**，这是异体关系的核心。粒度要到「义项」，不能只到字 |
| `yi.edges`（307 条） | 节点间有向边（异体／同某），按义项归到正字 | **要** |
| 来源前缀 | GHZR＝汉语大字典、TVAR＝台湾异体字字典、GHZH＝汉字海、IVD、SAT＝大藏经、ZITOOLS＝站方自建；另有 FZK、JMJ、GZJW、T13、V0/V1、FANGYAN（含义待查） | 来源要保留，许可按来源定 |
| `yi.ies` / `to_var1` / `to_var2` | 部件树（IES），部件变体折叠（如 `⿰⿱⿸乙丿一阝(邸)` → `邸(邑氐)`） | 要：部件索引、未编码形归属 |
| `yi.relatives` | 按部件的「相关字」（以 氐 为部件的 低抵貾…；以 昏 为部件…） | 要：同部件邻居 |
| `yi.kv` | 康熙字典原文、说文、IVD 序列、`ma`（各地区字源码）、`ids_zi_tools`、词源注、英文字源 | 部分要：康熙位置、IVD、IDS；释义另有来源（`config/gloss/`） |
| `font` | 若干字的 SVG 路径（当代标准字形、小篆） | 要字形，但从我们自己的字体出 |
| `yi.tubrief` / `POST /api/tu/` | 字形演化图（甲骨、简帛、书家、韵书、康熙切图），内嵌 base64 PNG | 可选；刻本时代的字书切图有用，见 §3.4 |
| `yin` | 读音（含日语训读） | 低优先 |
| `unihan` | Unihan 字段，站方用的是 **18.0.0** | 直接用 Unihan 原档 |

## 2. 使用场景：谁会来查这个库

按对本项目的价值排序。S1–S3 是这次的主需求，S4 以后是顺带能统一掉的散表。

| # | 场景 | 输入 → 输出 | 时效 | 现在用什么 |
|---|---|---|---|---|
| S1 | **出待审单**（`guji audit alt`） | 一批近似字 → 每字的族（异体一跳／两跳＋形近＋部件邻居），带边类型和来源 → 按字块图排序 | 批量，一册 1,000+ 格，几分钟内 | 本仓表＋部件檢索 rt＋字统网缓存＋形近表（`family_pool`） |

| S3 | **网站粗校页**（kaiyuanguji-web `/proofing`） | 只显示 `alt` 和字形雪碧图，零计算 | 出单时算好 | ai-team `GUJI-557/alt_build.py`（I.Ming＋Jigmo 出图） |
| S4 | Step5-b 稀见字候选检索 | 字块图 → 全字表 embedding 近邻（现 70,304 字，unicode-cjk-ab） | 管线内 | `cnn_candidates`，按书预建 `build-rare-index` |
| S5 | 字体模板／字形图 | 字 → 多套字体渲染图（扩展区用 Jigmo） | 管线内＋控制台 | `font_candidates`、`/api/glyphlib/font/{c}.png` |
| S6 | 异体三层（关系层／用字账／语义层）、`variant_tie`、义定形未定 | 字对 → 是不是异体、哪一类（T1/T2/T3）、方向 | 管线内 | `variants.json`（**在 5-b 的 `code_deps` 里**）、`never_group.json`、`local_edges.json` |
| S7 | 形近护栏、`ids_guard`、形近对表 | 字 → 形近字（IDS 差一槽／视觉余弦） | 管线内 | `config/ids/confusable_pairs_v1.tsv`、`ids_confusable_pairs_v1.tsv` |
| S8 | IDS／部件检索（RarePanel） | 部件或 IDS → 字 | 交互 | `config/ids/ids_lv1.txt`、`/api/rare/search` |
| S9 | 卡片修饰 | 字 → 释义、康熙位置、频次、整理本对应字 | 交互 | `config/gloss/gloss.json`、`config/kangxi/` |
| S10 | 简体白名单 | 字 → 是不是简体（`s2t(c) != c`） | 管线内 | OpenCC |

**10-19 已定的架构约束**（人审找字 §9）：
- 网站上不现算，出单时算好写进待审信息；
- 控制台跑在有模型的机器上，可以现算。

所以库的**主形态是能下载到本机的离线数据包**，供 cv 与控制台用。HTTP 服务是可选的第二形态（§5.2）。

## 3. 数据需求

### 3.1 字（已编码）

- **码位全集**：以 Unihan 当前版为准，约 10.3 万统一汉字（仓里的读数：`ids_lv1.txt` 102,032 字，`gloss` 全字表 102,998 字；字统网用的是 Unihan 18.0.0）。建库时以实数为准，并记下 Unicode 版本。
- **规范化**：
  - 兼容区一律折成统一汉字（`utils/cjk_compat`，10-19 起）；
  - 导入外部数据先做 NFC（MTHv2 里 復 U+F966 与 U+5FA9 并存）；
  - PUA 不作键（全字庫、教育部、全宋體三套 PUA 互不相通）。
- **属性**：
  - 区块、IDS（多套，保留地区标记 `(G,T,J…)` 与多种写法）、部首笔画；
  - 康熙位置（`kIRGKangXi`，`kx2ucs.txt`）、IVD 序列；
  - 简繁标记（OpenCC 判据）；
  - 释义（带许可，见 `config/gloss/README.md`）；
  - 本项目的频次：各书整理本、刻本字形库刻例数。

### 3.2 字（未编码形）

- 键用 IDS 串或 GlyphWiki 名，**不造 PUA**（variant_strategy 已定）。
- 字段：出处（哪部字书、页码）、归属的正字、字形图（GlyphWiki KAGE 渲染或字书切图）。
- 有 IRG 工作集「Unify to U+xxxx」判定的，记成「等价于某已编码字」。

### 3.3 关系边（核心）

每条边至少要有这些字段：

```
(a, b, 方向, 类型, 来源, 来源条目/义项, 许可, 证据, 人审状态, 加入版本)
```

- **类型**要分开，**不能混成一个「异体」**：
  - T1 纯异体（任何语境可互换，髪/髮、㫖/旨）；
  - T2 互通／一对多（鍾/鐘、注/註、后/後）；
  - T3 形近、通假、古文（己/已/巳、上/二）；
  - 简繁（只对简体刻本有意义，对繁体刻本方向是反的）；
  - 通假（`hydzd-borrowed`）；
  - 形近（视觉或 IDS 派生，**永不当异体**）；
  - 同部件／构件关系；
  - 本项目刻本实证（`local:keben`）。
- 来源标签和 T1/T2/T3 对不上：twedu 既收 㕔~廳 也收古文 上~二。一对字最终归哪类由本书用字账定。所以**边上存「来源说的类型」，书上存「这本书怎么用」**，两层分开。
- **方向**：要存 (正字, 异体)。`cjkvi/traditional`、`kTraditionalVariant` 的原文是简在前，导入时要掉头。
- **粒度到义项**：字统网的节点是「字典的义项」，同一对字可能只在某个义项上是异体。只存到字这一级会把 T2 当成 T1。
- **不传递**：
  - 查询缺省只走以正字为中心的一跳星形；
  - 全来源连通分量会长到 23,533 字（`config/variants/report.json`）；
  - **永不按共享成员并组**（叁 会把 三 和 參 串成一团）。
- **人裁回流**：人用以字找字从 p 选到 g、而库里 p–g 没有边时，记一条候选边。复核后进库，标 `local:`，每条写 why。**表会随审书自己长**，这是补上「公开库都缺的边」的唯一路（㫖/旨、互/亙）。

### 3.4 字形

| 层 | 来源 | 用途 | 注意 |
|---|---|---|---|
| 字体渲染 | I.Ming（IPA，传承字形，56,778 字）、Jigmo 三档（CC0，覆盖全部统一汉字）、genmin（OFL）、康熙字典体（TypeLand，**商业字体，可分发产物前须确认授权**） | 模板、排序、网站雪碧图 | 天珩全字库禁用（字形拼凑自商业字体）；花園明朝已停更，用 Jigmo |
| 字书切图 | 康熙字典公版扫描自切（Commons 哈佛武英殿本、国图、CADAL）：检测 44,633、赋字 32,899，和字统网对得上的 14,181 张里不一致 0.37% | 刻本时代的「标准」字形 | 字统网内嵌的康熙图只有 70×70 且重度二值化，不能用 |
| 刻本刻例 | 本项目字形库（中心库），共享刻例库 `glyphlib-qkp-v1`（1,076 例、827 字） | 最贴近真实刻本 | 借来的实例记成 `borrowed_human`，不当本书铁证 |
| 未编码形 | GlyphWiki dump（215.5 万条，可自由使用含商用），kage-engine 渲染一次约 14 ms | 族内未编码形的图 | **只作图、不作模板**：当模板时异体分歧靶 top-1 −16.8 |
| 演化图 | EVOBC（CC BY-NC-SA）等 | 可选，先秦–汉 | 本项目只做刻本，低优先 |

- **统一归一化**：64² 归一图（`clustering/normalize.py`、`extra_glyphs.py` 的口径）。
- **CNN 向量**：
  - 每字每字体一条，r5 主干，**fp16**（每字 512 字节；7 万字约 36 MB，10 万字约 51 MB）；
  - 不用 int8（族内 top-1 掉到 369）；
  - 向量要记 checkpoint 指纹，换模型就要整库重算并出新版本。
- **原则**：字体字形只出候选，**永不当精确判据**（对／错命中的分布重叠）。

### 3.5 部件索引

- IDS → 部件树，支持三种查法：部件组字、IDS 查字、「结构相同、只差一槽」的邻居（`IdsIndex`、`ids_guard` 的口径）。
- **部件变体折叠**：UCV 和部件檢索的 `vt.json`（853 条，如 ⻏→邑）、IDS lv2（按 UCV 合并部件变体，还没用）。
- 要兼容字统网那套 IDS 扩展语法（`.` 分隔、`#(…)` 笔画描述、`^`），现在的 `parse_ids` 认不了。

## 4. 查询接口需求（库内函数，cv 直接 import）

**性能**：
- 本地查族、查形近 <10 ms／字；
- 控制台以字找字从输入到出图 <200 ms；
- 一册 1,000+ 格的 `audit alt` 不再被外站卡住，目标是分钟级。

## 5. 非功能需求

### 5.1 版本与指纹（最容易踩的坑）

- `variants.json` 等表在 Step5-b 的 `code_deps` 里，改一下各书产物就判过期。新库**必须带版本号**，册 yaml 钉版本，做法照语料库版本化（`corpus: N`，底库 `bM`，见 `doc/datastore.md` §六、`语料库版本化方案.md`）。
- 换版本前要能先做指纹迁移（`fp-migrate`），否则一换库全书重算。
- 只给候选、不进放行的那部分（`alt`、以字找字），按现在的做法放在不进 `code_deps` 的模块里，换库不让产物过期。

### 5.2 发布形态

- **主形态：离线数据包**。像中心库的底库清单（`corpus-base`）、共享刻例库那样按版本发布，`guji db pull` 拉到本机只读。
  - 大小估算：关系边几十万条、几十 MB；fp16 向量 10 万字×几套字体，几百 MB；字形图另算。
  - 要能只拉需要的部分，比如不带图、只带关系与向量。
- **可选第二形态：HTTP 服务**，给没装模型的机器和网站用。
  - 10-19 讨论过 Cloudflare 还是自有云，当时定的是不在网站现算。
  - 要不要做、做在哪，请用户定（§9）。
- 如果做服务：只读、可缓存（字 → JSON 不变就带版本号做 CDN 缓存）、鉴权沿用 Worker 那套。

### 5.3 许可分层

- **每条边、每张图都带许可字段**，导出时能按「可商用／非商业／仅内部」过滤。
- 网站要不要展示只来自某些来源的候选（人审找字 §11.3，悬而未决），靠这个字段一键切。
- 部件檢索（WFG）、cjkvi、EVOBC 等非商业或无 LICENSE 的来源要标注出处；**进可分发产物前**要逐个确认。

### 5.4 溯源与可审

- 每条边可追到来源文件和条目号（字统网节点 id 那样）。
- 人裁回流边要写 why、谁裁的、在哪一格（`local_edges.json` 的格式）。
- 构建可复现：同一批输入，库要逐字节相同（照 `rebuild_from_store` 的验收口径）。

### 5.5 更新

- Unicode／Unihan 新版本，每年一次。
- GlyphWiki dump，每日更新，按需重拉。
- 本项目人裁回流，持续增长。

## 7. 已知坑（别再踩）

1. **异体关系不传递**。连通分量当等价类必然出事：最大连通分量 23,533 字，叁 把 三 和 參 串起来。
2. **简繁边会污染繁体刻本**：后/後、注/註 只靠简繁边连着，不能桥。
3. **hydzd 噪声造假组**：廳 把 聽 拉进组，歷 把 曆/厲 拉进组。
4. **机器转换不能当并组证据**：match_replace 自产的 註 形成正反馈，「注」的人审率一度到 97%。只认人裁确认的对。
5. **自动判据分不开真异体和不同字**：频次、上下文 Jaccard、来源分级都试过（真异体 決/决 min=22，不同字 倒/到 也是 22），只能靠人工审定的名单。`never_group.json` 现有 54 对。
6. **字统网的族按义项连**，混有通假、同音、构件关系，而且不对称。
7. **公开库全都缺的边**：㫖/旨、互/亙。只能靠人裁回流补。
8. **字体字形不能当精确判据**：I.Ming recall@5 只有 0.692，Jigmo 0.479。GlyphWiki 变体形当模板，在异体靶上 top-1 −16.8。
9. **大字表并进检索池会冲垮名次**：top-1 43→29；扩B 抢答 10 例、救回 2 例。要「小表定前 3 名，大表补召回」，按余弦分归并，**不能拼接**（RRF 只看名次）。
10. **康熙表含简体**（国 学 体 都带康熙页码），挡简体要用 OpenCC 判据。
11. **方向别丢**：旧构建丢过方向，后来才补 `directed`。
12. **yitizi 的许可两份文档记得不一致**（CC0／MIT），数据又不可溯源，用前核清。

## 9. 请用户定的问题（总设计之前）

> 10-19 晚：第 2、3、4 问由用户的许可定调答复；其余按建议默认走，用户可改。逐条见总设计 §2、§3、§5。

1. **范围**：只做刻本用得到的（已编码约 10 万字＋字书里出现的未编码形），还是连字形演化（甲骨、金文、简帛）一起？建议先只做前者。
2. **字统网缓存**：已取下来的族（派生事实，不含图）能不能作为新库的一个来源（标 `zi` 来源、仅内部）？还是新库完全不碰字统网，只拿它做对照？
3. **对外**：这个库或服务会不会对外公开？公开的话，非商业和无 LICENSE 的来源（部件檢索、cjkvi、EVOBC）要剔除或单独打包。
4. **教育部《異體字字典》**：要不要去申请授权？它能根治正字表缺失（`is_regular`），也是台湾异体最权威的源。
5. **服务形态**：只做离线包，还是再加 HTTP 服务？加的话用 Cloudflare（Worker＋R2，已有一套）还是自有云？
6. **仓**：新开仓（如 `open-guji/hanzi-db`），还是先放在 open-guji-cv 里？关系层现在在 cv 的 `config/` 下，且进 `code_deps`。
7. **项目卡**：按「项目驱动、计划优先」，要在 overview 开项目卡，并定负责人。
