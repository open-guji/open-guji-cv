## 0. 一句话

M8 把精校的骨架搭起来了，vol01 也走到了 1.0.0。但这一路上真正起作用的是**用户本人在控制台和裁定页上逐格裁、会话手改文本**：公众回路和 AI 裁决没有在真实流量上跑过；质检只查流程走没走完，没查字对不对；1.0.0 的文本里有手改，和冻结产物对不上；归档一册都没做成。
**M10 要做的，是把「0.1.0＋待审单 → 1.0.0 → 冻结、归档 → 清理工作区」做成一条能批量跑、能拿数字证明质量的流水线，先在 vol04 上走通一遍，再推到 vol05–vol10。**

## 0.5 用户 10-20 的决定（v0.2）

1. **抽检**：人力不够做每册 1,000 格的人工抽检。改成**自动复核**：用和放行通道无关的读者（OCR、看图模型）复核放行字，只把分歧交人；人工只做小量校准（每册约 50 格），用来估计自动复核的漏检率（§6 G6）。
2. **不在 book-text 里直接改字**。一切改动都写成人裁事件（含 manual-cells 之类的切分事件），进中心库，重跑涉及的页，再导出（§6 G2、D5）。
3. **网站用户的意见经 AI 裁决后落的裁决，算人裁，可以进字形库**：网站上做校对的大多是认真的读者，意见本身就是人的判断。没有任何人的意见、只是 AI 预判的，仍然要用户点头才算（原则 6、D3、D4）。
4. **vol01 冻结用最新的快照**（`snap/96mid1ogzk/vol01/20261020T0142`，cv_commit `456b30c`）；72:9:9、134:2:9 两个已知错要修，按第 2 条走人裁事件。
5. 其余按本文建议的默认做：vol02、vol03 照实标「按旧定义的 1.0」；书影落点选 A（原图打进私有归档包）；非正文页只进团队单，不上公众页；工作区仓轮换和 Cloudflare 以外的备份，等有具体方案时再问用户。

## 1. 目标与范围

### 1.1 目标
1. **1.0 的质量能拿数字说话**：每册 1.0 带一份质检报告，里面有放行错误率的 95% 上界（建议 ≤0.5%，门槛由用户定），已知的错一个不留。
2. **审一格的成本降下来**：待审单上只放真正要人看的格；卡片上的信息够判断；AI 先给出预判，用户整批点头，公众意见作为补充证据。
3. **每一格的字都有出处**：发布的文本＝冻结产物导出＋一份有出处的修订清单，不再有来路不明的手改。
4. **1.0 之后数据不丢，工作区也不再变大**：一册一个归档包，能恢复、能拿来做评测和训练；工作区按规则清理；1.0 后的局部修订有固定通道。

### 1.2 范围
起点是 M9 的出口：文本 0.1.0 进了 book-text，待审单进了中心库，cv 版本固定在一个正式 tag 上。
终点是 1.0.0 发布、冻结登记完成、归档包恢复演练通过、工作区里这册清理掉、1.0 后修订通道可用。
主要对象是 **vol04–vol10**（用户 10-20 定：1–3 册不再整理，专注 4–10 册）。vol01 只做补质检和归档，当作回溯试点；vol02、vol03 只定标签怎么处理（§10 第 4 项）。

### 1.3 不做什么
- 标点、专名号（另有人负责）。
- 降低人审率的算法（M7、M9，以及各方向的专家）。M10 只负责把精校里发现的问题按类回流给他们（§7 D1 的回流单）。
- 粗校流程、性能、结果存哪（M9）。
- 1.0 之后读者在阅读页提的改字和讨论（M11）。但 D3 的 AI 裁决器要按 M11 能直接复用来设计。
- 2.0 出版级。

## 4. 解决思路（原则）

1. **以发布的 char.json 为准做质检**，不只看 cv 产物。凡是和冻结产物导出不一样的格，都要能对上一条出处（人裁事件、manual-cells、修订单）。
2. **切分错了就修切分，不手改文本**。补齐 override 能力，修正写成带锚事件，重跑涉及的几页；实在来不及，手改也要进修订单、带出处。
3. **整理本只是证人之一**，质检里至少要有一路和整理本无关的信号：第二个模型读图、不用整理本训练的语言模型、另一个版本的证人。
4. **高风险的全看，低风险的随机抽**。抽检的用途是给出错误率上界，不是找错；找到一个错，就按同字组、同通道、同页型扩查。
5. **AI 先判，人整批点头，公众补证据**。现实是公众流量几乎为零，用户是事实上的终审人。把「AI 预判＋用户批量终审」做成正式主通道，公众意见作为一路证据进同一个裁决器。
6. **裁决要分得清来源，但不必分高低**（v0.2，用户定）：用户亲裁、网站意见经 AI 裁决（`source=web_ai`，带意见 id）都算人裁，进字形库；只有 AI 预判、没有任何人的意见的，要用户点头才落；看图结论（vision）照旧只送审。每条事件都结构化记来源、意见 id、模型与 prompt 版本，出错能按来源整批撤。
7. **出口动作做成检查项**，不写成说明文字。1.0 的每一条条件都要能用命令核，出数字。
8. **冻结就是冻结**：冻结的代码有 tag，快照在 R2 里 pin 住，在中心库登记。改冻结就是一次修订，要有新的 r 号和新版本号。
9. **工作区只是工作台**。到 1.0 就打冻结包，归档通过就清理；数据的长期落点是归档包、评测集和中心库。

| G3 | **机器检查全过**：close-check 终校档（含 2c、2d），字形库离群闸，并且体检时点晚于最后一次改库 | close-check 退出码 0；`glyph_audit_gate` 退出码 0 | F2 |
| G4 | **已知错单清零**：各处历史错例汇成一张表，对当前文本逐格核 | 仍然是错字的＝0 | 新增 |
| G5 | **高风险格全看过**：高风险通道（context、rare_ref、iron、match_solo、seal、witness3、coord_fallback 等）全量；形近组全册逐格；跨版本或跨模型分歧全部裁完；非正文页专项通读 | 每项「判错且没处理」＝0；vol01 基线估计约 1,170＋若干格 | F2 补洞 |
| G6 | **自动复核给上界**（v0.2，用户定：人工抽 1,000 格做不到）：全部放行格交两路和放行通道无关的读者复核（不看整理本的 OCR；只对分歧格再调看图模型），三方一致记「复核过」，分歧的交人；另由人校准约 50 格（复核过的随机 30 格＋判错的 20 格），估自动复核的漏检率 | 分歧格全部处理完；报「复核一致率」和按漏检率校正后的错误率上界；发现的错都修了、都按同字组扩查过 | F3 |
| G7 | 意见台账里没有未处理的意见 | 台账查询：未处理＝0 | F4 |
| G8 | **冻结与出口动作齐**：cv tag、R2 冻结包 pin 住、中心库三张登记表各有一行、yaml 顶层有 `cv_version`、`proofing=false`、文本线 `review` 字段（n、错数、上界、种子）、decision.json（可以为空）、lacuna 与字一致、已通知下游 | 新命令 `guji release check`：全部 ✓ | F5＋§4.4 出口动作 |

所有项写进 `<册>.1.0质检报告.json`；book-text 文本线的 `review` 字段和冻结包都引用这份报告。

抽检样本量参考（单侧 95% 上界）：1,000 格 0 错 → 0.30%，1 错 → 0.47%；3,000 格 0 错 → 0.10%。同一 cv 版本、同一流程的几册可以合并算，攒到 3,000 格就能对外说「本流程放行错误率 ≤0.1%–0.16%」。万分之一靠抽检证明不了（需要约 3 万格）（C §4.2）。

## 7. 领域拆分

分九个领域。每个领域在分块设计时还要细分成 0.5–4 小时的块，每一步写输入标准和验收标准。估时是第一感，标「估」。

### D1 待审分流（审什么、给谁审）
- **目标**：交给人的格又少又对路，成片的问题回流去修，不逐格审。
- **输入**：M9 出口的待审单（中心库 `feedback/lists/proofing/…`）；中心库里最新的人裁事件和绑定表；页型（Step1 页面分类）；「不上公众页」的页清单；cv 固定 tag。
- **输出**：
  1. 待审单 0.3：扣掉快照之后已裁的格；按正文和非正文分；每格标 `audience: public|team`；rev 自动递增，记 `based_on_db_rev`。
  2. 回流单：同一原因约 20 格以上的成组列出，交 M7、M9、CV，带格号和样例图。
  3. 每次导出一行统计：总待审／扣已裁／扣非正文／上公众／回流。
- **验收**：
  - 用 vol01 001-r2 重放：公众单＝4 格（9:7:17、10:7:16、90:1:3a、90:1:17a，和 book-text#169 一致），团队单＝其余 59 格，统计行几个数字能对上。
  - vol04 的待审单补齐 `img`、`ex`、`alt` 字段，覆盖率 ≥95%。
  - 网站横幅只认 COS index（n>0 才显示），004–010 没有待审单时不显示。
- **建议团队**：整理（主）、CV（字段）。估 4–6 小时。

### D2 审阅入口：网站精校页＋团队批量终审页
- **目标**：判一格要的信息都在卡上；公众点得对；用户能在手机上整批裁完。
- **输入**：D1 的待审单 0.3；控制台定字卡（`ReviewCardView.tsx`、`candidates.ts`）的候选顺序和档位；review-artifact 的自存机制。
- **输出**：
  1. **网站精校卡**：
     - 候选顺序改成整理本 → 字形库首选 → 次选 → OCR，同字合并并标来源；候选按钮带字形图，不靠读者的系统字体。
     - 上下文模型只是回声时不显示；□ 不显示大「？」。
     - 加列上下文小图 `ctximg`；同字例放到和本格一样大。
     - 夹注档改名「小注被当成正文切了」；切分档可以同时填字；加备注框；加撤回。
     - 快捷键、「只看未回应」、回应后自动跳下一张。
     - 每格显示「N 人回应、多数认为 X」；提交时记 `pick_src`、`pick_rank`，用来量候选命中率。
  2. **团队批量终审页**：按原因或字组分批，每格显示 AI 预判、理由和证据，操作是「同意／改判／看不出」，可以整批确认；点完自动写用户亲裁事件，回写台账。
- **验收**：
  - 用 vol04/05 的样本离线算：答案在按钮上的比例从约 70% 升到 ≥80%。
  - 手机 375px 宽一屏能看到字块图、候选和四档按钮。
  - 只用键盘能连续审完 20 格。
  - 用户在终审页上裁 20 格：事件逐条带锚进中心库，`guji audit count` 没有漏审、没有无锚事件。
- **建议团队**：网站（主）、整理。估 12–16 小时。

### D3 意见处理与 AI 裁决器（含每日自动串联）
- **目标**：把会话肉眼看图换成程序，每天无人值守地跑「拉意见 → 判 → 落 → 重跑 → 重出待审单」。
- **输入**：中心库的意见快照；待审单 0.3 的字段；字块图；正式库最新事件和绑定表（不是快照里的）；固定的 prompt 和模型。
- **输出**：
  1. **意见台账**：意见 id 规则；每条意见的状态（已落、已驳、交用户、看不出、被取代）。
  2. **AI 裁决器**：每格输出一条结构化判定 `{decision, verdict, tier, confidence, rationale, opinion_ids, model, prompt_ver}`，判定记录入库。没有公众意见的格也跑（做预判），供 D2 终审页用。
  3. **分档**：
     - A 档自动落：意见和至少两路独立证据一致。
     - B 档落了再抽检：抽 ≥20%，错率超阈值就整档降级。
     - C 档必须交用户：推翻已有人裁或放行字、「无字」、切分类、意见冲突、疑似刷票、低置信。
  4. 事件 id 带意见指纹，重跑不重复写。
  5. 每日任务，卡上自动记一行：收到几条／自动落几条／抽检几条／交用户几条／驳回几条。
- **验收**：
  - 回放金标：从 vol01–04 的用户亲裁里抽 ≥300 格，造合成意见（错票 ≥20%，含冲突和刷票）。A 档准确率 ≥99%，A+B ≥97%；推翻人裁、无字、切分类 100% 进 C 档。
  - 同一输入跑两遍，新增事件为 0。
  - 在迁过中心库的数据目录下能读到快照之后的新裁决（用 10:7:10 的情形造例）。
  - 在 vol04 上连续 3 天无人值守运行，每天摘要的数字和台账一致。
  - GUJI-589 四项补验做完，配好 `CELLREVIEW_IP_KEY`。
- **建议团队**：整理、H 道（主），CV。估 12–16 小时。M11 读者改字直接复用。

### D4 裁决落地的正确性
- **目标**：任何一条裁决都不会挡错格、写重复、撤不掉。
- **输入**：`feedback/events.py`（`counts_as_human`）、`consumers.py`（glyphdb_admit、crop_exclude）、`bindings.py`；设计 15《人裁锚定与重切后重绑定》的 P4；GUJI-623。
- **输出**：
  1. 事件来源结构化（v0.2，用户定）：`payload.source` 取 `user`／`web_ai`／`ai_prejudge`／`vision`，`web_ai` 带 `opinion_ids`、`model`、`prompt_ver`。`user`、`web_ai` 算人裁、进字形库；`ai_prejudge` 只有用户点头后才写成 `user`；`vision` 照旧只送审。
  2. 撤销语义：`v=revoke`，绑定表把它当作「没有裁决」；可以按「一次 AI 运行」整批撤销。
  3. 排除名单带锚、可撤销，不再比人裁先生效。
  4. 重切后旧的 seg_defect／damaged 裁决按锚判失效，回待审并预勾（GUJI-623）。
  5. rebound 之后统一按绑定后的格号；「看不出」写审阅记录（`cell_review`，不配消费者）。
  6. 写入端按事件 id 去重（10-19 有过 14 个重复 id）。
- **验收**：
  - 单测：`web_ai` 事件进字形库并带来源；按 `source`＋`opinion_ids` 能整批列出、整批撤销；revoke 之后绑定表视同没有裁决，名单条目撤掉。
  - 用 vol01 0.1.3 的 75 格情形重放：重切之后 □ 不再回来。
  - 用 vol02 的 124 格重放：有人裁字的格都能出字。
  - 改动牵涉 Step 指纹，按版本规矩出正式 cv 版本。
- **建议团队**：CV。估 8–12 小时。**D3、D5 都依赖它。**

### D5 精校期的切分修正（消灭手改）
- **目标**：重切清单上的问题都通过事件和重跑修好，文本里不再有手改。
- **输入**：各册重切清单（中心库 `feedback/lists/<册>-重切清单.tsv`，vol04–10 共 151 条）；`manual_cells`（row_segment 1.20）；GUJI-579、618–621（整列重切、逐页页型、补格删格、版框列框）。
- **输出**：
  1. override 缺口按 618–621 补齐，或者确认 `manual_cells` 能覆盖到哪、剩下的怎么办。
  2. 页级重跑和页级合并导出：只换改过的页，其余页原样保留。
  3. 来不及修的格进**修订单**（`hand_edits.tsv`：格号、原因、出处），G2 认它。
- **验收**：
  - vol04 的 29 条重切清单：修好的全部走事件＋页级重跑；修订单之外的格，产物导出和文本逐字节一致。
  - 职名页、双行小注各有一个实例跑通。
- **建议团队**：CV（主）、整理。估 10–20 小时（大头在 579 的四项）。

### D6 1.0 质检体系
- **目标**：做成「一条命令出报告」，按 §6 的 G1–G6 出数字。
- **输入**：冻结候选快照；候选 1.0 文本；证人（代字阁逐列本、四库光盘版、杳冥整理本）；已知错单；用最新 cv 在 `guji exp` 沙箱里的重跑产物，或影子模型的判读；M7 的字组表和 `variants.json`。
- **输出**：
  1. `guji qa <册>`：把 close-check、glyph_audit_gate、已知错单、跨版本分歧、码位一致性聚类、改库回溯（`recheck --dead`）、独立语言模型的形近替换检验串起来，出 `<册>.1.0质检报告.json/md`。
  2. **已知错单**：中心库 `feedback/lists/known-errors.tsv`，各处历史错例汇总，以后持续追加。
  3. **抽检流程**：用 review-artifact 出联系页；两个模型独立盲读（不给整理本），有分歧的和随机 10% 交人；结果写成 `audit` 批次的人裁事件，进 open-guji-dataset 新分片 `book-qa/`。
- **验收**：
  - 用 vol01 当前文本跑：报告能抓出 72:9:9、134:2:9；G2 列出全部手改格。
  - 另一个会话拿同样的输入复跑 L0–L3 的自动项，数字一样。
  - vol04 的抽检（R 层 1,000 格、P 层 200 格）跑完，报出上界。
- **建议团队**：整理（主）、CV。估 12–18 小时，另加用户看图约 1–2 小时一册（估）。

### D7 发布与冻结
- **目标**：出 1.0 的每一步都由命令完成、由命令核对；冻结之后改不动，要改就走修订。
- **输入**：D6 报告全过；D5 修订单；book-text 写入口（`bump_original.py`）。
- **输出**：
  1. `guji release check <册>`：逐项核 G8。

  3. freeze 改成认 R2 产物包，不再依赖工作区 git 的 snap 分支。
  4. 冻结册护栏：在冻结册上跑 pipeline 必须带 `--revision`，并且装的代码等于冻结 tag。
  5. 文本线 `review` 字段、decision.json 生成（GUJI-588 的生成器改读中心库）。
  6. 出口通知：标点、专名用 send.py，卡上留记录。
- **验收**：
  - vol04 出 1.0.0 时 `release check` 全部 ✓。
  - 删掉工作区里的 snap 分支后，close-check 1a 照样过。

- **建议团队**：CV、整理、文本。估 8–10 小时。

### D9 工作区清理与 1.0 后修订通道
