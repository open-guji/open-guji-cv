## 1. 问题 ①：尾字横笔被切——是 Step4，不是 Step3

先分诊：instances 里 49 个端点格，对现役 Step3 格量「格外 0.5 格内还有没有本字的墨」——
**48 个 dropped=0**（唯一 1 个是 frame_residue 列 p6c19）。Step3 的格已经包住整个字，
截断发生在 Step4 紧框。全书量「紧框 vs Step3 格内墨沿」：

| 位置 | n | 截底 | 截顶 | 丢字 |
|---|---|---|---|---|
| 首格 | 938 | 0.6% | 1.0% | 15 |
| 中间格 | 16425 | 0.6% | 1.0% | 19 |
| **尾格** | 793 | **24.6%** | 0.8% | 11 |

尾格截底 195 个：抹掉的那几行里满宽（≥0.85）的只有 11 个，122 个是宽横笔（三/上/五/正/
王/黃 的底横）、62 个窄墨（行/路 的钩尖、黃 的八）。

### 1.1 消融定位：不在任何一道剥离函数里

把 `strip_frame_debris / strip_frame_stub / carve_end_edge / strip_speckle_band /
mask_frame_bars_outside` 逐个换成恒等，9 页子集上尾格截底 **42 → 42/43/42/42/42**，一个
都不变。截断在条带裁切：`frame_band_inner` 用 `_nearest_bar` 在下框 hint ±40 行内找任何
「像框的行」（行墨 ≥0.5 或最长游程够长），末字宽底横（离框 20~40px、厚 2~8）被认成框，
`sy1 = min(sy1, frame_in_bot)` 把条带截在底横上方——底横根本没进图块。

### 1.2 修法：`border_line` 策略下按「满宽连续段」认框

与 Step2 `frame_residue` 同一把尺：行墨占比 ≥0.85、连续 ≥3 行、在 hint ±40 行内。
那把尺在 bxgb 2052 个端口上标定过（削干净的 d/e 档 1065 个零误报）。第一版按
「±12 行 + 厚 ≥6」认，8 个 frame_residue 列的残框（离线 15~30px）漏进紧框；换满宽段
后连这 8 列也对了。

顺手修了三处「四库刻本标的绝对阈值套到细笔画册子」：

| 处 | 症状 | 修 |
|---|---|---|
| `is_end_cell_junk` 孤「一」逃生口 | 墨量门槛 1000 按四库粗笔画标；bxgb「一」268~400，列端的「一」全判条渣丢掉（首 15 / 尾 11，静默丢字） | `min(1000, 3%×墙距×格高)` + 不贴图块两端 8px |
| `strip_frame_stub` | v2 的「整页」是一张列图，列外只剩 4~7px，那几列任何墨都把「列外墨率」推过 0.35 | 探测窗 <12px 不判 |
| `carve_end_edge/_char_body` | 字底的点/钩尖薄、小、贴端，三条框渣判据全中 | 框渣候选须宽 ≥0.3 图块宽 |

## 2. 问题 ②③：格线切在字中 / 切偏——候选集缺点，DP 整段错相位

切线金标（最近格线口径）现役 ≤10px 80.4%。>10px 的里一类反复出现：**同一列连续 5~8 条
格线偏 20~34px，每条切在墨 0.12~0.19 上，旁边 20 来像素就是零墨缝**。全书扫「切在墨上
且离最近零墨缝 ≥10px」：439 条格线、≥3 条的列 22 列（人裁只标到其中 4 列——探针能找出
人没看到的）。

### 2.1 排查：代价函数没错，是候选集缺点

把 DP 的 `step_cost` 闭包暴露出来逐步算：p15c16 真缝路径总代价 **0.28**，现役 **1.14**。
DP 却选了贵的——因为真缝 937 **不在候选集**：不是局部极小（旁边 913 更低），也不是孤立
低墨行（880~1000 整段低墨，LOW_INK 只取一个代表点、又落在旧波谷 12px 内被跳过）。
955→1004 只有 49px < 0.7·71 不可行，DP 只能从 955 起错相位走到底。

### 2.2 修法：周期锚定候选

每个候选 v 在 v±period 处补候选（±6px 内没候选才补，取那一小段曲线最低行，墨量真值，
只补首/末锚点窗口之外）。不改代价，只把「按周期该有一条缝」放进候选集。

| 尺子 | 现役 | 修后 |
|---|---|---|
| bxgb 切线金标 ≤10px（最近格线） | 80.4% | **92.8%** |
| bxgb p90 / mean | 21 / 6.1 px | **7.8 / 3.4** |
| bxgb R2 / R2x（切在墨上） | 28 / 42 | **24 / 21** |
| bxgb 相位漂移探针 | 439 条 / 22 列 | 410 / 20（p15c16 8→0） |
| vol01 522 条金标 ≤10px | 97.1% | 97.7% |
| vol01 R2 / R2x | 49 / 61 | 44 / 58 |
| 折线金标 | bxgb 10 好转 / 1 变差（p33c18 台子未套人裁格数）；vol01 逐条无变差 |

**一条被证伪的守卫**：给低墨落点加「附近有候选就不补」——看着稳妥，实测吐回一小半收益
（92.8% → 91.5%，R2 24 → 30）。要替掉的正是那些切在墨上的波谷。代价是空白格旁的格线
可能落在离缝中心 8px 的周期整数倍处（合成缝 22 行零墨，两处都在缝里），三条空白格单测
容差 ±3 → ±10。

### 2.3 一处误判（订正）

排查中曾把 p32c8 记成「空字位里落了个小墨点、既不是空白格又撑不起字格」的独立一类。
修后出图核对：那个「小墨点」是字**「一」**（過 868–943｜一 943–1001｜大 1001–1078），
修后切分正好；人裁 bi13=870 与 bi12=868 只差 2px，是审阅台不能删切线、把旧版腰斩
過字的那条多余切线拖到邻线上的痕迹。**没有这一类问题**，先前的结论撤回。

## 7. 第二批审阅（2026-09-19 晚，105 confirm / 12 seg_defect / 7 cutline）

### 7.1 「很多字反复审了很多遍，为什么没在库里匹配好」

bxgb:34:3:19「𠊓」：人裁 18 次进库，glyph_match 的 top 候选就是 𠊓、cov 0.9903——
但 same 档要 **cov ≥ 0.996 且 wmax ≤ 12**，0.99 落在 unsure，于是每一处都再出卡。
0.996 是给「同版同字两次印」标的，刻本同字异印常落在 0.99~0.996。
bxgb:34:18:9「宐」：候选里根本没有 宐（空 0.93 / 宣 0.91）——产物是昨天下午跑的，那时库里
只有 2 例 宐（今晚才到 7 例）；另一半原因是**产物不随库长大自动重跑**，审完一批得重跑
Step5 起才看得到效果。

修法（`c75fe02eb0`）：**共识升档**。unsure 档里 top 字 cov ≥ 0.99、比次优**异字**高 ≥ 0.03、
且该字已有 ≥ 3 例**人裁**的，判 same（`via="consensus:<n>"`）。按人裁 confirm 当真值：

| cov 区间 | n | top 正确 |
|---|---|---|
| ≥ 0.996（现役 same） | 353 | 96.6% |
| [0.99, 0.996) | 49 | 89.8% |
| [0.985, 0.99) | 23 | 82.6% |

单降门槛到 0.99 精确率 95.8%——比现役 same 还低，不行；加差距 + 人裁例数两条后真值内
100%（20/20），全书新增 126 个 same。**一个坑**：人裁例数不能用 `glyphs.n_confirmed`，
那一列把 align 通道的机器准入也累加（bxgb v1 的 3748 条全是 align），按它数会升 2349 格
而真值只覆盖 29；只数 `admissions.provenance='human'` 才是「人看过这个字」。

### 7.2 12 条 seg_defect 是什么

| 类 | 条目 | 结论 |
|---|---|---|
| p33c19（人裁 22 格的粘连密排列） | s1/3/11/18/21/22 六条 | 格 56~90px、切线墨 0.11~0.20，紧框上下各多 5~7px 邻字墨。切分本身是这一列的图像极限 |
| 已知真错 | 31:9:20（五/十）、4:6:10（翼/然 的上一格） | §6 |
| **紧框框进邻字笔尖** | 28:8:12 柏、34:15:21 爰、28:9:5 高 | 紧框比本字墨沿多出 9~10px，是上/下邻字压在格界外的笔尖 |
| 现役已对 | 30:1:1 春 | 重跑（含新人裁切线）后格线已变 |

「紧框框进邻字笔尖」是用户三类里的 ③「多一些邻字的污点」，机制：图块按格界外扩 8% 裁
（pad 是给本字略微越界的笔画留的），紧裁又是图块内全部墨的外接框。4 页 1422 格量了一遍：
**161 格（11.3%）紧框多出中位 6px 的邻字墨**，逐格看过抹掉的全是邻字笔尖（水/高/山/五/里/
王/張/柏/漢/不/道/云/二/十/間…）。修法（`91e0015663`）：pad 带里**不跨格界**的连通体一律
抹掉，跨过格界的留——严格信任 Step3 格界，与折线 `mask_outside` 同一纪律。端格尺子
1731 格 0 变差。

### 7.3 流程上的一条

审完一批 → 库长大 → glyph_match 立刻过期，但产物不会自己重跑；审阅台读的是旧产物，
新入库的字要到下一次重跑才生效。目前是我手动 `pipeline --from glyph_match`；要省这一步，
审阅台「结束一批」时该顺手触发 Step5 起重跑（或至少提示「库已变，产物过期」）。

### 7.4 「反复审」的真正根因：进库的图被整页二值化的纸缘留白啃掉了

共识升档只解释了 𠊓（库里有、cov 差一点）。「宐」人裁 7 次，重跑后候选里仍然没有它——
直接查匹配器：这个字位**自己的刻例就在库里**，自身相似度却只有 0.369（第 20196 名），
直接验证 f1 0.616 判 diff。把库存 canonical 图与现在的字块并排出来看：09-18/19 入库的
字高只有画布的 0.12（09-16/17 的是 0.26），归一后笔画碎成片。

原因：`glyphdb_admit` 进库前用 `binarize_page` 二值化，那个函数 2026-09-17 起最外 20px
**强制判纸**（挡整页扫描的纸缘渐变）；字块只有 64×88，四边各抹 20px 后只剩中间。
按入库日期分：

| 入库 | n | 自身相似度中位 | <0.7 |
|---|---|---|---|
| 09-16 | 80 | 0.89 | 2% |
| 09-17 | 300 | 0.88 | 5% |
| 09-18 | 22 | 0.38 | 100% |
| 09-19 | 383 | 0.43 | 99% |

修（`open-guji-cv` 本轮提交）：进库改 `edge_margin=0`；`scripts/repair_glyphdb_canonical.py`
从现在的字块重算 canonical + derived，修了 406 条，修后 09-18/19 自身相似度中位 **1.00**，
「宐」立刻 same。库已备份 `output/glyph.db.bak-20260919-canonical`。

**这两天你审的 405 个字，进库时全是碎的——等于白审。** 修完重跑 Step5 起，它们才真正
参与匹配。

### 8.2 30 条 seg_defect 里 16 条是每列第一个字，13 条在 p48/p54

出图核对（`warp_column` 矫正后的列顶 + 各层边界）：这两页 Step1 的上版框直线落在**首行字的
顶边**而不是框上——低 12~22px（整页首字顶边齐平，投影上是一条比厚框更「尖」的峰，和 p53
那次「窄峰反超真线」同一族）。后果两种，都是首字丢顶：

- 首字比上界高（二十/三 那类）：顶部整块不在列图里；
- 首字顶边恰在上界：`column_border_trim` 见「贴着列图顶端的薄横」按 a 档当框线削掉 6~16 行

## 9. 字形库指纹改内容指纹（2026-09-20，用户定「中期建议」）

### 9.1 现象与根因

rerun10 跑到一半，`status` 又见 `glyph_match` 起全线过期。查库：admissions / instances / exemplars /
glyphs 四表最新写入都是 `2026-09-20T00:26:58Z`（本地 17:26:58），全是 `provenance='human'`——
就是用户边审边 confirm，消费者 `glyphdb_admit` 落库。指纹 `db_fingerprint = (mtime_ns, size,
exemplars 条数)`，mtime 一动，之前算过的 Step5+ 全部过期，补一轮 `--from context_decide` 才收敛。
只读（开库、装匹配器、跑 status）实测不动 mtime；`seed_admit` 本身**不写库**（只出裁决，写库走
Event → `glyphdb_admit`），不是它把自己弄过期。

人裁进库让识别重算是**对的**；问题是 mtime 连备份复制、VACUUM、机器 align 进库都一并算上，
且 `seed_admit` 的人裁通道跟着整库指纹白跑。

### 9.2 改法

- `db_fingerprint`（`glyph_match`）：exemplars / glyphs / admissions / derived 四表各取
  (条数, 最大 rowid, 最新时间戳) 拼起来哈希；bxgb 77 MB 库上 24 ms。rowid 用来看见「撤旧再进」
  （条数不变、时间戳同秒）。库不存在 → `nodb`；读不了 → 退回 stat 戳，不抛。
- `human_verdicts_fingerprint`（`seed_admit.human_fingerprint`）：只看 `provenance='human'` 的
  admissions；机器 align 进库、字头改判不动它；人裁进库、撤裁（删行或改成 `human_stale_*`）才动。
- `glyph_match` 的匹配器缓存键、产物里记的 `db_fingerprint`、参数指纹三处统一用参数里那一份
  （原先前两处每页现算，边跑边审时三者各说各话）。
- `instances` 表不进指纹（扫 patch_png 140 ms 且随库线性涨）→ 纪律：只改 instances/derived 的
  写路径必须碰 `exemplars.added_at`（`refresh_instance_patch` 已如此；`repair_glyphdb_canonical.py`
  补上）。cv-pipeline-ops skill §2.3。

8 条新测试（`tests/test_db_content_fingerprint.py`）：touch/复制/VACUUM 不变；align 进库只动库指纹
不动人裁指纹；human 进库两个都动；撤旧再进同秒可见；`human_stale_` 改名可见；刷新图块可见；
缺库/坏文件不抛；`SeedAdmitParams` 用的是人裁指纹。

### 9.3 一次性代价与规矩

指纹算法换了 → bxgb 全书 Step5+ 过期一次（54 页），`--from glyph_match --pages all` 重跑。
往后的规矩：**审完一批再跑 Step5+**——人裁进库触发过期是设计如此，内容指纹只是把无关的写剔掉。

### 9.4 顺带查出：行尾翻转会让 code_hash 变

重跑 Step5+ 后 `status` 仍从 `column_gate` 起全线过期。逐项比对：参数哈希、上游 sha 都没变，
只有 `code_hash`；用 CRLF 版 `row_boundaries.py` 重算指纹与 manifest 逐位相同——另一个会话
18:37 把该文件存回了 LF（内容未改、`git status` 干净）。修法：`engine._module_source_hash`
哈希前 CRLF→LF 归一（`tests/test_engine_eol_hash.py`）；一次性迁移脚本
`scripts/migrate_manifest_eol.py` 把「仅行尾」的旧记录改成新指纹（bxgb 486 条仅行尾、0 条真过期）。
cv-pipeline-ops skill §1.2。
