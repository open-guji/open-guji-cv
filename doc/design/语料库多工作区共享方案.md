# 语料库在多个工作区之间：哪些独立、哪些共享

> 2026-10-18，Emerson。依据 sheldon 同日提的题：多个工作区（一个 book-id 一个）各有各的书，语料库怎样既保持独立又能共享，哪些数据该独立、哪些该共享，「和字形库有点像」。
> 接 [语料库版本化方案](语料库版本化方案.md)（P0–P2 已合）。**本文只出方案，不改代码**，`code_hash` 与殿本 corpus-v1 指纹都不变；等 sheldon 定了再实现。

## 一、现状：已经是「半共享」，但没有说出来

殿本 `corpus-v1` 清单登记的 51 份文件，按落点分是两堆（`core/corpus_pin.ITEMS`）：

| 落点 | 内容 | 份数／体积 |
|---|---|---|
| **引擎仓**（`root: repo`） | 字表/康熙部首、IDS 表、异体三表＋关系图＋用字账、形近表、L1 规则、夹注词表、泛古籍语料 `corpus/external` | 40 份／约 42MB（泛古籍语料 30MB、IDS 5MB 占大头） |
| **工作区**（`root: ws`） | 整理本参考文本、字频表、L2 答案表、工作区级异体补充 | 11 份／约 19MB（整理本 19MB 占大头） |

三个事实：

1. 引擎仓那 40 份**对所有书都是同一份**——这就是已经在共享的部分，只是 manifest 把它们抄进了每个工作区的清单，没有「这是共享的」这个概念。
2. 第二本书（北行日錄）进来就暴露问题：它没有 `corpus-pack/`、没有字频表、没有 L2，`group_flow` 字频/文意两种判法只能弃权；而它**能**白拿的那 40 份（规则、IDS、异体、形近）又得再登记一遍、版本号和殿本各数各的。
3. 钉子现在是「承诺」不是「隔离」：Step 永远读引擎仓**工作树**里的文件，`corpus: 1` 只是让指纹不变。只要引擎仓那 40 份里有一份被改，殿本的钉子就与实际内容不符（`guji corpus verify` 会报 changed，但产物不会过期）。一本书时无害；两本书想钉在不同版本时，这个承诺兑现不了。

## 二、对照字形库

字形库三层（`doc/workspace_layout.md` §三）：A 通用源料（字体、权重，引擎仓）／B 共享字形库（**还没建**）／C 本书字形（工作区，不可再生）。语料库照搬同一条线：

| 判据 | 字形库 | 语料库对应 |
|---|---|---|
| 与书无关、外部来的、很少变 | A 通用源料 | **A 通用源料**：字表、康熙部首、IDS 表、泛古籍语料 |
| 与书无关、**会随各书经验增长** | B 共享刻例库（未建） | **B 共享经验库**：异体三表＋关系图、形近表、L1 规则、夹注词表 |
| 只属于这一本书 | C 本书字形 | **C 本书语料**：整理本参考文本、字频表、L2 答案表、用字账 |

字形库那边有三条教训直接适用：

- **先落本书，审过才升格**（§3.1）。新发现的异体、形近、规则先长在某本书的 C 层，别人不受影响；够证据了再升到 B。
- **「升格」没有机制就别假装共享**（§3.2）。字形库至今卡在没有升格命令和多库挂载上。语料库这边要先把升格的口子设计好（见第四节），否则 B 层会退化成「谁都往引擎仓里随手改」。
- **索引/清单不是真源**。语料库的真源是文件，manifest 只是登记。

## 三、哪些该独立、哪些该共享

判断三问，依次问：①这份数据的**内容**是不是对任何一本书都成立（语言/字形事实）？②它是不是**从某一本书的人裁/文本算出来的**？③换一本书直接用，会不会算出**错的**判断？

| 数据 | 判定 | 层 | 理由 |
|---|---|---|---|
| 字表、康熙部首、IDS 表、部件库 | 共享 | A | ①是；外部来源，不随书变 |
| 泛古籍语料（`external/`） | 共享 | A | ①是；语料来源与具体某书无关 |
| 异体三表＋关系图 | 共享 | B | ①是；「A 是 B 的异体」不因书而异 |
| 形近表（含 `NEVER_MATCH_FAMILIES`） | 共享 | B | ①是；但 `confusable_human` 来自殿本/北行人裁，**升格要过证据**（第四节） |
| L1 规则（`rules.yaml`） | 共享 | B | ①是；规则是字级文意/字形事实 |
| 夹注词表、铁证闸追加形近 | 共享 | B | 同上 |
| 整理本参考文本 | **独立**（登记所属 Work） | C | ②是：它是某个版本的文本。同一 Work 的不同刻本可共用，见第六节 |
| 字频表（`freq.json`） | **独立** | C | ②是：从**本书**人裁计数算出，字频门槛（≥20 多数/少数=0）是本书证据，借别书的不等于本书有证据 |
| L2 答案表 | **独立** | C | ②是：键是本书的具体页/格 |
| 工作区级异体补充、用字账 | **独立** | C | ②是：用字账 `wuyingdian_zongmu.json` 目前放在引擎仓 `config/variants/books/`，实质属于殿本，**应迁到工作区** |
| 切坏图块排除名单、人裁事件、字形库 | 不属于语料库 | — | 字形库/人裁，已有归属 |

**一条反向规则**：C 层（本书）里的东西**不借给别的书**。北行日錄没有字频表就弃权，不拿殿本的字频表当先验——否则一本书的人裁证据会悄悄变成另一本书的放行依据，评测里也分不清。弃权要在产物里显式记为「无字频表」，不是静默。

### 灰区的裁法

- **册 vs 工作区**：一个工作区里有多册（殿本 vol01–10 共用一套语料）。语料库的粒度是**工作区**，钉子在**册** yaml（现状不变）；同一工作区的册可以钉不同版本，换版时逐册换。
- **同一部作品的不同刻本**（殿本总目 vs 文渊阁总目）：整理本文本是 Work 级的，但**现在只有一个 Work 一个刻本**，不为将来预先抽象。登记 `work_id`，等第二个同 Work 的刻本真进来，再把整理本抽成 Work 级共享（见第六节）。
- **字频表能不能作先验**：不能（见上）。但「字在整理本语料里的频次」是文本事实，由整理本算出，属于 Work 级文本的派生，不是人裁字频。当前 `rare_candidates` 用的就是后者的字表，随整理本走。

## 四、方案：两级清单——底库＋书库

### 1. 结构

把现在「每个工作区一份全包清单」拆成两级：

```
guji-workspace/_shared/corpus-base/b<M>/manifest.json   # 底库 = A + B（共享）
<书目录>/corpus-pack/v<N>/manifest.json                  # 书库 = C（本书）＋ "base": M
```

- **底库 `bM`**：A+B 两层所有文件的 sha256，加 `repo_commit`（这一版对应引擎仓哪个提交，要还原旧版去那个提交取）。整个 guji-workspace 一份，不可变快照，递增整数。
- **书库 `vN`**：本书 C 层文件的 sha256 ＋ `base: M`（这一版语料库引用底库 bM）。每个工作区各自递增。
- **指纹不变**：Step 指纹仍只带 `corpus-vN`（N 是书库版本）。N 解出 M，M 解出文件集。所以：
  - 殿本现有 `corpus-v1`（自包含，没有 `base` 字段）按「旧格式」继续有效，**指纹逐位不变，不需要 fp-migrate**。
  - 新书直接用两级格式。
- **每册钉子不变**：`corpus: N`。要升底库：出 `b(M+1)` → 各工作区出新书库 `v(N+1)`（`base: M+1`）→ 逐册改钉。每一步都是显式动作，没有自动传播。

这样「独立」体现在：书库各书各自编号、各自升级、互不牵连；「共享」体现在：底库只存一份，N 本书不重复登记 40 份文件，且能回答「现在有几本书落后在旧底库」。

### 2. 钉子是承诺还是隔离（本方案唯一的硬抉择）

引擎仓是单个工作树。两本书想同时钉不同底库版本，要么**物化**，要么**不允许**。三档，由低到高：

| 档 | 做法 | 代价 | 够不够用 |
|---|---|---|---|
| ① 承诺＋硬校验（**推荐先做**） | Step 仍读工作树；`pipeline` 起跑前对钉住的 `bM` 做 `verify`，不一致就**拒绝跑**（不是警告）；规定「同一时刻全部书钉同一个底库，落后的册先升再跑」 | 底库换版时所有活跃书要排队升一遍；旧版靠 `repo_commit` 还原 | 只要书不多（现在 2–3 本）就够 |
| ② 旧版单本回放 | 某书确需旧底库：在 `repo_commit` 的 git worktree 里跑引擎 | 手工，慢 | 偶发需要 |
| ③ 物化（内容寻址仓） | `_shared/corpus-cas/<sha256>` 存文件，Step 通过 `corpus_file(rel)` 解析到钉住版本的文件 | 要改所有读语料的 Step 的取路径（`CORPUS_STEPS` 5 步，且会触碰 code_hash，各书全体过期一次）；大文件靠 git 去重 | 书多到各自节奏不同才值 |

推荐 ①：现在只有一本书钉了版本，② ③ 是真有两本书节奏不同才付的钱。①的关键是把「钉子是承诺」写成**会拦人的校验**，而不是靠记得。

### 3. 写权限与升格

- **底库只有一个写入口**：引擎仓里改 A/B 层文件（走 PR，纯数据可自审合），合了之后 `guji corpus build-base` 出新 `bM`。多个会话同时往底库写会撞，所以这里串行；书库则每个工作区各写各的，没有冲突。
- **升格 = 从书库条目进底库**，只用于形近表、异体表、规则这类 B 层增长。判据（照字形库「审过才升格」）：①是字级事实、不依赖版式/字体/版本；②有证据（人裁裁决数或 A/B 报告）；③在已钉的其他册上跑过 `guji exp` 不退步才合入。命令形态：`guji corpus promote <条目>`，记来源书和证据，写进下一版 `bM+1` 的 manifest 备注。**不做的话 B 层会变成随手改仓库**。
- **本书补丁（overlay）暂不做**：北行想在殿本之外多加几条形近，先通过升格进底库（别的书钉在旧底库不受影响，这正是版本的意义）。真有「只想本书生效、不想别书看到」的条目再开 overlay，那是改 loader 的事，另议。

### 4. 新书怎么接入

`guji corpus init -w <书目录>`（新）：①写书库 `v1`，`base` 指当前最新底库；②列出本书缺什么（字频表、L2、整理本），逐项标「弃权」或「待补」；③册 yaml 加 `corpus: 1`。北行日錄、全唐文照此走：规则/IDS/异体/形近白拿，整理本（北行的校對本、全唐文的整理本）登记进书库，字频表等人裁攒够了用 `groups.freq` 算出来再出 `v2`。

## 五、升级一次底库的流程与代价

```
修改引擎仓 A/B 层文件 → PR 合入
  → guji corpus build-base          # 出 b(M+1)，写 repo_commit
  → guji corpus diff b<M> b<M+1>    # 新：列改了哪些文件、影响哪几个 Step、涉及哪几本书
  → 逐书：guji corpus build -w <书> # 出 v(N+1)，base 指 M+1
          guji exp / 评测对基线 A/B # 过了再改钉
          改册 yaml corpus: N+1 → guji status 看判过期的步骤 → 重算
```

`diff` 要能说出「这次升级只动了 `rules`，只有 `seed_admit` 受影响」。现在 `CORPUS_STEPS` 是一刀切（5 步一律带版本号）；**要不要做到按层依赖**（每步只对它读的层的版本敏感）是一个独立的优化，能少重跑，但每步要登记依赖层，增加维护。**建议先不做**，用 `diff` 先看清楚实际重跑代价再说。

## 六、没定与留白

1. **整理本抽成 Work 级**：等第二个同 Work 的刻本进来再做。现在只在书库登记里加 `work_id`，成本接近零，留好接口。
2. **底库放哪**：本方案把清单放 `guji-workspace/_shared/`（跟「guji-workspace 是唯一最终工作台」一致），文件暂留引擎仓。`泛古籍语料`（30MB）和 IDS（5MB）如果以后嫌占引擎仓体积，再迁到独立数据仓，清单里的 `repo_commit` 改成数据仓提交，其余不动。注意 guji-workspace README 写「整完即删」，而底库是长期的——放 `_shared/` 要在 README 里改成「_shared 不随书删」。
3. **`_shared` 的路径解析**：`-w` 指到书目录，底库在其上一级 `../_shared/`。默认按这个相对位置找，可由环境变量覆盖；解析不到就报错，不静默退回仓内样本（`corpus/README.md` 里分叉 4680 行的教训）。
4. **用字账迁位置**：`config/variants/books/wuyingdian_zongmu.json` 从引擎仓迁到殿本工作区。迁移本身会改变清单（从 repo 项变 ws 项），**殿本 v1 的清单要重出**（v2），这一步会带来一次殿本指纹变化；可以和第一次真正拆底库合并做。

## 七、分步做（等 sheldon 定了再开）

| 步 | 内容 | 验收 | 指纹影响 |
|---|---|---|---|
| P3-a | 两级 manifest 格式＋读取（`base` 字段，旧自包含格式仍读）；`guji corpus build-base`／`diff` | 单测造两个小工作区；殿本 v1 解出的文件集与现状逐份一致 | **无**（殿本 v1 逐位不变） |
| P3-b | `verify` 升级为起跑前硬校验（不一致拒绝跑，给出该出新版还是该还原文件） | 手动改一份底库文件，pipeline 拒绝启动 | 无 |
| P3-c | `guji corpus init`（新书接入），先拿北行日錄试 | 北行得到 `v1`，字频/文意两种判法在产物里显式记弃权，不是静默 | 北行首次钉版本，只此一次 |
| P3-d | `promote` 命令与证据记账；用字账迁位置 | 一条形近条目从殿本人裁升格进底库，北行钉旧底库不受影响 | 殿本重出书库版本 |
| P3-e（可选） | 物化到内容寻址仓 | 两本书钉不同底库同时跑 | 触碰 5 步 `code_hash`，各书过期一次 |

P3-a/b 与已有 P3（vol04 迁移前后逐格一致）互相独立，可并行。

## 八、要 sheldon 定的

1. **两级清单（底库＋书库）**：是否按这个方向？（推荐：是。另一条路是各书各抄一份，简单但版本号互不可比、无法回答哪些书落后了。）

3. **升格门槛**：「有证据＋在已钉其他册 A/B 不退步」够不够？

5. **北行日錄的字频/文意判法**：确认接受「无字频表就弃权、不借殿本」？
