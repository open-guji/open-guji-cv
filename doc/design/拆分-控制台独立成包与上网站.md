# 把控制台拆成独立包，再上网站给会员用（设计，2026-10-28）

> 起因：Sheldon 2026-10-28——把 CV 控制台从 cv 包里拆出来成独立的包，依赖尽量拆开；控制台要调命令或跑 pipeline 时，改成调 cv 的命令行。下一步把控制台部署到网站上：和主网站稍微分开、单独一个页面，部署流程和主网站分开，开放给会员使用。
> 本文只是设计与分步，**没有代码改动**。数字来自对 `dev`（06776fd，v0.5.31 之后）的静态 import 分析，脚本思路见第九节。
> 上位设计：[拆分-pipeline与manager.md](拆分-pipeline与manager.md)（10-27，以下简称「manager 拆分」）、[../契约.md](../契约.md)。本文是它在控制台这一块的细化，**不改它的分界判据**。

## 一、一句话结论

1. **控制台另起一个包 `guji-console`、一个仓 `open-guji/guji-console`**（名字待定，见第八节），与 pipeline（`open-guji-cv`）、manager（`guji-manager`）并列成三个包。控制台只是「看、裁、下单」的界面，不含任何影响识别产物的代码，所以**拆它不动任何 Step 的 `code_hash`，重跑分级 L0**。
2. 调用规则三条：
   - **跑和改（跑管线、重跑、消费事件、迁金标、发包）→ 子进程调命令行**（`guji-cv …` / `guji …`），控制台不 import 这些代码。跑管线这一条今天已经是这样（`console/jobs.py` 拼 `python -m open_guji_cv pipeline …`），要补的是其余几类写操作。
   - **读和现算（出卡、叠图、产物、字形库、评测看板）→ 只经一个门面模块**：先放在 cv 里叫 `open_guji_cv.api.console`，manager 一侧的东西搬进 `guji-manager` 后，同名函数改由 `guji_manager.api` 提供。控制台不许 import 门面以外的任何 cv 内部。
   - **人裁写事件 → 也走门面**（`append_event`）：一次点击一条，不能每次起一个子进程（cv 冷启动 1–2 秒）；而且事件的定位锚要按当时产物现算（M11 文档 §102），本来就要读产物。事件格式是契约（`feedback.events`），归 pipeline 定义。
3. 第一步（拆包）分四小步 **C0–C3**，C0–C2 都在 cv 仓里做、不发 pipeline 版；C3 建新仓并从 cv 删掉 `console/`，并进一个本来要发的 PATCH。
4. 第二步（上网站）：前端是静态页，单独一个子域或路径；后端 API 跑在服务器上，读服务器上从中心库拉下来的工作区；登录沿用 09-26 已做好的网站 OAuth（`client_id=collate`），**角色表加一级「会员」**。部署走 `guji-console` 仓自己的流水线，与网站仓的发布互不牵连。这一步要网站和部署两边配合（第七节）。

## 二、现状盘点

### 2.1 控制台有多大

## 三、三个包的关系

```
                 浏览器（本机 / 网站子页）
                        │ HTTP
              ┌─────────▼──────────┐
              │  guji-console      │  FastAPI + React；鉴权、任务队列、出卡、看板
              └──┬──────────┬──────┘
   读/现算/写事件 │          │ 子进程（跑和改）
  (in-process)   │          ▼
                 │   guji-cv pipeline|step|rerun|status …   ← pipeline 命令行
                 │   guji  events|gold|eval …               ← manager 命令行
                 ▼
     open_guji_cv.api.console   ──(manager 那部分迁走后)──▶ guji_manager.api
     （门面：只转发，不放逻辑）
```

- **依赖方向**：console → manager → pipeline；pipeline 不认识 console，manager 也不认识 console。
- **版本**：控制台自己一条版本线（tag `c-vX.Y.Z`），`main` 直接发，**不进任何指纹、不钉到册**。启动时先跑 `guji-cv version --json`，契约版本不在自己声明的 `supports_contract` 范围就拒绝启动（同 manager 拆分 §5.2 的护栏）。
- **跑的是哪版 pipeline**：控制台进程里 import 的是本环境装的那版 cv（只用于读）；下单跑批时照任务点名的版本，沿用 `jobs/runner.py` 的做法用对应 venv 的命令行。

## 四、门面 `open_guji_cv.api.console` 收什么

原则：**只转发现有函数，不放逻辑**（与 `api.py` 同一个写法），所以随时改都不动指纹。每个函数注明归属，manager 一侧的将来原名搬去 `guji_manager.api`。

| 组 | 函数（现位置） | 归属 |
|---|---|---|
| 册与工作区 | `load_book` `BookSpec`（core.book）、`workspace.*`（core.workspace，含 `discover_workspaces`）、`STEPS` `PIPELINES` 列表（core.step / core.pipeline / core.spec） | pipeline |
| 产物与图 | `ProductStore` `ImageCache`、`imread`、`binarized_or_none` `binarize_page`、`effective_raw_path` `precleaned_path`、`ColumnMapper`、`column_profile` `column_text_band` `denoise_column` `triage_column` | pipeline |
| 叠图与摘要 | `overlay` `preclean_overlay` `encode_png`（render.overlay）、`gate_summary`（gates.query）、`align_ref_summary` `book_corpus`（steps.align_ref）、`glyph_match_summary`（steps.glyph_match） | pipeline（只读摘要） |
| 字形库 | `char_table` `char_detail` `library_summary`（glyph_ledger）、`load_findings` `decisions` `freshness` `font_renderer`（glyph_selfcheck）、`ids_lookup` `rare_batch` `font_index_status`、`normalize_patch`、`cached_matcher_from_db` `GlyphDB` | pipeline |
| 事件 | `append_event`（包 `feedback.events.EventLog.append`）、`anchor_for`（feedback.anchor）、`read_events` | pipeline（格式归它） |
| 审卡与批次 | `review.cards.*` `review.batches` `*_cards` `verdict_view` | manager |
| 收割与消费 | `harvest` `routes` `consumers` `collate_*` | manager；**控制台只读其结果**，触发一律走命令行（`guji events route …`） |
| 评测与金标 | `eval.quality` `rate_history` `eval.registry` `llm_online_accuracy`、`gold.store/drift/transfer`（只读视图） | manager |
| 渲染与汇总 | `render.guji_markdown` `reading_layout` `approx`、`report.tiers` `progress` | 按 manager 拆分 §6.3 定 |

门面建好后，`tests/test_architecture.py` 加一条守卫：`console/` 下除 `open_guji_cv.api` / `open_guji_cv.api.console` / `open_guji_cv.products.kinds` / `open_guji_cv.errors` 以外，一条 `open_guji_cv.*` 都不许 import。现存的按清单进白名单，只许减不许增。

## 五、哪些动作改走命令行

| 现在控制台进程里做的 | 改成 | 已有命令？ |
|---|---|---|
| 跑管线、跑一步（`runs.py` → `jobs.py`） | 不变，已是子进程；改调 `guji-cv` 入口，`cwd` 不再写死 cv 仓根（现在 `repo_root()` 是 cv 源码目录，独立安装后不存在） | 有 |
| 按路由表消费事件（`feedback.py` 调 `consumers`） | `guji events route … --json`，进任务队列 | 有子命令，要补 `--json` |
| 收割 Artifact 裁决（`feedback.py` 调 `harvest`） | `guji events harvest … --json` | 有子命令，要补 `--json` |
| 金标迁移（`gold.py` 调 `gold.transfer`） | `guji gold migrate … --json` | 有子命令，要补 `--json` |
| 跑评测（`evals.py` 调 `run_eval`） | `guji eval run … --json`，进任务队列 | 有子命令，要补 `--json` |
| 字形库体检刷新 | `guji glyph-db selfcheck …` | 有 |

判据：**会写工作区里事件以外的文件、或耗时超过几秒的，一律走命令行进队列**；只读和写一条事件的留在进程内。

## 七、第二步：上网站、独立部署、开放给会员

### 7.1 形态

| 层 | 放哪 | 说明 |
|---|---|---|
| 前端 | 静态托管，单独一个子域（建议 `console.<网站域名>`，见第八节） | `guji-console` 构建出的 `dist/`。与主站同主域，登录跳转顺；不进网站仓、不跟网站一起发 |
| 后端 API | 服务器（建议沿用美国服务器，09-30 起搁置） | `guji-console` 的 wheel 或容器 + 一份 cv（读用）+ guji-manager；`--host 0.0.0.0 --root-path` 已支持（`console/app.py` `serve`） |
| 数据 | 服务器上的工作区 | 由 `guji db pull` / `guji source pull` 从中心库拉，**不在服务器上整册重算**；人裁事件经 `guji db push` 回中心库 |
| 登录 | 网站 OAuth（授权码 + PKCE，`client_id=collate`） | 09-26 已做完（`console/auth/`），只要网站登记新的 `redirect_uri` |

服务器 09-30 搁置的重启条件之一是「需要多人校对／对外展示」，这次正好满足；但重启服务器是运维的事，需要用户点头（第八节）。

### 7.2 会员能做什么（建议，待用户定）

现在只有两级：`reviewer`（网站 reviewer/editor）与 `admin`。加一级 `member`：

| 能力 | 会员 member | 校对者 reviewer | 管理员 admin |
|---|---|---|---|
| 看册、看产物、叠图、字形库、Step9 阅读 | ✓ | ✓ | ✓ |
| 在审卡上提交裁决 | ✓，事件标 `via=member`，**进待复核**，不直接进裁决表 | ✓ 直接生效 | ✓ |
| 复核会员裁决 | — | ✓ | ✓ |
| 消费事件、金标、评测、下单跑管线 | — | — | ✓（服务器上缺省关掉跑管线，只开重跑小样本） |

实现：`identity.py` 的 `_ROLE_TIER` 加 `member`；`guard.py` 加 `require_member`；路由逐个标级；事件信封加可选字段 `via`（契约加一字段——**只加可选字段，不改 `contract_version` 的语义**，要在契约文档里登记）。会员裁决的复核走现有「批次 → 回读」那套，不另造。

### 7.3 部署流程（与主站分开）

- `guji-console` 仓：PR 投 `main`，CI 跑测试与前端构建；打 `c-vX.Y.Z` tag 触发发布 workflow：①前端推静态托管；②后端构建 wheel/镜像，推到服务器并重启服务；③冒烟测试（`/api/version`、登录跳转、读一页叠图）。
- 先上 staging（同服务器另一端口 + `console-staging.` 子域），绿了再晋升，沿用网站「staging 绿即晋升」的做法。
- 凭据（`GUJI_OAUTH_CLIENT_SECRET`、`GUJI_OAUTH_ID_TOKEN_SECRET`、`GUJI_SESSION_SECRET`、中心库令牌）只在服务器环境变量和仓库 secrets，不进 git。

### 7.4 需要哪些 Project 配合（经协调者发）

| 谁 | 要做的 |
|---|---|
| 网站（kaiyuanguji-web） | ①OAuth 登记新 `redirect_uri`；②`id_token` 的 `role` 给会员发 `member`（现在网站「`reader` 不发」）；③导航加一个去控制台的链接；④确认会员账号体系（邀请制还是开放注册） |

## 八、要用户定的

1. **仓名与包名**：建议 `open-guji/guji-console`、包 `guji_console`。也可以不另起仓，作为 `guji-manager` 里的子包——更省事，但部署流程就和 manager 的发版绑在一起，与「部署流程独立」的要求不合，所以不建议。
2. **会员权限**：按 7.2，会员能看、能提交裁决但要校对者复核。还是只看不裁？
3. **网址**：子域 `console.<域名>`（建议）还是主站路径 `/console`（要网站反向代理转发，部署就和主站缠在一起）。
4. **服务器**：重启 09-30 搁置的美国服务器来跑后端，可以吗？
5. **顺序**：C0–C2 现在就可以做（不发版、不动指纹）；C3 建议等 manager 拆分的 M4 落定后再做，两次搬仓一起理顺 `guji` 入口点。第二步在 C3 之后。

## 九、风险

| 风险 | 对策 |
|---|---|
| 门面里有些函数将来要迁去 manager，控制台跟着改两次 | 门面按「组」导出、名字不变；迁移时只改门面的实现，控制台不动 |
| 服务器上的工作区和本地不同步，会员看到旧产物 | 页头显示工作区的中心库 rev 与拉取时间；`guji db pull` 定时跑；产物过期的页标 stale（现有指纹机制） |
| 会员裁决质量参差 | 一律进待复核；复核率、采纳率进人审率台账（`track_review_rate`） |
| 对外开放后的负载与安全 | 跑管线缺省关；图片接口加缓存与限流；鉴权已是「不在角色表就拒」 |
| 子进程跑写操作后，控制台进程内的缓存（`ProductStore` manifest 等）不刷新 | 现有约定是 `ProductStore` 每次新建（`console/deps.py`）；其余按根缓存的 Store 在任务完成回调里清一次 |

## 十、盘点怎么做的（可复现）

用 `ast` 解析 `open_guji_cv/console/**/*.py` 的全部 import（含函数内、相对 import），去掉指向 `console` 自身的，按目标模块与顶层包汇总，得第二节 2.2 的表（69 个目标、28 个文件）。反向边用 `grep -rn "console" --include=*.py open_guji_cv scripts tests | grep import` 找出，再逐条对 `steps/` `gates/` 里的 `code_deps` 字符串核是否进指纹。
