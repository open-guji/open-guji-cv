1. 找到并停掉还在推的循环（服务器 `cv-db-sync.timer`、各会话的 auto_cycle／proof_cycle）。看 `imports` 里最近的 push：`actor`、`source`（`push:<ws>@<base>`）、`stats.problems`。actor 为空的，多半是没设 `GUJI_ACTOR` 的云会话。
2. **立刻在 Neon 开时间点分支留底**（项目 `aged-credit-71244565`，历史保留默认 24 小时，过了就没了）：
   `POST /projects/<id>/branches`，`parent_id`＝main 分支，`parent_timestamp`＝清空前一刻（取 `imports` 里出事 import 的 `started_at` 前几十秒），建 `read_only` 端点。核对：`max(changes.rev)`、各 `glyph_*` 表按 `ws` 的行数。
3. 通知各方暂停对该工作区 push／sync。

## 恢复（要用户点头：写中心库）
1. 沙箱里 `GUJI_DATA_HOME=<临时目录>`，建 `workspace.yaml`（`id: <ws>`）和 `.central.json`（`{"ws":"<ws>","branch":"main"}`）。
2. `guji db pull -w <沙箱> --no-rebuild` 拉**当前** main（含出事后别人的合法写入）。
3. 另起一个目录，用 `PgSource`（连救援分支端点取行）＋ `WorkerSource` 取图，`workcopy.pull(..., force=True, glyph=None)` 拉**救援点**状态。
4. 把救援目录里 `output/glyph_store/` 的账本 jsonl 和 `patches/` 覆盖到第 2 步的目录。
5. `guji db push -w <沙箱> --dry-run`：逐表对照出事 import 的 `stats.per_table`（应是它的镜像：insert 对应当时 delete），`problems` 为空，`files／events／books` 无变更。
6. 真推。图已在 R2 时，`guji db push` 自带的上传核对对两万张图极慢，可用 `workcopy.push(conn, ws, uploader=None, glyph=None)` 直接写库（图按 sha 在桶里，第 3 步取图已证明都在）。设 `GUJI_ACTOR`。
7. 核对：各表行数与救援分支一致；按主键排序后的 `md5(string_agg(raw …))` 与救援分支逐表相等。
8. 通知各方 `db pull --force` 本机副本（先备份），确认账本非空再开循环。
