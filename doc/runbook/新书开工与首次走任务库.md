# 新书开工与首次走任务库：顺序与坑

2026-10-31 史記文淵閣本（Book 988g3f0wsu，手写本，借殿本字形库冷启动）第一次在任务库（A30，`guji job`）上跑时，
一路踩了下面这些坑。新开一部书时照这个顺序做，前一步没过不要做下一步。通用流程见 [整理一册书.md](整理一册书.md)。

## 一、正确顺序

1. **建工作区仓**：org `guji-workspace` 下一书一仓，仓根即工作区（`workspace.yaml`、`.central.json`），工作区 id ＝ Book ID。
2. **登记到任务库**：`open_guji_cv/jobs/spec.py::WS_REPOS` 加「书 ID → 仓」，走 PR 合进 dev（#809）。
   不登记就要在每张单里手写 `ws_repo`；忘写时执行方会去旧总仓 open-guji/guji-workspace 找目录，报
   `ls: cannot access '/root/guji-workspace/<书ID>-*'`。
3. **册配置齐了再推**：各册 yaml 的开关、语料、钉页表都推中心库（`guji db push`，要用户点头）。
   - 配了 `row_segment.layout_prior`（离线格位表）的册，表里要有这一册，否则 Step3 整册报错（`layout_prior 表 … 里没有 NN`）。
     史記用钉页表的书，改用 `page_map: pins`（#804），Step3 边跑边按钉位出格位表，不再离线补表。
   - **推之前查真源是否完整**：`ls <数据目录>/output/glyph_store/instances/`，本书人裁过的话这里应有本书实例。
     为空就是下面第三节第 1 条的坑，执行方的字形库会缺本书字样。
4. **字形库出快照并钉号**：`guji glyph-db snapshot -w <工作区>` 出 g<N>，各册 yaml 写 `glyph_pin: N`，推中心库。
   执行方按快照从 R2 拼出和本机逐字节相同的字形库（`output/glyph-g<N>.db`）；不钉号时执行方用的是它自己从真源重建的库，
   和本机不一定一样。
5. **交单**：`GUJI_JOBS_WHO=<名字> guji job submit spec.json`。spec 写 `ws_glob: "<书ID>-*"`（书 ID 由它定，不写会落到缺省的殿本）、
   `cv`（远端能取到的分支／tag／提交）。从没存过产物包的书只能跑全流程，不能 `--from` 中途起跑（没有铺底包）。
   先 `--dry-run` 看规整后的书 ID 和 `ws_repo`。
6. **验结果**：`guji products pack fetch <册> --label <包标签> --root <目录>` 拉回来，和本机同配置的结果比待审数；
   比 glyph_match 的 same 数最快能看出字形库对不对。对不上就别用这批包。

## 二、症状 → 原因速查

| 症状（`guji job show`） | 原因 | 处理 |
|---|---|---|
| prep「更新工作区」`ls: cannot access '/root/guji-workspace/<书ID>-*'` | 单子里 `ws_repo` 为空：书没登记 WS_REPOS，或交单用的 cv 早于登记 | 登记 WS_REPOS；单子里写明 `ws_repo` |
| prep「db-pull」`CentralError: 500 internal` | 中心库 files 表整文件行大，2000 行一页 Worker 读挂 | #812 起遇 500 自动减半；交单用的 cv 要含 #812 |
| 单子成功，但待审率比本机高几倍、glyph_match 几乎没有 same | 执行方字形库缺本书字样（见下节第 1 条） | 修真源、出快照钉号后重跑 |
| Step3 整册失败 `layout_prior 表 … 里没有 NN` | 离线格位表没这一册 | 补表，或改 `page_map: pins` |

## 三、坑的来龙去脉

1. **借库冷启动的书，人裁实例没进字形库真源**（#816 修）。冷启动借别的书的库时，借来库的 source（`v1`、`v2`、`vol01`）
   被记成「只属于借来库」；本书人裁入库的实例 id 是 `v2:<册>:…`，也挂在通用 source `v2` 下。旧的 `export_store` 遇到借来
   source 整个跳过，本书人裁就全丢了：中心库 `glyph_store/instances/` 为空，`patches/` 为空。本机 glyph.db 里有，所以本机跑一切正常，
   只有换机器（任务库执行方、新会话）才露馅。修后重新 `guji glyph-db export` 再推。
2. **交单所用 cv 的 jobs 模块决定 `ws_repo`**：`ws_repo` 在提交那一刻按交单机器上的 WS_REPOS 填。本机检出是旧分支时，即使 dev 已登记也填不上。
3. **本机跑和任务库跑别混**：同一册本机在跑时交单，结果会打架。交单前停掉本机重跑，或只交本机没跑的册。
4. **多页长跑的后台任务**：Bash 后台缺省 30 分钟超时会被杀；一册全流程 15–25 分钟，十册串跑要显式给长超时，或交任务库。
