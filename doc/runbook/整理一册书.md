## 〇、先读这一节

### 〇·五 先用脚本，卡了再看正文
`scripts/zhengli/zl.py` 把 S1–S20 里机器能做的都串成了**幂等、可断点续跑**的步骤，只在需要人／模型看图的地方停下（写 `reports/<册>/NEXT.md`）。

```bash
python scripts/zhengli/zl.py plan --book vol05 --ws $WS            # 看哪步做了、哪步没做
ZL_CLOUD=1 python scripts/zhengli/zl.py run --book vol05 --ws $WS --bg    # 后台跑到第一个闸
python scripts/zhengli/zl.py status --book vol05 --ws $WS          # 看进度与最近日志
python scripts/zhengli/zl.py run --book vol05 --ws $WS --only vision-gate   # 闸处理完后续上
python scripts/zhengli/zl.py intervene --book vol05 --step S11 --why "…" --waited-min 5   # 记一次介入
python scripts/zhengli/zl.py metrics --book vol05 --ws $WS         # 度量表
```
- 步骤：`env → ws → db → yaml → [import-snap] → survey → compute-a → calibrate → glyphdb → cache-verify → rare → compute-b → snap-pack → audit → contact → vision-gate(闸) → sheet(闸) → human-count → export → taboo → pending → close`。
- 导出要给文本版本号 `ZL_TEXT_VERSION`（首次 0.1.0；已在 book-text 上的写线上现行版本），不给就停，不替你猜。`close` 跑粗校档 `close-check --tier rough`，用 `pending` 步出的待审单草稿（`reports/<册>/_pending/`，不上线）核 2c，再出 R1–R5 报告 `reports/<册>/粗校报告.md`；2d 没交代的列列成草稿 TSV，剩下的活写进 NEXT.md。
- 它替你处理：拉中心库、缺依赖自动补装重试、网络抖动重试、疑似内存不足（含 BrokenProcessPool，前台后台都算）减半并行续跑、缓存只在有错位时 `--fix`、磁盘满即停、快照 CRLF 校验（`import-snap`）、书 yaml 合并标准开关（ruamel 往返；会重排原文就不写，改给片段让你手贴）、长命令一律后台 nohup、状态落 `<ws>/../zhengli-state/<册>.json`。

### 0.1 你要交付什么

一册书交付，指下面 14 项全部达标，见第四节。核心产物是三份文件：

| 文件 | 是什么 |
|---|---|
| `NNN.char.json` | 原刻逐字：格键 `页:列:格[a/b]`，原字，不加任何记号 |
| `NNN.cord.json` | 每个格在原图上的框 |
| `NNN.norm.json` | 规范层：转换表版本，加逐位例外 |

格式见 book-text `docs/ORIGINAL.md`、guji-format 规范 01/02。每册对 `open-guji/book-text` 开 PR 并入 main，文本线 0.x 带 `proofing: true`（book-text VERSIONING，2026-10-16 起；旧的 `wip/siku` 分支不再用），见 S19。另写一份收尾记录。

### 0.2 七条不能违反的规矩

1. **不改 `open-guji-cv` 的代码**。引擎有问题，开 `[整理→CV]` 卡，自己先做下一件事。
2. **人裁只能经控制台或 `guji` 命令写**，不手改 `feedback/events/` 下的文件。
3. **不加 `--force`，不从上游起跑**，除非本文明确写了要这样做。只从受影响的最上游一步起跑。
4. **审期间不整册重算**。发现问题先记下，等这一册审完再统一重算；重算必须出差异单。
5. **整理本和证人都不是标准答案**。己、已、巳在殿本里三字同形，只能按文意判。
6. **提交只 add 具体文件**，不 add `products*`、`cache/`；不强推；book-text 的产物不进 main。
7. **问人要省**：能自己判的自己判；必须问人的，攒成一张请审单一次问，见第三节。

### 0.3 名词

| 词 | 意思 |
|---|---|
| 册 | `vol04` 这样的 book id，对应书 yaml `books/vol04.yaml` |
| 工作区（ws） | `guji-workspace` 里这部书的目录，下文记作 `$WS` |
| 格 | 一个字位，id 形如 `vol04:12:3:7`（页:列:格），夹注加 a/b |
| 放行 | Step7 自动定字（admit=True）；没放行的格进待审队列 |
| 证人 | 现成整理本，用来对齐和对勘，**不是真值** |
| 人裁 | 人在控制台给的裁决，写成事件 |
| 页面坐标 | 产物里的 `bbox_page` 等页面框是 `raw_page_px@top-right`：**原点在页面右上角、x 从右往左量**（与原图 PNG 左右镜像，x' = 页宽 − x）。按格裁原图**别直接拿它当左上原点去切片**（会静默裁到另一个字），用 `core.anchor.crop_patch(img, ch.bbox_page)`，或 `core.anchor.to_cv(bbox, 页宽)` 换算。说明见 `products/kinds/chars.py` 模块头 |

### S5 Step1–7 管线
- **先做 S6 建库，再跑 Step5 起的步**。**推荐排法（T2 验证，约 2 小时到请审单）**：`--to cell_shrink` 跑 Step1–4 → 建库（S6）→ S5-b 备表／预渲／候选 → **一次** `--from glyph_match` 跑到 seed_admit，比「先 Step5–7、再补 5-b、再重落 seed_admit」少一次 seed_admit。
  - **不要把 Step1–4 和建库并行**：4 核上互相拖慢（row_segment 每页 14 秒 vs 单跑 3 秒）。
  - **云端后台 nohup 跑一条命令整册**，不分块：「9 分钟」只是前台工具超时；实测 4 核 Step1–4 约 15 分、Step5–7 约 60 分（glyph_match 每页 10–13 秒）。2026-10-20 起 `row_segment`、`cell_shrink`、`glyph_match`、`seed_admit` 也按页并行（`--jobs` 缺省＝CPU 数），见 `doc/segmentation_v2_pipeline.md`「登记并行」。seed_admit 并行前**先把字块缓存建好**（`guji cache warm`）：铁证要读别页的人裁刻例图；单进程峰值约 2.1 GB，进程数按可用内存自动压。
- 命令：`guji pipeline keben_body_v2 <册> --pages all -w $WS`；跑完 `guji status <册> --pages all -w $WS`。
  整册从头跑到尾、没有失败页时，跑完**自动把产物打包存进 R2**（标签 `<版本三段>-full`，不标 main，要标用 `guji products pack promote`）；要设 `GUJI_DATA_TOKEN`（正式令牌），不想存加 `--no-pack`。
  2026-10-20 起 `guji pipeline` 跑多步时**缺省每步一个子进程**（`--isolate-steps`），跑完进程退出、内存整体回收；
  单进程连跑时 torch、字形库匹配器、语言模型、证人索引一路叠着，殿本 vol06 到 seed_admit 主进程 3.5 GB。
  某一步崩了（异常、护栏拒跑）就停在那一步、返回非零，不再拿缺了的上游接着跑。要单进程连跑加 `--no-isolate-steps`；
  `--json` 报告只在单进程时有。
- **跑完 Step6 后手动推一次训好的语言模型**（2026-10-20 用户定手动推）：本机现训过的（日志里 context_decide 首页几十秒）才需要，R2 已有的会跳过：`GUJI_DATA_TOKEN=$GUJI_DATA_TOKEN_PROD guji products pack push-index`。键按语料内容与训练代码算，别的机器同一册直接取用。
- 验收：全部新鲜，失败 0。记下人审率：待审格数 ÷ 总格数。
- 坑：
  - 一条命令控制在 9 分钟内，按页分块跑。4 核实测：Step1–4 约 5 秒/页，约 90 页一块；Step5–7 约 25–30 秒/页，15–20 页一块；
  - status 报「过期」时先查原因，不要上来就 `--force`；
  - **代码指纹从 2026-10-06 起只认代码**，注释和 docstring 不算。在这之前算的产物，升级 cv 后会整体显示「代码或版本变了」。先跑 `guji fp-migrate <册> --pages all --code-formula -w $WS` 干跑：它按老口径回放指纹，逐位相等（代码、参数、上游都没变）的才改写。确认后加 `--apply`。对不上的才是真要重算的；
  - **语料库版本（2026-10-18 起，设计见 `doc/design/语料库版本化方案.md`）**：册 yaml 写 `corpus: N` 就把语料类输入钉在语料库 vN，指纹只认版本号。给一册开钉的顺序**不能反**：① `guji corpus build -w $WS` 出清单（工作区里已有就跳过），`guji corpus verify -w $WS` 要干净；② 在**有产物的机器**上先拉新 yaml（加了 `corpus: N`），马上跑 `guji fp-migrate <册> --pages all --trust -w $WS` 干跑，再加 `--apply`（只会改写 `glyph_match`、`rare_candidates`、`align_ref`、`context_decide`、`seed_admit` 这五步的指纹，几何步不动）；③ `guji status` 看这五步没有因自己的指纹过期。不先迁移就让 yaml 生效，这五步会整体判过期、白白重算。⚠️ `--trust` 不验老指纹，只在你确认这册产物本来就是新鲜的时候用（先 status 看过，没有因「代码或版本变了」过期的步）；老产物先走上一条的 `--code-formula`。升语料库（vN+1）默认不影响已钉册；哪册要用新版，把它的 `corpus:` 改成新号，再按上面顺序迁移或重算。**钉了版本的册，读语料的五步开跑前会核清单（2026-10-19 起）**：清单里的文件被改了或缺了就拒绝跑，出新版本改钉或把文件改回去（临时绕过 `GUJI_CORPUS_DRIFT=warn`）。新书用两级清单：`guji corpus init -w $WS`（钉最新底库），见 `doc/datastore.md` 第六节「两级语料库清单」。
  - **老产物里有「自证放行」**：09-26 之前算的 glyph_match 会拿库里同一个物理格的自身图块来比，比上的就放行。新代码摘掉了这一路，所以老册整册重算后，**待审会比旧数字多一批，这是预期，不是故障**。vol02 的 p20 就是例子，详见 overview#407。请审时照实报格数。
  - 换过字形库后，glyph_match 不会自动判过期，此时要 `--from glyph_match --force`。这是本文唯一允许 `--force` 的地方。

#### S5-b 生僻字候选（`rare_candidates`）：什么时候要跑、怎么跑（overview#429）
- **什么时候要跑**：书 yaml `params.seed_admit` / `align_ref` / `context_decide` 里开了 `rare_ref`（`rare_agree`、`shadow_promote` 已于 W2 删除）或 `rare_topk` 时，`guji status` 会多出 `rare_candidates` 这一步；都没开就自动跳过，不用管。
  - 开了开关却没跑 5-b，seed_admit 照常出结果，但相应通道 **0 格**，等于没开。现在会有两处提示：
    - `guji status` 在那一步下面印「⚠ rare_ref 开着但 rare_candidates 缺 N 页，这些页 rare_ref 通道未生效」；
    - 跑批日志开头印同一句。
  - 5-b 补跑后，seed_admit 自动判过期。直接再跑 `--from seed_admit` 就行，不用 `--force`。
- **先备好模板索引，再跑这一步**。这一步慢不在算候选，在第一页**现建 CNN embedding 模板表**：字表乘 8 套字体，逐字渲染、前向，单核每秒约 25 字。四庫一册是两档：基集 cjk-a 29,689 字，升级档 ext-b 42,438 字，共约 **45–50 分钟**，看着像卡死在第一页（#429 那次 p3 停了 18 分钟）。表落在 cv 的 `models/glyph_cnn_r5/emb_<key>.npz`。key 按内容算（checkpoint、字体、字表），所以同一套字表的书共用一张表。缺表时 `guji pipeline` 开头会印「⚠️ Step5-b 模板索引未预建」，并写出 key。备表**首选第 0 条**：
  0. **从向量包落成（10-20 起，几秒）**：`guji cache pull-rare-index --book <册> -w $WS`。从 hanzi 库的全字表向量包（R2 公开域名，不要令牌，缺省 8 位约 26 MB）按字表取行落成同一个 `emb_<key>.npz`，旁边写 `.source.json` 记版本与精度；已有的表来源不同（本地现建、旧快照）会被替换，全队统一。只认与本机模型、字体、渲染代码同规格的包，没有就提示走下面两条。8 位与全精度在真刻本上找对率持平（总设计 `doc/design/汉字字形与关系库-总设计.md` §10「B2 续：精度」）。已有 5-b 产物不用因此重跑：指纹不变，候选只在第 5–10 名之间换顺序。
  1. **导现成的**：四庫 vol04 的两个 key 是 `c58003867002d48b`（基集）和 `bec61ba15252b3bc`（升级档），已经在 guji-workspace 的包 `snap/96mid1ogzk/rare-index-vol08/20260928T1136` 里（另有 vol10 的包；T2 实测 vol05 与 vol08 包 key 一致，起跑无「未预建」提示）。导入命令是 `guji snap import snap/96mid1ogzk/rare-index-vol08/20260928T1136 -w $WS --ws-repo <guji-workspace 克隆> --cv-repo <open-guji-cv 克隆>`，这是纯附件包，只落 `models/` 下的两张表，不碰 products。导入前先起一次 `guji pipeline … --from rare_candidates --to rare_candidates`，看开头那句提示里的 key 和包里的对不对得上，看完即可 Ctrl-C。对不上就走第 2 条；
  2. **自己建**：`guji cache build-rare-index --book <册> --jobs 4 -w $WS`。分片多进程建，结果与单进程逐位相同。四庫 vol04 两档在云端 4 核上 **10 分钟**（单核要 46 分钟），4 个进程合计峰值约 2.4 GB。建出的表与 09-28 那份包里的逐位相同。已有的表会跳过。
- **快照导入后先预渲字块**：快照只带 products，不带 `cache/`，5-b 第一次读字块要逐格现切，每页约 13 秒，占了这一步九成时间。用 `guji cache warm --book <册> --pages all --jobs 4 -w $WS` 多进程先切好：vol04 实测 121 页 288 秒，约每页 2.4 秒；切出的图与串行逐位相同，页戳由主进程补齐，`guji cache verify` 干净。本地一直在跑的册，缓存本来就在，这步可以省。
- **命令**（表备好、字块预渲之后）：`guji pipeline keben_body_v2 <册> --pages all --from rare_candidates --to rare_candidates -w $WS`，然后 `--from seed_admit` 重落 Step7。
  - 耗时（vol04 云端实测，cv `claude/Q3-rare-perf-1006` 起）：进程起来后的第一页约 35 秒，用来读表、建真刻例原型；之后每页约 **1.4 秒**。整册 200 页 316 秒，**约 6 分钟，一条命令跑完**。
  - 在此之前的 cv（真刻例原型缓存只有一档），每隔几页会有一页多花约 30 秒，整册约 25 分钟（#429）。
  - 不预渲字块的话，每页再加 11–13 秒。
  - 从快照起步的整套：备表 10 分钟（导包更快）＋预渲约 9 分钟＋5-b 约 6 分钟。
  - 这一步没标 `parallel_safe`，`--jobs` 对它不起作用。
- **坑**：不要几个进程同时冷启动同一册的 5-b（书级跑批锁本来也不让）。每个进程会各自现建同一张表，而且落盘的临时文件名相同，可能互相踩。

### S6 字形库重建（在 S5 的 Step5 之前做）
- 命令，按顺序：
  1. `guji glyph-db rebuild -w $WS --no-borrow`：从真源 `output/glyph_store/` 加 `feedback/events/` 重建。**它会删掉重建 `glyph.db`，所以必须第一个做**。
     派生表示（归一、骨架、HOG）缺省按 CPU 数多进程算（`--jobs` 可改），库内容与单进程逐位相同（殿本 1.85 万例：派生表示单进程 163 s → 4 进程 38 s；整条命令连补放人裁 265 s → 55 s）。新机器 `guji db pull` 里的那次重建同样多进程；
  2. 导字体域，两条：
     `guji glyph-db import-font -w $WS --edition font:jigmo --jobs 4`
     `guji glyph-db import-font -w $WS --edition font:iming --jobs 4`
     **先找预建件**（2026-10-20，`clustering/font_pack.py`）：同一套字体文件、字表、渲染代码出过的字体域，本机
     `cache/fontdb/` 有或 R2 有（要读令牌）就整表拷进来，两套合计下载约 1.8 GB（8 路并发约 45 秒）、拷表约 45 秒；
     拷进来的行与逐字渲染的逐列相同，字体域指纹相同。结果里带 `from_pack` 就是走的预建件。
     没有预建件才逐字渲染：`--jobs 4` 云端 jigmo 约 8 分、iming 约 4.5 分（缺省 1 进程慢一倍以上，放后台跑）。
     渲完的机器（或换了字体、字表、渲染代码之后）推一次给别的机器用：`guji glyph-db font-pack-push -w $WS`
     （正式令牌，手动；推完删本机导出的包，`--keep-pack` 留着）。`--no-pack` 强制逐字渲染。
     包的键含字体文件、字表和渲染链上几个模块（`font_glyphs`、`canonical`、`normalize`、`features`、`glyph_db`）的代码指纹，
     这几个模块一改（哪怕只改导入流程），旧包就对不上、要重渲重推。
  3. `guji glyph-db stats -w $WS`：刻本域和 font 域都有数，记进卡（stats 不直接分列两域，看 sources）。
  4. **字形库版本**（GUJI-727，2026-10-21 起；设计 `doc/design/字形库按版本钉-细设计.md`）：
     - 出号：`guji db sync -w $WS` 推干净后 `guji glyph-db snapshot -w $WS --note "…"`，出 g<N>（清单 `config/glyph-pack/g<N>/manifest.json`，
       顺手建好 `output/glyph-g<N>.db`，从当前库拷字体域，所以先做完第 2 步）。内容与上一版相同拒绝。**推要用户点头**：`guji db push -w $WS`
       推清单，清单登记的文本随这次 push 按 sha 传 R2（刻例图早已在桶里）；`guji glyph-db pin-verify -w $WS --pin N` 只从 R2 拼一遍核对新机器建得出来。
     - 用：册 yaml 写 `glyph_pin: N`。`guji db pull/sync` 和 `guji pipeline/step` 起跑前会自动建缺的 `glyph-g<N>.db`（本机没有的文件从 R2 取）；
       也可 `guji glyph-db pin-build -w $WS [--pin N]`。`guji glyph-db pin-list -w $WS` 看各版本、库文件在不在、哪些册钉了它。
     - 人裁照常写当前库；本格的裁决经事件通道立即生效，经字形库传播到别的格的要等改钉。
     - 让旧册吃新人裁：出 g<N+1> → 册 yaml 改 `glyph_pin: N+1`（seed_admit 整册判过期，glyph_match 的库指纹是软参数、不过期）→
       `guji recheck <册> --glyph-diff N`（N 是改钉前的号）只点名受影响的格 → `guji pipeline --from glyph_match` → `guji products diff` 出差异单。
- `guji-cv` 与 `guji` 现在是同一套命令。
- 坑：
  - 已经有本书人裁之后就不再借别书的库，只有冷启动时才借；
  - 字体域让 `glyph.db` 从约 230 MB 涨到约 3.1 GB，预留盘。

### S7 缓存校验
- 命令：`guji cache verify --book <册> -w $WS`，有错位就加 `--fix`。
- 验收：错位为 0。
- 耗时：**戳与现行产物对得上的页免查**（2026-10-20）：引擎重跑一页前先清这页缓存、写完记戳，读缓存时戳对不上整页作废，
  这类页的缓存一定是这一代产物切的。所以刚整册跑完的册几乎全部免查，秒级（原来要约 5 分钟）。真正要查的是没戳的老缓存
  和产物从别处换进来（tar、`snap import`、还原备份）的页——它们照旧逐列渲染比对。`--full` 连有戳的页也查。
- 坑：从别处换进产物、或更新字形库之后，必须先校验缓存，否则重算会读到错位的字块，而状态仍显示「新鲜」。

### 看图结论存成事件（S8、S10 共用，overview#428）
- 为什么：模型看图判的结论是日曰、入人八、己已巳这些形近组的强真值来源，只写 md 就攒不起来。但它**不是人裁**，不能当人裁用。
- 存：`$WS/reports/<册>/看图结论.jsonl`，UTF-8，一行一格，**只追加**（改结论就在末尾追加一行新的，同一格按 `ts` 后到覆盖）：
  ```
  {"cell": "vol04:12:3:5", "v": "wrong", "char": "曰", "shown": "日", "judge": "<模型名>", "note": "中横右端不接框", "group": "日曰", "ref": "曰"}
  ```
  | 键 | 必填 | 说明 |
  |---|---|---|
  | `cell` | 是 | 字位 id `<册>:<页>:<列>:<格>`（夹注格末尾带 a/b），和放行错穷举表、控制台同一个 |
  | `v` | 是 | `ok` 放行字对 / `wrong` 放行字错 / `unsure` 看不清 |
  | `char` | `wrong` 时填 | 看图认为该是的字；认不出可留空，照样送审 |
  | `shown` | 建议填 | 判的时候这格放行的字。现行字已不是它时，这条结论不再送审 |
  | `judge` | 是 | 模型名（也可以命令行 `--judge` 统一给） |
  | `note` / `group` / `ref` / `ts` | 否 | 理由 / 形近组（己已巳、日曰、入人八…）/ 整理本此位的字 / 判的时刻（ISO，UTC） |

  别的键会报错；有一行不合格式，整批不写。**以 `open_guji_cv/feedback/vision.py` 的文档串为准**，旧卡上的例子键名不对。

## 六·一、云端会话额外要注意

- ws 只稀疏克隆本书，别册原图排除；`guji snap pack` 在稀疏克隆上会失败，只对这条命令加 `GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=core.sparseCheckout GIT_CONFIG_VALUE_0=false`。
- 产物不进 git，容器会回收：S5 整册算完、每次重落之后都 `guji snap pack` 推快照，分支名记卡。
- 提交邮箱用 `<id>+<login>@users.noreply.github.com`，否则推送被隐私规则挡。
- `pkill -f`、`pgrep -f` 会匹配到自己的 shell，用 PID 杀进程。
- 开会话时把要用的仓一次挂好，不靠会话自己 `add_repo`（要用户批准，会卡住）。拉源仓给**完整 40 位提交号**，短号会 ref_not_found。
- Windows 本地发来的快照包：`_manifest.jsonl` 按 CRLF 算哈希、git 里存 LF，`guji snap import` 会判 sha256 不对。用 `python scripts/zhengli/snap_import.py <分支> -w … --ws-repo … --cv-repo …`（容忍行尾，cv 统一行尾后可不用）。导入的产物落在 `--ws-repo` 那个 ws 克隆下的工作区目录。Windows 上 `guji snap` 会卡在 `fcntl`（只 `watch` 用，归 #413）。
- 沙箱里设了 `GUJI_PRODUCTS_DIR` 时，`guji snap import` 也落到它指的产物根（2026-10-17 起；此前无视它、直接写进 ws 克隆的 `products/<书>`，会碰到正式产物）。导入前仍建议先 `--dry-run`。
- GitHub 评论服务端会自动加署名；按规矩不带署名的，发完用 `update_issue_comment` 去掉。
