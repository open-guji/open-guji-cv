## 〇、先读这一节

### 〇·五 先用脚本，卡了再看正文
`scripts/zhengli/zl.py` 把 S1–S20 里机器能做的都串成了**幂等、可断点续跑**的步骤，只在需要人／模型看图的地方停下（写 `reports/<册>/NEXT.md`）。

```bash
python scripts/zhengli/zl.py plan --book vol05 --ws $WS            # 看哪步做了、哪步没做
ZL_CLOUD=1 python scripts/zhengli/zl.py run --book vol05 --ws $WS --bg    # 后台跑到第一个闸
python scripts/zhengli/zl.py status --book vol05 --ws $WS          # 看进度与最近日志
python scripts/zhengli/zl.py run --book vol05 --ws $WS --only vision-gate   # 闸处理完后续上
python scripts/zhengli/zl.py intervene --book vol05 --step S11 --why "…" --waited-min 5   # 记一次介入
python scripts/zhengli/zl.py metrics --book vol05 --ws $WS         # 度量表
```
- 步骤：`env → ws → yaml → [import-snap] → survey → compute-a → calibrate → glyphdb → cache-verify → rare → compute-b → snap-pack → audit → vision-gate(闸) → sheet(闸) → human-count → export → taboo → close`。
- 它替你处理：缺依赖自动补装重试、网络抖动重试、疑似内存不足降并行重试、磁盘满即停、快照 CRLF 校验（`import-snap`）、书 yaml 合并标准开关（ruamel 往返；会重排原文就不写，改给片段让你手贴）、长命令一律后台 nohup、状态落 `<ws>/../zhengli-state/<册>.json`。
- **没覆盖、仍要人或会话做的**：S4 异常页看图、版面先验抄值、S8 看图（见 S8「大批量看图」）、S11 的第 4 节、S12 人裁、S14 提交、S15 入测试集、S18 目测、S19 推 book-text、S20 收尾记录。脚本在这些点停下并写清楚做什么。
- 云端：开会话时**把要用的仓（cv、ws、overview，入测试集还有 dataset，推 book-text 还有 book-text）一次挂好**，别靠会话自己 `add_repo`（T2 因此等了约 6 分钟）。
- 脚本是 v2 初版：`yaml`、`import-snap` 的校验垫片在 vol02 上试过，其余步骤的命令照本文原样编排、**尚未整册实跑**。首次整册使用请盯一遍，出问题把现象补进对应步的「坑」。

### 0.1 你要交付什么

一册书交付，指下面 14 项全部达标，见第四节。核心产物是三份文件：

| 文件 | 是什么 |
|---|---|
| `NNN.char.json` | 原刻逐字：格键 `页:列:格[a/b]`，原字，不加任何记号 |
| `NNN.cord.json` | 每个格在原图上的框 |
| `NNN.norm.json` | 规范层：转换表版本，加逐位例外 |

格式见 book-text `docs/ORIGINAL.md`、guji-format 规范 01/02。四庫各册都推到 `open-guji/book-text` 的 **`wip/siku`** 一条分支（2026-10-06 起，不再开 `wip/siku-volNN`）。另写一份收尾记录。

### 0.2 七条不能违反的规矩

1. **不改 `open-guji-cv` 的代码**。引擎有问题，开 `[整理→CV]` 卡，自己先做下一件事。
2. **人裁只能经控制台或 `guji` 命令写**，不手改 `feedback/events/` 下的文件。
3. **不加 `--force`，不从上游起跑**，除非本文明确写了要这样做。只从受影响的最上游一步起跑。
4. **审期间不整册重算**。发现问题先记下，等这一册审完再统一重算；重算必须出差异单。
5. **整理本和证人都不是标准答案**。己、已、巳在殿本里三字同形，只能按文意判。
6. **提交只 add 具体文件**，不 add `products*`、`cache/`；不强推；book-text 的产物不进 main。
7. **问人要省**：能自己判的自己判；必须问人的，攒成一张请审单一次问，见第三节。

### 0.3 名词

| 词 | 意思 |
|---|---|
| 册 | `vol04` 这样的 book id，对应书 yaml `books/vol04.yaml` |
| 工作区（ws） | `guji-workspace` 里这部书的目录，下文记作 `$WS` |
| 格 | 一个字位，id 形如 `vol04:12:3:7`（页:列:格），夹注加 a/b |
| 放行 | Step7 自动定字（admit=True）；没放行的格进待审队列 |
| 证人 | 现成整理本，用来对齐和对勘，**不是真值** |
| 人裁 | 人在控制台给的裁决，写成事件 |

## 一、开工前

### S1 环境自检
- 做：建 Python 3.12 虚拟环境，装依赖，自检。
- 命令：
  ```bash
  cd <cv仓> && uv venv .venv --python 3.12 && uv pip install -e ".[console,torch,dev,shadow]" ruamel.yaml
  .venv/bin/python -c "import torch, scipy, cv2, joblib, sklearn; print(torch.cuda.is_available())"   # Windows 是 .venv/Scripts/python
  ```
  - 没有 GPU 的机器（云端）先从 CPU 索引装 torch，再装 extra，否则会拖下几 GB 的 CUDA 轮子：
    `uv pip install torch --index-url https://download.pytorch.org/whl/cpu`。
- 环境变量：`PYTHONIOENCODING=utf-8`；`GUJI_WORKSPACE=$WS`。
- 验收：torch、scipy、cv2、joblib、sklearn 都能 import；`guji status <册> -w $WS` 能出表。
- 坑：
  - **必须装 `shadow` extra（scikit-learn==1.9.1，与 `models/shadow_admit/*.json` 一致）**：标准配置的 `shadow_veto: true` 要它，缺了 seed_admit 整册 `ModuleNotFoundError: joblib`（T2 返工 11 分钟）；
  - 云端 python3 是 3.13，`uv venv --python 3.12` 自己会下，可用；
  - 缺 torch 或 scipy **不报错，只悄悄降级**：切点判官、CNN 候选失效，截条图出空白。所以必须自检。
  - 不要跑全量测试，它会卡在 rare 冷启动。

## 二、算

### S4 Step0 预检与拆页
- 命令：`guji survey <册> -w $WS`。宽或高超过本册中位的 1.3 倍、或不到 0.7 倍的页列为异常；版心用 `guji locate-gutter`。
- 异常页逐页看图，三选一：拆页顺移、标非正文、保留。**拿不准就停下问人，附图。**
  - 「标非正文」不用手标：封面、扉页、书名签由 `border_detect_gate` 自动判 page_type，跑完 Step1 用 `guji status` 查一眼即可。
- 坑：
  - 顺移页号之前，先在 `feedback/events`、`verdicts`、`glyph_store/instances` 三处 grep 这几页，**有命中就停手问人**；
  - 同一册有多处拆页时，合成一张顺移表；
  - 改过页面的册，在 `Commons修图记录.md` 加一行。

### S5 Step1–7 管线
- **先做 S6 建库，再跑 Step5 起的步**。**推荐排法（T2 验证，约 2 小时到请审单）**：`--to cell_shrink` 跑 Step1–4 → 建库（S6）→ S5-b 备表／预渲／候选 → **一次** `--from glyph_match` 跑到 seed_admit，比「先 Step5–7、再补 5-b、再重落 seed_admit」少一次 seed_admit。
  - **不要把 Step1–4 和建库并行**：4 核上互相拖慢（row_segment 每页 14 秒 vs 单跑 3 秒）。
  - **云端后台 nohup 跑一条命令整册**，不分块：「9 分钟」只是前台工具超时；实测 4 核 Step1–4 约 15 分、Step5–7 约 60 分（glyph_match 每页 10–13 秒，`--jobs` 在这一步看不出页级并行）。
- 命令：`guji pipeline keben_body_v2 <册> --pages all -w $WS`；跑完 `guji status <册> --pages all -w $WS`。
- 验收：全部新鲜，失败 0。记下人审率：待审格数 ÷ 总格数。
- 坑：
  - 一条命令控制在 9 分钟内，按页分块跑。4 核实测：Step1–4 约 5 秒/页，约 90 页一块；Step5–7 约 25–30 秒/页，15–20 页一块；
  - status 报「过期」时先查原因，不要上来就 `--force`；
  - **代码指纹从 2026-10-06 起只认代码**，注释和 docstring 不算。在这之前算的产物，升级 cv 后会整体显示「代码或版本变了」。先跑 `guji fp-migrate <册> --pages all --code-formula -w $WS` 干跑：它按老口径回放指纹，逐位相等（代码、参数、上游都没变）的才改写。确认后加 `--apply`。对不上的才是真要重算的；
  - **老产物里有「自证放行」**：09-26 之前算的 glyph_match 会拿库里同一个物理格的自身图块来比，比上的就放行。新代码摘掉了这一路，所以老册整册重算后，**待审会比旧数字多一批，这是预期，不是故障**。vol02 的 p20 就是例子，详见 overview#407。请审时照实报格数。
  - 换过字形库后，glyph_match 不会自动判过期，此时要 `--from glyph_match --force`。这是本文唯一允许 `--force` 的地方。

#### S5-b 生僻字候选（`rare_candidates`）：什么时候要跑、怎么跑（overview#429）
- **什么时候要跑**：书 yaml `params.seed_admit` / `align_ref` / `context_decide` 里开了 `rare_ref`、`rare_agree`、`shadow_promote` 任一个时，`guji status` 会多出 `rare_candidates` 这一步；都没开就自动跳过，不用管。
  - 开了开关却没跑 5-b，seed_admit 照常出结果，但相应通道 **0 格**，等于没开。现在会有两处提示：
    - `guji status` 在那一步下面印「⚠ rare_ref 开着但 rare_candidates 缺 N 页，这些页 rare_ref 通道未生效」；
    - 跑批日志开头印同一句。
  - 5-b 补跑后，seed_admit 自动判过期。直接再跑 `--from seed_admit` 就行，不用 `--force`。
- **先备好模板索引，再跑这一步**。这一步慢不在算候选，在第一页**现建 CNN embedding 模板表**：字表乘 8 套字体，逐字渲染、前向，单核每秒约 25 字。四庫一册是两档：基集 cjk-a 29,689 字，升级档 ext-b 42,438 字，共约 **45–50 分钟**，看着像卡死在第一页（#429 那次 p3 停了 18 分钟）。表落在 cv 的 `models/glyph_cnn_r5/emb_<key>.npz`。key 按内容算（checkpoint、字体、字表），所以同一套字表的书共用一张表。缺表时 `guji pipeline` 开头会印「⚠️ Step5-b 模板索引未预建」，并写出 key。备表二选一：
  1. **导现成的**：四庫 vol04 的两个 key 是 `c58003867002d48b`（基集）和 `bec61ba15252b3bc`（升级档），已经在 guji-workspace 的包 `snap/96mid1ogzk/rare-index-vol08/20260928T1136` 里（另有 vol10 的包；T2 实测 vol05 与 vol08 包 key 一致，起跑无「未预建」提示）。导入命令是 `guji snap import snap/96mid1ogzk/rare-index-vol08/20260928T1136 -w $WS --ws-repo <guji-workspace 克隆> --cv-repo <open-guji-cv 克隆>`，这是纯附件包，只落 `models/` 下的两张表，不碰 products。导入前先起一次 `guji pipeline … --from rare_candidates --to rare_candidates`，看开头那句提示里的 key 和包里的对不对得上，看完即可 Ctrl-C。对不上就走第 2 条；
  2. **自己建**：`guji cache build-rare-index --book <册> --jobs 4 -w $WS`。分片多进程建，结果与单进程逐位相同。四庫 vol04 两档在云端 4 核上 **10 分钟**（单核要 46 分钟），4 个进程合计峰值约 2.4 GB。建出的表与 09-28 那份包里的逐位相同。已有的表会跳过。
- **快照导入后先预渲字块**：快照只带 products，不带 `cache/`，5-b 第一次读字块要逐格现切，每页约 13 秒，占了这一步九成时间。用 `guji cache warm --book <册> --pages all --jobs 4 -w $WS` 多进程先切好：vol04 实测 121 页 288 秒，约每页 2.4 秒；切出的图与串行逐位相同，页戳由主进程补齐，`guji cache verify` 干净。本地一直在跑的册，缓存本来就在，这步可以省。
- **命令**（表备好、字块预渲之后）：`guji pipeline keben_body_v2 <册> --pages all --from rare_candidates --to rare_candidates -w $WS`，然后 `--from seed_admit` 重落 Step7。
  - 耗时（vol04 云端实测，cv `claude/Q3-rare-perf-1006` 起）：进程起来后的第一页约 35 秒，用来读表、建真刻例原型；之后每页约 **1.4 秒**。整册 200 页 316 秒，**约 6 分钟，一条命令跑完**。
  - 在此之前的 cv（真刻例原型缓存只有一档），每隔几页会有一页多花约 30 秒，整册约 25 分钟（#429）。
  - 不预渲字块的话，每页再加 11–13 秒。
  - 从快照起步的整套：备表 10 分钟（导包更快）＋预渲约 9 分钟＋5-b 约 6 分钟。
  - 这一步没标 `parallel_safe`，`--jobs` 对它不起作用。
- **坑**：不要几个进程同时冷启动同一册的 5-b（书级跑批锁本来也不让）。每个进程会各自现建同一张表，而且落盘的临时文件名相同，可能互相踩。

### S6 字形库重建（在 S5 的 Step5 之前做）
- 命令，按顺序：
  1. `guji glyph-db rebuild -w $WS --no-borrow`：从真源 `output/glyph_store/` 加 `feedback/events/` 重建。**它会删掉重建 `glyph.db`，所以必须第一个做**；
  2. 渲染字体字形，两条，`--jobs 4`（缺省 1，慢一倍以上），每条控制在 9 分钟内：
     `guji glyph-db import-font -w $WS --edition font:jigmo --jobs 4`
     `guji glyph-db import-font -w $WS --edition font:iming --jobs 4`
  3. `guji glyph-db stats -w $WS`：刻本域和 font 域都有数，记进卡（stats 不直接分列两域，看 sources）。
  - jigmo 一条约 8 分 20，贴近 9 分钟上限，慢机会超：放后台跑。
- `guji-cv` 与 `guji` 现在是同一套命令。
- 坑：
  - 已经有本书人裁之后就不再借别书的库，只有冷启动时才借；
  - 字体域让 `glyph.db` 从约 230 MB 涨到约 3.1 GB，预留盘。

### S7 缓存校验
- 命令：`guji cache verify --book <册> -w $WS`，有错位就加 `--fix`。
- 验收：错位为 0。
- 耗时：刚跑完 Step1–4 的册也要约 5 分钟；`cache warm` 只要 7 秒但那时已无事可做，不必为了 S7 去跑它。
- 坑：从别处换进产物、或更新字形库之后，必须先校验缓存，否则重算会读到错位的字块，而状态仍显示「新鲜」。

### S8 放行错穷举（请审之前必须做完；先做 S9）
- 做：列出「已放行、不是人裁、和证人不同」的格，分系统类和非系统类，非系统类逐格看图。
- **它不是真穷举**：只覆盖和证人对得上的格。和证人对不上、或证人缺段的放行格，靠下面的「新放行分层看图」兜。
- 先按列扫乱码：罕用码位占比高的列、列图宽偏离本册中位的列，逐列看图；证人整段缺夹注的段落单列一档。
- 命令：先跑 S9 的 `guji collate`，再跑 `guji audit admitted <册> -w $WS`。
  - 产出 `$WS/reports/<册>/<册>.放行错穷举.md`，另有同名 `.json`。
  - 清单分三档：
    - **认字差异**：证人是别的字，或多字、缺字。**只有这一档要逐格看图**，在表末列填「看图结论」：对、错→应为X、看不清；
    - **异体差异**：例如刻本「卽」、证人「即」。刻本原字照录不算错，按组扫一眼即可；
    - **系统性**：码位、用字账一类，按类核一次。
  - 看完复制到 overview `书/<册>/放行错穷举-vN.md`。判为错的格，或看不清的格，进 S11 请审单。
  - **看图结论同时存成 jsonl 导入**（见下面「看图结论存成事件」）：只写 md 攒不成强真值。
- vol03 实测：355 格里认字差异 36 格，异体 196 格，系统性 123 格。
- 坑：context 通道是放行错的大头；iron_gate 要单独统计。
- **大批量看图的做法（T2 验证）**：把待看格做成**字块对照联系页**（每张 60 格，每格「前字块｜本字块｜后字块＋放行字」，放大），逐页看。**认字差异档必须带上下文且放大看**：只看字块会漏（T2 的 note_lexicon「雨／兩」要靠「兩江總督採進本」才看出）。`seal` 通道里印章遮挡下无字的格（T2 有 30 格）没有字，不判对错。联系页生成器目前各会话自备，尚无标准脚本（待补）。
  - `看图结论.jsonl` 的 `ts` 要自己填（UTC ISO）。
  - 导入会同时写共享分片 `feedback/verdicts/char-recognition/vision-checks/items.jsonl`：这是 `import-vision` 的设计，提交时要知道它在。
- **准确率验收（每册必做，也用于验开关）**：按页分层抽 300 格已放行、非人裁的格看图，报「看了几格、错几格、看不清几格」；按放行通道分开报（`evidence` 里的通道名），新开的通道每条至少看 100 格（不足全看）。开关前后对比时，只对「新放行的格」看图（超过 200 按页分层抽 200）；新册没有人裁，「与人裁不一致」没有检验力，不要用。
  - 看图要用**引擎列图**（`cache/<册>/column_image` 加 `bbox_col`），不能用原图加 `bbox_page`，两者坐标系不同。
  - 结论照下面「看图结论存成事件」导入。

### 看图结论存成事件（S8、S10 共用，overview#428）
- 为什么：模型看图判的结论是日曰、入人八、己已巳这些形近组的强真值来源，只写 md 就攒不起来。但它**不是人裁**，不能当人裁用。
- 存：`$WS/reports/<册>/看图结论.jsonl`，UTF-8，一行一格，**只追加**（改结论就在末尾追加一行新的，同一格按 `ts` 后到覆盖）：
  ```
  {"cell": "vol04:12:3:5", "v": "wrong", "char": "曰", "shown": "日", "judge": "<模型名>", "note": "中横右端不接框", "group": "日曰", "ref": "曰"}
  ```
  | 键 | 必填 | 说明 |
  |---|---|---|
  | `cell` | 是 | 字位 id `<册>:<页>:<列>:<格>`（夹注格末尾带 a/b），和放行错穷举表、控制台同一个 |
  | `v` | 是 | `ok` 放行字对 / `wrong` 放行字错 / `unsure` 看不清 |
  | `char` | `wrong` 时填 | 看图认为该是的字；认不出可留空，照样送审 |
  | `shown` | 建议填 | 判的时候这格放行的字。现行字已不是它时，这条结论不再送审 |
  | `judge` | 是 | 模型名（也可以命令行 `--judge` 统一给） |
  | `note` / `group` / `ref` / `ts` | 否 | 理由 / 形近组（己已巳、日曰、入人八…）/ 整理本此位的字 / 判的时刻（ISO，UTC） |

  别的键会报错；有一行不合格式，整批不写。**以 `open_guji_cv/feedback/vision.py` 的文档串为准**，旧卡上的例子键名不对。
- 导入：`guji events import-vision $WS/reports/<册>/看图结论.jsonl --book <册> -w $WS`（先加 `--dry-run` 看一眼计数）。
  - 写到 `$WS/feedback/vision/vision-看图结论.jsonl`：`kind=vision_check`、`actor=model`、`payload.source=vision`、`payload.judge=<模型名>`；同一文件再导一遍，没动的行不重复写；
  - 同时进裁决表分片 `char-recognition/vision-checks`，`label_origin=vision`（`--no-gold` 只写事件）。进测试集要显式 `guji gold import char-recognition/vision-checks`，评测按来源分层报。
- 下游口径：**不进字形库、不算人裁定字（`human_chars`）、不算已裁、不进绑定表**。判 `wrong` 的格**只送人审，不改字**：回到待审队列，卡上挂 `vision_flag` 和看图认的字，控制台 doubt 筛 `vision_flag` 一键筛出来。人在控制台裁过的才进字形库、才算数。
  - 判 `unsure` 的**只记账，不进待审队列**。要人看，就写进请审单第 4 节。
  - 导完核一次 `guji glyph-db stats`：刻本域条数不应变。
- `feedback/vision/` 在 `feedback/` 下，S14 `guji store commit` 一并提交。

### S11 请审（问人）
- **要在 S8 导入看图结论之后再生成**（才把看图判错的格算进队列，T2 359→363）。「看不清」的格不进队列，只能写第 4 节。
- 先生成请审单：`guji audit sheet <册> -w $WS`，产出 `$WS/reports/<册>/<册>.请审单.md`。前三节自动填写：待审队列按类计数、失效老裁决（已预勾）、人裁字≠放行字；第 4 节「按字位改判」由你把 S8、S10 看图判为错的格追加进去。格式要求如下：
  - 在哪：控制台地址 → 册 → 步 → 标签；
  - 一共几格，预计几分钟；
  - 每格：字位、现在是什么字、建议是什么字、理由；
  - 不审时默认怎么处理。
- **一次只给一类活**：待审队列、按字位改判、看原图，三类分开问。超过 30 分钟拆成几次。
- 控制台：`guji console --no-auth`，打开 http://127.0.0.1:8640/。
- 用户不在控制台前（云端会话）：把请审单做成 Artifact 审查页，每格附字块图和上下文截条，链接贴卡（审查页的 `check_fixedpoint.py` 要 playwright，云端 venv 没装，要手装）；用户回复后在本会话起控制台，用 `POST /api/events` 代写，写完照 S12 核数。

### S12 人裁核数（用户审完当场做）
- 命令：`guji audit count <册> -w $WS --since <请审单发出的时间> [--expect <请审单字位清单.txt>]`。
  - 报：事件数、字位数、按裁决类别计数、同一格裁了多次的、**没带锚点的**；给了 `--expect` 还报漏审和单外多审。
  - 退出码非 0 表示有漏审，或有没带锚点的事件，要当场处理。
- 验收：审过的条数和请审单对得上，没漏，没重复，事件都带锚点。

### S13 收尾闸
- 命令：`guji status <册> --pages all -w $WS --json`（输出第一行是「工作区 …」头，不是纯 JSON，解析前先截到第一个 `{`），看 `closure_gaps` 和 `closure_mismatches` 两个字段。
- 验收：
  - `closure_gaps` = 0；
  - `closure_mismatches` 逐格扫一眼，真错的进请审单；
  - `vision_pending`（看图判错、人还没裁的格）是报告项，不挡收尾；但这些格也在待审队列里，`close-check` 第 2 项「待审清零」会算上它们，要请人裁掉。

|---|---|---|---|

## 六·一、云端会话额外要注意

- ws 只稀疏克隆本书，别册原图排除；`guji snap pack` 在稀疏克隆上会失败，只对这条命令加 `GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=core.sparseCheckout GIT_CONFIG_VALUE_0=false`。
- 产物不进 git，容器会回收：S5 整册算完、每次重落之后都 `guji snap pack` 推快照，分支名记卡。
- 提交邮箱用 `<id>+<login>@users.noreply.github.com`，否则推送被隐私规则挡。
- ws 有别的未提交改动时，`guji store commit --push` 的 `pull --rebase` 会报 128，先把其余改动提交。
- `pkill -f`、`pgrep -f` 会匹配到自己的 shell，用 PID 杀进程。
- 开会话时把要用的仓一次挂好，不靠会话自己 `add_repo`（要用户批准，会卡住）。拉源仓给**完整 40 位提交号**，短号会 ref_not_found。
- Windows 本地发来的快照包：`_manifest.jsonl` 按 CRLF 算哈希、git 里存 LF，`guji snap import` 会判 sha256 不对。用 `python scripts/zhengli/snap_import.py <分支> -w … --ws-repo … --cv-repo …`（容忍行尾，cv 统一行尾后可不用）。导入的产物落在 `--ws-repo` 那个 ws 克隆下的工作区目录。Windows 上 `guji snap` 会卡在 `fcntl`（只 `watch` 用，归 #413）。
- GitHub 评论服务端会自动加署名；按规矩不带署名的，发完用 `update_issue_comment` 去掉。

## 七、停下来问人的情况（判准表）
