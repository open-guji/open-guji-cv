## 一、起服务

控制台由 systemd 用户服务托管，开机自启、挂了自动拉起，正常不用手动起停。

```bash
systemctl --user status guji-cv-console.service   # 看是否 active (running)
curl -s http://127.0.0.1:8640/ -o /dev/null -w '%{http_code}\n'   # 本机应为 200
curl -sk https://43.162.109.111/healthz   # 对外应返回 "ok"（这条不需要密码）
```

**代码/依赖要跟上 main**：服务跑的是 `~/open-guji-cv`（独立 worktree，对外这份建议直接跟 `main` 分支，不用再纠结 `production`）。

```bash
cd ~/open-guji-cv
git fetch origin '+refs/heads/*:refs/remotes/origin/*'   # 这台的 git 配置默认 fetch 不带全部分支，普通 git pull 可能拉不到刚推的新 main——遇到"commit 对不上"先这样全量 fetch 一次
git checkout main && git merge --ff-only origin/main      # 或已在 main 上就直接 git pull
.venv/bin/python -m pip install -e ".[console,torch,dev,shadow]"   # 依赖可能变了，重装一遍，shadow 漏装会在 seed_admit 整册时报 joblib 缺失
systemctl --user restart guji-cv-console.service
systemctl --user reset-failed guji-cv-console.service   # 如果之前连续崩过触发了 StartLimitBurst，先重置再 start/restart
```

**2026-10-10 踩过的坑**：main 分支升级后，控制台启动必须给 `GUJI_WORKSPACES_ROOT`（工作区总目录，老代码读的是 `GUJI_WORKSPACE_DIRS`，新代码不认这个了），缺了直接报错退出（`code=exited, status=1`）。已加进 `~/open-guji-cv/runs/console.env`：

```
GUJI_WORKSPACES_ROOT=/home/sheldon/guji-workspace
```

这个目录下每本书一个子目录、子目录里有 `books/<id>.yaml`，控制台的工作区下拉框从这里扫出来。改了 `console.env` 之后一定要 `systemctl --user restart`（`EnvironmentFile` 不会热加载）。

### 对外入口（Caddy 反代 + Basic Auth）

配置在 `/etc/caddy/Caddyfile`（不进 git，服务器本地改）：

- `https://43.162.109.111` 反代到 `127.0.0.1:8640`；`/healthz` 不鉴权，其余整站挡在 `basic_auth` 后面
  （控制台自身在 `GUJI_CONSOLE_NO_AUTH=1` 时是本机免鉴权全员 admin，所以必须靠 Caddy 这层挡住公网）。
- 改配置后：`sudo systemctl reload caddy`（不用整个重启，reload 不丢连接）。

## 二、加用户

当前是单一共享账号（Caddy `basic_auth` 一条 `用户名 密码哈希`），不是每人一个账号。要加第二个账号：

```bash
caddy hash-password --plaintext '新密码'   # 输出一串 $2a$14$... 的 bcrypt 哈希
```

在 `/etc/caddy/Caddyfile` 的 `basic_auth { ... }` 块里再加一行 `新用户名 新哈希`（一行一对，Caddy 原生支持多用户），`sudo systemctl reload caddy`。

**密码不进任何仓库、issue、任务书**——只在服务器本地的 Caddyfile 里，谁要用密码找用户本人要，不要在协作记录里写明文或哈希之外的线索。

## 五、服务挂了怎么办

```bash
systemctl --user status guji-cv-console.service      # 看 Active 状态和退出码
journalctl --user -u guji-cv-console.service -n 50 --no-pager   # 看最近日志
```

**常见原因**：
- `StandardError=inherit`，真正的报错在 `~/open-guji-cv/runs/console.log`（`StandardOutput` 走这个文件），先看这个文件尾部。
- 连续崩 5 次（10 分钟内，`StartLimitBurst=5`）会进入 `failed` 状态、不再自动重启——这种情况 `systemctl --user restart` 没用，要先 `systemctl --user reset-failed guji-cv-console.service` 再 `start`。
- 前台跑一次能看到完整报错（比后台日志直观）：
  ```bash
  cd ~/open-guji-cv
  set -a; source runs/console.env; set +a
  .venv/bin/python -m open_guji_cv console --no-browser --port 8640
  # Ctrl-C 或另开一个终端按 pid kill 掉，确认没问题后再交回 systemd 管
  ```
- 内存被 cgroup 硬顶（`MemoryMax=3584M`）杀掉：`systemctl --user status` 的 CGroup 那段能看到 memory peak；`OOMPolicy=continue` 已经设了子进程被杀不连带停控制台，但主进程自己被杀还是会触发 `Restart=always`。
- 对外访问不了但本机 `curl 127.0.0.1:8640` 正常：先查 Caddy（`systemctl status caddy`、`sudo ss -tlnp | grep :443`），再查腾讯云安全组有没有放行 443/80（这台的安全组改动不在本仓会话的权限范围内，需要有控制台权限的人去腾讯云后台查，参考 `机器清单.md` 里记的账号范围）。

## 六、已知限制

- 这台机器 2 核 7.4G，**不要在上面跑整册重算**（整册重算走专门的云端跑批会话，见 #493；这台只跑控制台这类轻量常驻服务）。

## 七、会话怎么开（10-11 事故后补）

10-10～10-11 这台的会话（overview-73／Eliot）卡了近一天：**用 tmux 直连方式开的会话，在终端里弹出了一个确认问题，没人应答，而且从别的界面（issue、SendMessage）完全看不到这个问题在等**，于是一直卡着，CV 经理和用户都以为会话挂了，#331 里的一件小活临时改派给别的会话做。

- **不要用 tmux 直连的方式开这台的常驻会话**：那种方式下终端里弹出的确认提示没人盯着看，一旦卡在权限确认上，外部（issue 评论、GitHub、别的会话）完全看不出来，只能干等。
- **要问的问题写进卡（issue 评论）里，不要只停在终端提示上**：会话该做什么、要不要等人确认，写清楚讲给人看的问题，不要指望终端里的确认框被看到。
- **常用权限尽量预先放行**：这台会话常跑的 `git add/commit/push`、`curl`、`systemctl --user` 这类操作，提前在权限配置里放行，避免反复撞上确认提示（本身也会增加卡住的概率）。
- 判断会话是否真的卡住：看它最近一次 GitHub 评论／提交的时间，再看本机有没有在跑的进程（`ps`、`systemctl --user status`）；拿不准先直接在那个会话窗口里说一句（比等 issue 回复快）。

## 八、收割链路演练（点卡→收割→推分支，10-11 演练过一遍）

L3 补标签批（`guji label-batch make cutline-gold|column-end`）的收割不走控制台「收割」按钮（那个按钮喂的是旧 Artifact 格式），走法是：**浏览器点卡 → `POST /api/events` 落事件（只写不消费）→ `guji label-batch harvest <批次id>` 把事件解析进 dataset 分支 → `git push`**。10-11 用一个独立测试批次（`TEST-harvest-drill-1011`，3 张卡，没碰 A 批）走通一遍，全程≈3 秒（远小于目标 10 分钟）：

```bash
# 1) 出测试批次（约 70s，不计入点完后的耗时，只在备料阶段做一次）
cd ~/open-guji-cv
.venv/bin/python -c "
from open_guji_cv import steps as _s
from open_guji_cv.cli_v2 import main
import sys
sys.argv = ['guji', 'label-batch', 'make', 'cutline-gold', 'vol02', '--n', '3',
            '--id', 'TEST-xxx', '-w', '<工作区>', '--dataset', '~/open-guji-dataset']
main()
"

# 2) 点一张卡＝浏览器前端自动 POST 的接口，可手动模拟（约 30ms）：
curl -s -X POST "http://127.0.0.1:8640/api/events?ws=siku-zongmu" \
  -H "Content-Type: application/json" \
  --data-binary @event.json
# event.json: {"batch":"<批次id>","step":"row_segment","unit":"boundary","kind":"cutline",
#   "events":[{"id":"<卡id>","verdict":"ok","slot_above":N,"slot_below":N+1,...}]}
# 返回里 consume_skipped 字段出现＝正常（L3 批不自动消费，等 harvest）

# 3) 收割进 dataset（约 1s；注意 harvest 的 kind 参数是批次 id，不是 cutline-gold/column-end）：
.venv/bin/python -c "
from open_guji_cv import steps as _s
from open_guji_cv.cli_v2 import main
import sys
sys.argv = ['guji', 'label-batch', 'harvest', '<批次id>',
            '--dataset', '~/open-guji-dataset', '-w', '<工作区>']
main()
"

# 4) dataset 分支提交推送（约 2s）：
cd ~/open-guji-dataset
git checkout -b claude/<分支名>
git add <收割改动的 items.jsonl>
git commit -m "..."
git push origin claude/<分支名>
```

**断点排查**：
- 第 2 步若报 `KeyError: 未注册的产物种类`：CLI 没先 `from open_guji_cv import steps`（PR #27 修了 `cmd_label_batch` 这条，但用 Python 直调内部函数时要自己补这行）。
- 第 3 步报「没有批次 X」：`harvest` 的位置参数是**批次 id**，不是 `cutline-gold`/`column-end`（跟 `make` 不同）。
- `guji label-batch harvest` 不带 `-w` 会读不到服务器上 `guji-workspace` 里的批次文件（仓内默认路径跟批次实际落点不是一个地方）。
- 演练完的测试批次/分支记得清（测试文件直接删，测试分支 `git push origin --delete` 再 `git branch -D`），别留下垃圾批次污染批次台账。

## 九、一次性人审任务（不进 `guji label-batch` 框架）怎么搭

像 overview#431「13 对异体字确认」这类一次性、临时的看图判断任务（不是 cutline-gold/column-end 那两种标准 L3 批），没必要改 `open_guji_cv` 代码新开一个 `kind`。做法（10-11 搭过一次，**没碰 cv 代码，没重启控制台**）：

1. 从相关 dataset 分支把要看的图（crops）`git show <branch>:<path> > 本地文件` 拉下来（不用 checkout 切分支，避免分支切换风险）。
2. 写一个独立静态页（纯 HTML+JS，自己建目录，如 `~/variant-review/`），把数据写死在页面的 JS 常量里（**务必程序化核对一遍 id 列表，别手抄**——手抄这批 13 对里抄错过 2 组）；提交逻辑直接 `fetch POST` 到控制台已有的 `/api/events`（这个接口本来就是通用的，batch id 自己起一个新名字即可，不需要注册）。
3. 在 Caddyfile 里加一段 `handle_path /<路径>/* { basic_auth {...同现有哈希...} root * <本地目录> file_server }`，**插在现有 `handle {}` 兜底块前面**（Caddy 按顺序匹配，不然会被兜底块吃掉）。
4. `sudo caddy validate --config /etc/caddy/Caddyfile`（注意 caddy 在 `/usr/local/bin`，`sudo` 默认 PATH 可能找不到，要写全路径）→ 通过再 `sudo systemctl reload caddy`（**reload 不是 restart**，零停机，不影响正在跑的主控制台进程）。
5. 验证：`curl https://.../<路径>/`，没带密码应该 401（跟主站一样受 basic_auth 保护）；核心控制台 `/healthz` 仍 200，证明没被这次改动带崩。
6. 结果收在 `feedback/events/<batch id>.jsonl`，是通用事件格式，不会被当成 L3 批（除非调 `guji label-batch make` 登记过同名 id），谁要落到正式账本（如用字账）按各自写域规矩来，我这边只管把原始裁决交出去。

## 十、点卡状态备份（10-11 Mila 定，不用再问）

每个工作区的 `review/batches/`、`feedback/events/`、`feedback/lists/` 没有独立备份——写入本身是原子的（见 `EventLog.append`：写 `.tmp` 再 `os.replace`，不会写坏），但没有误删/误覆盖后能回滚的副本。补法：

- 脚本：`~/ops-scripts/backup-review-state.sh`（**不在 cv 仓、不在任何 git 仓里**，纯本机运维脚本）。对每个 `~/guji-workspace/<书>/` 有 `feedback/events` 的工作区，把 `events/`、`lists/`、`review/batches/` 整份拷进 `<工作区>/.snap_backup/review-state/<UTC时戳>/`；每工作区留最近 30 份，超出自动删旧的（跟产物那边 `.snap_backup`／`BACKUP_KEEP` 的做法同一个思路，但这个管点卡状态，产物备份是 `open_guji_cv/snap/manifest.py` 自己的另一套，两者不混）。
- 定时：`crontab -e` 加了 `*/10 * * * * ~/ops-scripts/backup-review-state.sh >> ~/.local/state/review-backup.log 2>&1`（10 分钟一次）。
- **"点前存"**：起一个可能要点很久/很多张的大批次前，手动跑一次 `~/ops-scripts/backup-review-state.sh`，不用等下一个 10 分钟整点。
- 只读拷贝，不碰正在写的原文件；跑的时候哪怕撞上用户正在点卡也安全（`cp -a` 读的是当时落盘的版本，不会跟 `EventLog` 的原子写冲突）。
- 磁盘占用：单份快照按当前数据量约 10MB／工作区，30 份上限约 300MB，80G 盘上可忽略。

## 十一、新加 `handle_path` 静态页 403（不是 401）——家目录权限（10-11 踩过）

在 Caddyfile 加一条 `handle_path /<路径>/* { ... root * /home/sheldon/<目录> file_server }`（§九的做法）之后，**浏览器已登录过主站、带着缓存的 basic_auth 凭据去访问新路径，会报 403**（不是 401）——主站本身仍能正常打开。

**病因**：主站 `/` 走 `reverse_proxy 127.0.0.1:8640`，不需要 Caddy 自己读磁盘，所以哪怕家目录权限很紧也不受影响；但 `file_server` 这条路由要 Caddy 进程自己去读 `/home/sheldon/<目录>/index.html`。这台机器 `/home/sheldon` 是 `drwx------`（只有 `sheldon` 自己能进），Caddy 跑在独立系统用户 `caddy` 下（`systemctl show caddy -p User` 能看到），连家目录第一层都进不去——basic_auth 过了之后，文件系统直接把它挡成 403。

**验证方法**（不用真密码就能查，不用等 curl）：`sudo -u caddy cat /home/sheldon/<目录>/index.html`——报 `Permission denied` 就是这个问题；Caddy 没配访问日志（这台站点块没加 `log` 指令），journalctl 里查不到任何 403 记录，**查不到日志不代表没问题**，别被这个带偏。

**修法**：`chmod o+x /home/sheldon`——只加"外人能穿过去"的执行位，不加读权限（验证：`sudo -u caddy ls /home/sheldon` 仍 `Permission denied`，列不出来；`.ssh`、`.claude.json` 等各自权限不受影响，`caddy` 用户依然读不到）。只有本来就是 `755`/`644`（本意就是给人访问的静态页）的目录能被这条权限放过去。**以后在这台机器下新开一个 `handle_path` 静态站点，先确认过这条**，不用每次都现踩一遍。

## 十二、自己搭的审阅页 POST `/api/events` 报 500（纯文本、不是 JSON）——`kind` 字段不在合法枚举里

§九这类独立静态页提交事件时，**`kind` 不能随便起名字**——`open_guji_cv/feedback/events.py` 的 `Event` 模型用 `Literal` 锁死了一串合法值（`verdict/band/border_class/recrop/not_a_char/confirm/relabel/skip/damaged/mark/flag/split/merge/note/cutline/border_offset/head_raise/n_body_slots/collate_ok/char_convention/mark_jiajie/variant_deny/collate_verdict/unmark_jiajie/glyph_audit/return_resolve/needs_review/admit_candidate/vision_check`），自造一个不在里面的字符串（比如 10-11 我写的 `runt_review`、`variant_pair`）会在 `make_event()` 里被 pydantic 拒绝，FastAPI 异常中间件直接吐纯文本 `Internal Server Error`（不是 JSON），前端如果直接 `res.json()` 会在这步报一个看不懂的 `SyntaxError`，容易误判成权限/路由问题。

**排查**：先看 `~/open-guji-cv/runs/console.log` 的 traceback（`journalctl --user -u guji-cv-console.service` 这台没转发日志，查不到，白查）；`ValidationError...kind` 一眼能看出来。

**修法**：没有特殊消费逻辑需求时一律用 `kind: "note"`（最通用，不会被任何 `routes.yaml` 消费者特殊处理，纯粹落盘当原始记录）；要分类用 payload 里自己的字段（如 `kind_tag`），别指望顶层 `kind` 能自由取名。

**顺手要做的**：静态页的提交函数别直接 `await res.json()`，先 `await res.text()` 再 `try/catch JSON.parse`，否则非 JSON 响应（500/502 之类）会把真实状态码和报错吞掉，只剩一句 SyntaxError，排查时方向全错。

## 十三、要某几列/格的图，但那本书从没建过缓存——`guji cache column`/`cache get` 现建

搭 §九这类审阅页要用列图时，`/api/column-review/img/...`、`/api/cutline/img/...` 这些控制台接口**只读缓存，不现算**——`image_cache().get()` 没有就是没有，不会自己渲染。这台机器上 vol01/02/03/04/05 早年整册跑过，`cache/<册>/column_image` 是全的；**vol06–10 从来没建过列图缓存**，接口会报「没有列图」。

两条命令都能现建单张（不用整册跑批，几秒钟一张）：
```bash
# 1) 已经建过同类缓存、只差这一张列图：直接要
.venv/bin/python -m open_guji_cv cache column --book <册> --page <页> --col <列> -w <工作区> --out <本地路径.png>

# 2) 那本书这个 kind 的缓存从来没建过（"没有列图"报错）：走 materialize 现算
.venv/bin/python -m open_guji_cv cache get --book <册> --kind column_image --key p<页4位>c<列2位> -w <工作区> --out <本地路径.png>
# key 格式用 python -c "from open_guji_cv.core.spec import column_key; print(column_key(页, 列))" 生成，别手拼
```
第 2 条会把算出来的图顺手写进 `cache/<册>/column_image/`（下次第 1 条就能直接取），**不碰 `products/` 正式产物，只是缓存层**，随便删随便重建。
