## 二、类型与方法

**类型只分两类**（sheldon 10-24 定），注册表里的 `GroupSpec.kind` 就是它：

| 类型 | `kind` | 是什么 | 判的原则 |
|---|---|---|---|
| **同义** | `variant` | 同一个字的不同写法（异体），如 尙尚、參㕘叅、刊刋 | **看刻形**：照录刻本上的写法。刻形分不开，或已定统一录一个码位的，走码位归一（工作区 `config/codepoints.yaml`，各册共用） |
| **不同义** | `near_form` | 字形相近的不同字（形近），如 己已巳、日曰、子于 | **看文意**：不管刻得像哪个字，一律按文意定（sheldon 10-17）。文意没有区分力、字形反而分得开的（宋朱未、各名、心必），看字形 |

**方法不另分类**。每组注册一个**方法数组**（`FlowSpec.methods`），数组里的方法可以任意组合：
- `combine="first"`：依次试，第一个给出字的方法说了算；
- `combine="agree"`：每个方法都跑，给了字的必须一致。

复核（别的通道已放行、放行字在组里的格再判一次）默认跑同一个数组；组声明了 `review_methods` 就改跑它。
同义组复核只跑字形方法（`registry.SHAPE_REVIEW`，2026-10-24 起 13 组）：字频永远说主形，拿它复核会把真次形也降掉。判出组里另一形就降审，不改字。

能用的方法见 `groups/methods.py` 模块头。各组实际用的数组见[总表](字组总表.md)。

## 三、人工数据

### 1. 格式：一行是一格的一种标注

汇总文件是 dataset 仓 `char-groups/labels/unified.jsonl`，由同目录的 `build_unified.py` 生成，可以反复重跑。字段的完整说明在该目录的 README。要点如下：

| 字段 | 含义 |
|---|---|
| `id` | `册:页:列:格号`，夹注格号带 `a`／`b` |
| `kind` | `shape` 刻形（图上刻的是哪个字）；`reading` 文意（按上下文定的字）；`cut` 切线或折线（部件分界，坐标 0–1、左上原点）；`parts` 部件读法 |
| `form` | 结论字；看不清、不是字时为 null，原因写在 `status` |
| `by` `date` `src` `file` | 谁、哪天、从哪来（`central:<批名>` 表示中心库人裁事件；`variant:<组>`、`review:<页>` 表示数据集里的原件） |
| `also` | 同一格同一 `kind` 的其他来源（多个来源合并成一行） |
| `verified` | `{n, agree}`：这一格这一类有几个独立来源、结论是否一致（2026-10-24 起） |
| `corrected_from` | 与最终结论不同的早先结论 `[{form, src, date}]`，即被更正过，如 10-24 vol04 的 8 格 變→𠮓（2026-10-24 起） |
| `in_central` | 有没有中心库来源（流水线读得到）（2026-10-24 起） |

合并规则：同一格同一类的多条来源，结论取日期最晚的一条（同日时，中心库事件优先），所以更正写进中心库后，重建汇总就生效。

### 2. 存放

- **原件**放在 dataset 仓：审查页的点选、切线落盘在 `char-groups/variant/<组>/labels.jsonl`，字块图在同目录 `crops/`；文意复审在 `char-groups/review/`。
  - 审查页结论只存在页面里不算落盘。
  - 收页当天要写成文件，并在 `char-groups/标注清单.md` 登记一行：批、日期、格数、位置、是否进中心库。
- **中心库**的人裁事件是流水线唯一读得到的人裁。
  - 凡是要给 seed_admit 当证据的（刻形 confirm、码位更正），都要写成中心库事件。
  - 写中心库要 sheldon 在线程里亲口说「推」。
  - 只用来训练的（切线、部件读法）留在数据集即可。
- **模板库**（`config/groups/<组>/ids_bank.json`）的 `source.labels` 要写清标签从哪来：人裁、放行字当标签、看图补的格，以及去掉了哪些格。放行字只跟着整理本或台账走，**不等于刻形**。拿它当标签前，先按册留出，把和标签不一致的格逐格看图。

### 3. 数据准不准：三种量，都进状态报告

| 量什么 | 怎么量 |
|---|---|
| 人裁本身 | 同一格有多个来源或复核过的，算一致率；被更正的条数单列。另有一种错是**格号漂移**：人裁记在旧格号上，重切以后同一个号指向别的字（10-24 v0 表里 大太 组「人裁 㫖、放行 大」、即卽 组「人裁 愼」都是这样），核对前要按锚点重绑（`feedback/anchor`）。人裁也会录错，比如 10-24 查出 vol04 的 變／𠮓、㣲／微 人裁前后不一致。定录法以刻形和 IDS 为准 |
| 切线、折线 | U-Net 交叉验证的墨迹像素归段准确率，和直线基线对照；机器预填后人改了几成 |
| 方法 | 按册留出的给字率、错数、门槛；文意规则的册外回测冲突数（规则是从 vol01–10 整理本挖出来的，对这几册零冲突是必然，要用没见过的册回测） |

## 四、状态报告

    guji groups status --prod <产物根>[,…] --labels <dataset>/char-groups/labels/unified.jsonl \
        --codepoints <工作区>/config/codepoints.yaml --out <dataset>/char-groups/status --tag <这一轮的标签>

产物根下是 `<册>/seed_admit/p*.json`（`guji products pack fetch` 的布局，或工作区的 `products/`）。口径写在 `eval/group_status.py` 模块头。

| 列 | 含义 |
|---|---|
| 出现格 | 放行字在组里的格，加上进过组流程的格 |
| 组判、组判率 | 进过组流程的格；组流程给出字的比例 |
| 放行率、送审 | 出现格里最终放行的比例；送审的格数 |
| 人裁核对、不一致 | 已放行、且有人裁的格里，和人裁不一致的格数（先按 codepoints 归一）。不一致不等于错：人裁可能晚于产物；人裁字不在本组里的单列为「疑格号漂移」（人裁记在旧切分的格号上）。其余要逐格看 |
| 人工数据 | 刻形、文意、切线、部件各几条，其中多少条在中心库 |
| 多来源／更正过 | 人工数据里有几条是多个来源的、其中几条来源之间结论不同（被更正过）——人裁本身准不准的读数 |

每轮重落后，在推库之前跑一次，结果提交到 dataset 仓。看哪组变好、哪组变差，变差的组要在它的卡里写原因。

## 五、加一组、改一组

1. **先写卡**：`doc/字组/<组 id>.md`，按下面的模板。写清字形差别（IDS）、类型、打算用的方法数组、数据从哪来。
2. **注册**：在 `groups/registry.py` 加一项。同义组只在 `seed_admit.group_flow` 里判；只按刻形判、不进全局 `GROUPS` 的，放 `SHAPE_GROUPS`。然后重生成总表。
3. **上线门槛**：
   - 新方法、新模板库、新规则，按册留出评测，门槛定到**留出 0 错**；
   - 用 vol04–20 现有产物回放，比较放行数、送审数和放行字的变化；改了字的格要逐格看图；
   - 误判样例随 PR 给出。
4. **册配置**：新组要加进各册 yaml 的 `group_flow`（中心库，要「推」）。冻结册（vol01、vol05）不动。
5. **跑状态报告**：第四节的命令，结果和 PR 一起给。

### 卡的模板

```markdown
# <组 id> <成员>（同义｜不同义）

## 字形差别
各字的 IDS 和刻本上实际能看到的差别；殿本的特殊刻法。

## 怎么判
方法数组（与总表一致）和为什么这么选；复核、陪衬字、两段判等设置；门槛和它是怎么定的。

## 试过的和负结果
方法、日期、结果、为什么没用。

## 人工数据
有哪些批（日期、格数、位置、是否进中心库）；模板库或规则的标签来源；已知的录错和更正。

## 现状与待办
最近一次状态报告的读数；还送审的格主要卡在哪；下一步。
```
