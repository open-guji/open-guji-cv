- **前置**：无

## 要解决什么

各个步骤的数据、金标、测试集定义是否清晰。尤其是数据是否有很好地汇总、更新，方便统计。

数据包括：
- 每一册、每一页，有多少输入、多少输出
- 哪些自动放行，哪些人审，人审哪些通过，哪些驳回
- 如果有多个决定，每个决定占百分之多少
- performance 怎么样

其中有些是 golden standard，有些是 guardrail，有些是 statistics。

测试集定义在 open-guji-dataset，最好和这些步骤一一对应。

先派 agent 实测分片是否存在、行数是否对得上、命名是否按 Step 组织、三类数据是否分开存放，

### 4. 三类统计（吞吐量/候选占比/performance）仍缺一键命令 → 未处理，标记为已知缺口

已有一键命令（`guji status` / `guji check quality|rulers|round|rate`）覆盖判据 A–F、
四把尺子、人审率台账；但"每册每页输入输出量""多候选/通道各占比""performance/速度"
三类仍需临时手写脚本，dwell 计时文档自己也写"目前无基线"。这是新增基础设施的活，
工作量超出本次"审阅+回填"的范围，已记入 `STEP_MAP.md`「已知空白」一节，留作后续任务。

### 5. benchmark/guardrail/statistics 三类数据跨仓分散、无统一命名规范 → 已写定义文档

术语先纠正一下：**benchmark（测试集）与 gold standard（金标）不是并列的两类**——
gold standard 是 benchmark 里每条样本携带的标注答案，是包含关系。跟 benchmark
真正并列、性质不同的是 **guardrail**（护栏/排除名单，运行时会被代码读取用来拦截
决策）和 **statistics**（统计量，跑完产生的既成事实记录）。

**已处理**：在 `open-guji-cv` 仓新建 [doc/data-taxonomy.md](https://github.com/open-guji/open-guji-cv/blob/main/doc/data-taxonomy.md)，
定义三者的区别、盘点现状分布（benchmark 在 `open-guji-dataset` 相对集中；guardrail
5 个真实文件淹没在 `config/` 三十多个非护栏配置里；statistics 分散在 `output/` 与
`feedback/`，台账类与一次性报告类没有子目录区分），并给出"新数据往哪放"的判断规则。
**明确不做**：不重命名现有目录、不搬移任何已被代码引用的文件、不建软链接——
当前仓里有其他并行任务在跑，此时动路径风险高于收益，留到以后专门评估。
