## 一、三台机器各干什么

| 机器 | 角色 | 做 | 不做 |
|---|---|---|---|
| **服务器**（美国云，7.5G 内存） | **生产**：对外校对平台 | 跑控制台给校对者用；持有生产数据（各书 `products/`、`glyph.db`、人裁事件）；**唯一写人裁与字形库的地方**；发布之后的**批量重算**（夜间、`guji-batch.slice` 里） | 不改代码、不跑实验、不跑测试、不训模型、不开开发会话 |
| **Claude Code 云端** | **开发与测试** | 所有代码改动、单测、评测；试验一律在沙箱（`GUJI_PRODUCTS_DIR`）；数据从 git 拉（原图、字形库真源、人裁事件都在 git） | 不写生产数据；不直接动服务器 |
| **用户本机**（Windows，有 GPU） | **训练与少数重算** | 模型训练；GPU 才跑得动的大批量；只读字形库（`GUJI_GLYPH_READONLY=1`，09 §〇） | 不写字形库；不当生产 |

**一句话**：代码从云端流向服务器，模型从本机流向服务器，人裁从服务器流回 git 给大家读。

## 二、每样东西的真源与流向

| 东西 | 真源 | 谁写 | 怎么到服务器 | 怎么到云端／本机 |
|---|---|---|---|---|
| 代码（open-guji-cv） | git | 云端各道 | **发布**（§三）：服务器只跟 `production` 分支 | `git clone` main |
| 模型 checkpoint | cv `models/<名>/`（>100 MB 走 Release 附件） | 本机训练 | 随代码一起发布（模型发布就是一次代码发布） | 同左 |
| 原图、书配置 | guji-workspace（git） | 开书时写一次 | `git pull` | `git clone` |
| **人裁事件、裁决、绑定表、字形库真源** | **服务器**（校对者在这里点） | **只有服务器** | — | 服务器定时推 guji-workspace（`glyph_store_sync` 现在只推字形库，**要扩到人裁事件**，见 §五·K） |
| 产物 `products/`、缓存 | 各机本地，可重算 | 服务器跑生产的；云端跑沙箱的 | 服务器发布后自己重算 | 云端沙箱自己算 |

## 三、发布：算法稳定了才统一更新一次

**main 是开发线，`production` 是服务器跟的线。**云端各道照常往 main 合；服务器只在「发布」时才动。

### 3.1 发布节奏：**现阶段不设限**（用户 09-26 改）

校对平台还没上线、很不成熟，**会更新得很频繁，先不考虑发布频率**。`production` 分支照样保留（服务器只跟它、有健康检查与回滚），
但总管随时可以把 `production` 快进到 main 上验过的提交，不必攒一周。等平台正式对外、有外部校对者在用了，再定节奏。

### 3.2 发布前的最低闸

全量测试「失败＋skip 的测试 ID 集合」不退即可；各道护栏与影响清单照 `guji release check` 输出看，**不作硬门槛**，出问题靠回滚。

### 3.3 服务器怎么知道、怎么更新（拉模式，不需要对外开口子）

服务器上一个定时器（每 15 分钟）跑 `guji deploy check`：

1. `git fetch`，看 `production` 有没有前进；没有就退出。
2. 有，但**正有跑批在跑**（书级跑批锁在）→ 记一行「待部署」，下次再看。（维护窗口现阶段不设，平台上线后再加。）
3. 可以部署：`git checkout production` → 装依赖 → 前端已是构建产物随仓走 → **重启控制台服务**（`systemctl --user restart guji-cv-console`）→ 健康检查（`/` 与 `/api/...` 返回 200）。
   **健康检查失败就自动回滚**到上一个 tag，重启，写告警。
4. 部署成功后 `guji status` 各书，把**过期的步排进夜间重算队列**（`guji-batch.slice`，一次一本）。
5. 写部署记录：推一张单到 overview `项目进展/图片初步数字化/进度/inbox/部署/<时戳>-deploy.md`（部署了哪个 tag、重算了什么、耗时），CV 总管的 Monitor 就能看到。

**为什么不用 webhook 推**：服务器要对外开的只有校对平台那一个口子；部署走拉，不必再开一个能触发代码更新的入口。

### 3.4 服务器上还有的开发会话怎么过渡

现在服务器上还有 S 道（vol02 切分）在改代码、跑批。过渡规则：
- S 这一轮 vol02 重跑做完、出快照之后，**以后切分的代码改动都在云端做**；服务器只执行发布后的 vol02 重算。
- 从那以后服务器上不再开开发会话。要在服务器上做的只有：发布部署（自动）、生产重算（自动）、偶尔的运维（一次性任务卡）。

## 四、对外开放校对平台：要补的与要装的

### 4.1 代码要补（云端做，**开放之前必须完成**）

现状（读过代码）：控制台写死绑 `127.0.0.1:8640`，**没有任何登录与权限**；`runs`（起跑批）、工作区切换、写人裁都对能连上的人开放。直接开端口等于让任何人能起跑批、改人裁。

| 要补 | 说明 |
|---|---|
| 登录 | **不自建，走 OAuth 授权码流程**（用户 09-26）：平台跳到开源古籍网站 `/oauth/authorize` 验证 → 回调带一次性码 → 平台后端到 `/oauth/token` 换签名的 id_token（email、role）→ 平台发自己的会话。平台与网站只约定这两个端点和签名密钥，解耦；直连 IP 与将来同域都能用 |
| 角色 | 沿用网站的 `reviewer`/`editor`（→ 校对者：看页面、提交裁决）与 `admin`（→ 管理员：另可起跑批、切书、看运维页）；未登录 401，跳网站登录 |
| 路由分级 | 每条 API 标注要什么角色；`runs`/跑批/工作区管理只给管理员 |
| 裁决记人 | 每条人裁事件带校对者 id；多人同一格裁法不一时的处理（先记下两条，不自动覆盖，进复核队列） |
| 多人并发写 | **依赖 H 道「人裁单写者」**（跨进程写锁＋并发测试）——排队中的这张卡要提前 |
| 监听地址与前缀 | `--host` 参数；**现阶段直连美国服务器（IP＋端口）**，不挂网站域名；留 `--root-path`，将来同域时用 |

### 4.2 服务器要装（一次性，服务器上做）

1. **现阶段直连**：服务器 IP＋端口；建议仍由 Caddy 在前面挡一层（将来要上 HTTPS、换域名时只改 Caddy）。裸 IP 没法签正式证书，直连阶段是 HTTP——OAuth 回调里的一次性码与平台会话 cookie 在明文里走，**只适合内部试用**，对外前要上 HTTPS。
2. 云厂商控制台的**安全组／防火墙放行 80、443**（这一步只能用户在云厂商网页上点）。
3. 装 `guji-deploy.timer`（§3.3）、把人裁事件并进定时推送。
4. 控制台服务改从 `production` 分支起。
