## 一、背景：影像不是文字

中国现存古籍约二十万种。过去二十年，大量善本已被扫描成影像放上各馆的检索系统，
各馆公开的古籍影像以数十万册计。但事情停在了这里：**影像不是文字，文字不是知识**。
研究者只能逐行读原件，无法检索；想训模型的人找不到干净、可溯源、带版本信息的语料。

从影像到可靠文本这一步，现有两条路都不够用：

- **通用 OCR**：古籍是繁体、异体字、刻本或手写、双行夹注、无标点、版框栏线干扰，
  通用模型（PaddleOCR、识典古籍等）在这类材料上的准确率不足以直接使用；
  而且字表是硬上限，简体模型对本书 40% 的字种根本不可达。
- **专业整理**：出版社人海战术，一部中等篇幅的书数月工期、成本以十万计；
  成果通常还丢掉版式（夹注压平、眉批消失、异体字归并），而这种损失是不可逆的——
  下一个人会以为这本已经做过了。

本项目是开源古籍（Open-Guji）三个板块中「**文本化**」板块的核心引擎，
在整条流水线里的位置：

```
索引（book-index）─ 资源采集（bookget-py / IA）─▶ 影印图
                                                     │
                                          ┌──────────▼──────────┐
                                          │  本项目：open-guji-cv │  ← 整理本（book-text / 维基文库 / 用户提供）
                                          │  切分 → 识别 → 定字   │
                                          └──────────┬──────────┘
                                                     │ 逐字位转写 + 字形库 + 版式（夹注/抬头）
                                          排版（luatex-cn / webtex-cn）─▶ 发布（kaiyuanguji-web）
```

上游整理本很关键：本项目不是「从零 OCR」，而是**用影像校对已有的高质量文本，
同时用文本约束影像的识别**——差异处即潜在错误，人工从「全量通读」降到「只看差异」。

## 二、目标：做到什么算成

### 2.1 总目标

给定一部古籍的影印图，结合已有的高质量整理本，产出**逐字位、忠于刻本字形、
保留版式、可直接排版**的高精度文本。对应 BP 里程碑：

| 里程碑 | 本项目要交的 |
|---|---|
| **v0.1 走通全程**（当前） | 自研 OCR 引擎充分支持异体字的识别与校对；一部标杆古籍完成从影像到校对的全流程闭环 |
| **v0.5 从样本到规模** | OCR 与版面识别达到生产可用、不再是流程瓶颈；异体字映射库成型并集成到工具链 |
| **v1.0** | 基本古籍完成高质量校对与版式还原 |

BP 对文本化写的长期精度目标是「第一轮机器识别达到 99% 甚至更高，全面支持 Unicode 字符集」，
并「尽量保留生僻字、异体字，甚至 Unicode 未收字」。

### 2.2 分层目标（用户 2026-09-03 定）

管线分两条线、九步（详见 [流程与模块.md](../../design/流程与模块.md)），目标按线分层：

| 线 | 步骤 | 目标 | 口径 |
|---|---|---|---|
| **切分** | Step1–4：版框界行 → 单列射影 → 逐字切分 → 字框收缩 | **100%** | 「能从图上分开的都分对，分不开的（真粘连）都标出来」，不是逐像素完美 |
| **识别与定字** | Step5–6：字形库匹配 + OCR + 上下文裁决 + 整理本对齐 → 自动进库 / 落人审 | Step5 可略低；Step6 靠上下文与 AI 选字 | 自动放行错误率 **≤0.1%**（零容忍进库错字），正文页人审率 **≤1.5%** |

人工效率的量化口径（`pipeline_review_2026-09-04.md`）：

| 指标 | 目标 |
|---|---|
| 人审率（需要人点的字位 / 全部字位） | 正文页 ≤1.5% |
| 自动放行错误率（对整理本金标 + 用户裁决双真值） | ≤0.1% |
| 每条裁决耗时 | 常规 ≤3 s，生僻字 ≤15 s |
| 生僻字候选 top-10 命中率 | ≥80% |

## 三、方针与原则

这些是踩坑后定下的硬规矩，各模块设计都受它约束：

1. **忠于刻本字形**（用户 2026-09-05 定）。字形库存的永远是刻本上实际刻的形；归一到通行字
   只为理解含义、积累异体数据。事件里 `shape`（刻的形）与 `reading`（文意）分开存。
2. **OCR 只供候选不投票**。任何单一图像信号（OCR、字体模板、拆字 CNN）都不能自动放行；
   自动放行必须有**两路零同源证据互证**（整理本 × 形状，或上下文 × 形状）。
3. **人裁一票定案**，任何自动通道不许覆盖。己/已/巳永远人审。
4. **判据 A 零容忍**。错字进了字形库，后面的页会继承这个错，所以 A 红灯立刻停。
5. **启发式判据只筛候选，不定案**。定案要逐条放大看图；自动 healed 被用户复标回来 12 条、
   模型自投 127 条误报，都是这条的代价。
6. **样本不够时别改算法**。IDS 护栏（拦 487 条对的、3 条错的）、频次加权都是这么否掉的，负结果进测试。
7. **每一步有独立的金标与评测**。改动验证三件套：单测全绿、四把尺子不退、双真值准确率不退。
8. **数值长期、图像即算**。产物带指纹，上游一改下游整链自动过期但不自动重跑；
   金标带锚点（原图 bbox + 内容指纹）以对抗切分重跑带来的漂移。
9. **不训大模型、不抓无授权数据**。不做笔画级识别；IDS 用 MIT 许可的 yi-bai/ids；
   不抓 zi.tools（只深链）；不用 HisDoc1B（机构申请 + NC-ND）。

## 四、分工与工作方式

**2026-09-26 起按七条道分工**（S 切分／R 识别证据／D 定字放行／H 人裁与字形库／P 交付／C 控制台／K 框架窗口），
每条道的代码写域、共享状态的唯一写者、书的跑批位、验收标准都写在 **[进度/并行分工.md](进度/并行分工.md)**；
谁占着哪条道登记在 [进度/任务书/排班.md](进度/任务书/排班.md)。

正本文档：切分线读 cv 仓 `segmentation_v2_pipeline.md`、`step3_touching_and_jiazhu.md`；
识别定字线读 cv 仓 `variant_strategy.md`、`review_loop_sop.md`，以及本文件夹 [进度/总览/14](进度/总览/14-准确率优先-Step6与Step7重设计.md)（准确率优先的新放行规则）。

日常循环：**一轮 12 页**（≈2000 字位 ≈ 15～20 条人审 ≈ 一次坐下审完）。跑一批 → 审 → 收割消费 →
看判据 A–F → 全绿跑下一批，红灯才修算法。前台用控制台 `guji-cv console`（127.0.0.1:8640），
后台用 `pipeline / step / status / eval / gold / batch / events` 命令，不直接调 `scripts/`。

## 六、离目标还差什么（一眼看）

- **切分**：四把尺子在正文页已接近 100%（R1 100% / R2 可改善 0.14% / R3 0 / R4 0.51%），
  剩的是真粘连、「切进字里」与顶部被切两类机制、以及**非正文版式**（职名页 41 页、目录页、无界行页）整页无解。
- **识别定字**：人审率 vol01 0.11%、vol02 2.17%，已达标；瓶颈是**生僻字**（库没样本、整理本用通行字）
  与 T2 案語类开放文本的夹注；换一本书库从零起，「所有字一开始都是生僻字」。
- **规模化**：只做过一种刻本风格；字形套机制、跨书复用、共享库指纹争用都还没解。
  vol04～vol10 原图已备好（同一刻本风格，非跨风格考验），管线尚未跑，是下一步扩大产量
  最现成的存量，不是新的技术风险。
- **下游**：TeX 输出没有方案，与 luatex-cn / guji-platform / book-text 都**未接通**；
  现在唯一能给人看的成品是对勘 HTML 报告与审查页。
- **环境**：仓库 3.8 GB，`glyph.db` 100.6 MB 逼近 GitHub 单文件上限，产物出 git 的 P3 未落地。
