# 参数分层：哪些是公用的、哪些是一册书的、哪些是一页的

  `estimate_period` 的 `lag_lo=70, lag_hi=160` 写死在函数签名里，
  换一本字更小的书就锁 2 倍谐波。

## 零、一句话

**问题不是"这两个数该改成多少"，是"这两个数没有地方可放"。**

`lag_lo/lag_hi` 现在是**函数默认值**——在整个参数体系之外。它既不是全局常量
（换书就错），也没法在册配置里配（册级那一层根本不存在），更不进指纹
（改了它，已有产物照报"新鲜"）。修法不能是"把 70 改成 49"，那只是把一本书的
错换成另一本书的错。

## 一、现状：已经有三层，但**没有册级那一层**

### 1.1 参数解析链（`core/engine.py:126-134`）

```python
# 参数三层：Step 默认值 < 管线 yaml 的 `params:`（这条链的默认） < 调用方覆盖
#（CLI `--params` / 控制台表单）。同一 Step 两层都有时按字段合并，调用方优先。
```

| 层 | 写在哪 | 谁写 | 例子 |
|---|---|---|---|
| L1 Step 默认 | `steps/*.py` 的 Pydantic model | 开发者 | `RowSegmentParams.ink_threshold = 128` |
| L2 管线 | `pipelines/*.yaml` 的 `params:` | 开发者 | `modern_body.yaml` 给 `column_gate.count_mode: detected` |
| L3 调用方 | CLI `--params` / 控制台表单 | 跑的人，**一次性** | `--params '{"row_segment_runs":{"interior_blank":true}}'` |

### 1.2 缺的那一层，**代码注释里已经写明白了**

`pipelines/modern_body.yaml:30-38`，一字不改抄下来：

> `row_segment_runs` 的 `interior_blank` **故意不在这里设默认**：
> 两本现代书要的值相反，而参数只有三层（Step 默认 < 管线 yaml < CLI），
> **没有册级那一层**。写成管线默认就会连带改北行日錄……
> 方格排版的书跑的时候显式传：`--params '{"row_segment_runs": {"interior_blank": true}}'`

这就是本设计要解决的问题的**独立第二例**。`lag_lo/lag_hi` 是第三例，
而且更糟——它连 L1 都不算，是函数签名里的裸默认值，`--params` 也够不着。

### 1.3 册级现在放得下什么：`BookSpec` 的散装先验

`core/book.py` 里已经有一批"标定出来的数值"，它们**不走 params 体系**，
而是 BookSpec 的独立字段，各步自己去 `ctx.book.X` 读：

| 字段 | 含义 | 怎么标定 |
|---|---|---|
| `expected_cols` / `chars_per_line` | 版式常量 | 数出来的 |
| `pitch_prior` | 列距 | 量出来 |
| `period_prior` | 字格高 | `measure_book_period()` |
| `bottom_gap` | 下版框跨页先验 | `measure_book_bottom_gap()` |
| `top_band_frac` / `bottom_band_frac` | 版框搜索带 | 本轮新加，扫参数扫出来 |
| `leaf_layout` | 筒子页与否 | 看出来的 |

**这层是对的，问题是它是散装的**：每加一个先验就往 BookSpec 上焊一个字段、
往用它的那步塞一次 `ctx.book.X`、还要记得在 `StepSpec.book_deps` 里声明
（`core/engine.py:205-207`），漏一条就是指纹漏洞——`三.3` 那条教训就是这么来的。

### 1.4 页级：已有三个先例，其中一个**已经把本设计的判准写出来了**

- **`BookSpec.preclean`**（`book.py:85`）：`{页号: [规则, ...]}`，
  写在册 yaml 里，只对登记过的页生效。`siku-zongmu/books/vol01.yaml:26` 有一条
  真实的 48 页反色带配置，**带一大段 note 说明为什么这么配**。
  它不经 Engine——`guji preclean` 另出一张修好的图，Step1 起自动读。
- **`preclean` 的 `gate_override`** —— 全仓**唯一一处成文的「页级参数覆盖」**，
  真实用例 `vol05.yaml:35`（0.28）、`vol07.yaml:22`（0.30）。
  `utils/preclean.py:46-47` 把口径写死了：

  > **个别页可以单页放宽闸**（`gate_override` + `gate_reason`），
  > 但**不许为了让某页过闸去调 `BODY_INK_GATE`** —— 那是全局闸，
  > 调松了别的页修坏了也看不出来。

  而且 `preclean.py:220` 强制 `gate_override` **必须同时写 `gate_reason`**。
  **这就是本设计要推广的判准**：个案走个案层、全局常量不为个案让步、例外必须带理由。
  §四.4 只是把它推广到其余四类。
- **`config/crop_exclusions.jsonl`**（工作区级）：实例级排除名单，
  append-only，每条带 `date` / `origin` / `reason` / `evidence` / `note`。

### 1.5 指纹：params 自动进，BookSpec 字段要手动声明

- `params_hash`（`engine.py:65`）= 整个 params model 的 sha256 —— **L1/L2/L3 任何
  一层变了，产物自动过期**，不用额外做什么。
- `StepSpec.book_deps`（`spec.py:88`）= 手写的字段名 tuple，进 payload 的 `book` 键。
  **写漏了就是静默的陈旧产物**。

⚠️ **实测：全仓只有 `border_detect` 一条声明**（`border_detect.py:38`）。
读了 `ctx.book.<先验>` 却没声明的至少有 7 处：

| 位置 | 读了什么 |
|---|---|
| `gates/column_gate.py:102,191` | `expected_cols` / `chars_per_line` / **`period_prior`** |
| `gates/border_detect_gate.py:58`、`line_detect_gate.py:39` | `expected_cols` |
| `gates/row_segment_gate.py:90`、`steps/row_segment.py:56` | `chars_per_line` |
| `steps/row_segment_runs.py:82` | `pitch_prior` |

**就是说现在改 `period_prior` / `pitch_prior` / `chars_per_line`，这些产物都不会过期。**
这不是设计缺陷，是 `book_deps` 这个补丁**只补了发现问题的那一步**。

### 1.6 标定回流：有函数，但**是人工抄进 yaml**

`measure_book_period()` / `measure_book_bottom_gap()` 读现成产物算出册级常量，
但**这两个函数在全仓没有任何调用者**——grep 只命中定义处与注释引用。
没有 CLI 子命令、没有脚本调它们，标定是人在 REPL 里跑完抄进 yaml 的。

`reports/bxgb/geometry.json` 更彻底：它由**工作区自带的一次性脚本**

`measure_book_period` 有一条**很要紧的自觉**（`row_boundaries.py:1497`）：

    continue

任何自动回流设计都必须保留这条。

## 二、参数该按什么分：**不是按"作用范围"，是按"谁有权定 + 怎么定出来"**

直觉上会按"全局/工作区/册/页"分四层就完事。但 `lag_lo/lag_hi` 这个例子说明
**范围不是最要紧的那个维度**——真正决定一个参数该怎么存的是另外两问：

### 问一：这个数的**权威来源**是什么？

| 类 | 来源 | 特征 | 例子 |
|---|---|---|---|
| **A 算法常量** | 开发者定，跨所有书 | 改它 = 改算法行为，要过金标 | `LOW_INK_FRAC=0.12`、`ROSTER_EL_T=0.5` |
| **B 版式事实** | 书本身就长那样，**数得出来** | 唯一正确答案，不存在"调" | `expected_cols=20`、`chars_per_line=21`、`leaf_layout=folio` |
| **C 标定量** | 从这本书的图**量出来** | 有真值，量法可复现，有误差 | `period_prior=70.6`、`pitch_prior=119`、`bottom_gap` |
| **D 策略选择** | 人裁定，无客观真值 | 两本书可以相反且都对 | `interior_blank`、`cut_judge=unet`、`frame_guard` |
| **E 个案例外** | 这一页/这一格特殊 | 带证据、可追溯、只影响一处 | `preclean` 的 48 页、`crop_exclusions` |

**`lag_lo/lag_hi` 是 C 的派生量**——它不该被独立配置，它该**从 `period_prior` 算出来**。
这是本设计最要紧的一条判断，见 §三。

### 问二：这个数**什么时候能定下来**？

| 时机 | 说明 | 例子 |
|---|---|---|
| **开工前一次算定** | 跑个标定脚本，写进配置，基本不再动 | `period_prior`、`bottom_gap`、`top_band_frac` |
| **跑的过程中每页现算** | 页级估计，配置只给先验/兜底 | 页级 `period`（估不出才用 prior） |
| **审阅中反复调** | 看了结果才知道好不好，要迭代 | `cut_judge`、各种阈值 |
| **人裁后回流** | 由裁决表反推 | 切点金标、`crop_exclusions` |

## 三、`lag_lo/lag_hi` 该怎么放：**派生量不配置，只配置它的源**

这是整个设计的样例，值得单独说清楚。

### 3.1 错误的修法：把它做成一个可配参数

看上去很自然——加进 `ColumnGateParams`，册 yaml 里配 `lag_lo: 49`。**但这是错的**：

1. **它和 `period_prior` 冗余且会互相矛盾**。两个数描述同一件事（这本书字多高）。
   有人改了 `period_prior` 忘了改 `lag_lo`，就出现"先验说 70.6、搜索窗口 [80,161]"
   这种自相矛盾的配置，而且**不报错**，只是又开始锁谐波。
2. **它要求配的人懂自相关**。`period_prior` 是"字格高 70.6px"，量得出、说得清；
   `lag_lo` 是"自相关搜索下界"，配错了没有任何直观后果可看。
3. **它没有真值**。B/C 类参数配错了能被量法验出来，`lag_lo` 配成 49 还是 52 无从验起。

### 3.2 正确的修法：**窗口是 `period_prior` 的函数**

```python
def period_search_window(prior: float | None) -> tuple[int, int]:
    """自相关搜索窗口。必须满足两条：含真周期、排除 2x 谐波。
    prior 为 None 时退回历史默认 (70,160)——行为逐位不变。"""
    if prior is None:
        return (70, 160)
    return (int(prior * 0.7), int(prior * 1.4))
```

- **唯一真相源仍是 `period_prior`**，一个数、可量、可验、已经在 yaml 里。
- `0.7/1.4` 这对系数是 **A 类算法常量**——它编码的是"自相关窗口要含真值、排 2x"
  这条算法事实，与书无关，跨书不变，改它要过金标。
- 三本书实测：bxgb 谐波 30.4%→0%；zongmu vol01/vol02 中位逐页相同。

**判据**：一个参数如果能由另一个更基本、更可量的参数算出来，
**就不该独立可配**。配置项之间不该有冗余——冗余就是矛盾的温床。

### 3.3 但它必须进指纹 —— 而且这里**已经有一个现存的漏洞**

`column_gate` 的 `StepSpec`（`gates/column_gate.py:91-98`）**根本没有 `book_deps`**
（全仓只有 `border_detect` 声明了一条）。而它的兜底路径已经在读
`ctx.book.period_prior`（`column_gate.py:191`）——**就是说现在改册 yaml 的
`period_prior`，闸2 产物照报「新鲜」**。这不是改成派生窗口之后才有的风险，
是当下就存在的、`三.3` 那条教训的一个未修实例。

改成派生窗口后 `period_prior` 会影响**每一页**的 period（不再只是兜底路径），
漏洞的后果从"空栏页兜底值不更新"放大成"全书周期不更新"。所以
`book_deps=("period_prior",)` 必须与 §3.2 同一次改动落地，不能分开。

## 四、建议的落点：五类各归各位

### 4.1 A 算法常量 —— 留在代码里，别配置化

模块级常量 + 标定注释，就是现状（`LOW_INK_FRAC` 那一套）。**不要**因为
"参数化更灵活"就把它们挪进 yaml：它们改一次要过全量金标，放进配置等于
邀请每本书各调一套，跨书可比性当场没了。

新增一条**硬约束**：算法常量的 docstring 必须写明"标定自哪本书/哪批金标"。
`lag_lo=70` 的病根就是它按四庫總目标的，但**签名里看不出来**。

### 4.2 B 版式事实 + C 标定量 —— 册级，`BookSpec`，但要收拢

保持 BookSpec 字段的做法（它是对的），但补三件：

1. **每个字段必须有标定方法**：要么"数出来"，要么指名一个 `measure_*` 函数。
   `top_band_frac` 的注释已经是范本。
2. **`book_deps` 要能自动推**。现在靠手写字段名 tuple，漏了就是静默陈旧。
   可行的收紧：让 Step 通过一个受检的访问器读册配置（如 `ctx.book_dep("period_prior")`），
   访问即登记，运行期校验"读到的字段都在 `book_deps` 里"，不一致直接报错。
   这比靠人记可靠。
3. **派生量集中一处**，像 §3.2 那样，别让每个调用点各算各的。

### 4.3 D 策略选择 —— **这是要补的那一层：册级 params 覆盖**

`interior_blank` 与 `lag_lo` 是同一个洞的两面。补法是在解析链里插一层：

```
Step 默认  <  管线 yaml  <  【册 yaml 的 params:】  <  调用方覆盖
```

册 yaml 里：

```yaml
params:
  row_segment_runs:
    interior_blank: true    # 方格排版；北行日錄不能开，见 note
```

代价很小：`load_book` 多读一个键，`Engine.__init__` 的 `merged` 多合一层，
**指纹自动覆盖**（params 整体进 `params_hash`，不用碰 `book_deps`）。
收益是把"跑的时候记得传 `--params`"这种**口头约定**变成配置——
现在那条约定只写在 yaml 注释里，谁忘了传谁的结果就是错的，而且不报错。

⚠️ 一条边界：**只有 D 类该进册级 params**。B/C 类仍走 BookSpec 字段——
它们是"这本书的事实"，不是"对这本书的策略选择"，混进 params 会让
`measure_*` 标定函数不知道该往哪写回。

### 4.4 E 个案例外 —— **把 `gate_override` 的成规推广开**

这一类不用发明，`utils/preclean.py` 已经把规矩立好了（§1.4），照抄即可：

1. **个案走个案层**，不许为了一页去动全局常量（`BODY_INK_GATE` 那条禁令）；
2. **例外必须带理由**（`gate_override` 强制配 `gate_reason`，`preclean.py:220`）；
3. 页级写册 yaml（`preclean` 形状），实例级写工作区 `config/*.jsonl`
   （append-only，带 `date`/`origin`/`reason`/`evidence`）。

判据：**个案例外必须带证据和日期**。没有证据的个案例外三个月后没人敢删，
会永久沉淀成噪声——这正是 `gate_reason` 强制存在的理由。

⚠️ 反过来也要守住：`gate_override` 那条禁令的一般形式是
**「个案压力不得上浮成全局默认」**。`lag_lo` 的病根恰是它的反面——
一本书（四庫總目）的标定值被固化成了全局默认。

### 4.5 工作区级 —— 目前不需要，别提前发明

调研下来，工作区级真正独有的只有路径（`core/workspace.py` 已解决）与
`config/` 下的名单。**没有发现"同一本书在不同工作区要用不同算法参数"的需求**。
建议暂不设工作区级参数层——多一层就多一处"到底是哪一层生效"的困惑。
等出现真实第二例再加。

## 五、标定回流：从"人工抄"到"算得出、可复核"

现状比"人工抄"还弱一档：**`measure_*` 根本没有调用者**（§1.6），
它们是写好了放在那里、靠人自己想起来在 REPL 里跑的。这条链有三个毛病：
没人跑；抄错没人知道；**没人记得什么时候该重标**
（换了 Step1 算法，`period_prior` 其实该重标——而它现在连过期都不会报）。

建议（按代价从小到大，不必一次做完）：

1. **`guji calibrate <book>` 子命令**：跑齐所有 `measure_*`，
   **打印"当前 yaml 值 vs 实测值"的对照表**，不自动改文件。
   人看一眼就知道哪个先验漂了。这一步代价最小、收益最大。
2. **标定产物落 `reports/<book>/calibration.json`**，带日期与量法版本。
   `reports/bxgb/geometry.json` 已经是这个形状，把它规范化即可。
3. **`guji status` 里加一列「先验过期」**：yaml 里的值与最近一次标定差超过阈值
   就标黄。与现有"产物过期"同一个位置，不用新造 UI。

⚠️ **不要做全自动回写 yaml**。理由是 `measure_book_period` 自己那条注释：
拿先验算先验是循环论证。自动回写会让一次坏标定悄悄固化，而且抹掉人写的 note
——那些 note（如 vol01 48 页那段）往往比数值本身更值钱。

## 六、这件事的一般教训

1. **"函数默认值"是参数体系的暗角**。`lag_lo=70` 躲过了所有机制：不在 params
   里（`--params` 够不着）、不在 BookSpec 里（yaml 配不了）、不进指纹（改了不过期）。
   凡是**跨书会变的数**，都不该藏在函数签名里。
   → 可做成一条 lint：`utils/` 下的数值默认参数要么有"跨书不变"的注释，要么改成必传。
2. **参数之间的冗余比参数本身更危险**。`lag_lo` 若做成可配，就与 `period_prior`
   描述同一件事而可以互相矛盾——**而且矛盾时不报错，只是悄悄变差**。
   能推导的就别配置。
3. **标定注释要写"标自哪本书"**。`lag_lo=70`、`bottom_gap` 的 325~327、
   `ROSTER_EL_T=0.5` 都是从具体某册标出来的。写明来源，换书的人才知道该不该重标。
   `BookSpec.bottom_gap` 的注释已经做到了（"三册恰好都落在 325~327px，但那是同一套
   版式，换一种版式没有理由仍是这个数"），该成为定式。
