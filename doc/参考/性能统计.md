# 跑批耗时统计（2026-11-03 立，11-25 按四大步重整，CV0）

回答「哪一步慢、慢在哪、改了有没有变快」。方案与分期见 Claude Doc《CV 管线性能统计方案》（https://claude.ai/artifact/KsR2RKgb3PRtAEChHwLhNn）。

## 记了什么

`guji pipeline`／`guji step`（凡走 `Engine.run()` 的）每次运行写一份 `<产物根>/../perf/<册>/<run_id>.jsonl`，一行一条：

| 行 | 内容 |
|---|---|
| `run` | 册、管线、步、页数、`--jobs`、cv 版本与 commit、命令行、任务库单号（`GUJI_JOB_ID`）、机器（主机、核数、内存、类别、云端容器号） |
| `page` | 真跑的每一页：计算耗时 `elapsed`，主进程开销 `overhead`（`check` 算指纹、`cache_invalidate`、`land` 落盘），步内分段 `spans`、计数 `counts`。新鲜跳过的页不写，只在 step 行计数 |
| `step` | 每步：跑／跳过／失败页数、墙钟、计算合计、p50／p90／max、并行效率、CPU 秒、峰值内存、开销合计、分段合计、最慢 20 页 |
| `end` | 墙钟、是否中断 |

放在产物根**外面**：产物包、冻结登记、部署检查都把产物根下的目录当步／册扫。`GUJI_PERF=0` 关掉，`GUJI_PERF_DIR` 换目录。

## 怎么看

```
guji perf top [--days 7] [--book 册] -w $WS     # 各步合计，按墙钟排
guji perf show <册> [--run ID] -w $WS           # 一次运行（缺省最新）各步明细、分段、最慢的页
guji perf pages <册> <步> [--slowest 20] -w $WS  # 某步最慢的页及其分段
```
都可加 `--json`。

## 全队汇总（任务库 D1 guji-jobs）

连得上任务库（2026-11-22 起是 Cloudflare D1 `guji-jobs`，令牌 `JOBSDB_TOKEN`，连法见 manager `databases.toml [jobs]`）时，
每次运行写完自动把 run 一行、每步一行（含分段合计、最慢 20 页）推到 `perf_run`／`perf_step`，一次约 15 KB。
**不推中心库**（Sheldon 11-03 定）；连不上就只落本地；**跑测试时不推**（manager 11-25 起，查到测试的合成步进了正式库）。

```
guji perf top --remote [--days 7] [--book 册] [--by host|cv_version|book]
guji perf spans <步> --remote [--days 7]   # 一步的分段排行（步内各道关、冷缓存再生）
guji perf job <单号>
guji perf push [--book 册]
```

`top --remote` 分两段：

1. **任务阶段**（执行方记在 `event` 里的 prep／run／push／uid／recheck…）。`run` 就是跑本仓管线；其余在 `Engine` 外面，
   perf 文件里没有。`prep` 再拆成准备脚本的各段（cv、db-pull、取原图、模板索引…；执行方从「== 准备耗时」解析，
   记在事件 `data.prep_parts`，11-25 起才有）。
2. **run 里各步，按四大步分组**：1 版面 layout、2 切字 cut、3 识字 read、4 定字 decide，取自管线骨架 `stages:`；
   出口闸（border_detect_gate、cut_gate、column_gate…）归它挂的那一步所在的大步。已退役的步（row_segment_gate）也归对，
   不在任何管线里的（测试合成步）归「其他」。

`guji pipeline` 缺省每步一个子进程、各写一份记录，用 `GUJI_PERF_GROUP` 同一个组号串起来（表里 `grp` 列）。

## 在 Step 里打点

```python
from ..core import perf

with perf.span("读模板表"):
    ...
perf.count("字块缓存未命中")

@perf.timed("cnn前向")
def forward(...): ...
```
嵌套的 span 记成 `外/内`。**Step 模块和它的 `code_deps` 进产物指纹**：在里面加 span 会让各册这步判过期。
只加计时、产物逐字节不变的，用 `scripts/code_equiv.py check` 证明后登记进 `core/code_equiv.py`，同一个 PR 提交。

### 不改 Step 源码的分段计时（2026-11-04 起，11-25 第三轮）

manager `cli_perf.PERF_HOOKS` 点名一批函数／方法，`guji step`／`pipeline` 起跑时 `install_hooks()` 把它们换成计时薄壳
（`perf.timed`），分段记进每页的 `spans`，随步级汇总推到任务库。壳只调原函数、原样返回，Step 源码不动，
**指纹不变、不用登记代码等价**。现有名单：

| 大步 | 步 | 分段 |
|---|---|---|
| 切字 | row_segment | `segment_column`、`fit_row_boundaries`、U-Net 判官 `UNetJudge.owner/scores/guided_seam/assess`、配页 `layout_for` |
| 切字 | column_band、cell_shrink | `band_strip`；`CellShrinkStep._column_chars`、`restore_trimmed_ends` |
| 识字 | glyph_match | 各道关、`GlyphMatcher._match` 及其里面的 `verify._elastic_align` 等 |
| 识字 | rare_candidates | `rare_for_batch`、`candidates_batch`、`CnnCandidates.topk_batch/emb_topk_batch…`、`StrokeEvidence.rerank_rows` |
| 定字 | seed_admit | 各道关、铁证闸再匹配、字组流程、影子闸、人裁重读 |
| 各步 | — | `RunContext.image`／`raw_page`（读缓存图、读原图）；**每个有 `render` 的步自动套壳**（`<Step类>.render`） |

**冷缓存再生**：缓存图（列图、字块）不在时由产出它的那一步 `render` 现算，花费记在**下游**那一步名下。
`top`／`spans` 把最外层的 `*.render` 单独小计。11-18～25 实测：单跑 glyph_match／seed_admit 的新容器里，读字块现算
占 glyph_match 计算的约 35%、seed_admit 的约 50%（全唐文每页 8–11 秒）。

限制：只换按名字查的调用点（模块全局、类方法、函数里现 import 的）；别处 `from x import f` 早拿走的引用不计；
拿函数身份做判断的（如 `GlyphMatcher._verify is verify_pair_elastic`）不换；书仓自带的 row_boundaries 副本（全唐文 k≤4）
不计。并行时子进程 fork 继承；Windows（spawn）子进程里不计。`GUJI_PERF=0` 不换。函数改名了 manager
`tests/from_cv/test_perf_hooks.py` 会红，把名单跟着改；新加的步进了管线骨架 `stages:` 就自动归组（`tests/test_perf_stages.py` 守）。
