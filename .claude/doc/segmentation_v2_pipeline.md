# 切分管线重定义（v2：四步）

## 背景

现有切分链路是 Phase 2（`border_detect.py` 版面检测）+ Phase 3
（`grid_segment.py` 字符网格）糊在一起的老设计，两步内部各自有很多特例
判据（详见 `phase2_detectors.md`/`phase3_char_grid.md`/`char_clustering_design.md`）。
这一轮探索出的两个独立新算法——`peak_line_search.py`（半高宽匹配度 + 位置
角度联合搜索找边框/界行）、`row_boundaries.py`（弹性DP切字格）——分别在
vol02/133、vol02/135、vol01/33、vol01 133~142 等页上验证过比现有算法更准
（详见各自设计文档），但都还只是"跟生产并存的独立工具"，没有正式取代
生产管线。

这次要做的是**把整条切分链路重新切成四个边界清晰的步骤**，每步有严格的
输入输出格式和独立的金标测试集，可以逐步开发、逐步验证、逐步替换生产，
而不是像现在这样版面检测和网格切分内部揉在一起改。

**这份文档只整理四步的总体框架**，细节（尤其 Step 1）下一轮再深入。

## 坐标系约定（新，四步统一遵守）

跟旧管线（`phase2_layout`/`phase3_char_grid` 现有产物）不一样，这是这次
明确要改的：

- **原点在页面右上角**（旧管线是左上角）。
- 列号、格号等一切"第几个"的计数**从 1 开始**，不是从 0 开始（旧
  `phase3_char_grid` 的 `cells[].index` 是 0 开始，新管线不再沿用）；
  列号从右到左递增（第 1 列在最右侧），跟古籍阅读顺序一致——这一点旧
  `design.md` 里其实已经这么约定，只是从来没有贯彻到坐标系本身，新管线
  要坐标原点和计数方向都对齐这个阅读顺序，不再是"计数从右到左、坐标
  原点却在左上角"这种拧巴状态。
- y 轴仍是向下递增（从页面顶端往下数，不用跟着列号一起反）。
- 具体到某一步内部数组下标要不要也跟着从 1 开始（比如某条曲线的采样点
  序号），还是只有对外的"第几列/第几格"这种业务字段从 1 开始——留到细化
  Step 1 时定，本文档先占位。

## 四步总览

每步一节，格式统一：定义 / 输入 / 输出 / 现有实现 / 测试集现状。

### Step 1：边框探测

**定义**：从原始扫描图上找出版框（上下内外边框）和界行（列间分隔线），
显式处理倾斜和模糊/磨损；有抬头列的页面额外定位抬头框。

**输入**：**最原始的扫描图**（`rebuild_src/<book>/<page>.tif`）——不用
`output/` 下 s3 裁剪 + s4 直线增强之后的产物。理由跟 `peak_line_search.md`
里"跳过S2去斜+S3裁剪"的实测一致：s4直线增强能把边框位置挪动最多96.6px，
这个量级足以让边框探测本身的结果失真；这一步的算法（位置+角度联合搜索）
本来就是设计给未矫正的原始图用的，不需要预处理帮忙去斜/裁剪。

**输出**（已定版，`open_guji_cv/utils/border_geometry.py`）：

```python
@dataclass
class HLine:               # 水平线(上/下版框)
    y_at_right: float       # 该线在页面右端(新坐标系x=0处)的y值
    slope: float             # dy/dx，x向左递增
    kind: str                 # "top" | "bottom"

@dataclass
class VLine:                # 竖直线(外边框/界行)
    x_at_top: float          # 该线在页面顶端(y=0处)的x值
    slope: float             # dx/dy

@dataclass
class HeadRaiseBorder:      # 某一抬头列自己的内外上边框(局部量，非整页一条线)
    col: int                  # 列号，从右到左、从1开始
    inner_y: float
    outer_y: float

@dataclass
class BorderDetectionResult:
    width: int
    height: int
    top: HLine
    bottom: HLine
    verticals: list[VLine]           # 从右到左排列：[0]=第1列外边框(最右)
    head_raise: list[HeadRaiseBorder]  # 目前恒为空列表，见下

def detect_borders(gray, expected_cols: int) -> BorderDetectionResult: ...
```

一般水平线只有 top/bottom 两条；本版没有把"2~4条"这个更宽的口子做成
数据结构（只固定了 top+bottom），抬头框的纵坐标改用专门的 `HeadRaiseBorder`
承载，不是塞进"水平线"字段——每个抬头列的抬头框是**局部量**（只影响这
一列，不贯穿整页），跟贯穿全页的版框线放在同一个"水平线列表"里语义
不一致，拆开更清楚。

**外边框（已定版）**：上下版框其实各有内外两层；左右外边框只在"纸边"
那一侧存在——书是筒子页对折装订，偶数页纸边在左、奇数页在右，版心/
装订那一侧没有独立的外边框（被切/装订吃掉，不是没探测到）。外边框跟
对应内边框物理上是平行的（同一块印版/同一张纸的两条边），**斜率锁定跟
内边框一致，只需要一个"沿垂直方向的偏移量"**，不需要独立的位置+角度
两个自由度——`BorderDetectionResult` 已加上这四个字段：

```python
@dataclass
class BorderDetectionResult:
    ...
    top_outer_offset: float | None = None    # None=没测到；有值=沿y方向相对top的偏移量
    bottom_outer_offset: float | None = None
    v_outer_side: str | None = None           # "left" | "right"，由页码奇偶决定
    v_outer_offset: float | None = None       # 相对 verticals[0](right)/verticals[-1](left) 的偏移量
```

`detect_borders()` 仍然没有实现外边框自动探测（连自动判据都没有，跟
抬头框一样），这几个字段目前只在人工金标里有值，代码路径恒为 `None`。

**现有实现**：`open_guji_cv/utils/peak_line_search.py` 提供底层探测算法
（半高宽匹配度找峰 + 位置角度联合搜索），跟生产 `border_detect.py`/
`detectors/borders.py` 并存，未接入生产管线。`border_geometry.py` 是新加
的坐标系转换层——`peak_line_search.py` 内部完全不用改，仍按标准图像坐标
（左上角原点、x向右）工作，`detect_borders()` 探测完之后做一次坐标转换
（`_hline_to_new`/`_vline_to_new`，含把 `peak_line_search` 内部"锚点在
页面中心"的约定重新锚定到"页面顶端/右端"），包成新约定的输出。

**抬头框探测**：`detect_borders()` 的 `head_raise` 字段目前恒为空
列表——**没有可靠的自动探测算法**（试过"扫描墨量占比"，会把普通列的
装饰花边也误判成抬头，见 `row_boundaries_design.md`「抬头列」节）。
`HeadRaiseBorder` 加了 `estimated: bool` 字段——有的页面（vol01/32）抬头框
的上边框被物理装订/裁切吃掉，人工标注时也只能推测大致位置，不是"看得见
但没标准"，跟真正观测到线的记录不能同等确信度使用。

**测试集**：`open-guji-dataset/border-detection`，**14 页**（普通页
vol01/137、138、24、65 + 曾以为是抬头、核校后确认不是的 vol01/9、14、
142、141 + 真抬头页 vol01/32、33、49、26、47、51）。图源用 `rebuild_src` 原始
扫描；内边框种子取自 `peak_line_search` 自动探测，外边框/抬头框没有
自动探测种子，人工从粗猜的起点标定。vol01/32 的 5 个抬头框上边框全部
`estimated=true`（见上）。现有旧测试集（`text-band`、`page-crop` 等）
测的是边框探测出错之后下游的症状，不是边框坐标本身的金标，跟这个子集
不重复；单测 `tests/test_border_geometry.py` 只验证坐标转换数学本身，
不能替代真实页面的金标。

**"真抬头"的判据踩过一次坑**：第一批选页时以为"边框上方有清晰字迹凸出"
就是抬头，按这个标准挑了 vol01/9、14、142 三页标注，结果人工核校后
`head_raise` 全空——回看 32/33/49 才发现真正的判据是**边框线本身在
该列位置有台阶**（整条线向上凸一截、带竖直连接线），9/14/142 只是
"上諭"这个高字紧贴着一条完全笔直的边框，边框没有为它抬高。按新判据
重新筛出的 vol01/26、47、51（标注页发布中，见 `artifacts/README.md`）
才是真正的下一批候选；47/51 是"凡例"性质段落，同页里"聖諭""聖裁"
"御批""列朝"等多个尊称词各自抬到不同高度，比 32/33/49 单一抬头列
更复杂，故意选来扩展样式覆盖面。

第二批核校还顺带揪出 `find_vertical_lines` 一个真实 bug：vol01/141
用户在标注页上发现两条竖直线被拖到几乎重叠，回查代码确认是相邻粗
候选切出的窗口有时切在同一条真实线中间、两侧窗口各自精修都收敛到
这条线上，`expected_count` 按分数截断时会把两个名额都占走、挤掉别处
一条真实列线；已修（`_dedup_by_position`，按分数贪心去重，合成图单测
覆盖），改动已过 5 页 eval 无回归，详见下方准确度表格里 141 的数据。

**算法准确度**（`detect_borders()` vs 14 页金标，逐条线在两个自然
端点算坐标误差，`竖直线`/`水平线` 分开统计，脚本未入库、跑法见下）：

| | 基线（5页） | 窄窗口第二候选（5页） | 窄窗口第二候选（11页） | 窄窗口第二候选（14页，含复杂凡例页） |
|---|---|---|---|---|
| top 均值/最大 | 8.5px / 39.8px | 1.1px / 6.9px | 0.5px / 6.9px | **1.9px / 29.1px** |
| bottom 均值/最大 | 14.6px / 43.2px | 8.9px / 27.5px | 7.0px / 38.9px | **7.0px / 38.9px** |
| 竖直线均值/最大 | 2.6px / 19.2px | 2.6px / 19.2px | 2.0px / 19.2px | **2.7px / 38.8px** |

竖直线（`find_vertical_lines`）在 11 页里已经很准（vol01/141 去重bug
修完后均值2.0px），但扩到14页后新增的 vol01/47（"凡例"复杂抬头页）
暴露了一个新的失败形态，水平线基线原有两类失败：

1. **抬头装饰墨迹把决策带偏**（vol01/49 顶部）：抬头列的墨迹伸到版框
   线以上，整带全局搜索里这坨墨迹的半高宽匹配度（207.4）比真正的边框
   （170.8）还高，`joint_search_coarse_to_fine` 直接锁死在装饰墨迹上，
   误差 37-40px。
2. **锁到外边框而不是内边框**（vol01/137、138、**141** 底部——141是
   新样本里第4个复现这个模式的页面，同样是内边框分数明显弱于外边框，
   整带最强峰选中外边框）：误差 21-39px。

两类问题有个共同物理特征：**真正的内边框永远比这些干扰峰更靠近页面
中心**（装饰墨迹在边框外侧、外边框在纸边更外侧）。改法：`find_horizontal_border`
先按原逻辑跑一次整带搜索拿到 `primary`（保证所有已经正确的页面原样
不受影响），再只在 `primary` 位置附近 **±60px 窄窗口**内找"比 primary
更靠近页面中心、匹配度达到 primary 20% 以上"的候选，找到就换上去，否则
保留 primary。5 页里两个失败页（49 顶/137+138 底）全部改善，抬头页 49
顶部几乎打平金标（2.8px），137/138 底部误差砍半（35-43px→21-28px，
没能完全打平，说明窄窗口内真正的内边框峰有时候本身也不是最强的次候选，
仍有优化空间）；扩到11页后新增的141同样落在这个"底部内外边框confusion"
模式里（误差17-39px），是同一个已知限制的第4例，不是新失败形态；其余
新增的6条本来就对的线（9/14/24/65/142的top+bottom，141的top）零回归。
第三批里51的底部（20.4/33.4px）同样是第5例，26的12条线全部零误差。

**新发现的第三类失败**（vol01/47，14页扩测才暴露，尚未修）：整页10条
竖直线**系统性**偏斜——顶端误差13-39px，但底端误差大多只有1.5-3.6px
（col8/10除外），典型的"斜率被带偏"特征（一头偏一头准，说明是角度
估计错了，不是位置错了）；顶部边框误差也有13-29px。47是这批里最复杂
的"凡例"页——顶部有4个抬头列，"御製"甚至有两级台阶（同一列两次
不同高度的墨迹），紧凑地挤在一起还带竖直连接线。怀疑是 `find_vertical_lines`
精修阶段的位置+角度联合搜索，在页面顶部这坨密集又不规则的抬头墨迹里，
被"抬头连接线也是竖直墨迹"这一点带偏了角度——联合搜索本来就是为
版框线的微小残余倾角设计的，全局自由角度在这种局部强干扰源附近会被
拉着走，跟"第二次改进尝试"（窗口内二次联合搜索精修）踩的坑同宗同源。

**根因已经用叠加图目视确认**（预测线跟金标线画在原图上对比，见
scratchpad `vis_p47_vlines.py`，未入库）：抬头框自己就带着一段**竖直
墙线**——从版框顶端的"台阶"往下连到主边框水平线那一段竖线（前面
`HeadRaiseBorder` 设计里说的"竖直连接线"），这段墙线又高又直，半高宽
匹配度不比真正的列线低，`joint_search_coarse_to_fine` 在窗口顶部会把
它当成候选线的一部分一起拟合，越往下墙线没了、才回归到真正的列线
墨迹——一条线的顶段被"借"给了墙线，底段才是真的，拟合出来的斜率
自然就是两段的折中，顶部误差大、底部误差小正是这个机制的直接体现。

**为什么现在还不修**：唯一干净的修法是先知道页面上哪里有抬头框（这样
就能把墙线所在的窄条从竖直线搜索窗口里挖掉），但抬头框目前**没有
自动探测**——`detect_borders()` 的 `head_raise` 字段恒为空，试过"扫墨量
占比"会把普通列的装饰花边也当成抬头（`row_boundaries_design.md`「抬头
列」节记过）。反过来先做抬头框自动探测又是一个不小的子问题，不该为了
修一页的竖直线误差顺手把这个也做了。

**47的模式已确认不是孤例**：拿同一批"凡例"页（vol01/48）目视叠加对比，
预测竖直线在抬头台阶区域同样明显偏进字身（跟47是同一种视觉表现），
确认这不是47一页的巧合，是这类密集多列抬头版式的通病。33/133/135/136
几页复核过没有复现（33是32/33/49那种单列朴素抬头，133/135/136目视
确认边框是直线没有台阶，跟9/14/142一样是"字紧贴边框"假阳性，不是
真台阶）——目前锁定为**47/48/50-53 这个特定"凡例"聚簇**的通病。

**抬头框自动探测第一版原型（scratchpad `proto_head_raise_detect.py`，
未入库、未接入 `detect_borders()`）**：思路不用"扫墨量占比"，改用"每列
局部窗口里，主边框上方是否有一条只跨这一列宽度的独立细横线"——复用
`find_horizontal_border` 同一套半高宽匹配度算法，只是把搜索范围从整页
宽度收窄到单列的x范围。14页金标上跑第一版：召回不错（12个真抬头列
命中10个）但精确率很差——几乎所有"其实没有抬头"的页面（137/138/9/14/
65/141/142）都在主边框上方~30px处冒出一批假阳性，且**同一页内这些假
阳性的y几乎一致**（比如138的6个假阳性全部落在304-313px内）——诊断出
这是**外边框本身**被当地重新找到了一遍，不是抬头台阶（外边框贯穿全页，
本来就该在每一列都测到差不多的y）。加了一个"同一页内≥4列命中同一y
（±15px）就整簇丢弃"的去重后，138/9/24/65 从有假阳性变成全干净，
14/141 的假阳性从6-7个降到0-1个，**32/26 这两个简单的单/双列抬头页
做到了金标零误差全对**；但复杂多列页（47/49/51）出现了新问题——真正
的抬头台阶有时候y恰好跟旁边几列的外边框假阳性接近，被一起当成"页级
误报簇"给误删了，47从命中3/3掉到1/3，49从1/1掉到0/1。**净效果是喜忧
参半**：单列/双列朴素抬头页（32/26型）解决了，但没解决最初动机所在的
47型复杂多列抬头页，反而在这类页上从"精确率低"换成了"召回率低"这个
新问题。**未接入生产**，先如实记录这个阶段性结果；47型的竖直线偏斜
依然未修。

**追加排查：候选离主边框的距离（`dist`）单独也不是干净的判据**——把
14页所有候选（TP/FP都算）按 `dist=border_top_y - 候选y` 摊开看：单/双列
朴素抬头页（32/26）的真候选普遍 `dist` 较大（51-126px），外边框假阳性
普遍较小（18-48px），乍看像是能简单卡个阈值分开；但复杂多列页（47/49/
51）里恰恰有一批**假阳性的 `dist` 也很大**（47col6=110、49col6=116、
51col2=125、51col8=121——量级上跟同页真候选 47col9=130、51col1=127
完全混在一起），推测是这类页顶部结构本来就密集（相邻列的抬头台阶/
连接墙线互相靠得近），单纯量距离会把"离得远的别的干扰"也当成候选。
`ratio`（跟主边框匹配度之比）同样不干净——真候选 ratio 从 0.40 到 4.85
都有，假阳性也是从 0.39 到 131（后者是明显的离群噪声，但门槛卡在哪都
会两头漏）。**结论**：单靠"候选离边框多远"或"候选匹配度多强"这两个
一维特征，在47型复杂页上都分不开真假；下一步如果要继续，思路应该换成
用**二维结构**——真台阶除了那条横线，理论上还有前面反复提到的"竖直
连接墙线"陪着（下到主边框水平线为止），外边框假阳性和普通噪声候选
没有这根柱子；检测的时候可以要求候选横线的两端往下各延伸一段要有竖直
墨迹陪同，而不是只看横线本身的半高宽匹配度。这个方向还没试，先记下来，
不在这轮继续往下扎。

**踩过的坑（负结果，已撤销）**：第一次尝试是"整条带内多候选 NMS + 相对
分数阈值 + 挑离页面中心最近者"，不限制窗口范围。结果灾难性回归——
137 顶部本来 0.1px 精确命中，被带内一个纯属笔画噪声的候选（离 primary
约350-375px）顶替，误差冲到 378px；32 顶/33 底/49 底同样被拖崩。根因：
样本内真候选（内/外边框对）的分数比跟纯噪声候选的分数比区间是重叠的
（真实~41-58%、噪声~27-58%），**没有一个固定阈值能把两者分开**；一旦
搜索范围铺满整条带，噪声候选离中心可能碰巧比真候选还近，被误选中。
这是窄窗口方案改成"只在 primary 附近 ±60px 内找第二候选"的直接原因——
±60px 覆盖了已观测到的所有真实内外边框间距（30-45px），同时把 350px+
外的噪声排除在搜索范围之外。

第二次尝试是想把 137/138 底部剩下的 21-28px 残差也打平：找到窄窗口内
的粗候选之后，在它周围再开一个更小的窗口（±25px）重新跑一次位置+角度
联合搜索精修，类似 `find_vertical_lines` 对候选窗口的精修方式。结果也是
负结果，已撤销——联合搜索允许角度自由变化，在这么小的窗口里，一条
"斜穿过两坨相隔几十像素的墨迹"的对角线有时候比任何一条水平线本身分数
更高（合成图单测就是照这个机制最小复现的：窗口内两条水平墨迹相隔 33px，
精修后返回的是一条斜率 0.036、位置介于两者之间的假线，不是任何一条真
线），vol01/138 底部真实验证也确认了同样的劣化（21.2px→46.5px，比不
精修还差）。教训：这套"位置+角度联合搜索"本来就是为整条带/大窗口设计
的（角度自由度用来找版框线本身的微小倾斜），窗口一旦缩小到跟候选间距
同量级，角度自由度反而会被滥用去连接不相关的两坨墨迹——窄窗口内的第二
候选目前只用局部极大值的粗位置，不做二次联合搜索精修。

### Step 2：单列射影变换 + 去噪

**定义**：给定 Step 1 里某一列的左右两条边线，把这一列做射影变换矫正成
竖直矩形，并去掉噪点（书斑、墨渍等非文字干扰）。

**输入**：原图 + Step 1 输出中该列的左右边线 `(position, slope)`。

**输出**：该列去透视后的竖直矩形灰度图（去噪后）。

**现有实现**（已定版，`open_guji_cv/utils/column_projection.py`）：

```python

    top_y/bottom_y 是新坐标系 y，应传该列的上下版框 y（不是整页边缘）。
    输出宽度取两端间距较大者（避免内容被压扁），沿用标准图像坐标系
    （矫正后的列图不再是页面的一部分，没必要维持右上角原点约定）。"""

def denoise_column(warped_gray, ink_threshold=128, min_blob_area=6) -> np.ndarray:
    """清掉二值化后面积 < min_blob_area 的孤立小连通体（书斑/墨渍/灰尘），
```

之前 `row_boundaries.py`/`peak_line_search.py` 探索时各自写过一次性射影
矫正代码（只用两条边线的 position+slope，取满页高不按上下版框裁），现在
收拢成这一处；`denoise_column` 是新加的，之前完全没有这部分。合成图单测
（`tests/test_column_projection.py`）验证了倾斜列矫正后应变成均匀矩形、
退化输入报错、孤立小点被清除但笔画保留。

**测试集**：单测覆盖了函数本身的数学正确性，但**真实页面的金标测试集
目前没有**——"矫正得准不准"要拿真实倾斜列跟人工标的"矫正后应该长什么样"
比对，这类金标还没建（跟 Step 1 一样，需要人工在真实页面上标注）。

### Step 3：单列文字切分

**定义**：把 Step 2 输出的单列矩形图切成一个个字格，包括正常字、空白格、
抬头字、双行小注（a/b 两半）。

**输入**：Step 2 输出的单列矩形灰度图。

**输出**：字格边界列表，每格标注类型（字/空白/抬头/夹注a/夹注b）。

**现有实现**：`row_boundaries.py`（弹性DP：候选=波谷+页面共享周期先验+
三层硬约束）是"切普通字格"这部分的现成实现，vol02/135、vol01/33 两页
验证过；`top_slack` 参数解决了"抬头但格数不变"的情况，"抬头到多一个字"
的情况还没解决（见 `row_boundaries_design.md`）。**双行小注还完全没有
接进这条新链路**——生产 `grid_segment.py` 里有夹注 a/b 拆分的逻辑
（`jiazhu-tail` 等分片专门测这个），但那是旧管线的实现，没有迁移到
`row_boundaries.py` 这条新链路上。

**测试集**：`open-guji-dataset/char-segmentation/row-boundaries`
（vol02/135 普通页 + vol01/33 含 4 个抬头列，抬头列里"多一字" vs "不多字"
两种都有金标）——覆盖普通字格切分和部分抬头场景，**双行小注没有专门
测试集**（`jiazhu-tail` 测的是生产旧管线的段端修复，不是新链路）。

### Step 4：字框收缩

**定义**：把 Step 3 给出的粗字格（矩形）收缩成贴合字身墨迹的最小矩形框。

**输入**：Step 3 的字格粗框 + 原图（或 Step 2 的矫正图）。

**输出**：每个字格对应的最小外接矩形框。

**现有实现**：生产 `open_guji_cv/clustering/extractor.py::CharExtractor.
extract_page`（连通体归属 + 清边 + 弯曲界行处理等一整套已经调好的逻辑）。
这一步用户已经确认"可以直接复用旧算法"，vol01 十页抽查（133~142）验证过
效果——配合 Step 1 用新算法但要注意**逐列单独去斜**，不能像最初尝试那样
拿全页共享一个 shear 喂给它（会在残余倾角偏离页面中位数较大的列上把
相邻字的连通体判串，细节见 `artifacts/README.md`「vol01 新算法逐字框选」
条目）。

**测试集**：`open-guji-dataset/char-segmentation/instances`（`clean`/
`contaminated`/`truncated`/`not_text` 四分类）和 `cells`（合成数据、像素级
金标）是现有最接近的测试集——测的是"图块干不干净/完不完整"，跟"框是不是
最小矩形"角度略有差异（该数据集原则是"多裁一点空白不算失败，只看墨对不
对"），可以先复用，够不够精确覆盖"最小矩形"这个具体要求，留到细化这一步
时再看。
