# 切分管线重定义（v2：四步）

## 背景

现有切分链路是 Phase 2（`border_detect.py` 版面检测）+ Phase 3
（`grid_segment.py` 字符网格）糊在一起的老设计，两步内部各自有很多特例
判据（详见 `phase2_detectors.md`/`phase3_char_grid.md`/`char_clustering_design.md`）。
这一轮探索出的两个独立新算法——`peak_line_search.py`（半高宽匹配度 + 位置
角度联合搜索找边框/界行）、`row_boundaries.py`（弹性DP切字格）——分别在
vol02/133、vol02/135、vol01/33、vol01 133~142 等页上验证过比现有算法更准
（详见各自设计文档），但都还只是"跟生产并存的独立工具"，没有正式取代
生产管线。

这次要做的是**把整条切分链路重新切成四个边界清晰的步骤**，每步有严格的
输入输出格式和独立的金标测试集，可以逐步开发、逐步验证、逐步替换生产，
而不是像现在这样版面检测和网格切分内部揉在一起改。

**这份文档只整理四步的总体框架**，细节（尤其 Step 1）下一轮再深入。

## 坐标系约定（新，四步统一遵守）

跟旧管线（`phase2_layout`/`phase3_char_grid` 现有产物）不一样，这是这次
明确要改的：

- **原点在页面右上角**（旧管线是左上角）。
- 列号、格号等一切"第几个"的计数**从 1 开始**，不是从 0 开始（旧
  `phase3_char_grid` 的 `cells[].index` 是 0 开始，新管线不再沿用）；
  列号从右到左递增（第 1 列在最右侧），跟古籍阅读顺序一致——这一点旧
  `design.md` 里其实已经这么约定，只是从来没有贯彻到坐标系本身，新管线
  要坐标原点和计数方向都对齐这个阅读顺序，不再是"计数从右到左、坐标
  原点却在左上角"这种拧巴状态。
- y 轴仍是向下递增（从页面顶端往下数，不用跟着列号一起反）。
- 具体到某一步内部数组下标要不要也跟着从 1 开始（比如某条曲线的采样点
  序号），还是只有对外的"第几列/第几格"这种业务字段从 1 开始——留到细化
  Step 1 时定，本文档先占位。

## 四步总览

每步一节，格式统一：定义 / 输入 / 输出 / 现有实现 / 测试集现状。

### Step 1：边框探测

**定义**：从原始扫描图上找出版框（上下内外边框）和界行（列间分隔线），
显式处理倾斜和模糊/磨损；有抬头列的页面额外定位抬头框。

**输入**：**最原始的扫描图**（`rebuild_src/<book>/<page>.tif`）——不用
`output/` 下 s3 裁剪 + s4 直线增强之后的产物。理由跟 `peak_line_search.md`
里"跳过S2去斜+S3裁剪"的实测一致：s4直线增强能把边框位置挪动最多96.6px，
这个量级足以让边框探测本身的结果失真；这一步的算法（位置+角度联合搜索）
本来就是设计给未矫正的原始图用的，不需要预处理帮忙去斜/裁剪。

**图源已核实干净（2026-09-02）。** `rebuild_src/vol02` 与下载源
`data_zongmu/zongmu_v01` **187/187 页字节完全相同**——`rebuild_src` 就是解压出来
的原始下载，没跑过任何预处理。`peak_line_search.py` 和 `border_geometry.py` 里
**一个 cv2 调用都没有**（纯 numpy），导出脚本直接 `cv2.imread(..., IMREAD_GRAYSCALE)`
读 TIFF，所以 Step1 这条链路上不存在直线增强。

⚠️ 但要知道一件事：**扫描件本身就是 1-bit 双值 TIFF（CCITT G4 压缩）**，
`data_full/zongmu/*.png` 也只是把同一张双值图存成 RGB（灰度级只有 2）。
**全库没有灰度原图可退。** 所以图看着"边缘很硬、像被增强过"是扫描源本身的性质，
不是我们处理出来的——这一点会反复引起误会，量任何跟"墨的浓淡"有关的东西之前
先记着：这里的"墨占比"永远是**面积占比**，不是灰度深浅。

**输出**（已定版，`open_guji_cv/utils/border_geometry.py`）：

```python
@dataclass
class HLine:               # 水平线(上/下版框)
    y_at_right: float       # 该线在页面右端(新坐标系x=0处)的y值
    slope: float             # dy/dx，x向左递增
    kind: str                 # "top" | "bottom"

@dataclass
class VLine:                # 竖直线(外边框/界行)
    x_at_top: float          # 该线在页面顶端(y=0处)的x值
    slope: float             # dx/dy

@dataclass
class HeadRaiseBorder:      # 某一抬头列自己的内外上边框(局部量，非整页一条线)
    col: int                  # 列号，从右到左、从1开始
    inner_y: float
    outer_y: float

@dataclass
class BorderDetectionResult:
    width: int
    height: int
    top: HLine
    bottom: HLine
    verticals: list[VLine]           # 从右到左排列：[0]=第1列外边框(最右)
    head_raise: list[HeadRaiseBorder]  # 目前恒为空列表，见下

def detect_borders(gray, expected_cols: int) -> BorderDetectionResult: ...
```

一般水平线只有 top/bottom 两条；本版没有把"2~4条"这个更宽的口子做成
数据结构（只固定了 top+bottom），抬头框的纵坐标改用专门的 `HeadRaiseBorder`
承载，不是塞进"水平线"字段——每个抬头列的抬头框是**局部量**（只影响这
一列，不贯穿整页），跟贯穿全页的版框线放在同一个"水平线列表"里语义
不一致，拆开更清楚。

**外边框（已定版）**：上下版框其实各有内外两层；左右外边框只在"纸边"
那一侧存在——书是筒子页对折装订，偶数页纸边在左、奇数页在右，版心/
装订那一侧没有独立的外边框（被切/装订吃掉，不是没探测到）。外边框跟
对应内边框物理上是平行的（同一块印版/同一张纸的两条边），**斜率锁定跟
内边框一致，只需要一个"沿垂直方向的偏移量"**，不需要独立的位置+角度
两个自由度——`BorderDetectionResult` 已加上这四个字段：

```python
@dataclass
class BorderDetectionResult:
    ...
    top_outer_offset: float | None = None    # None=没测到；有值=沿y方向相对top的偏移量
    bottom_outer_offset: float | None = None
    v_outer_side: str | None = None           # "left" | "right"，由页码奇偶决定
    v_outer_offset: float | None = None       # 相对 verticals[0](right)/verticals[-1](left) 的偏移量
```

**外边框自动探测 `detect_outer_borders()` 已定版并接入**（2026-09-01），
四个字段都由代码填，口径统一为**外延**（朝外那侧的半高边缘），跟
`detect_head_raise()` 的 `outer_y` 一致。

做法：**先测竖直外框，再拿它当上下的间距先验**。竖直外框那一侧墨最稳
（峰值 0.48~1.00），量出来的 `abs(v_outer_offset)` 就是这一页的内外间距；
上下外框只在这个先验的 ±16px 里找（先按边校正，见下）。

依据是用户给的判据「内外边框的间距应该全页基本一致」的**修正版**：一致性
只在**同一条边**上成立，四条边彼此**不等距**。清楚页同页实测——竖直外延间距
比 top 大 **10.8±4.5px**、比 bottom 大 **5.9±4.2px**（n=5），所以先验套到上下
之前要减掉这个差（`OUTER_PRIOR_SHIFT`），否则窗口中心整体偏外。
（原先只量了竖直的 38.4±4.0px 和抬头框的 37.0px，两者都属"竖直"一族，
所以看着"全页一致"——那是取样偏差。）

实测（14 页金标）：

| 字段 | 覆盖 | 对金标 | 对真墨外延 |
|---|---|---|---|
| `v_outer_side` | 14/14 全对 | — | — |
| `v_outer_offset` | 14/14 | 均值 2.9px | — |
| `top_outer_offset` | 9/14 | 均值 5.5px | **均值 1.2px**（最大 4.0）|
| `bottom_outer_offset` | 6/14 | 均值 1.2px | **均值 0.9px**（最大 3.1）|

按边校正前后（对真墨外延）：top 1.6→**1.2px**、bottom 5.6→**0.9px**。
top 对**金标**反而从 3.3→5.5px「变差」，那是**金标错**不是算法错——
vol01/14 的 `top_outer_offset` 金标 38.6px，真墨外延在 21.2px（峰墨 0.65），
算法报 20.5px。这一项**必须拿真墨当基准，不能用上框金标**。

**上下外框有一半不该报数**，一律返回 None：先验窗口内没有 ≥0.30 的版框墨就
认没有。试过用弱档（ink≥0.12）补覆盖，6 例里 3 例误差超 10px，是负结果。

#### 版框几何常数（90 页实测）

单位 px，均值 ± 标准差。

| 边 | 条数 | 内框线宽 | 外框条宽 | 内心→外条近沿 | 内心→外条外延 |
|---|---|---|---|---|---|
| 上框 | 41 | 5.8 ± 0.7 | 16.3 ± 5.5 | 19.6 ± 4.6 | 35.9 ± 6.6 |
| 下框 | 16 | 5.7 ± 0.6 | 16.4 ± 3.3 | 17.8 ± 2.4 | 34.3 ± 3.7 |
| 竖直·右 | 20 | 4.4 ± 0.5 | 19.4 ± 2.3 | 21.0 ± 2.2 | 40.5 ± 3.5 |
| 竖直·左 | 29 | 4.6 ± 0.6 | 19.8 ± 2.0 | 20.0 ± 2.3 | 39.9 ± 2.8 |

量法：`scripts/measure_frame_geometry.py`（vol01+vol02 抽 90 页正文页，106 条清楚边）。
**不需要人工标注**——清楚的页上内框线本身就是最强的墨，直接从真墨量；量之前先把
原点精修到真墨线心，算法残差不进结果。「清楚」= 内框峰墨 ≥0.45、外条峰墨 ≥0.60，
**且内框线半高宽 ≤10px**——最后这道闸是必须的，末行字那一片墨也能有 0.5 以上的
行墨占比，光看墨量拦不住，混进来会把下框外延从 34.3±3.7 拉成 30.3±9.8。

三条要点：

- **版框四边不等距。** 同页配对差（竖直外延 − 上/下外延）：上框 **+4.2±6.5px 中位
  +3.6（n=23）**、下框 **+6.3±3.9px 中位 +6.8（n=12）**。所以「内外间距全页一致」
  只在**同一条边**上成立，跨边要按边校正（`OUTER_PRIOR_SHIFT`）。
- **负结果：这两个差不能用小样本拟。** 头一版拿 5 页拟出 top=−10.8/bottom=−5.9，
  扩到 90 页后 **top 那个差了 2.5 倍**（真值 −4.2），bottom 才对得上。而 14 页金标
  那套评测在 −3~−10.8 之间**分辨不出来**（都是 1.2~1.3px），挑不出对的值——只能
  靠直接量。top 这个差本身散得厉害（±6.5），别当精确常数用。
- **外条近沿不可用，只有远沿（外延）稳。** 外条是从**内侧**磨掉的：清楚页近沿
  在 +15~+17，磨损页漂到 +28~+34，而远沿只从 +33~+38 漂到 +39~+45。拿近沿反推
  内框位置会错十几 px。

⚠️ 上下外框的**人工金标口径本身不统一**（14 页实测：top 外延6/中心3/内沿1，
bottom 外延8/内沿3/中心1），所以剩下那点差**部分是标注口径的散布**，别照着
它继续调参。竖直外框那一侧口径是干净的（外延 12/14）。

#### 界行三段折线（用户 2026-09-02 定的方案，已落地）

**数据模型**：`VLine` 从 `(x, k)` 扩成 `(x, k1, k2, k3)`——以上下内版框为界把版框内
高度三等分，每条线加两个折点。`x_at_top` 就是 x，`slope` 就是 k1，再加 `k2`/`k3`
和折点 `y1`/`y2`（存下来是因为版框有斜率，每条线的折点 y 差几 px，`x_at()` 才自洽）。
`k2 is None` 就是原来的直线；**所有只调 `x_at()` 的下游代码不用改**。折点以上/以下
按 k1/k3 外推。**整页要么全直线要么全三段**，看 `BorderDetectionResult.vline_segments`
（用户要求"要变整个页面都变"）；页级另记 `bend_w80_med`/`bend_w80_max`。

**要不要切三段先量再定**：直线拟合下算每条线的 w80，页级中位 ≥ `BEND_W80_MED`=7
或任一条 ≥ `BEND_W80_MAX`=24 才切；否则原样返回。**门槛 7 是量出来的，不是拍的**：
200 页实测直线主峰在 4~6（137 页），把 7~9 档的 37 页强制跑折线，**18/18 页全部
降到 4~5、每页 9~10 条线都动了**——这一档已经是真的轻微弯。定 7 会切约 31% 的页
（63/200），代价只是 Step2 多做两次射影；每条线另有"折线得分不比直线高就退回"的保险。

**拟合**（`fit_vlines_polyline`）：**不按 k1→k2→k3 顺序贪心搜**——前一段的误差
会往下传。直接搜四个折点的 x（这条线跟上版框、1/3、2/3、下版框的交点），连续性
天然满足；目标 = 相邻段「墨落在线上」的加权行数，就是投影峰在 0 处的高度、用户说
的「投影最能出现高峰」。每个折点在直线估计的 ±24px 里找，坐标下降 3 轮（实测 2 轮
收敛）。最后换算成 (x,k1,k2,k3)，精确等价。某条线折线得分不高于直线就退回直线
斜率（k2=k3=k1），格式仍是三段。

两个踩过的坑，都在打分/过滤上：

- **打分要用三角核** `{0:3, ±1:2, ±2:1}`。界行 3~6px 宽，±1 硬窗口在线上是一段
  平台、折点定不到线心（合成页实测偏 2.9px）；三角核让线心处唯一最高。
- **行过滤要有第二道闸：局部一致性**。第一道「窗口里墨宽 ≤9px」拦不住 ≤9px 的笔画
  碎片——界行断掉的行里混进一小截笔画就算数。**vol02/3 就这么被判成最弯的页之一
  （w80 36），其实界行是直的。** 真线（哪怕弯）在 y 方向连续、碎片是跳的：这一行
  墨的 x 跟相邻 9 个有效行的中位差 >3px 就剔。加闸后 vol02/3 → w80 5、留在直线。
  （先前写的「vol02/3 是另一种形态：峰高但宽」——**那是碎片污染，不是勾/折**，
  下面那段已改。）

**Step2**：一个单应变换表示不了折线。`warp_column` 看到折线就按折点把列切成横带
各自射影、共用 `out_w` 后竖向拼接；相邻带共享同一组源角点，拼缝天然对齐。左右两
条线的折点 y 差几 px，带界取均值，那几 px 里把线当直线，误差亚像素。
`column_warp_matrix` 的逆只对直线成立——三段页要反算列图坐标得按 y 找对应带的矩阵。

**真页验证**（w80 直线→折线 / 峰值；"直线"是拟合前留下的 `verticals_straight`）：

| 页 | w80 | 峰值 | 备注 |
|---|---|---|---|
| vol01/119 | 21.0 → **7** | 0.57 → 0.94 | 界行在每段内部还有 ±3~5px 波浪，三等分的固有残差；两条外框线残留 21/24 |
| vol02/95 | 18.0 → **5** | 0.60 → 0.85 | 全修 |
| vol01/151 | 16.5 → **5** | 0.55 → 0.98 | S 形弯，全修 |

出来的改前 w80 全被第一段的斜率带偏（vol01/151 曾报 20、47 报 25、11 报 19，真值
16.5 / 14 / 9）。`measure_gutter_straightness.py` 和验证脚本都踩过、都已改。

#### 界行「直不直」的指标：投影峰高 + x 跨度（用户 2026-09-02 给的判据）

把一条界行整条投到 x 轴上——线越直，墨全落在同一个 x 上，峰就越高越窄；线越弯，
墨被摊到更多 x 上，峰变矮变胖。这比「拟直线再看残差」直观，而且不用先假设线是直的。
脚本 `scripts/measure_gutter_straightness.py`，输出 `output/gutter_straightness.json`。

三个量（`peak` 投影峰值÷采样行数、`w50` 半高宽、`w80` 装下 80% 墨的最窄 x 跨度）。
**判据用 `w80`**：`w50` 在线弯成两段时会出现双峰、被误判成"窄"。

200 页正文页实测：**w80 中位 6.0px**（25分位 5.0 / 75分位 7.1 / 90分位 10.0）。
界行本身 3~6px 宽，所以 w80≈5~6 就是"墨全在一根柱子里"——跟用户预判的"最直只有
3~4px 宽"对得上。**w80 ≥ 10px 判为弯，占 29/200 = 14.5%。**

最弯的页（w80 中位 / 峰值中位；正常页是 6.0 / 0.95 上下）：

| 页 | w80 | 峰值 | 页 | w80 | 峰值 |
|---|---|---|---|---|---|
| vol01/119 | 21.0 | 0.557 | vol01/69 | 15.0 | 0.595 |
| vol02/95 | 20.5 | 0.552 | vol01/140 | 12.5 | 0.644 |
| vol02/3 | 20.0 | 0.827 | vol02/63 | 12.5 | 0.634 |
| vol01/151 | 18.5 | 0.528 | vol01/9 | 12.0 | 0.713 |
| vol01/47 | 16.5 | 0.590 | vol01/10 | 12.0 | 0.674 |

两条读法：

- ~~vol02/3 是另一种形态（峰高但宽）~~ **改判：那是笔画碎片污染，不是勾/折**——
  加局部一致性闸后 w80 36→5，界行是直的（见上一节）。vol01/11 单条 `w80_max` 64
  那条是落在正文上的假线，同样是污染。**指标要有这道闸才可信。**
- **这个指标独立复核了 vol01/47**。此前查「vol01/47 竖直线系统偏斜」时的结论是

#### 上下内框：两个量法教训（金标其实是对的）

`vol01/137`、`/138`、`/141` 的金标 `bottom_inner` 曾被判为「整条画在白纸上」
（线上行墨 0.010/0.033/0.000）。**复核结论：三页都印上了，只是磨得极淡，
金标是对的**，不用改。

**教训一：偏心的量法会凭空造出结论。** 原来的 `eval_border_hlines_vs_ink`
只拿金标当脊线种子（±11px），金标离"自己的"脊线永远 ≤HALF，结构上不可能
输；金标压根不在墨上时还直接"样本不足"跳过。它报的

换中立量法后：28 条边里 **23 条金标与算法本来就重合**。

**教训二：判「有没有线」不能用绝对墨门槛。** 换两条判据才判对：
（a）**相对本底的局部峰**——本底实测是 0.000，金标处 0.02~0.10 的墨已是本底的
8~39 倍；清楚页 250~450 倍、淡但明确的页 105~180 倍，**是连续衰减谱不是有无**；

#### ⚠️ 上面这个"根因"是错的，已推翻（2026-08-31）

曾经写在这里的根因是"抬头框自带的竖直墙线把 `joint_search_coarse_to_fine`
的角度带偏了"，依据是**顶部区域**的叠加图——那张图上算法线确实明显偏进
字身。准备照这个思路动手修（用刚定版的 `detect_head_raise()` 把墙线挖出
搜索窗口）之前，先补了一次量化核对，结论跟目视判断相反，**修法作废**。

**问题出在量法**：金标的 `verticals_inner` 是人工在标注页上拖出来的
**直线**，而这批书的界行**是弯的**。"算法直线 vs 金标直线"量的是两条
都不完全对的直线互相差多少，不是"算法离真实界行多远"。

**换了个第三方基准重量**：不拿金标当基准，改在图上找**真墨脊线**——在版框
内每隔 20 行取一段横切，在候选线附近找墨列和的峰，要求峰值处 ≥55% 的行有
墨、半高宽 ≤25px（排掉字的笔画），取半高以上那段的加权质心做亚像素定位，
再用 MAD 剔外点稳健拟合。**只量内部界行（每页 8 条）**——最外那两条旁边
20~31px 就是外边框，任何窗口都可能跳过去，量不干净。

> ⚠️ 第一版量法太松（窗口 ±50px、只取 argmax、无亚像素、无剔外点、步长
> 120，还把最外两条算了进去），报出来的是 算法 5.90 / 金标 6.36 / 最佳直线
> 4.27 / 弯曲 30.0px ——三个距离和弯曲幅度**都被外边框和字的竖笔画抬高了
> 约 3 倍**。下面是严格版的数，结论方向不变但幅度小得多。

14 页 × 8 条内部界行 = 112 条（金标重拟**之前**）：

| | 离真墨均值 |
|---|---|
| **算法直线** | **1.82px** |
| 人工金标直线 | 2.20px |
| 最佳拟合直线（直线模型的天花板） | 1.30px |
| 真墨弯曲幅度（峰-峰） | 6.0px |

两条结论：

1. **算法比人工金标更贴真墨，一页都没反过来**（137/138/47 差得最明显，
   其余页两者接近）。vol01/47 上算法比金标贴近 **3.25px**（5.36 vs 8.62）
   ——所谓"算法在 47 上系统性偏斜 13~39px"，偏的是金标那条线。47 的金标
   是标注时 10 条全部手工拖过的（其余页大多沿用算法种子没动），拖的时候
   按顶部区域对齐，直线到了页面中段就离开了界行。

   **两个口径正好互相印证**：一致性口径下"算法 vs 金标"有非零差的页恰好
   只有 137/138/9/141/47 这 5 页（其余 9 页差 ≤0.1px，因为金标直接沿用了
   算法种子、标注时没拖），真墨口径下算法更贴的也恰好是这几页。

2. **直线模型本身还有一点点空间，但不多**：界行峰-峰只弯 6.0px，最佳直线
   能到 1.30px，算法 1.82px——**差距只有 0.52px**。（第一版量法算出"弯
   30px、天花板 4.27px"，据此写过"必须换曲线模型"，那是量法误差造成的
   过度结论，已撤。）

#### 金标已按真墨重拟（2026-08-31，用户授权）

既然量清楚了，就把金标修好而不是留着当已知噪声。人工核过的**条数、顺序、
身份**原样保留（那是人的贡献，也是自动方法给不出的），只重拟**几何**。
三道验收闸，任一不过就保留人工值：样本量/跨度、必须真的更贴真墨、拟合
区间内位移 ≤14px。

第三道闸是踩出来的：搜索半宽放到 35px 时，**最外那两条线会跳到旁边 20~31px
的外边框上**，位移 16~40px、方向一律朝外，"离墨距离"看着还大幅改善——
其实是换了一条线。半宽收到 20px（小于内外边框间距）+ 位移闸，双保险。

结果：**140 条里重拟 119 条**，其余保留人工值（原值全部留档在样本 JSON 的
`verticals_inner_manual`，逐条判定记在 `refit.lines`）。

| | 重拟前 | 重拟后 |
|---|---|---|
| 金标离真墨 | 2.20px | **1.41px**（天花板 1.28px）|
| 算法离真墨 | 1.79px | 1.79px（没动算法）|
| 金标比算法更贴的页 | 0 / 14 | **14 / 14** |

金标现在基本贴到了直线模型的天花板，可以当准确度基准用了。

**`head_raise` 同样按真墨重拟了**。口径按用户定的——`inner_y` = **线心**、
`outer_y` = **外延**（外框常是一条 15~23px 的粗条，取朝外那一侧的边缘），
墨量**只在该列的窄窗口里**算（抬头框只存在于这一列）。

- `inner_y` 13 例全部重拟，移动 −3.4 ~ −10.7px。原值**全部同号**偏低：
  金标位置墨占比只有 0.000~0.096（根本不在墨上），上方 4~11px 才是那条
  墨占比 0.33~0.96 的细锐线。
- `outer_y` 11 例重拟为外延，移动 −9.7 ~ +2.9px。原值多数已落在粗条靠外
  的位置（条内 2~41% 处），这次把口径定死。
- 金标新增 `inner_observed`/`outer_observed` 两个字段分别记这两个坐标是不是
  量出来的，`estimated = not(inner_observed and outer_observed)`——跟
  `HeadRaiseBorder.estimated` 的语义对齐。18 条记录里 inner 观测 13 例、
  outer 观测 **11** 例：**vol01/51 的 c2/c8 外框在扫描里根本没印上**
  （`outer_y` 处墨占比 0.000）。

量法上两个坑值得记：

- **墨占比门槛必须是绝对值，不能用"峰值的一半"**。外框常常是满墨(1.0)，
  相对门槛会被抬到 0.5，而真内框只有 0.33~0.47——vol01/47 四例全被杀掉。
- **拦"跟外框/字混淆"靠间距先验**：要求 `inner-outer` 落在 25~52px，把外框
  本身（间距太小）和下面第一个字的横画（实测在 y≈350 一带，间距太大）两头
  排掉；合规候选里取**最靠里**那条，即使比较浅。

**这次重拟有一个很强的独立验证**：重拟后 `detect_head_raise()` 的误差
**inner 6.9→0.6px、outer 3.3→0.4px**（最大 1.2px）。生产探测器用的是半高宽
匹配度找峰，重拟用的是列内线心/外延——两套毫无关系的方法吻合到亚像素，
只可能是两边都对上了同一条真实的墨线。（`detect_head_raise()` 原本返回的是
粗条内的峰值位置，比外延低 2~4px；这次一并改成同样的外延口径 `_outer_edge()`，
否则会一直带着这个系统偏差。）

**顺带验证了"内外边框间距全页一致"这条判据**：手标的页级 offset 四处都
聚在 36~40px（上 36.3±6.2 / 下 38.2±5.1 / 侧 38.4±4.0）。抬头框按定版口径
量（外延 → 内框线心）是 37.0 ± 5.7px；**把两种形态拆开更干净**——9 例粗条
（宽 18~23px）是 **39.5 ± 1.8px**，正好落在页级 offset 的区间里；2 例外框
印成细线的（vol01/49 c6 宽 4px、51 c1 宽 7px）是 24.1 / 27.1，细线的外延
≈线心，自然短一截。所以这条判据成立，但**必须先说清楚"从条的哪儿量"**
——金标原来那个 35~47px 是 inner 偏低约 6.6px 造成的，不是版式本身在变。

**一致性口径的数字会变大，那不是回归**：金标重拟后重跑「算法 vs 金标」，

### 抬头框自动探测（`detect_head_raise()`，已定版）

**结果**：14 页金标上 TP=15 / FP=0 / FN=3。三个 FN 全在 vol01/32——那页
5 个抬头框的上边框被物理装订/裁切吃掉了（金标本身 `estimated=true`，
是人工推测值），算法在那页命中的 2 个 y 误差也有 +46px，**不该指望**。
把 32 排除，**13 个可观测抬头框（`estimated=false`）13/13 全中**：

| | 值 |
|---|---|
| 可观测抬头框命中 | **13 / 13** |
| 普通页误报（137/138/9/14/142/24/65/141 八页） | **0** |
| `inner_y` 误差均值 / 最大 | **6.9px / 11.2px** |
| `outer_y` 误差均值 / 最大（实测到 outer 的 11 例） | **3.3px / 6.8px** |

`inner_y` 那 6.9px **全部是同号的**（13 例都是 −4 ~ −11px，算法一律
比金标偏上）——这是金标标注习惯造成的系统偏差（标注时手柄拖到线的
下缘而不是线心），不是算法抖动。真要收掉得重标金标，不是调算法。

**先把形态量出来，再设计判据**——这一轮真正解决问题的是"把 18 个金标
抬头框逐个量一遍墨占比和半高宽"（scratchpad `stat_head_raise_lines.py`
+ `diag_head_raise_v3.py`，后者把窗口/候选/金标线都画到图上）。量完
锤实三条，之前四版原型全部死在这三条上：

1. **`inner` 是唯一稳定的信号，`outer` 不可靠。** 13 个可观测金标上，
   `inner` 位置全都有一条**半高宽 4~8、墨占比 0.38~0.97 的细锐线**，
   无一例外。`outer` 却有两种完全不同的形态：vol01/33、26、47 上是
   **半高宽 17~23 的粗满墨条**（墨占比 0.83~1.00），vol01/51、49 上
   **墨占比只有 0.00~0.18**——扫描里根本没印上（51/c2、51/c8 的金标
   outer 位置实测墨占比恰好是 0.000，那两条线是人工照着版式补的）。
2. **"细锐"这个筛子对 `outer` 是反的。** 之前用 `半高宽<=14` 筛候选，
   把 33/26/47 的粗条 outer（17~23）全枪毙了。
3. **竖直连接墙线是块级的，不是列级的。** 连续抬头列共用**一个**抬头
   框，块内部的界行在抬头区继续往上延伸，那不是墙——墙只在整个抬头块
   的最外两侧。vol01/33 的 c7 正好在 c6~c8 块的中间，实测两侧墙覆盖率
   只有 0.00 和 0.04；47 的 c4、c5 同样是 0。按列查墙必然误杀块中间。

**定版算法**（常数全部来自上面的实测，见 `border_geometry.py` 里
`HR_*` 那组）：

1. 每列在主上边框上方开一个 **230px 深**的窗口（下沿留 25px 避开主边框
   自己的内外双线），按行算墨占比曲线；
2. 找局部极大值，按形态分两类：**细锐线**（半高宽 ≤10 且墨占比 ≥0.35）
   和**粗满墨条**（半高宽 15~32 且墨占比 ≥0.75）；同一条线上的多个极大
   值点按 12px 去重；
3. 取最上面的细锐线作 `inner`。`outer` **优先**认它上方 20~55px 的粗条
   （取粗条的上沿）；没有粗条时才认"最上两条细线其实是内外框"（49/c6、
   51/c1 那种 outer 也印成细线的）；两者都没有就按中位间距 38px 推，
   `estimated=True`；
4. `inner` 离主边框的距离要落在 **90~210px**（实测真值 117~137px）——
   这一条是压掉普通页误报的主力：普通页窗口里唯一的细锐线是**外边框
   自己**，距离只有 26~45px，直接被挡掉；
5. 相邻列 `inner_y` 差 ≤18px 的聚成一个**抬头块**，墙线只查块的最外两
   侧，且在名义界行 x 附近 **±25px 内搜**（界行 x 来自
   `find_vertical_lines`，vol01/47 顶端就系统性偏 13~39px，固定窄条会
   整条错过真墙——这一改是 47/c9 从墙覆盖率 0.00 变成 1.00 的原因）。

单测在 `tests/test_border_geometry.py`：普通页不误报、粗条 outer 形态、
outer 整条缺失仍能报出（`estimated=True`）、块中间列不需要自己的墙、
无墙的孤立横线要拒绝——五条各自锁住上面一个踩过的坑。

**四版失败原型的记录**（都在 scratchpad，未入库；留着是因为每一版死法
不同，换个思路重走很容易再踩）：

**v1（`proto_head_raise_detect.py`）**：思路不用"扫墨量占比"，改用"每列
局部窗口里，主边框上方是否有一条只跨这一列宽度的独立细横线"——复用
`find_horizontal_border` 同一套半高宽匹配度算法，只是把搜索范围从整页
宽度收窄到单列的x范围。14页金标上跑第一版：召回不错（12个真抬头列
命中10个）但精确率很差——几乎所有"其实没有抬头"的页面（137/138/9/14/
65/141/142）都在主边框上方~30px处冒出一批假阳性，且**同一页内这些假
阳性的y几乎一致**（比如138的6个假阳性全部落在304-313px内）——诊断出
这是**外边框本身**被当地重新找到了一遍，不是抬头台阶（外边框贯穿全页，
本来就该在每一列都测到差不多的y）。加了一个"同一页内≥4列命中同一y
（±15px）就整簇丢弃"的去重后，138/9/24/65 从有假阳性变成全干净，
14/141 的假阳性从6-7个降到0-1个，**32/26 这两个简单的单/双列抬头页
做到了金标零误差全对**；但复杂多列页（47/49/51）出现了新问题——真正
的抬头台阶有时候y恰好跟旁边几列的外边框假阳性接近，被一起当成"页级
误报簇"给误删了，47从命中3/3掉到1/3，49从1/1掉到0/1。**净效果是喜忧
参半**：单列/双列朴素抬头页（32/26型）解决了，但没解决最初动机所在的
47型复杂多列抬头页，反而在这类页上从"精确率低"换成了"召回率低"这个
新问题。

**v1 追加排查：候选离主边框的距离（`dist`）单独也不是干净的判据**——把
14页所有候选（TP/FP都算）按 `dist=border_top_y - 候选y` 摊开看：单/双列
朴素抬头页（32/26）的真候选普遍 `dist` 较大（51-126px），外边框假阳性
普遍较小（18-48px），乍看像是能简单卡个阈值分开；但复杂多列页（47/49/
51）里恰恰有一批**假阳性的 `dist` 也很大**（47col6=110、49col6=116、
51col2=125、51col8=121——量级上跟同页真候选 47col9=130、51col1=127
完全混在一起），推测是这类页顶部结构本来就密集（相邻列的抬头台阶/
连接墙线互相靠得近），单纯量距离会把"离得远的别的干扰"也当成候选。
`ratio`（跟主边框匹配度之比）同样不干净——真候选 ratio 从 0.40 到 4.85
都有，假阳性也是从 0.39 到 131（后者是明显的离群噪声，但门槛卡在哪都
会两头漏）。**结论**：单靠"候选离边框多远"或"候选匹配度多强"这两个
一维特征，在47型复杂页上都分不开真假；下一步如果要继续，思路应该换成
用**二维结构**——真台阶除了那条横线，理论上还有前面反复提到的"竖直
连接墙线"陪着（下到主边框水平线为止），外边框假阳性和普通噪声候选
没有这根柱子；检测的时候可以要求候选横线的两端往下各延伸一段要有竖直
墨迹陪同，而不是只看横线本身的半高宽匹配度。**这条"换二维结构"的判断
是对的**——定版算法的墙线检查就是它，只是必须做成块级而不是列级。

**v2（`proto_head_raise_v2.py`）**：按上面的结论加了竖直墙线检查，但
窗口深度还是 `BAND_ABOVE=130`。TP=11 / FP=8。诊断时才发现窗口根本不够
深——实测 18 个金标抬头框的 outer 全部落在主边框上方 137~197px，inner
在 101~156px，**130px 的窗口里两条线经常一条都看不见**，命中的往往是
窗口里凑巧存在的别的墨迹。这一版还顺带暴露了一个**金标本身的 bug**：
导出脚本用 `lo <= 手柄x <= hi` 区间包含判列号归属，而手柄就压在界行上
（实测 12 个手柄里绝大多数离边界只有 0.1~8.4px），落哪一侧全看浮点毫厘
——等于抛硬币，33/47/49/51 四页列号判错、还判出了物理上不可能的重复
（一列两个抬头框）。已按"吸附最近界行 → 归左边一列"重导，见数据集那边
`border-detection/README.md`「抬头框的标注语义」。改完 v2 就变成
TP=11 / FP=8 / FN=7。

**v3（`proto_head_raise_v3.py`）**：窗口放到 230px，并加了一条看起来
很硬的结构约束——**抬头框跟主版框一样是内外双线，要求候选必须成对**
（间距 26~55px）。**精确率一步到 100%（14 页零误报），召回崩到 28%**。
根因就是上面第 1 条：vol01/51 三列的 outer 在扫描里压根没印上，硬要求
成对把整页杀光；47 大半列的粗条 outer 又被 `半高宽<=14` 提前筛掉，也配
不成对。**教训**：版式手册上写着"内外双线"，不等于扫描图上量得到两条
线——判据只能建立在"实际量到了什么"上，不能建立在"版式应该是什么"上。

**踩过的坑（水平线探测的负结果，已撤销）**：第一次尝试是"整条带内多候选 NMS + 相对
分数阈值 + 挑离页面中心最近者"，不限制窗口范围。结果灾难性回归——
137 顶部本来 0.1px 精确命中，被带内一个纯属笔画噪声的候选（离 primary
约350-375px）顶替，误差冲到 378px；32 顶/33 底/49 底同样被拖崩。根因：
样本内真候选（内/外边框对）的分数比跟纯噪声候选的分数比区间是重叠的
（真实~41-58%、噪声~27-58%），**没有一个固定阈值能把两者分开**；一旦
搜索范围铺满整条带，噪声候选离中心可能碰巧比真候选还近，被误选中。
这是窄窗口方案改成"只在 primary 附近 ±60px 内找第二候选"的直接原因——
±60px 覆盖了已观测到的所有真实内外边框间距（30-45px），同时把 350px+
外的噪声排除在搜索范围之外。

第二次尝试是想把 137/138 底部剩下的 21-28px 残差也打平：找到窄窗口内
的粗候选之后，在它周围再开一个更小的窗口（±25px）重新跑一次位置+角度
联合搜索精修，类似 `find_vertical_lines` 对候选窗口的精修方式。结果也是
负结果，已撤销——联合搜索允许角度自由变化，在这么小的窗口里，一条
"斜穿过两坨相隔几十像素的墨迹"的对角线有时候比任何一条水平线本身分数
更高（合成图单测就是照这个机制最小复现的：窗口内两条水平墨迹相隔 33px，
精修后返回的是一条斜率 0.036、位置介于两者之间的假线，不是任何一条真
线），vol01/138 底部真实验证也确认了同样的劣化（21.2px→46.5px，比不
精修还差）。教训：这套"位置+角度联合搜索"本来就是为整条带/大窗口设计
的（角度自由度用来找版框线本身的微小倾斜），窗口一旦缩小到跟候选间距
同量级，角度自由度反而会被滥用去连接不相关的两坨墨迹——窄窗口内的第二
候选目前只用局部极大值的粗位置，不做二次联合搜索精修。

### Step 2：单列射影变换 + 去噪 + 界行清除

**定义**：给定 Step 1 里某一列的左右两条边线，把这一列做射影变换矫正成
竖直矩形，去掉噪点（书斑、墨渍等非文字干扰），并**清掉矫正图两侧的残余
界行**。

第三项是 2026-08-31 这一轮补进来的。界行是 Step1 给的左右边线**本身的
墨迹**，有宽度（约 5~10px）；`warp_column` 把边线映射到 x=0/x=out_w，
于是半条线必然留在矫正图里——14 页 126 列实测**没有一列是干净的**，两侧
6px 内墨占比中位 0.65~0.75。这些残墨会污染 Step3 的行投影和 Step4 的连通体
归属，属于这一步该收拾的东西，不该甩给下游。

**输入**：原图 + Step 1 输出中该列的左右边线 `(position, slope)` + 上下界。

**输出**：该列去透视后的竖直矩形灰度图（去噪 + 两侧界行已清）。

`strip_column_rules` **抹白而不裁切**：矫正图的局部坐标系是 Step3
（`row-boundaries` 金标就挂在上面）和 Step4 共用的锚，裁一刀所有挂在上面的

`column_text_band` 的判据：界行是贯穿整列的竖直墨线，在投影上是**紧贴边缘、
墨占比很高的一小段**；字身墨再密也到不了那个占比（字与字之间有空隙）。从两端
各自往里吃掉「界行本体（≥`rule_coverage`）+ 紧跟着的裙边（≥`skirt_coverage`）」，
整个过程限制在 `max_rule_frac`=15% 宽度以内。**宁可留残墨也不切字**——留下的
残墨 Step4 还有一道防线，切掉的字谁也补不回来。某一侧压根没有界行（版心侧被
装订切掉）时第一步就不满足，返回 0 / 宽度本身，不会误吃。

**上下界口径（新定版）**：`warp_column` 的 `top_y`/`bottom_y` 是标量，而版框
是斜的（上版框斜率实测最大 0.032），"这一列的上下界在哪"取决于沿版框线的哪个
x 取值——接口从来没写死，`column_bounds()` 把它固化：**一律取页面右端锚点
x=0**（即 `HLine.y_at_right`）；**抬头列改用该列抬头框的 `inner_y`**（同一列
有多级台阶时取最小的那个，即最高的一级，才装得下全部抬头字）。

代价是已知的、如实记着：越靠左的列，x=0 锚点离该列真实版框越远——126 列实测，
`y_at(0)` 与「该列中心处的版框 y」相差 **top 均值 14.6px / 最大 60.5px**、
bottom 均值 8.7px / 最大 26.5px（最差都在 vol01/47、33 这类上版框斜率大的页面
的最左几列）。也就是说最左列的矫正图上端可能比真实版框低 60px，会切进首字。
这是选口径时明知的取舍，不是 bug；要改就改 `column_bounds` 这一个函数，
`warp_column` 不动。

**`out_w = max(顶宽, 底宽)` 会不会把内容压扁/拉伸——查过了，不会**（负结果，
两条证据）：

1. **数学上**，梯形→矩形的射影映射把**每一条源图水平线都归一到 out_w**。在
   梯形量最大的 vol01/47 c6 上逐行实测：顶端缩放 1.0010、25% 处 1.0297、
   中点 1.0602、75% 处 1.0925、底端 1.1269，而每一行映射后都精确落在
   0..191。所以 `max`/`min`/`mean` **只决定输出的整体分辨率，不改变顶底之间的
   相对形变**——那个相对形变由梯形本身决定，跟取哪个没关系。`max` 是对的选择，
   因为它保证没有任何一行被下采样。
2. **实测上**，如果这个归一在制造形变，那梯形越大的列，矫正后「字身带宽度
   顶半 vs 底半」的差就该越大。111 列（另 15 列半边字太少量不出来）测下来：
   顶底相对差中位 1.6% / 均值 5.5%，跟该列梯形量的**相关系数 r = −0.173**，
   连符号都是反的。没有证据表明 `max` 口径在制造形变。

   量法的局限如实记：字身带宽度是**自动代理量**（按约一个字格高切片、取墨质量
   5%~95% 跨度的中位数），不是人工核校的；两个大离群值（vol01/47 c6 +0.336、
   c9 −0.309）都落在 47 这页——那页 Step1 的竖直线本来就有已知的系统性偏斜
   （见 Step1 节），不能归到 `out_w` 头上。

真正决定形变的是**梯形量本身是不是真的**（纸面透视 vs 某条界行斜率估歪了），
那个只能靠人看字，就是下面这个金标要回答的。

**测试集**：`open-guji-dataset/char-segmentation/column-warp`。金标两部分：
**文字带左右边界**（一条走廊 `[canonical, human]`，不是一个点）+ **上下两端的
版框残墨类别**（只记类别不记坐标）。详细口径、选列规则、跑分都写在该子集的
README，这里只记结论和踩过的坑。

**输入分了两套，别混着比**（2026-08-31 拆开）：

| | `legacy-page-anchor/`（归档） | `samples/`（现行） |
|---|---|---|
| 列的左右边线 | `border-detection` **人工金标** | `detect_borders()` **算法探测** |
| 矫正窗口 | 整页共用 `top.y_at(0)` | `page_column_windows()` **逐列**算 |
| 抬头列上界 | `head_raise.inner_y` | `head_raise.outer_y - 8px` |
| 量的是 | **Step2 自己**（隔离 Step1 误差）| **Step1+Step2 端到端** |
| 样本 | 25 列，命中 43/50，吃字 2 列各 1px | 17 列，命中 30/34，**吃字 0 列** |

两条链路的边线实测差 **0.76~27.6px**、列图宽度差到 **38px**（vol01/47 c7），
不是同一张图。`eval_column_warp.rebuild()` 认样本里有没有 `input` 那一块，
两套都能跑。现行口径是生产链路真正会喂给 Step2 的图，所以定为主集；归档那套
仍回答"假设 Step1 完全正确、Step2 收尾有多准"，不删。

**上游还会一直改，所以「怎么少重标」本身是个要解决的问题。**
金标已经因为上游改动作废过三轮（`head_raise` 列号归属 → 10 列 top_y 变了但
标注全部幸存；`verticals_inner` 按真墨重拟 → 7/32 失效；输入换成算法边线+
逐列窗口 → 15/32 失效）。前三轮都是**手工**逐条复核的，费时且容易漏——第三轮
差点只复核"还留在金标里的"那些，那样会永久丢掉 2 条"上一轮失效、这一轮又有效"
的标注。现在固化成 `scripts/migrate_column_warp_gold.py`：

| 金标 | 留用判据 |
|---|---|
| 主判据（两类金标都用）| **图变没变**——导出时给每条标注存一份图像指纹（文字带存整列图 `column_fingerprint`，上下版框存两张端裁剪图 `end_fingerprint`），迁移时重算比平均绝对差 ≤6 灰阶就原样留用 |
| 补救通道（只对 `clean` 列）| 图真变了之后，把人标的 `human_left/right` 放到新图上，那两处墨占比仍 ≤0.01 就免人工留用（`canonical_*` 按新图重推）——判据是**金标自己的定义**「边界处墨量接近 0」 |

**不拿算法的一致性当留用判据**——那会让金标永远测不出算法错，是循环论证。

**补救通道踩过一个坑（已修）**：早先把"零墨"当主判据，结果拿它去查 `mixed` 列
必然报警——`mixed` 的含义就是"这一列压根找不到墨量归零的边界"（实测 vol01/47
c2/c7 的左侧从头到尾在 0.04~0.09 之间、没有任何零区，那正是人判 `mixed` 的
原因）。三条被误报成"失效"。改成以指纹为主判据、零墨只当 `clean` 列的补救
通道之后，32 条文字带 + 64 条端裁决**全部留用、0 条需重标**。

容差是标定过的：列图横向平移 1~3px 时指纹差 ≈0（带跟着移、图其实没变，正是
"变化不大就不用重标"该有的行为），平移 8px 才开始报警（17/40 超阈值）。
没有 `end_fingerprint` 的老样本一律判"需重看"，不猜。

**实战验过一次**：修完下面那个界行 bug 之后重算，64 条端裁决里 **61 条图没变、
原样留用，只有 3 条真变了**（正是清掉界行残条的那三张）。文字带 32 条里
**29 条留用、3 条失效**。这就是这套机制该有的样子——上游改动只推翻真正受影响
的那几条。

**`border_class` 一条都不能迁**（负结果）：类别取决于"窗口裁到哪"，而窗口
口径正是第 3 轮改掉的东西。新窗口**故意**把主版框线放在列图第 0 行，126 列
实测上端 `c`（没残墨）从 24 掉到 6、下端 `b`（粘连）从 2 涨到 42——旧的 `none`
是**被口径作废**的，不是噪声，带过去会污染金标。22 条已一致的裁决只好全部作废
重标。**教训**：金标挂在"某一张具体列图"上时，凡是改变这张图取景范围的上游
改动，都要先问"这个标签的定义还成立吗"，再谈"数值差多少"。

**当前准确度**（现行口径，32 列 / 13 页全部标完，`scripts/eval_column_warp.py`）：

| | 结果 |
|---|---|
| 文字带·命中走廊 | **58/64 条界**（`clean` 组 55/60、`mixed` 组 3/4）|
| 文字带·吃进字身 | 1 列 1px（在 `mixed` 组，那一列本来就没有干净边界）|
| 文字带·欠多少到走廊 | 1.0px 均 / 最大 18px |
| 上下版框·类别一致 | **60/63**（64 条端裁决，1 条 idk 不计分）|

人裁 30 列 `clean` + **2 列 `mixed`**（vol01/47 c2、c7——左侧墨量从头到尾在
0.04~0.09 之间、没有任何零区，界行和字身确实分不开）。上下版框剩下 3 条不
一致：26 c5 上端算法找到间隙、人判粘连；47 c6/c9 底端算法削 1~2 行、人判没
残墨（削这点无害）。

**「先清左右、再做上下」原来漏了一种界行**（用户审阅时点出来的，已修）：标上下
版框的裁剪图里还看得到左右墨条。查下来**不是顺序错**（顺序早就固化在
`clean_column`），是**侧界行判据缺了一档**——真实界行是**弯的**而 `VLine` 是
直的，所以界行常常只在列的**某一段**探进带里；整列平均之后那一段被稀释，
`column_text_band` 从边缘扫、发现边上没墨就判"这侧没界行"直接放行。两处修：

1. `strip_column_rules` 改成**分横条**做（默认 240 行一条），一条一个带——
   整列一个带追不了弯界行。
2. `column_text_band` 补**内缩档**：边缘空白但窗口里藏着一条**孤立窄条**
   （峰 ≥0.40、宽 ≤22px、两侧都归零）就是探进来的界行，切到它的内侧末端。
   这一档用单独的、更宽的搜索窗口（28% 宽度）——实测那些条落在离边 24~35px，
   贴边档的 15% 窗口够不着。

vol01/47 上实测 5 处这样的残条，全部清掉、字身没动（`吃进字身` 仍是 0 列）。
两个负结果：**内缩档不能只看峰值**——126 列实测"文字腹地"（两侧各去 25%，那里
绝无界行）的列投影峰值最高 **0.533**，而内缩界行峰值最低 **0.40**，完全重叠；
分得开的是**形状**（界行是零→窄条→零的孤立结构，字身峰是宽鼓包的一部分）。
**取"第一段墨"也不行**——会被去噪剩下的 1~2% 麻点截断（vol01/47 c4 的真界行条
峰值 0.98，被 x=9 处一个 0.013 的麻点挡住，判成"没有条"），要取**峰值最高的
那一段**。

**上下版框分档**（`column_border_trim`，用户给的 a/b/c 三档 + 实测补的 d）：
a=边缘有墨且迅速归零（整段削）/ b=边缘有墨且不归零、跟字粘连（只削 3 行）/
c=边缘没墨（不动）/ d=边缘先空白、往里才碰到薄横线（"内缩版框"，空白连同横线
一起削）。分档靠三把尺子，都拿金标标定：**厚度**（版框线 3~13 行 vs 首字
91~121 行，中间完全没样本，阈值取 30）、**起始陡度**（版框粘着字时头 3~4 行冲到
0.74~0.93，纯首字头 8 行最高 0.50）、**内缩档的最低墨量**（0.15，挡掉噪点）。

**起始陡度这把尺子原来只用在内缩档，漏了贴边档**（拿 64 条金标一比才发现）：
贴边遇到厚墨段一律判 `b`（粘连），把"末字顶到边缘"整批误报成版框——64 条里错
7 条，全是底端。补上之后 53/63 → **60/63**。

**行墨占比本身不能当判据（负结果）**：正文中段的字身行墨占比最高能到 **0.747**、
中位 0.598，跟内缩版框横线的 0.56~0.93 完全重叠——带长横画的字整行就是满的。
只有把探测限制在"某段墨的头几行"才分得开，因为字的顶边必然是细的。单测
`test_column_border_trim_row_coverage_alone_would_have_failed` 是照这个机制做的护栏。

#### Step 2 → Step 3 的交接：只推过了闸的列

`scripts/export_step3_input.py` 把 Step2 已经处理好、且**过了金标**的列导成
Step3 的输入（`output/<book>/step3_input/<page>/c<N>.png` + `manifest.json`）。
起因是 Step3 那一轮量到的最大瓶颈不是 Step3 自己，是上游连坐：40 页里 13 页
Step1 没把列切对，Step3 拿到的**根本不是一列**，逐格全对率从 27/29 掉到 8/21、
fp 从 2 涨到 72。先立一道闸，Step3 那边量出来的数才说明得了 Step3 准不准。

**准入闸三级**：L1 页级（探出 9 列、每列宽度在本页中位数 ±15% 内——跟 Step3
分层用的是同一条，不另立门户）/ L2 列级自检（原始投影两侧外 25% 里的最低墨占比
≤ 0.012，即"这一侧找得到墨量归零的边界"）/ L3 人裁（金标 `verdict == clean`
且 `border_class` 两端都不是 `idk`）。默认 `--tier gold` = L1 ∧ L3。

vol01 现状：14 页 126 列 → **推出 24 列 / 12 页**。vol01/47 被 L1 整页挡下
（列宽 `224` 对中位数 `192`，1.17 超线），其余 13 页上 92 列还没标金标、1 列
（49 c2）人裁 `border_class bottom = idk`。24 列拿 manifest 里的参数跑
`segment_column` **24/24 有解**。

**负结果：除了 L1，我手上没有第二条经过验证的列级筛选力。** 三条候选：

1. **「清理后带内靠边的残墨」是循环论证** —— 带边界本来就是按"墨量接近 0"
   挑的，量它必然小。实测两条人判 `mixed` 的列是 0.008/0.003，反而比一批
   `clean` 列（最高 0.088）**还低**。护栏
   `test_side_floor_is_measured_on_the_raw_column_not_the_cleaned_one`。
2. **「带宽偏离本页中位数」区分不出来** —— 126 列的偏离 p95 只有 5.5%、最大
   19.5%，而最大的那条恰是人判 `clean` 的列。
3. **L2 现在用的「两侧最低墨」分得开，但没被独立验证过** —— clean 上限
   0.0109 vs mixed 下限 0.0136，只差 24%，而 `mixed` 一共只有 **n=2**；而且
   这两条都在 vol01/47，L1 已经先挡了整页，所以 L2 在现有 14 页上**一列都
   没多筛掉**（`--tier gate` 实测 117/117 全放行）。门槛按"误杀便宜、误放贵"
   往紧里取（手上 126 列，少几列不心疼；放一条坏列进去会污染 Step3 的量法）。
   护栏 `test_gate_threshold_still_separates_the_human_verdicts` 会在调参或
   上游改列图时先响。

要更细的列级准入，得先扩金标——现在任何列级判据都是在 n=2 上标定。

**两条接口口径**（`manifest.json` 的 `contract` 字段里也写着）：

- **页级共享量用该页「全部 9 列」算，不是只用准入的那几列。** `period`
  （`estimate_shared_period`）和 `ref_w` 的设计前提就是"同页多列取中位数比
  单列自估稳"；一页只准入 2 列时拿这 2 列算中位数，等于退回单列自估。页面
  既然过了 L1，9 列几何上都是"一列"。**准入闸管的是"哪些列推过去切"，不是
  "哪些列参与算页级先验"。**
- **`content_x` 必须随图传。** 交出去的是**抹白不裁切**的图，界行的墨已经
  没了，于是 Step3 内部的 `find_content_window` 在这张图上**一堵墙也找不到**，
  24 列无一例外返回整幅宽度——比 Step2 定出来的带宽 9.6%（最大 17.0%）。
  影响量过了、**比预想小**：整幅宽 vs 裁到带内，24 列里只有 1 列（51 c1）
  的格类型不同（空白格 19 ↔ 20），其余 23 列逐格一致；方向还跟"窗口变宽 →
  `blank_thresh_frac × dst_w` 抬高 → 多判空白"的直觉**相反**。所以这不是
  紧急的正确性问题，是一条该写明的接口约定——带既然是 Step2 定的，就没道理
  让 Step3 再猜一遍。

`border_top`/`border_bottom` 直接沿用 `windows.json` 的
`border_*_in_column`（抹白不改坐标，版框线的 y 还在原处）；抬头列按 Step3
的口径给 `top_slack = border_top`。**`n_raised` 不给**——`raised` 只是几何
标记，vol01/33 col4 就是"抬头但格数不变"，纯信号判据不可靠，由调用方按版式
先验/人工核校定。

### Step 3：单列文字切分

**定义**：把 Step 2 输出的单列矩形图切成一个个字格，每格标上类型（正文字/
空白/抬头字/双行小注的哪一半），并给出该列的阅读顺序。

**输入**：
- Step 2 输出的单列矩形灰度图（`warp_column` + `denoise_column`）；
- **页级共享量两个**：纵向字距 `period`（`estimate_shared_period`）和横向
  列距 `ref_w`（各列内容窗口宽度取中位数）——两个都必须是页级的，不能用
  本列自己算的，理由分别见下方「周期用页面先验」和「尺子」；
- 该列的格数（`n_body_slots` + `n_raised`，见下方 slot 编号约定）与上下
  版框在**列图坐标**里的 y。

**输出（已定版）**（`open_guji_cv/utils/row_boundaries.py`）：

```python
CELL_KINDS = ("char", "blank", "jiazhu_a", "jiazhu_b")   # 不含 "raised"，见下

@dataclass
class Cell:
    slot: int                 # 格号：正文 1..n_body_slots，抬头多出来的格
                               # 编 -1..-n_raised（从上到下），跳过 0；夹注两半共用同一个 slot
    y0: float; y1: float      # 纵向边界
    x0: float; x1: float      # 横向范围：正常格=内容窗口全宽，夹注半格=各自那半
    kind: str                 # CELL_KINDS 之一
    order: int                # 本列阅读序，从 1 开始
    gap_center: float | None  # 夹注格的缝中心 x（a/b 共用），非夹注为 None
    ink_ratio: float
    raised: bool = False      # 顶边有没有伸到 border_top 以上，纯几何量、不进 kind
    @property
    def sub(self) -> str | None:   # "a"/"b"/None，对齐生产 CharInstance.sub

@dataclass
class RowBoundaryResult:      # 原有字段不动，新增后两个
    boundaries: list[float]; blank_intervals: ...; valleys: ...; period: float
    cells: list[Cell]                     # Step 3 的正式产物
    content_x: tuple[float, float] | None # 剥掉界行之后的内容窗口 [x_lo, x_hi)

def segment_column(col_gray, period, n_body_slots=21, n_raised=0, *, border_top=0.0,
                   border_bottom=None, ref_w=None, top_slack=0.0, content_x=None,
                   ink_threshold=128, min_ink_ratio=0.01, raise_tol=2.0,
                   detect_jiazhu=True, **dp_kwargs) -> RowBoundaryResult | None

def reading_order(cells) -> list[Cell]    # 读序唯一权威，别自己按 slot 排
```

**`content_x`（2026-09-01 补，Step2 换 `clean_column` 之后加的）**：Step 2
后来扩成了「射影变换+去噪+界行清除+上下版框清除」（`clean_column`），产出的
图是**抹白不裁切**——界行/版框的墨被抹成背景色，坐标系不变。这对 Step 3
自己的 `find_content_window`（靠"墨量贯穿"找墙）是个问题：墙的墨没了，
它在图上一堵墙都找不到，会把整幅宽度当内容窗口（`scripts/
export_step3_input.py` 实测 24 列全部如此，宽 9.6%~17%）。`segment_column`
加了 `content_x` 参数，给了就直接用、跳过 `find_content_window`——Step 2
既然已经把这条带定出来了（`clean_column` 的 `diag["band"]`，随
`export_step3_input.py` 的 manifest 一起传），Step 3 没道理自己重猜一遍。
**不传（默认 `None`）走原来的路**，适配"界行墨还在"的输入（`denoise_column`
而非 `clean_column` 的产物），已有调用方/已有金标零影响——这条口径差本身
也不是紧急正确性问题（同一批 24 列量过，只有 1 列的格类型判断因此不同，
方向还跟"窗口变宽会多判空白"的直觉相反），只是接口该说清楚，Step 2 定出来
的东西不该被 Step 3 悄悄重算一遍、猜错了还不报错。

**`slot` 用负数编号抬头多出来的格**（用户 2026-08-31 定，定版即用）：跟
之前"1..n_slots 连续编号"的版本比，改动是把格数拆成两个数——
`n_body_slots`（正文格数，版式常量）+ `n_raised`（抬头额外多出来的格数，
默认 0）。正文从 1 编到 `n_body_slots`，抬头多出来的格排在最前面（物理上
在最上面），编成 `-n_raised..-1`，**跳过 0**。理由：改之前"抬头但格数
不变"（如 vol01/33 列4，`n_raised` 实为 0）跟"抬头多一格"（列1/2/3，
`n_raised=1`）在旧编号下 slot 1 指的不是同一条物理网格线——列4 的 slot 1
就是版框下第一格，列1/2/3 的 slot 1 却是多出来的那个抬头格，同一个数字
跨列不指同一个位置，没法直接比较"第几格"。改成负数区之后，**只要
`n_body_slots` 相同，任意两列的 slot `k`（`k≥1`）永远是同一条物理网格线**
——不管这一列有没有抬头、抬头占了几格，都不影响正文区的编号。

`n_raised` 只影响编号，不影响 DP：`fit_row_boundaries` 内部仍然只按
`n_body_slots+n_raised` 这一个总格数跑，跟改之前用一个 `n_slots` 完全
一样。夹注相邻性判断（`jiazhu_split.link_runs`、`reading_order` 的连续
夹注段识别）一律用**物理位置**（1..总格数，永远连续），不用 `slot`——
`slot` 在抬头/正文交界处跳过 0，拿它判断"是否相邻"会在这一格上出错；
`reading_order` 为这一条边界专门加了 `-1` 与 `1` 相邻的特判。

**坐标系**：Step 3 全程在**列图坐标**里（标准图像坐标：左上角原点、x 向右、
y 向下），沿用 Step 2 的约定——列图矫正之后已经不是页面的一部分了。所以
「a = 右子列」在这里就是 **x 较大**的那半。回页面坐标是调用方的事（Step 2
的射影变换矩阵是唯一的换算依据）。

**Step 3 → Step 4 的接口口径**：Step 4（字框收缩）拿到的是
`(cells, 列图)` 这一对。三条约定：

1. **粗框就是 `(x0, y0, x1, y1)`**，夹注半格给的已经是半宽框，Step 4 不需要
   再自己劈；
2. **`kind == "blank"` 的格不进 Step 4**——空白格没有墨可收缩，硬收缩会把
   噪点当字框住；
3. **裁紧是 Step 4 的事，Step 3 一律不裁**。这不是分工洁癖：夹注判据量的是
   「墨迹跨度占列距的比例」，裁紧之后**每一格都是满宽**，判据必然失效
   （生产原话：「缝在格框图块上量的原因不变：单字 0.6~0.7 列宽是唯一不重叠
   的量，裁紧后谁都是满宽」）。Step 4 若要回头复算夹注，必须拿裁紧前的格框。

`Cell.raised` 是**几何标记**（这一格的顶边伸到 `border_top` 以上了），
**不是 `kind`**（2026-09-01 改，用户定：「不需要区分抬头和普通字，它们
都是字，按坐标来区分位置」——`kind` 现在只有 `char`/`blank`/`jiazhu_a`/
`jiazhu_b` 四种，抬头字的 `kind` 仍是 `"char"`，只是 `raised=True`）。这条
改动是从「Step3 格类型试点金标」（39 格试标）里踩出来的：单格裁紧图上
根本看不出"顶边有没有伸到版框线以上"这种相对位置信息，人标的时候只能
按字面意思判断"这是不是字"，两格真抬头字（vol01/33 col2 的"天""而"）都
被标成了"字"——不是标错，是旧 schema 把一个几何问题当成了内容分类问题
在问。改成独立字段后这两格自动对上（`kind="char", raised=True`），
39/39 全部一致，不用重标。`raised` 也不告诉你这一列该有几个字，见下方
「抬头列」。

**现有实现**：
- `row_boundaries.fit_row_boundaries`（弹性 DP：候选=波谷 + 页面共享周期
  先验 + 三层硬约束）负责纵向切分，接口原样不动；
- `row_boundaries.segment_column` 是这一步的**正门**，把「列图 → 行投影 →
  DP → 逐格定类型 → 夹注拆 a/b → 排读序」串起来；
- `row_boundaries.find_content_window` 剥界行（见下）；
- `open_guji_cv/utils/jiazhu_split.py` 是**从生产 `clustering/extractor.py`
  迁移过来的**双行小注检出（见下）。

#### 双行小注：从生产迁移，不是重写

生产 `extractor.py` 的这套判据是在两册实审里逐条踩出来的，迁移时**逐条
保留原判据与阈值**，只做两处必要适配。对应关系（`jiazhu_split` 模块头也有
同一张表）：

| 生产（`extractor.py`） | 新链路 |
|---|---|
| `_jiazhu_gap_center` | `jiazhu_split.gap_center` |
| `flag_jiazhu_runs` | `jiazhu_split.link_runs` |
| `extract_page` 里的「段端收编」 | `jiazhu_split.adopt_run_tails` |
| `extract_page` 里的「a/b 拆分」 | `row_boundaries.segment_column` |
| `jiazhu_reading_order` | `row_boundaries.reading_order` |

原样搬过来的五个坑（细节见 `char_clustering_design.md`「双行夹注 a/b 子列
拆分 + 读序」「异常宽列缝」两节，这里只列**为什么不能改**）：

1. **尺子必须是列距**：`span/ref_w ≥ 0.75` 里的 `ref_w` 是页级列距。换成
   图块宽度会随窗口宽窄漂移（vol02/171 补宽缝后同一段夹注的比值从 0.88 掉到
   0.83，反而判不出来）；换成文字带宽度是灾难（文字带的定义就是「正常居中字
   的范围」，任何正常字除以它都接近 1，vol01 夹注列从 10 涨到 36，涨出来的
   全是「如／外／頗／郭」这种左右结构被拦腰劈开）。
2. **缝要落在墨迹跨度的中段 30%~70%**，不是图块的中段——图块两侧留白多少由
   窗口宽窄决定。
3. **单格判据必须配列上下文**：连续 ≥2 格、缝中心对齐 ±8px 才算数。
4. **桥接 + 噪点段否决**：段里个别行单侧墨太少会把连段拦腰截断（一次只桥
   1 格、两侧必须实测）；纸面碎点段 span/缝/均衡全能骗过，只有连通体结构
   分得开（按段中位 maxCC < 500 整段否决）。
5. **段端收编分两型，分型不能拿墨占比**：b 侧最大连通体 ≥250 是真笔画→整行
   拆 a/b，<250 是残渣→只发 a 半。生产踩过红线事故：vol02/4:5:20 末行
   「一|璉」的「一」只占 18% 墨，被比例判据划成残渣、整个字被丢掉。

两处必要适配：

- **尺子换成列图内容窗口宽度**：新链路里 Step 2 的列图宽度就是相邻两条界行
  的间距，物理上即列距（vol02/171 实测 `ref_w=175~185`，生产 `grid.period`
  为 184.2），阈值 0.75 可以原样沿用。**仍要传页级中位数**，不能传本列
  自己的宽度——那正是坑 1。
- **界行必须先剥掉**（新链路独有，见下）。

不变的还有一条：判据仍在**裁紧前的格框图块**上量，同一列所有格共用同一个
x 原点（缝中心才能跨格比较）。

#### 新链路独有的坑：界行会让夹注判据整体失效

生产的格框图块经过连通体归属清理，界行残墨已被抹掉；新链路的列图是 Step 2
**贴着两条界行**矫正出来的，最左最右两条就是界行本身。界行贯穿全高，一格里
只要有一个像素的界行残墨，这一格的墨迹跨度就顶满列宽——`SPAN_T` 判据对
**每一格**同时失效，整列的字都「像夹注」。

实测（同 40 页，只看 Step 1 把列切对的那 26 页 / 29 个夹注列，其余分层见
下方「实测」）：

| 剥墙口径 | 逐格全对 | fp | fn | DP 无解 |
|---|---|---|---|---|
| `wall_ink_frac=0.5, wall_pad=0`（修之前）| 25 / 29 | 4 | 1 | 5 / 350 列 |
| `wall_ink_frac=0.25, wall_pad=3`（现在）| **27 / 29** | **2** | 1 | 4 / 350 列 |

差值不大，因为「连续 ≥2 格 + 缝对齐 + 段中位连通体」这三层列上下文本来就
挡掉了大部分误报——但挡不住成段的：典型个案 vol02/171 col4 的「出」「於」
（正是生产文档点名过的「左右结构被拦腰劈开」那一类），不剥墙时整列每一格
的 `span/ref_w` 都是 1.00、`SPAN_T` 对全列同时失效，这两个连着的左右结构字
就凑成了一个「连续 2 格、缝对齐」的假夹注段；剥墙之后它们的 span 掉回
0.8 以下，正确拒判。**这一层不能只靠列上下文兜底**：`SPAN_T` 是生产文档里
写明的「唯一不重叠的量」，让它对全列失效等于把判据的地基抽掉。

`find_content_window` 按「贯穿性」剥墙：某个 x 上的墨占该列全高的比例
≥ `wall_ink_frac` 才算界行，只从两侧往里啃、最多啃 15% 宽度。两个阈值都是
量出来的（vol02/171 九列）：

- `wall_ink_frac = 0.25`——真实界行**不是**贯穿到底的实线，这批页量到的整列
  墨占比只有 **0.30~1.00**（刻版磨损 + 矫正错位），0.5 会漏掉一多半；正文字
  在边缘 28px 内的整列墨占比是 0.0x 量级，两者之间空得很。
- `wall_pad = 3`——界行的墨是**渐弱**的（某列 x=0..3 的单格墨量实测
  87/51/19/3），只按阈值切会把尾巴留在窗口里。多让 3px 没有代价：版式本来就
  有 20 多像素的 inset（生产 `measure_insets` 量到 `inset_l=26/inset_r=22`）。

取「窗口内最靠内的那堵墙」而不是「第一个不是墙的 x」——矫正后的界行常常是
断续的，遇断口就停会把半条界行留在窗口里。

#### 实测：跟生产的 jiazhu 标注逐格对照

新链路 Step1→2→3 端到端跑真实页面（`output/vol02/<page>.png`，
`detect_borders(expected_cols=9)` → `warp_column`+`denoise_column` →
`segment_column(n_slots=21)`），把每列判出的夹注 slot 集合跟生产
`output/vol02/phase4_chars/index.jsonl` 里带 `jiazhu` flag 的实例对照
（生产 `idx+1` 对新链路 `slot`）。脚本在 scratchpad，未入库。

**必须按「Step 1 有没有把这一页切对列」分层看**，混在一起的数字没有意义：
Step 1 少探到或多探出一条竖直线，这一页所有列的编号和窗口就整体错位，
Step 3 拿到的根本不是「一列」。分层判据只用几何（探出 9 列、且每列宽度都在
本页中位数 ±15% 内）：

| 分层 | 页 | 有夹注的列 | 逐格全对 | 只差一格相位 | 真不一致 | tp / fp / fn |
|---|---|---|---|---|---|---|
| **Step 1 切对了列** | 26 | 29 | **27** | 1 | 1 | 144 / 2 / 1 |
| Step 1 没切对 | 13 | 21 | 8 | 0 | 13 | 46 / 72 / 21 |

Step 1 切对的那一层里，两处非全对都查清楚了：

- **vol02/56 col7**：新链路 `[6,7,8]`、生产 `[7,8,9]`，找到的是**同一批格**，
  只是纵向格号相位差一格。两条管线的「第几格」本来就不是同一个定义（生产
  的 `cells` 里有 `margin` 格参与编号），这类差异不是夹注检出错误。
- **vol02/19 col9**：新链路比生产多一格，目视核对下来**是生产漏了**
  （两边的格号按「段末单半格」对齐——生产的 `8a` 和新链路的段端单字尾是
  同一格）。这是
  四库提要的「浙江巡撫採進本」7 字奇数小注：新链路出 3 个整格（採|浙、
  進|江、本|巡）+ 1 个段端单字尾（撫，只发 a 半），按读序 a 全部再 b 全部
  正好拼出「浙江巡撫／採進本」7 字；生产那边只有 `6a/6b`、`7a/7b`、`8a`
  五个实例，第一格「採|浙」没检出，文本少两个字。**这是一处目视个案，不是
  金标**，但它说明这条链路至少没有比生产退步。

Step 1 没切对的那一层，误报形态也是一致的：并进一个窗口的两列正文，几何上
本来就**长得跟双行小注一模一样**（两列小字并排、缝对齐、跨度顶满），
`fp=72` 里绝大部分是这种整列 19 格全判夹注。这类不该由 Step 3 兜底——
Step 3 的输入契约就是「一列」。

**DP 无解率**：350 列里 4 列（1.1%）在 `n_slots=21` 下判无解。这是设计内的
行为（约束不满足就返回 None，不给错结果），但也说明硬约束的参数需要随金标
扩大而复标，见下方「已知局限」。

#### 已知局限

- **`n_body_slots`/`n_raised` 由调用方给，本步不判断**。普通列是版式常量
  （这两册 21），抬头列可能多一格，纯信号判据不可靠（见下）。传错了 DP
  会判无解或整列滑格，不会「自适应」。（下面这批 40 页实测和「抬头列」
  节的数据是接口改成负数 slot 之前跑的，当时还是单一 `n_slots` 参数——
  数字本身不受影响，只是当时的「n_slots=22」对应现在的
  `n_body_slots=21, n_raised=1`。）
- **上游连坐**：Step 1 少探到一条竖直线，这一页的列宽就整体错位
  （vol02/105 实测量到 `wins=[87,84,172,171,167,186,505]`——只出来 7 列，
  两列窄成 85px、一列宽到 505px），Step 3 拿到的根本不是一列，无从谈起。
  Step 3 的失败要先排除这一类。
- **DP 硬约束会拒掉真实列**：vol02/171 col6 在 16~23 任何格数下都判无解，
  逐候选查下来是候选链最后一步只有 75px，恰好低于
  `lo_ratio=0.7 × period(110) = 77px`——差 2px 就整列没有可行解。`lo_ratio` 是在 vol02/135 一页上调出来的，扩页之后
  「参数大概率需要微调」这条预言在这里应验了。**没有动它**：手上没有
  这一页的纵向金标，凭一列的症状改一个跨页共享的硬约束，是拿已验证的
  9 列去赌。要改得先扩金标。
- **空白段内部的切分点精度天然差一档**（没有真实字缝，靠 `synth_step` 撒的
  合成候选撑可行性），合成图单测实测该处误差可到 20px 量级，真实字缝上的
  点是个位数。
- `raised` 只说「这一格伸到版框线以上」，不解决「这一列几个字」。
- **夹注读序只在列内**：跨列的连续夹注段（一段小注写满一列又续到下一列）
  没有处理，`reading_order` 的输入就是一列。

#### 抬头列：`top_slack` 到底该给多少（本轮新测量）

`row_boundaries_design.md`「抬头列」节记过一个未解决问题：vol01/33 的列
1/2/3 是「抬头到多一个字」型（`n_slots=22`），`top_slack=1×period` 修不好
（均值误差 2.6 / 88.2 / 1.3px，首点分别偏 46 / 107 / 24px），当时给的根因是
**「窗口放宽后进入的区域本身不干净，DP 被首字自己的笔画间隙带偏」**。

这一轮拿金标（`row-boundaries/samples/vol01_33.json` 自带 `row_proj`，不需要
图源就能复现）扫了一遍 `top_slack`，**根因不是那个**：

| `top_slack` | 列1 | 列2 | 列3 | 列4 | 五个普通列 |
|---|---|---|---|---|---|
| 0（不管抬头） | 36.0 | 101.5 | 45.2 | 0.0 | 0.0 |
| 1×period（原结论） | 2.6 | **88.2** | 1.3 | 0.0 | 0.0 |
| 1.2×period | 0.6 | 12.3 | 0.6 | 0.0 | 0.0 |
| 开到列图顶端 | **0.6** | **12.3** | **0.6** | 0.0 | 0.0 |
| 开到列图顶端（**所有列**都开） | 0.6 | 12.3 | 0.6 | 0.0 | 0.9~1.2 |

真正的原因平淡得多：**这三列的首字顶边界就在 `border_top - 1×period` 外面
一点点**（列1 差 20px、列2 差 3px、列3 差 4px），金标首点压根不在候选窗口
里，DP 只能在窗口内挑一个错的。窗口再开一点就进来了，而且**继续开到列图
顶端也不会变坏**（1.2× 到 2.5× 逐档实测完全一样）——原结论说的「放宽后
被首字笔画带偏」在这一页上没有发生。

两条可以直接用的结论：

1. **抬头列的 `top_slack` 直接开到列图顶端**（`top_slack=border_top`），
   不要按 period 的倍数抠。
2. **开错了代价很小**：把五个普通列也全开（等于抬头判断全判错），普通列
   只从 0px 退化到 0.9~1.2px。这条对「抬头框还没有自动探测」是个好消息——
   这个参数不需要一个准确的抬头判别器兜底。

列2 剩下的 12.3px 要单独说：它是**第 4~16 点整段常量 −20px**，两头都是
0。而金标那一段本身是严格等距的（544, 664, 784, …, 每步正好 +120），像是
标注工具均匀填的、不是逐点核校的；算法给的那一段同样严格 +120，只是相位
差 20px。**这 20px 不宜直接当成真实误差**，要人回去复核那一段金标。

### Step 4：字框收缩

**定义**：把 Step 3 给出的粗字格（矩形）收缩成贴合字身墨迹的最小矩形框。

**输入**：Step 3 的字格粗框 + 原图（或 Step 2 的矫正图）。

**输出**：每个字格对应的最小外接矩形框。

**现有实现**：生产 `open_guji_cv/clustering/extractor.py::CharExtractor.
extract_page`（连通体归属 + 清边 + 弯曲界行处理等一整套已经调好的逻辑）。
这一步用户已经确认"可以直接复用旧算法"，vol01 十页抽查（133~142）验证过
效果——配合 Step 1 用新算法但要注意**逐列单独去斜**，不能像最初尝试那样
拿全页共享一个 shear 喂给它（会在残余倾角偏离页面中位数较大的列上把
相邻字的连通体判串，细节见 `artifacts/README.md`「vol01 新算法逐字框选」
条目）。

**测试集**：`open-guji-dataset/char-segmentation/instances`（`clean`/
`contaminated`/`truncated`/`not_text` 四分类）和 `cells`（合成数据、像素级
金标）是现有最接近的测试集——测的是"图块干不干净/完不完整"，跟"框是不是
最小矩形"角度略有差异（该数据集原则是"多裁一点空白不算失败，只看墨对不
对"），可以先复用，够不够精确覆盖"最小矩形"这个具体要求，留到细化这一步
时再看。
