# 切分层反馈：边框混入的四个惯犯位置（进库实审回流）

**日期**：2026-08-24
**证据源**：用户在进库审查页（14/15 页批次）亲手重切的 9 个字位 +
此前 4~13 页实审标出的 46 条 contaminated（`review_label_only` 分片）。
**金标落点**：`open-guji-dataset/char-segmentation/instances`，
`seed="review_recrop"` 条目带 `old_bbox`（切分实际输出）与
`corrected_bbox`（人工拖框金标），由
`scripts/build_recrop_shard.py` 回流。

## 一、四个惯犯位置（用户实审归纳）

| 位置 | 症状 | 实测例 |
|---|---|---|
| **列首字**（idx=0） | 吃进上横版框 | frame_bar_top 类 intrusion 多发于此 |
| **列尾字**（idx=末） | 吃进下横版框；实际更糟——**整格上飘 35~55px**（见二） | 14:1:20 / 14:3:20 / 14:7:20 / 14:8:20 |
| **最左列**（col 最大） | 左缘吃进**断断续续的内边框**，且这条内边框没被版面检测认出来 | 14:9:4（左缘 +25px）/ 14:9:18（+17px） |
| **最右列**（col=1） | 同理，右侧内边框/界行 | 15:1:20（左右各收 11/7px）/ 14:1:20（+23/−26px） |

**核心诉求（G2 版面检测）**：内边框（版框内侧那条不连续的细线）
必须被**识别为边框并从字格中排除**，与外版框同等对待。目前
phase2 只认外框，最左/最右列的格子直接顶到内边框上，线的墨就进了
图块。断续（刻板磨损导致时有时无）不是不检的理由——正因为断续，
逐格用墨量阈值判不出来（`detect_intrusion` 对这类召回最差），只能
在版面层用整页证据（同一 x 位置跨多列的共线短段）把线找出来。

## 二、列尾格的真实病因是格线整体偏移，不只是「多裁了框」

重切 9 例里 5 例是**框整体竖移**而非单边多裁：旧框比人工金标高
35~55px（`grid_shift`），即列尾格上飘——本字下半截在框外、框内上部
是上一字的尾巴。单看「把下边框裁掉」修不了这类：需要 phase3 网格
在列尾处对齐到墨的实际分布（列尾格的下缘应贴住最后一行墨或下版框
内侧，而不是按等分格线硬切）。

量化（新框 − 旧框，px；正=向下/向内）：

```
instance        dy0    dy1   备注
14:1:20  (列尾)  +63    +29   兼最右列，左右也各收 23/26
14:3:20  (列尾)  +55    +33
14:7:20  (列尾)  +56    +37
14:8:20  (列尾)  +50    +34
14:9:18 (列尾近) +73    +6    兼最左列，左缘 +17
```

同页四个列尾全部上飘 50±10px ——这是**系统性**格线偏移（该页版框
定位或行数估计偏差），不是单格噪声。建议 phase3 加一条列级自检：
列尾格墨的重心若显著低于格心（或格内上缘墨带与上一格连通），整列
下移重排。

## 三、下游已有的兜底与它的边界

- `crop_quality.detect_intrusion`（rule_bar_left/right、
  frame_bar_top/bottom）：细直条满贯检测，实测召回 56%、误报 1.0%。
  它只**提示**审查页、不参与准入；对断续内边框和 grid_shift 基本无感
  ——前者不满贯，后者混入的是邻字墨不是直条。上游修好一条，这里的
  兜底就少压一条给人。
- 进库侧已把重切做成纯几何事件（`apply_recrop`），人工可修但成本高：
  每格拖框 ≈ 15s，全书外推是小时级人工。**切分层修一次，全书受益。**

## 四、怎么用这批金标

```bash
# 9 条 review_recrop：old_bbox 是坏例、corrected_bbox 是金标
cd open-guji-dataset/char-segmentation/instances
python - <<'EOF'
import json
for e in json.load(open("expected.json")):
    if e.get("seed") == "review_recrop":
        print(e["page"], e["col"], e["idx"], e["defect"],
              e["old_bbox"], "->", e["corrected_bbox"])
EOF
```

- 回归口径：新切分在这些 (page,col,idx) 上的 bbox 与 `corrected_bbox`
  的 IoU（建议 ≥0.85 为过）；
- 自检口径（`eval_instance_quality.py` 既有）：这些格至少要被 flag
  进审查队列——修不好也不能无声放行。
- 分片是**定向富集**（只有切错的才被重切），不能读作全书错误率。

## 2026-08-25 复核：改进跑到产物里了，但这一类缺陷没被修好

用户反馈「前几个字切分还是不对，改进过的算法不该出这种错」。查下来三件事：

**① 产物是最新的。** 用当天的代码把 vol01 整册 `segment` 重跑一遍，与盘上
的 `phase3_char_grid` 逐页比：**205/206 页 JSON 全等**，只有第 4 页
`cell_h` 差 0.03%（114.368 vs 114.331，书级共识的浮点毛刺）。
`a78fb618d1` 之后碰过切分层的提交只有一条纯提速（输出字节一致），
其余分支（G1/G2/G5/匹配）都没有未合并的切分代码。所以不是「忘了重跑」。

**② 但在这批缺陷上，新算法与旧算法一样。** 拿数据集里 24 条人工重切
（`char-segmentation/instances`，`seed=review_recrop`，带 `corrected_bbox`
人工金标）当尺子，取 id 未漂移的 18 个字位量 IoU：

| | vs 人工修正框 IoU 均值 | 中位 |
|---|---|---|
| 重切分**之前**的算法框 | 0.657 | 0.654 |
| 重切分**之后**的算法框 | 0.671 | 0.657 |

变好 9 个 / 变差 9 个 —— **等于没动**。这一轮的改进（版框断段剥离、抬头
行、列端曲线切边）都在别的缺陷上，列尾格整体偏移这一类没被碰到。
所以用户看到「似乎没有被改」是对的。

**③ 人工重切成果在整册重跑时被抹掉了。** 重切改的是 `index.jsonl` 的
bbox + 磁盘 patch，而 `segment`/`chars` 会把这两样整份重写。逐提交查
`index.jsonl` 里的 `recropped` 旗：`8dc0009435` 有 24 条 →
`bc7dbc48c9`（合并 main）剩 4 条 → `1beec69a83 裁剪定版` 起**归零**，
一直到现在。

真源不在产物里，在数据集分片里，所以能重建：
`scripts/replay_recrops.py`（幂等）把 `corrected_bbox` 贴回 index.jsonl +
重裁 patch + 同步库内 `patch_png`/`bbox` 并清掉过期派生缓存；字位漂过号
的按同页最佳 IoU 重新认领（17/18 页就是这么找回来的），认领不到就跳过
报出来（`vol01:16:6:0` 那一格已被新切分正确地并掉，不用找）。
已在 `scripts/run_pipeline.sh` 里挂到 `chars` 之后自动跑，防止再丢。

vol01 落地：23 条贴回，库内 14 条同步，重切位「库内字节 == 磁盘字节」
23/23 一致。

**留给切分层的靶子**：这 18 个字位就是现成的回归集，IoU 0.671 是基线。
