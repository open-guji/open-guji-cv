# 字表标准与语言模型混合

写给做 **J 单字识别 / K 上下文纠正** 的人。两件事：
「合法的字有哪些」（字表）与「哪个字更可能」（语言模型）。

---

## 一、字表标准：字体 cmap + Unihan

### 为什么需要它

识别引擎的字表覆盖不到的字，**排序再好也出不来**。这不是精度问题，
是可达性问题，两者要分开量。

在本书整理本（《總目》，341,241 字 / 4,637 字种）上实测：

| 字表 | 规模 | 本书不可达字种 | 不可达字次 |
|---|---|---|---|
| Unihan 全部已编码汉字 | 102,998 | 0 (0.00%) | 0 (0.00%) |
| 汉仪仿宋 FS001+FS002（cmap 并集）| 89,109 | 1 (0.02%) | 1 (0.00%) |
| 汉仪仿宋 FS001（BMP 那档）| 27,809 | 44 (0.95%) | 75 (0.02%) |
| PP-OCR 识别字表 | 6,280 | 1,858 (40.07%) | **37,637 (11.03%)** |

**PP-OCR 缺的不是生僻字，是繁体常用字**：說(2518) 則(2009) 謂(1446)
論(1044) 諸(1042) 採(847) 稱(828) 編(826) 一个都不在字表里。PP-OCR 是
简体中文模型，繁体刻本上这是系统性缺口，不是偶发。

三级扩展把它压下去：

| 扩展 | 剩余不可达字次 |
|---|---|
| 原始字表 | 11.01% |
| ＋ opencc 简→繁（`traditional_candidates`）| 1.79% |
| ＋ Unihan 异体字（一跳）| **1.20%** |
| ＋ Unihan 异体字（两跳）| 1.20%（两跳没有额外收益）|

剩下的 1.20%（彖 詁 筮 帙 歟 弁 墀 禘 蓍 澔 裒 衽 祫 …）**没有简体对应、
也没有异体字通路**，任何字典式扩展都够不着。要动它只有一条路：拿覆盖
这些字的字体渲染模板，做字形匹配（接 `GlyphKnnSource`）。

### 怎么建

```bash
# Unihan：https://www.unicode.org/Public/UCD/latest/ucd/Unihan.zip 解压
python scripts/build_charset.py --unihan <解压目录> \
    --corpus corpus/zongmu_wuyingdian_reference.txt --ocr-dict \
    --font <FS001.ttf> --font <FS002.ttf>
```

产出 `config/charset/`：

| 文件 | 内容 |
|---|---|
| `charset.ranges.tsv` | 合法字表，按**码位区间**存（十万级字表逐字存 1.5MB 且几乎全是连续段，区间形式 7 千行就够）|
| `variants.tsv` | 异体字 → 正字，2,727 条，带 provenance 列 |
| `report.json` | 各来源的规模与本书不可达率 |

### 字体只取 cmap，不取字形

`read_font_cmap()` 只读 cmap 表。**码位表是事实数据，字形外框才是受版权
保护的表达**——商业字体（如组织里的汉仪仿宋 FS001/FS002，带商业版权与
非商业授权限制）可以用来当字表来源，但它的外框不该进这个公开仓库。
将来做渲染模板时，模板本身也不应入库，应由本地字体现场生成。

字体家族常按平面拆成多个文件（FS001 = BMP，FS002 = 扩充 B–F，两者
**不相交**）。逐档报覆盖率会得出「FS002 漏了 99% 的常用字」这种荒唐
结论——家族的字表是各档的**并集**，脚本自动加一行 `font:*`。

### 异体字边的取舍

采信 `kSemanticVariant` / `kSpecializedSemanticVariant` / `kZVariant` /
`kTraditionalVariant` / `kSimplifiedVariant`。

**`kSpoofingVariant` 一律排除**——那是为防钓鱼域名而设的**形近易混字**，
不是异体字。把它当异体字会直接制造混淆。

默认 `--restrict-to-corpus`：只保留至少一端在语料里出现过的边。原因是
下游 `context_refine` 的「本版用字习惯」会把同语义组里语料最常用的表面
形**补进候选**，一条错误的异体边就等于往候选里注入一个错字。本书用不到
的异体关系留着只有风险没有收益。

### 正字方向按**本版语料频次**定

`pick_orthodox()` 的优先级是：语料频次 > 非简体 > 码位小。所以本版得到
的是 蓋→**葢**、略→**畧**、穎→**頴**、説→**說**（本版通篇用后者）。

这看着"反了"，但方向就该这样：语义层代表的唯一用途是给语言模型做统计，
用本版最常写的那个形当代表，n-gram 的计数才不会被同一个词分散到几个
表面形上。副作用是 `is_variant` 的含义变成「不是本版最常用的那个表面
形」，而不是「Unicode 意义上的异体字」——数据集文档里要写清楚。

**手工条目永远覆盖自动条目**：`config/dicts/variants.tsv` 里那 10 条是
人工确认过的，自动表无权改判。

## 二、语言模型混合：通用低权重 + 本书高权重

### 想法与实现

单一语料训不出好用的古籍 LM：通用古文语料量大但不认识本书的书名、
人名、术语；本书语料认识这些但量小。`InterpolatedLM` 把两者**线性
插值**：`p = Σ wᵢ·pᵢ`。

```bash
python -m open_guji_cv refine book9 \
    --corpus corpus/zongmu_wuyingdian_reference.txt \
    --general-corpus corpus/external/daizhige_zhaoling.txt \
    --general-weight 0.1 --lam 0.65
```

### 为什么是线性插值，不是对数线性

对数线性（几何）混合是 `Σ wᵢ·log pᵢ`：任何一个分量给出接近零的概率都会
把结果拖到零。通用语料没收录的本书专名**恰好就是这一类**，等于把混合
的收益全否掉。线性混合只要有一个分量给了质量，结果就有质量——这才是
「兜底 + 加尖」想要的行为。单测见 `test_lm_mixture.py`。

### 实测（context-correction，1,404 槽位，λ=0.65）

| 本书分量权重 | top1 | 增益 | 救回 | 改坏 | 有害翻转 |
|---|---|---|---|---|---|
| 0.00（纯通用）| 90.53% | +1.21% | 38 | 21 | 1.67% |
| 0.50 | 91.17% | +1.85% | 43 | 17 | 1.36% |
| 0.75 | 91.31% | +1.99% | 45 | 17 | 1.36% |
| **0.90** | **91.45%** | **+2.14%** | 45 | 15 | **1.20%** |
| 1.00（纯本书）| 91.03% | +1.71% | 41 | 17 | 1.36% |

基线 89.32%，headroom 5.20%（金标在候选里但不是首选）。+2.14% 吃掉了
headroom 的 41%。**混合优于两个端点。**

### 已接进生产（2026-08-24）+ 种子实集复验

本节标定已接线：`seeding.build_seed_lm` = 本书 3-gram **0.9** + 通用
**0.1** 线性插值，通用 LM（~10M 字，训 ~30s）按源文件指纹落盘缓存
（`corpus/external/.general_lm_cache.json`，gitignore）。seed CLI
`--general-corpus` 缺省自动发现 `corpus/external/*.txt`，传 `none` 关闭。

在种子队列实集（1681 真实槽位，候选含**库匹配证据**）上复验出一条
新纪律：**先验变强之后，无门槛全局重排在任何 λ 下净亏**（λ 0.10~0.95
全扫）。LM 的正确接法是 seed context 通道那样的**门槛化裁决**（语义
margin ≥ 0.70 才动手）：混合 +2.32%（救 41/坏 2），仍优于纯本书
（坏 10）与纯通用（救 30）两端。数字与量法见 pipeline_handbook「上下文
纠正第二轮基线」。

### 通用语料的体裁比体量重要

同为 500 万字，只换体裁（本书卷首是**上谕公文**）：

| 通用语料 | 纯通用 | 纯本书 | 混合（本书 0.9）|
|---|---|---|---|
| 诏令奏议 / 经世文编 / 政书 / 职官 | **+1.21%** | +1.71% | **+2.14%** |
| 儒藏 / 易藏（经解）| **+0.00%** | +1.71% | +1.64% |

经解语料对上谕页一点收益都没有，混合还略微拖后腿。**先问体裁，再问
体量。**

### λ 是有害翻转的主开关

`context_rank.LAMBDA` 是 OCR 项与 LM 项的配比（本书权重固定 0.75）：

| λ | 增益 | 有害翻转 |
|---|---|---|
| 0.75 | +1.28% | 1.04% |
| 0.70 | +1.64% | 1.04% |
| 0.65 | +1.64% | 1.44% |
| 0.55（旧默认）| +1.14% | 2.39% |
| 0.45 | +0.14% | 3.59% |
| 0.35 | **−1.07%** | 5.02% |

旧默认 0.55 给 LM 的话语权过大，有害翻转比 0.70 高一倍有余。`refine` 的
默认值已改成 **0.65**。继续降 λ 直接转成净负——**语言模型压过字形证据
就开始编字**。调纠正强度先动 λ，别先动权重。

### 这不是给自举 LM 平反

消融实验（见 `context_refine` 模块文档）证明自举语料（约 15% 识别噪声）
**单独**用作 LM 是净有害的。混合改变的是它的**用法**：噪声分量拿低权重、
且旁边有一个干净的大分量压着，才谈得上安全。本轮实测的两个分量都是干净
的外部文本，自举分量仍未验证，`--with-lm` 保持默认关闭。

### 两条纪律

**本书语料必须挖掉测试页。** 本书 LM 的语料就是本书整理本，而金标也是
从同一份整理本对齐来的。`eval_context_correction.py` 先剔除每个测试页的
金标窗口（前后各多挖 200 字）再训练，并**打印挖掉了多少字**；打印为 0
就是挖漏了，后面的数字一概作废。通用语料同样打印与测试页金标的 8-gram
重合率（当前配置 0.0）。

**字形层不可被语义层改写。** 纠正只允许在冻结候选内重排，不得引入候选
外的字。这是评测里的**硬断言**（`glyph_layer_immutability`），不是可以
用准确率换的参数。参考文本与语料多为正字化文本，放开这条就会把本版的
异体用字"改正"掉，破坏字形库的真实性。

## 三、外部语料怎么准备

```bash
python scripts/prepare_corpus.py --src <殆知阁 史藏/诏令奏议> --src ... \
    --out corpus/external/daizhige_zhaoling.txt \
    --max-chars 5000000 --max-per-file 50000 --to-traditional \
    --holdout corpus/zongmu_wuyingdian_reference.txt
```

三个要点：

1. **简→繁是用可控噪声换语料量。** 网上的大宗古籍语料多是简体转录本，
   而 opencc 简→繁是一对多（发→發/髮），必然引入错误。所以转换后的通用
   语料**只配拿低权重**。
2. **必须限单文件配额。** 不限时几部大部头就把配额吃光——实测 1,251 个
   文件只用上 32 个，语料看着有 500 万字，覆盖的却只是几种文体。
3. **泄漏检查是必做项。** `--holdout` 会打印最长公共子串与 8-gram 重合率。
   不接近零就换语料或剔文件，别心存侥幸。

`corpus/external/` 里的文件是**派生产物**（可由脚本重建），入库是为了让
上面那些数字可复现。
