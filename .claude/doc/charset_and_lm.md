# 字表标准与语言模型混合

写给做 **J 单字识别 / K 上下文纠正** 的人。两件事：
「合法的字有哪些」（字表）与「哪个字更可能」（语言模型）。

---

## 一、字表标准：字体 cmap + Unihan

### 为什么需要它

识别引擎的字表覆盖不到的字，**排序再好也出不来**。这不是精度问题，
是可达性问题，两者要分开量。

在本书整理本（《總目》，341,241 字 / 4,637 字种）上实测：

| 字表 | 规模 | 本书不可达字种 | 不可达字次 |
|---|---|---|---|
| Unihan 全部已编码汉字 | 102,998 | 0 (0.00%) | 0 (0.00%) |
| 汉仪仿宋 FS001+FS002（cmap 并集）| 89,109 | 1 (0.02%) | 1 (0.00%) |
| 汉仪仿宋 FS001（BMP 那档）| 27,809 | 44 (0.95%) | 75 (0.02%) |
| PP-OCR 识别字表 | 6,280 | 1,858 (40.07%) | **37,637 (11.03%)** |

**PP-OCR 缺的不是生僻字，是繁体常用字**：說(2518) 則(2009) 謂(1446)
論(1044) 諸(1042) 採(847) 稱(828) 編(826) 一个都不在字表里。PP-OCR 是
简体中文模型，繁体刻本上这是系统性缺口，不是偶发。

三级扩展把它压下去：

| 扩展 | 剩余不可达字次 |
|---|---|
| 原始字表 | 11.01% |
| ＋ opencc 简→繁（`traditional_candidates`）| 1.79% |
| ＋ Unihan 异体字（一跳）| **1.20%** |
| ＋ Unihan 异体字（两跳）| 1.20%（两跳没有额外收益）|

剩下的 1.20%（彖 詁 筮 帙 歟 弁 墀 禘 蓍 澔 裒 衽 祫 …）**没有简体对应、
也没有异体字通路**，任何字典式扩展都够不着。要动它只有一条路：拿覆盖
这些字的字体渲染模板，做字形匹配（接 `GlyphKnnSource`）。

### 怎么建

```bash
# Unihan：https://www.unicode.org/Public/UCD/latest/ucd/Unihan.zip 解压
python scripts/build_charset.py --unihan <解压目录> \
    --corpus corpus/zongmu_wuyingdian_reference.txt --ocr-dict \
    --font <FS001.ttf> --font <FS002.ttf>
```

产出 `config/charset/`：

| 文件 | 内容 |
|---|---|
| `charset.ranges.tsv` | 合法字表，按**码位区间**存（十万级字表逐字存 1.5MB 且几乎全是连续段，区间形式 7 千行就够）|
| `variants.tsv` | 异体字 → 正字，2,727 条，带 provenance 列 |
| `report.json` | 各来源的规模与本书不可达率 |

### 字体只取 cmap，不取字形

`read_font_cmap()` 只读 cmap 表。**码位表是事实数据，字形外框才是受版权
保护的表达**——商业字体（如组织里的汉仪仿宋 FS001/FS002，带商业版权与
非商业授权限制）可以用来当字表来源，但它的外框不该进这个公开仓库。
将来做渲染模板时，模板本身也不应入库，应由本地字体现场生成。

字体家族常按平面拆成多个文件（FS001 = BMP，FS002 = 扩充 B–F，两者
**不相交**）。逐档报覆盖率会得出「FS002 漏了 99% 的常用字」这种荒唐
结论——家族的字表是各档的**并集**，脚本自动加一行 `font:*`。

### 异体字边的取舍

采信 `kSemanticVariant` / `kSpecializedSemanticVariant` / `kZVariant` /
`kTraditionalVariant` / `kSimplifiedVariant`。

**`kSpoofingVariant` 一律排除**——那是为防钓鱼域名而设的**形近易混字**，
不是异体字。把它当异体字会直接制造混淆。

默认 `--restrict-to-corpus`：只保留至少一端在语料里出现过的边。原因是
下游 `context_refine` 的「本版用字习惯」会把同语义组里语料最常用的表面
形**补进候选**，一条错误的异体边就等于往候选里注入一个错字。本书用不到
的异体关系留着只有风险没有收益。

### 正字方向按**本版语料频次**定

`pick_orthodox()` 的优先级是：语料频次 > 非简体 > 码位小。所以本版得到
的是 蓋→**葢**、略→**畧**、穎→**頴**、説→**說**（本版通篇用后者）。

这看着"反了"，但方向就该这样：语义层代表的唯一用途是给语言模型做统计，
用本版最常写的那个形当代表，n-gram 的计数才不会被同一个词分散到几个
表面形上。副作用是 `is_variant` 的含义变成「不是本版最常用的那个表面
形」，而不是「Unicode 意义上的异体字」——数据集文档里要写清楚。

**手工条目永远覆盖自动条目**：`config/dicts/variants.tsv` 里那 10 条是
人工确认过的，自动表无权改判。

## 二、语言模型混合：通用低权重 + 本书高权重

### 想法与实现

单一语料训不出好用的古籍 LM：通用古文语料量大但不认识本书的书名、
人名、术语；本书语料认识这些但量小。`InterpolatedLM` 把两者**线性
插值**：`p = Σ wᵢ·pᵢ`。

```bash
python -m open_guji_cv refine book9 \
    --corpus corpus/zongmu_wuyingdian_reference.txt \
    --general-corpus corpus/external/daizhige_zhaoling.txt \
    --general-weight 0.1 --lam 0.65
```

### 为什么是线性插值，不是对数线性

对数线性（几何）混合是 `Σ wᵢ·log pᵢ`：任何一个分量给出接近零的概率都会
把结果拖到零。通用语料没收录的本书专名**恰好就是这一类**，等于把混合
的收益全否掉。线性混合只要有一个分量给了质量，结果就有质量——这才是
「兜底 + 加尖」想要的行为。单测见 `test_lm_mixture.py`。

### 实测（context-correction，1,404 槽位，λ=0.65）

| 本书分量权重 | top1 | 增益 | 救回 | 改坏 | 有害翻转 |
|---|---|---|---|---|---|
| 0.00（纯通用）| 90.53% | +1.21% | 38 | 21 | 1.67% |
| 0.50 | 91.17% | +1.85% | 43 | 17 | 1.36% |
| 0.75 | 91.31% | +1.99% | 45 | 17 | 1.36% |
| **0.90** | **91.45%** | **+2.14%** | 45 | 15 | **1.20%** |
| 1.00（纯本书）| 91.03% | +1.71% | 41 | 17 | 1.36% |

基线 89.32%，headroom 5.20%（金标在候选里但不是首选）。+2.14% 吃掉了
headroom 的 41%。**混合优于两个端点。**

### 已接进生产（2026-08-24）+ 种子实集复验

本节标定已接线：`seeding.build_seed_lm` = 本书 3-gram **0.9** + 通用
**0.1** 线性插值，通用 LM（~10M 字，训 ~30s）按源文件指纹落盘缓存
（`corpus/external/.general_lm_cache.json`，gitignore）。seed CLI
`--general-corpus` 缺省自动发现 `corpus/external/*.txt`，传 `none` 关闭。

在种子队列实集（1681 真实槽位，候选含**库匹配证据**）上复验出一条
新纪律：**先验变强之后，无门槛全局重排在任何 λ 下净亏**（λ 0.10~0.95
全扫）。LM 的正确接法是 seed context 通道那样的**门槛化裁决**（语义
margin ≥ 0.70 才动手）：混合 +2.32%（救 41/坏 2），仍优于纯本书
（坏 10）与纯通用（救 30）两端。数字与量法见 pipeline_handbook「上下文
纠正第二轮基线」。

### 通用语料的体裁比体量重要

同为 500 万字，只换体裁（本书卷首是**上谕公文**）：

| 通用语料 | 纯通用 | 纯本书 | 混合（本书 0.9）|
|---|---|---|---|
| 诏令奏议 / 经世文编 / 政书 / 职官 | **+1.21%** | +1.71% | **+2.14%** |
| 儒藏 / 易藏（经解）| **+0.00%** | +1.71% | +1.64% |

经解语料对上谕页一点收益都没有，混合还略微拖后腿。**先问体裁，再问
体量。**

### λ 是有害翻转的主开关

`context_rank.LAMBDA` 是 OCR 项与 LM 项的配比（本书权重固定 0.75）：

| λ | 增益 | 有害翻转 |
|---|---|---|
| 0.75 | +1.28% | 1.04% |
| 0.70 | +1.64% | 1.04% |
| 0.65 | +1.64% | 1.44% |
| 0.55（旧默认）| +1.14% | 2.39% |
| 0.45 | +0.14% | 3.59% |
| 0.35 | **−1.07%** | 5.02% |

旧默认 0.55 给 LM 的话语权过大，有害翻转比 0.70 高一倍有余。`refine` 的
默认值已改成 **0.65**。继续降 λ 直接转成净负——**语言模型压过字形证据
就开始编字**。调纠正强度先动 λ，别先动权重。

### 这不是给自举 LM 平反

消融实验（见 `context_refine` 模块文档）证明自举语料（约 15% 识别噪声）
**单独**用作 LM 是净有害的。混合改变的是它的**用法**：噪声分量拿低权重、
且旁边有一个干净的大分量压着，才谈得上安全。本轮实测的两个分量都是干净
的外部文本，自举分量仍未验证，`--with-lm` 保持默认关闭。

### 两条纪律

**本书语料必须挖掉测试页。** 本书 LM 的语料就是本书整理本，而金标也是
从同一份整理本对齐来的。`eval_context_correction.py` 先剔除每个测试页的
金标窗口（前后各多挖 200 字）再训练，并**打印挖掉了多少字**；打印为 0
就是挖漏了，后面的数字一概作废。通用语料同样打印与测试页金标的 8-gram
重合率（当前配置 0.0）。

**字形层不可被语义层改写。** 纠正只允许在冻结候选内重排，不得引入候选
外的字。这是评测里的**硬断言**（`glyph_layer_immutability`），不是可以
用准确率换的参数。参考文本与语料多为正字化文本，放开这条就会把本版的
异体用字"改正"掉，破坏字形库的真实性。

## 三、外部语料怎么准备

```bash
python scripts/prepare_corpus.py --src <殆知阁 史藏/诏令奏议> --src ... \
    --out corpus/external/daizhige_zhaoling.txt \
    --max-chars 5000000 --max-per-file 50000 --to-traditional \
    --holdout corpus/zongmu_wuyingdian_reference.txt
```

三个要点：

1. **简→繁是用可控噪声换语料量。** 网上的大宗古籍语料多是简体转录本，
   而 opencc 简→繁是一对多（发→發/髮），必然引入错误。所以转换后的通用
   语料**只配拿低权重**。
2. **必须限单文件配额。** 不限时几部大部头就把配额吃光——实测 1,251 个
   文件只用上 32 个，语料看着有 500 万字，覆盖的却只是几种文体。
3. **泄漏检查是必做项。** `--holdout` 会打印最长公共子串与 8-gram 重合率。
   不接近零就换语料或剔文件，别心存侥幸。

`corpus/external/` 里的文件是**派生产物**（可由脚本重建），入库是为了让
上面那些数字可复现。

## 四、形近对消歧：上下文是这一类字的**主判据**

用户 2026-08-26 提的问题：入/人、日/曰、論/諭 这几对反复出现，
「即使他们有的时候匹配的是比较准确的，当然确实这个是非常容易弄混，
所以这个时候要借助上下文」。给的两条路——n-gram，和大模型直读——
拿 154 条人裁金标盲测过了，**两条都成立，而且差距远大于预期**。

测试集在 `open-guji-dataset/confusable-context`（题面、答案、首轮各臂
冻结基线都在里面），结果页
[artifact f06d703d](https://claude.ai/code/artifact/f06d703d-0dab-4950-b130-09c87ae18882)。

### 首轮结果（n=154，2026-08-26 二次核对后）

| 臂 | 真难档 n=32 | 送分档 n=122 | 合计 |
|---|---|---|---|
| 多数类基线 | 96.9% | 70.5% | 76.0% |
| 字形层 top-1 | 71.9% | 62.3% | 64.3% |
| OCR | 62.5% | 67.2% | 66.2% |
| **n-gram(3) 留出** | 87.5% | 97.5% | **95.5%** |
| **大模型（盲测）** | 93.8% | 100.0% | **98.7%** |

逐对看，用户点名那三对都治得了：**人/入**（类别均衡、OCR 掷硬币 50%、
字形 64%）两条上下文臂都到 95%；**論/諭** OCR 只有 11%——不是不准，
是系统性认反——n-gram 89%、大模型 100%；**日/曰** 大模型 100%。

### 三道泄漏防线（不做这三条，数字全是假的）

1. **金标只收人裁。** 自动进库的字多数由整理本锚定，拿它当金标去考一个
   在整理本上训练的 LM，等于开卷考。
2. **参照文本也要挖空。** 管线「没锚上」≠ 整理本那一位是空的——实测
   43 条难档里仍有 12 条参照文本直接写着答案。
3. **n-gram 必须报留出口径。** 不剔测试原文时送分档是 **100%**，那是背
   下来了不是学会了；剔掉降到 95.9%，两者的落差就是记忆的贡献。

### 已/巳：第一版「治不了」是错的——金标本身被字形污染了

第一版（2026-08-26 上午）实测已/巳这一对所有臂都卡在 62~69%，写成了
「这一对压根不该问上下文」，还举了实锤：`[016]`「實在流傳**巳**久」
金标 巳、`[059]`「實在流傳**已**少」金标 已——语境同构而金标相反。

**这个结论本身是错的**，用户看完之后指出问题：「我之前手动判断的时候，
其实有一些是以字形为准的」。核对发现 13 条人裁金标里 4 条正是这样
判的——「實在流傳巳久」「書籍巳屬不少」这类明显是「已经」语义的位置，
被判成了「巳」，纯粹因为刻本上那一笔是封口的，不是因为文意需要一个
地支/专名。`[016]` 那条实锤本身就是这么来的：align.char 早就给了「已」，
人只是照着字形把它翻了过去。

**用户裁定：录入时一律以上下文文意为准，字形不重要**，并要求把此前
按字形判的改回来。用 `scripts/correct_admission.py`（新写，改判已入库
人裁字位的工具——`admit_instance()` 是幂等闸不是改判口，改已入库的
要显式改 `instances`/`admissions`/`glyphs.n_confirmed`/`exemplars` 四张
表）逐条核对 align/图块改判：

* `vol01:7:5:20`、`vol01:8:2:11`、`vol01:9:9:10`、`vol01:14:2:18`：
  巳→已（文意/align 双证，或至少文意单证时无更优解）
* `vol01:21:3:19`：巳→**己**——align.ref_char 本来就是「己」（「則因
  己身」，因己身服药经年，语义比因已身/因巳身都通顺），图块目视核对
  底部钩画开口未封也更像己。**这条超出已/巳二元对立**，不算进这个
  pair，出了测试集。

改判后重测（已/巳，n=12）：

| 臂 | 准确率 |
|---|---|
| 多数类基线 | 100%（这批样本碰巧全是「已」）|
| 字形层 top-1 | **67%**（低于多数类基线——字形在这里是负资产）|
| OCR | 92% |
| n-gram | 83% |
| 大模型 | 92% |

字形层不但没赢，反而**输给瞎猜**——这才是当初「治不了」结论的真正
成因：不是上下文方法不行，是拿被字形污染的金标去考它们，考卷本身
就是错的。

**这批样本多数类基线 100% 是巧合，不是「已/巳 已解决」。** 巳仍有真实
存在的场景（干支纪年纪日），这 12 条恰好没碰上；等审到真正的巳用例，
才能验证上下文方法能不能正确转向。

### 己/已/巳 混用的历史考据

用户问：「这个古人对己已巳的用法似乎和现在不一样……有没有什么在某个
朝代特定的用法？还是说大家都知道，估计里就是在随便混用？」查证结果：

**不是某朝代的特定规矩，是校勘学里一个老问题，且恰好命中我们这套版本
系统本身。** 已/巳字源上本来就是同一个字（甲骨文同形，段玉裁：地支
「巳」久已用为「已然」之「已」，「已」是从「巳」分化出来的后起字）。
现代课堂教的「己不封口、已半封口、巳全封口」是**今人总结的辨认口诀，
不是古人的书写规矩**——古代刻工压根没把它当回事。北师大出版科学研究
院的校对研究直接点名：宋元刻本（汲古阁藏本）已经混，**清代《欽定四庫
全書》本——己已巳仍然混用**，光绪翻刻本也混。四库馆本身有《功过处分
条例》专门追责誊录讹字，都没能把这三字挑出来单独整顿——说明当时的人
根本不觉得这是错，两个字形共享一个身位，随手写哪个都行。

己不一样——它是**真的另一个字**（自己 vs 已经/地支），不是同词异写。
`vol01:21:3:19` 实锤过己被错认成巳（align 与图块目视双证）。

### 落地：已接进生产准入规则

用户裁定分两层：

1. **过去判错的要纠正**（已完成，见上）。
2. **以后怎么录入**——「在第三层这个大语言模型或者是n gram这一层，
   尽量的自己去判断，根据语义来判断，当语义不清楚的时候才叫有人来
   判断」。

`open_guji_cv/clustering/seeding.py` 新增 `SEMANTIC_MERGED_PAIRS`
（当前只有 `{("已","巳")}`，narrow 集，不等于 `NEAR_FORM_CHARS`）：
上下文通道的 near_form 护栏加了一条例外——命中的字若在这张表里，不拦，
照走 `ctx_decider` 按文意判断，margin 过阈（默认 0.70）才自动进库，够
不着阈值仍然人审（安全阀没关：真正拿不准的位置照样落回人）。字形层
`NEVER_MATCH_FAMILIES`（`GlyphMatcher` 用，防止**形状判据**自己会认错）
完全不动——`match.py` 同时补了 `("己","已")`、`("己","巳")` 两对（防
21:3:19 那类错），但**没有**进 `SEMANTIC_MERGED_PAIRS`：己是真的另一
个字，上下文通道对它照样要拦。

单测 `test_semantic_merged_pair_context_bypasses_near_form`
（`tests/clustering/test_seeding.py`）覆盖：near_form + signal_conflict
+ replace_align 三条疑问全命中的场面（换作表里任何别的形近字这里就该
卡人审），只因为字属于 SEMANTIC_MERGED_PAIRS 就照走 context 通道

### 字形与释读必须分开存——不能用同一个字段改（2026-08-26 补）

第一版落地时踩了自己定的规矩：改判 4 条已/巳实例时，把 `instances.label`
（`GlyphMatcher`/`glyphs`/`exemplars` 的**字形索引键**）也一并改成了
「已」。用户看完后指出问题：「校对古籍的时候字形是什么我们就录什么，
但这是特殊情况，只有这三个字按语意改」——这句话里藏着一个此前没分清
的区别：

* **释读（reading）**：这个字位「说的是什么」，人/context 通道判的就是
  它，只有已/巳/己 这三个字允许它偏离字形（其余所有字，释读=字形，
  diplomatic transcription 是唯一规矩，绝不因「觉得该是别的字」改）。
* **字形（shape）**：刻本上实际刻的形状，进 `GlyphMatcher` 的匹配索引。
  **这个字段永远照录，连已/巳/己 也不例外**——字形层的 near_form 护栏
  本来就是防「形状判据自己会认错」，如果连字形库本身都被释读污染，
  未来一个真的刻成同一形状、该读别的字的实例会**错误继承这次的释读**，
  字形匹配整条链就失真了，等于自己拆自己刚立的护栏。

**改法**：`GlyphDB.admit_instance()` 新增 `shape` 形参（缺省 = `char`，
绝大多数调用不受影响）——`char` 走 `admissions.char`/`instances.semantic`
（释读），`shape` 走 `instances.label`/`glyphs`/`exemplars`/
`unicode_cp`（字形索引）。`seeding.py` 的 SEMANTIC_MERGED_PAIRS 分支
现在这样定字形信号：**优先用 OCR 的原始识别**（它是纯视觉分类器，
不掺文意判断，`vol01:8:2:11` 那类实锤里 OCR 认的形状信号往往和最终
釋讀不同，恰恰是这个字段该存的东西）；OCR 缺失或不在家族里时才退回
释读本身（没有独立形状信号，不引入分岔）。`scripts/correct_admission.py`
同步改写：现在**只碰** `instances.semantic`/`admissions.char`，绝不碰
`label`/`glyphs`/`exemplars`——早先误伤字形库的 4 条实例已用一次性
脚本撤回（`label` 复原为改判前的原字，`semantic`/`admissions.char`
维持改判后的释读不动）。

单测 `test_semantic_merged_pair_context_bypasses_near_form`
补了字形/释读分岔的断言：`instances.label`=OCR 给的形状信号、
`instances.semantic`=释读、`admissions.char`=释读、且这个实例**不会**
出现在释读字符的字形示例（exemplars）里。

**审查页也补了提示**（`open_guji_cv/clustering/review/seed_export.py`）
——`_render_evidence` 遇到 near_form 且候选里含已/巳 时，把疑问说明
换成「候选里有已/巳——这两个字史上就是同一个词的两种写法，字形不重要，
直接按文意选，不用管封不封口」，直接把答案摆出来，省得用户对着图块
纠结封口不封口——这是唯一允许「字形不用管」的例外，其余形近字家族
（大/太、諭/論……）字形照样重要，提示语不跟着换。单测
`test_semantic_merged_pair_gets_shape_not_important_hint`
（`tests/clustering/test_seed_export.py`）覆盖两种情形都对。
