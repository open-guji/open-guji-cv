# 全书跑批与「共享字形库」的指纹冲突（2026-09-06/07 实测）

> 三次尝试让 vol02 全书收敛（九步全新鲜）都没成，原因不是 bug，是**机制上的**。
> 记下来，免得下次再花一晚上重演。

## 现象

`--pages all --from glyph_match` 跑完、退出码 0、日志显示 752/752 全成功，
但 `guji status` 立刻报 `seed_admit 过期 188`。反复跑三轮，每轮结束都过期。

## 根因：库指纹按 **mtime** 算，而库是**全书共享**的

`steps/glyph_match.db_fingerprint`：

```python
raw = f"{st.st_mtime_ns}:{st.st_size}:{exemplars 行数}"
```

`glyph_match` 的 `params_hash` 含它，`seed_admit` 也自带一份（v1.4 起为了让人裁
进库能触发重跑）。于是：

**任何一次对 `output/glyph.db` 的写入，都会让所有册、所有页的这两步立刻过期。**

而写库的路径很多，且都是正常操作：

- 控制台提交裁决 → `glyphdb_admit` 消费者写库；
- 别人跑 `seed_admit`（哪怕是**另一册**）；
- 库自洽审计撤例、`seed-ingest` 等维护脚本。

2026-09-07 09:55 实测：另一会话在跑 **vol01** 的 `--from glyph_match --force`，
与我的 vol02 **产物毫无交集**，但它的 `seed_admit` 一写库，我这边 vol02
188 页全部过期。

## 这不是纯粹的误报

库确实是共享的：vol01 新进的刻例会进入 vol02 的匹配候选。所以「库变了 → vol02
的匹配结论可能变」在逻辑上成立，指纹没说错。**但它使得「全书收敛」在有人审阅时
不可达**——审阅本身就在改库，而审阅是这条线的日常。

## 结论与对策

1. **别把「九步全新鲜」当成常态目标**。它只在「没人审阅、没人跑别的册」的静默窗口
   里可达。要全书数就挑这种窗口跑，或接受快照口径。
2. **取数不必等全书收敛**。判据是按页算的，只要**那批页**是用当前库算出来的就有效。
   jz 集 22 页的数就是这么取的（0.34% 夹注人审率），完全可信。
3. **起长批前查一下有没有别人在跑**（含别的册）：

       Get-CimInstance Win32_Process -Filter "Name='python.exe'" |
         Where-Object { $_.CommandLine -match 'pipeline' }

4. **别去杀别人的跑批**——那是别的会话正在做的活。停自己的。

## 如果要根治（没做，留给以后）

指纹改成**按内容**而非 mtime：例如只哈希「本册用得到的字种集合 + 各字种的
exemplar 数」，vol01 加了 vol02 用不到的字就不该让 vol02 过期。
代价是每次算指纹要查库（现在只 stat 文件），得权衡。
在没人抱怨之前不值得动——本条只记清楚现状，不改。
