# 字形库优先的增量识别：G3/G4/G5 合并重设计（2026-08-23）

## 0. 一句话

不再「先聚簇、再给簇定字」，改成**「字形库优先」**：每个新图块先与
已验证的字形库匹配——完美匹配直接继承 Unicode（识别完成）；不完美
匹配取多候选、补 OCR、交上下文裁决；裁决后的结果回灌进库，库随阅读
增长。聚类从「不可逆的上游步骤」退化为「匹配到同一库条目」的副产品。

## 1. 为什么改（全部有实测支撑）

**簇级定字的结构性风险已经发生过。** glyph_store 的 94 个「人工」标签
全是簇级确认后传播给成员的（label_status=propagated），逐张复核 11 个
错（11.7%）——一个脏簇就把错标撒给全簇。簇一旦聚错，纠正要连根重来。

**几何聚类已贴到 purity 硬约束的墙上。** g3g4_error_analysis.md 的结论：
形近字对与同字对在任何全局相似度下分布重合，coverage 判据 + 严操作点
(0.992, 12) 是 never-make-worse 的极限；剩余碎片率（3.0~3.5）躺在
unsure 带里，几何上无解，本来就要靠候选+上下文/人工去解——**那为什么
不把候选+上下文放进主干，而把不可逆的合并请出主干？**

**字形库优先的可行性已模拟验证**（char-clustering 金标分片，逐页增量，
匹配 = HOG kNN(10) + verify_pair_cov 完美档 (0.992, 12)）：

| 场景 | 完美匹配覆盖率 | 匹配精度 |
|---|---|---|
| vol02 册内增量（库从 0 长起）| 16.5% → 后半段 19.9% | 99.60% |
| vol01 册内增量 | 11.0% → 14.3% | 99.7~100% |
| vol02 查询 + vol01 当种子库 | **23.0% → 24.3%** | 99.57% |

三个场景的全部「错配」都是已知数据问题而非匹配错误：二/一 =
归一化吃笔画实锤实例（vol02:157:2:4）、彖/象 = 标签歧义、詳/羣 =
已知标签错、注/註 = **异体字**（语义层同字，字形层匹配没错）。
**净匹配错误率 ≈ 0。** 覆盖率随库规模单调涨：跨册种子立即 +7pt，而
模拟库只有 ~20 页；全书 200 页 + 前 11 册积累后，常用字每字几十个
已验证刻例，完美命中率会显著高于 24%。

## 2. 架构

```
                     ┌──────────────────────────────────────────┐
                     │            字形库 GlyphDB（真源）           │
                     │  (归一图, surface char, semantic char,    │
                     │   provenance, evidence)  ←──────┐        │
                     └───────────┬─────────────────────│────────┘
                                 │ kNN(HOG) 取候选       │ 回灌（带准入门槛）
  切分图块 ──归一化──→ 新实例 ──→ verify_pair_cov 三档 ──┤
                                 │                     │
              ┌──────────────────┼──────────────┐      │
              ▼ same（完美匹配）   ▼ unsure        ▼ diff │
        继承库条目的字        候选集 = unsure 命  OCR top-k │
        （识别完成，记        中的字 ∪ OCR top-k  + s2t    │
         匹配证据）          + s2t              │        │
              │                  └──────┬───────┘        │
              │                         ▼                │
              │                 上下文/LM 裁决（M5/refine）│
              │                    │           │         │
              │              margin 高       margin 低    │
              │                    │           ▼         │
              └────────────────────┴──→ 审查队列（M6）──→ 人工
                                   全部路径的定字结果──────┘
```

三档判决沿用 `verify_pair_cov` 现有语义，**一行判据代码都不用改**：

| 档 | 条件（现操作点）| 动作 |
|---|---|---|
| same | cov ≥ 0.992 且 wmax ≤ 12 | 继承匹配条目的 surface char；记录 (匹配条目 id, cov, wmax) 为证据 |
| unsure | 0.85 ≤ cov < 0.992 | 命中条目的字进候选集（带 cov 当先验），与 OCR top-k+s2t 合并 → 上下文裁决 |
| diff | cov < 0.85（对全部 kNN 候选）| 纯 OCR+上下文；可能是库中没有的新字 |

## 3. 库的准入与治理（本设计的命门）

传播错标的教训 → 三条纪律：

1. **逐实例证据，不做盲传播。** 每个实例永远带着自己的判定路径
   （匹配了哪个条目/候选来自哪/上下文 margin 多少）。库条目改判时，
   只需重放**匹配过它的实例**——纠错局部化，不再连根重来。
2. **准入分级**（provenance，从高到低）：
   - `human`：审查确认（现有 review 流程）；
   - `context`：上下文裁决且 margin ≥ 阈（阈值由 context-correction
     测试集标定）；
   - `align`：整理本对齐（equal 层 + 采信闸后的 replace 层）。
   完美匹配**只继承**，不提升 provenance；一个实例要成为**新库条目**
   （而非普通成员），须 `human` 或高 margin `context`。
3. **形近否决表随库走。** cluster_leak 家族（諭/論、大/太、間/問…）
   作为库级 never-match 对：这两族字的条目互相永不做 same 判定，
   强制走候选+上下文。几何判据打不过的敌人交给语义层，不硬扛。

条目结构沿用 glyph_store schema（char/semantic/unicode_cp/provenance），
异体字（注/註 类）按现有纪律处理：匹配发生在**字形层**（surface），
语义归并交给 VariantMap——模拟中的 注/註「错配」正是字形层的正确行为。

### 3.5 首批进库（种子）协议：双信号 + 人工审查，逐页推进

库优先架构的一切建立在「库里的字是对的」上，所以种子的准确性是
100% 目标而不是统计目标。可用的两个独立信号源，**单独都不保证对**：

- **OCR 信号**：逐块 RapidOCR top1 + s2t（ocr_carrier）。book9 金标实测
  单独 88.75%，且 PP-OCR 字表缺 40% 传承字类型（彖 这类字它永远给不出）。
- **整理本信号**：用户提供的高质量整理本 TXT，经 align_label 8-gram 锚定
  + 采信闸（replace 段 ≤3 且两侧 equal≥2）对到每个字位。质量相当高但
  **不保证完全对**（整理本自身的错、异体字取舍、对齐窗口错位都可能）。

**双信号一致 = 强信号**：OCR 结果与整理本对齐字相同（s2t/VariantMap 归一
后比较）。两个信号错的方式不相关——OCR 错在形近/字表缺字，整理本错在
录入/版本差异——同时错到**同一个错字**上的概率极低。vol02 实测 purity
0.99934 的标签层再叠 OCR 一致过滤，抽检未见反例。

**疑问判定（任一命中即入审查队列，不入库）**：

| # | 触发条件 | 为什么可疑 |
|---|---|---|
| 1 | OCR ≠ 对齐字（归一后仍不同）| 双信号打架，必有一错 |
| 2 | OCR prob 低（阈值在 char-ocr 集上标定）且无整理本对齐 | 单信号且弱 |
| 3 | crop_quality 判 degraded（残留/截断）| 图块本身可能不是完整的字 |
| 4 | 字属 never-match 形近家族（諭/論、大/太…）| 两个信号源都容易在这里犯**同样的**错 |
| 5 | 与库内**同字**已有条目做 verify 全为 diff | 库内不自洽：要么这个错、要么库里那个错 |
| 6 | 对齐来自 replace 层（即便过了采信闸）| replace 本来就是 OCR 与整理本不一致的位置 |

**流程（逐页往前推进）**：

1. 取下一页，每个字位跑双信号 + 疑问判定；
2. 无疑问（双信号一致 + 六条全不命中）→ 以 `align` provenance 直接进库；
3. 有疑问 → 进该页审查队列，**用户逐条裁决**；确认后以 `human`
   provenance 进库（永不因为「大概率对」跳过审查）；
4. 本页清完再进下一页——前页的库立即为后页服务（完美匹配命中的字位
   直接继承，疑问越来越少，审查负担随库增长单调下降；模拟已证覆盖率
   16%→24% 的增长曲线）。

**下一阶段（本流程跑通后）改审查交互程序**，需求清单：

- 按页组织审查队列（当前按簇/按缺陷类型）；
- 每条展示：图块原图 + 归一图、OCR top-k（带 prob）、整理本对齐字
  （带对齐 op：equal/replace）、命中的疑问条目编号、库内同字最近邻
  （若有）及其 cov；
- 单键操作：确认候选之一 / 手输正字 / 标记非字（DROP）/ 存疑跳过；
- 确认即写库（`human` provenance）并即时对后续字位生效；
- 页完成度与全书推进度可视。

## 4. G3/G4/G5 各自去哪了

| 原步骤 | 新角色 | 变化 |
|---|---|---|
| G3 归一化 | 不变，仍是入口纯函数 | P3 缺陷修复照旧（吃笔画 bug 直接影响匹配精度，优先级升高）|
| G4 聚类 | **退出主干**。匹配到同一条目 = 隐式聚类；显式 clusterer 保留为离线工具：审查蒙太奇、unsure 带挖掘、新册冷启动时的批量预分组 | verify_pair_cov / 特征 / kNN 全部复用，只是不再做不可逆合并 |
| G5 候选+识别 | **进入主干**，是 unsure/diff 档的一等分支 | GlyphKnnSource 从「候选来源之一」变成主匹配器；RapidOcrSource 为补充 |
| G6 上下文 | 不变，是 unsure/diff 档的裁决者 | margin 阈值多了一个用途：库准入 |
| M6/M7 审查回灌 | 不变 | 审一条 = 一个高置信库条目 + 命中过它的实例批量解决 |

**渐进落地，不推倒现有管线**：cluster→label 流水继续可用；新增
`recognize` 命令走库优先路径，两者在同一测试集上对比，赢了再切主干。

## 5. 评测体系怎么改（测试集几乎全部复用）

| 数据集 | 新角色 | 指标 |
|---|---|---|
| char-clustering 分片 | **库匹配基准**：库/查询切分（册内增量 + 跨册种子两种协议）| `match_coverage`（完美档覆盖率）、`match_precision`（**硬约束 ≥0.999**，替代 purity 的位置）、覆盖率-库规模曲线 |
| hard_pairs | 不变 | diff 对 = 库级 never-match 回归；same 对 = unsure 档召回 |
| char-normalization | 不变（回归门）| 不变；吃笔画类缺陷升 P0（直接毒化库）|
| char-ocr | unsure/diff 分支基准 | top1/top5 不变 |
| context-correction | 裁决者基准 + **margin-准入阈标定集** | 新增：margin 阈下的准入精度 |

模拟脚本的协议就是基准协议：逐页增量、gold 进库为上界；实跑用
context-margin 准入后重量一次，差值就是「裁决分支的贡献」。

## 6. 风险与对策

1. **库越大，形近误配机会越多。** 对策：never-match 表 + 完美档只认
   (0.992,12)（对级 1932 对实测零误配）+ 上下文对 same 档也做低成本
   校验（现有 check_cluster_consistency 改成 check_match_consistency）。
2. **效率。** 每实例 kNN(10) + ≤10 次 verify ≈ 聚类同量级（已有并行
   预计算）；库大了 kNN 用 GlyphDB 的 SQLite 索引 + 每字保代表刻例
   （medoid + 极端例，沿用 n_reps 思路）控制候选池。
3. **冷启动。** 新册/新版本：先跨册种子（+7pt 起步），OCR+对齐兜底；
   前 11 册有整理本，align 层可持续供种。
4. **库条目错了怎么办。** 逐实例证据 → 改条目、重放其匹配列表即可；
   这正是相对簇级传播的核心优势，要在实现里守住（不许出现「继承后
   丢弃证据」的捷径）。

### 7.2 自动通道全谱（vol01 前 11 页 6~12 轮实审逐步定型，2026-08-24；
2026-08-27 补 match_replace/match_ref_weak/match_solo_ocr/match_margin
四条 + near_form 护栏两处松绑）

用户 2600+ 条真实裁决把最初的「零疑问才自动」扩成十条通道。**OCR 的
置信度不参与任何自动判断**（实测 100% 也照样认错形近字），它只供审查
候选；例外是 match_solo/match_solo_ocr 的残差窗防线用它的**字符**读数
当第二证据。

| 通道 | 条件 | provenance | 标定依据 |
|---|---|---|---|
| 常规 | 过闸对齐 × 载体一致 + 六条疑问全不命中 | `align` | 协议原案 |
| dual_degraded | 双信号一致 + 仅 degraded_crop | `align` | 实审 58/58 全准 |
| match_ref | 库 verify same × 整理本同字（语义层比），near_form 也放（33/33）| `align` | 进库字取**库匹配形**（「之」页 OCR 报「芝」实锤：无对齐时 proposed 曾误取 OCR 字）|

### 7.4 字体字形当兜底候选源（2026-08-24 接线，实测）

两套开源字体（I.Ming 传承字形 56,778 字 / Jigmo CC0 全覆盖 98,682 字）
按 glyph_db_expansion_research §0 的分层结论接入：**只做语义候选层**。

**为什么不能更进一步**：字体形与刻本形的相似度分布重叠——bench
`separable=false`，字体检索 recall@1 仅 21%。拿阈值定生死是不可能的，
只能"把正确字带进候选集"，让整理本与上下文 LM 去裁。

**只在刻本库弱时查**（529 条人审难例分层实测）：

| 刻本库档 | 字位 | 现有候选已含金标 | 字体@10 | 字体能救 |
|---|---|---|---|---|
| same / ≥0.99 / ≥0.98 | 119 | **99~100%** | 33~67% | **0** |
| ≥0.95 | 165 | 79% | 63% | 22 |
| **<0.95** | 215 | **44%** | 49% | **63** |
| 无候选 | 30 | 67% | 43% | 3 |

库强的层现有候选已经含金标 99~100%，查字体是白花钱还添噪声；增益全部
来自库弱的层。故 `FONT_COV_GATE = 0.95`。

**决策层 A/B**（382 条锚定页人审难例，211 格触发查字体）：

| | 定字对 | 门槛进库 | 其中对 | 门槛精度 |
|---|---|---|---|---|
| 不查字体 | 357 | 247 | 245 | 99.2% |
| 查字体 | 362 | 260 | **258** | 99.2% |

**定字对 +5、门槛进库对 +13、错 +0**，精度不变。第 14 页真管线重播：
137/163 自动（84%），其中 12 格查了字体库。

三条纪律钉在 `seeding.FONT_*` 注释与单测里：① 永不参与准入裁决
（`admission_decision` 根本没有字体入口，是**接口层**保证）；② 只在
`cov < 0.95` 时查；③ 权重 0.6 低于任何真证据（库 3.0 / 语料 2.5 /
OCR 1.5）且按检索名次衰减。字体库进 `glyph_store/glyphdb.sqlite`
（gitignore，`glyph-db import-font` 一键重建），与进库用的
`output/glyph.db` 物理隔离——刻本库只进真实刻本字形。

**踩到的坑**：合并 main 的新切分后，OCR 载体（旧 164 格）比索引
（新 163 格）多一条，`carrier_slots` 不核对索引就把整列文本后移一位
——锚定照样"成功"、采信闸全灭、**不报任何错**，整页看着像"没锚定"
（第 14 页过闸对齐 162/180 → 0/163，自动率 82% → 38%）。已修：
`carrier_slots(valid_ids=...)` 丢掉索引里没有的格并告警，seed 侧传索引
id；两条回归单测钉住。**凡是重跑过切分的册，载体必须一起重建。**

### 7.3 三信号交叉分析：什么时候能自动（2026-08-24，529 条人审回放）

把用户人审的 529 条**难例**（简单的早被自动收走，故这里的准确率是
**下界**）按信号组合回放，量出三条结构性事实：

**一、三路信号可信度极不对称**

| 信号 | 覆盖 | 难例准确率 |
|---|---|---|
| OCR | 每个字位 | **45.0%**（置信度也不可信：「人/入」那条给了 0.95 仍错）|
| 整理本·过闸对齐 | 锚定页 | **95.8%** |
| 整理本·免闸参考 | 锚定页 | **94.8%**（几乎与过闸持平，此前几乎没利用）|
| 库 verify same | 库里有此字 | **100%**（27/27）|
| 库 top 候选（不分档）| 库里有此字 | 50.1% ← 库不是一个信号，是一条**可信度曲线** |

库匹配按 cov 分档：same 100% / ≥0.99 100%（9/9）/ ≥0.98 **95.2%**（4 条
错例）/ ≥0.95 68.5% / <0.95 10.2%。**0.99 是实测拐点**，印证了
MATCH_SOLO_COV 从 0.98 上调的裁定。

**二、要害不是准确率，是误差相不相关**

| 两信号一致时 | n | 准确率 |
|---|---|---|
| OCR × 整理本 | 118 | **100%**（误差源独立：OCR 错在形近，整理本错在录入）|
| 整理本 × 库 top | 144 | **100%**（文本证据 × 形状证据，同源性为零）|
| OCR × 库 top | 138 | **97.1%** ← **不能当双信号** |
| 三者全一致 | 49 | 100% |

那 4 条 OCR 与库一齐说错的：已/巳（cov 0.949）、人/入（0.905，OCR 0.95）、
日/曰（0.957）、今/全（0.883，图块被界行侵入）。**四条的整理本全是对的**
——OCR 与库被同一批形近字骗，这是它们共同的盲区。

**三、落地：match_ref 通道放宽（R2）**

据此把库 × 整理本通道从「库须 verify same + 整理本须过闸」放宽到
**「库 top 候选与整理本（含免闸参考）语义一致」**——144/144 全对。
回放 1694 个已定字位：自动率 **69% → 77%**，少 144 条人审。

near_form 仍拦本通道：命中里的 33 条形近字虽全对，但 n=33 撑不起拆
护栏，而上面 4 条反例恰恰全出在这一族。留待更大样本。

**四条可以背下来的原则**

1. 整理本在场时它有一票否决权（4 条 OCR×库 错例它 4/4 全对）；
2. OCR 只供候选，置信度不参与任何自动判断；
3. 库匹配按 cov 分档采信，0.99 是拐点；
4. 凑双信号要挑**误差独立**的两路——文本 × 形状可以，OCR × 形状不行。

确认 483 + 仅定字 46、非字 32、跳过积压 4、待审 186（第 11 页 157 +
第 14 页 29）。库 1648 例 / 607 字（align 1106 / human 473 / match 56 /
context 13）。
