# Step 5 / Step 6 的 benchmark 怎么定义（2026-09-04）

> 用户问：「Step5、Step6 的 benchmark 怎么定义，是否需要建立测试集，尤其是引入
> 一些新算法之后。」本文回答三件事：**量什么**（指标）、**拿什么量**（测试集）、
> **新算法进来时怎么保证数字还能比**（冻结与分层纪律）。
>
> 配套：`pipeline_review_2026-09-04.md`（瓶颈与四刀 A-D）。

## 0. 一句话

**Step 5/6 不该有"一个准确率"**。这两步的产物是**候选 + 一个是否敢自动放行的决定**，
所以要两组正交的指标：**候选质量**（召回，决定人能不能在候选里点到）和
**放行质量**（精度 + 覆盖，决定人要点多少次）。测试集大体够用但有**三个真缺口**，
其中最要命的一个是：**现有 Step6 实集在 p4-p14，而 dev_set 在另外 11 页，
只有 29 个槽位重叠**——A-D 四刀的效果，现有测试集量不出来。

---

## 1. 为什么不能只报一个准确率

Step 5/6 的输出不是"这个字是什么"，而是一个三岔决定：

```
自动放行（进库、进文本）  ←  必须几乎不出错，错了会毒库
落人审队列              ←  越少越好，但漏放行只是慢，不是错
判非字 / 弃权            ←  第三态，不能算进准确率的分母
```

拿单一准确率量它会同时掩盖两种相反的失败：闸开太大（错误进库）和闸关太死
（人审爆炸）。**必须成对报**，这与 handbook「比值要连着分母读」是同一条纪律。

还有一条口径陷阱：**自动放行的准确率天然虚高**——放行的本来就是容易的那批。
所以任何"自动放行 100%"都必须连着**覆盖率**一起读，且**人审集要单独报**。
本项目现在是 92.1% 自动 / 放行对金标 100%，这两个数缺一个都没意义。

## 2. 指标定义

### 2.1 Step 5-a 字形库匹配（`glyph_match`）

| 指标 | 定义 | 现值 | 硬约束 |
|---|---|---|---|
| **match_precision** | 判 `same` 的字对里真同字的比例 | 1.0000 | **≥0.999**（毒库防线，不可退让）|
| match_recall@P≥0.999 | 上述精度下能判 same 的真同字对占比 | 0.40（闸 0.986）| 越高越好 |
| **rank@1 / rank@5** | kNN top1 / top5 命中金标字 | **99.5% / 99.8%** | 这是**候选**指标，与闸无关 |
| unsure 带占比 | 判 unsure 的比例（要人或其他证据兜） | 人审集 127/152 | 越低越好 |
| **near_form 拦截召回** | 真形近对里被护栏拦下的比例 | 表内 100%、表外 0 | IDS 护栏后应 →1 |

**rank 与 precision 必须分开看**，这是本项目最容易搞混的一处：库的**排序**几乎不错
（99.5%），错的是**置信闸**。只报 precision 会以为库很强，只报 rank 会以为可以直接
采信。两个都报才看得出"该改闸，不该改算法"。

### 2.2 Step 5-b OCR 候选（`ocr_candidates`）

| 指标 | 定义 | 现值 |
|---|---|---|
| top1 / top5 | 对金标 | 84.5% / 91.7% |
| **字表不可达率** | 金标字不在识别字表里的字次占比 | 1.20%（扩展后）|
| **候选召回@k** | 金标字落在 top-k 的比例（**这才是 OCR 在本项目的真指标**）| top5 91.7% |

OCR 在本项目**永不投票**（97.1% 那条老账），所以 top1 只是参考，**召回@k 才是它的
KPI**。换 PP-OCRv5/v6 要看的就是召回@k 和不可达率，不是 top1。

### 2.3 Step 6 上下文裁决（`context_decide`）

| 指标 | 定义 | 现值 | 纪律 |
|---|---|---|---|
| **top1_gain** | 相对"不用上下文"基线的净提升 | +2.32% | 必须连 harmful_flip 一起报 |
| **harmful_flip_rate** | 把本来对的改错的比例 | 1.20% | **单独报，不许并进 gain** |
| 门槛后精度 | margin ≥ 阈时的准确率 | 303 条实审全对 | |
| 门槛后覆盖 | margin ≥ 阈的比例 | 249/1933 | |
| **弃权率** | margin 不足而弃权 | 129 条人审因它 | 弃权不是错，但要量 |

形近对单列（`confusable-context` 154 题）：n-gram 95.5% / 大模型 98.7% /
字形层 64.3% / 多数类基线 76.0%。**必须带多数类基线**——字形层 64.3% 低于瞎猜
76.0%，不带基线就看不出这一层是负贡献。

### 2.4 端到端（这才是用户关心的）

| 指标 | 定义 | 现值 | 目标 |
|---|---|---|---|
| **人审率** | 需要人点的字位 / 全部字位 | 7.9% | **≤1.5%** |
| **自动放行错误率** | 自动放行里判错的比例（双真值）| 0/1619 | ≤0.1% |
| **每条裁决耗时** | 中位数 | **无基线**（事件 ts 是收割时间）| 常规 ≤3s |
| **生僻字 top-10 命中率** | 用户最终定的字在候选 top-10 的比例 | 现 14 条完全没有 | ≥80% |

前两个是一对（不可分开看），后两个是 A-D 的直接验收标准。

## 3. 测试集：有什么、缺什么

### 3.1 现有（`open-guji-dataset/`）

| 分片 | 规模 | 状态 | 能量什么 |
|---|---|---|---|
| `glyph-match/pairs` | 67,965 对 | 实集 | match_precision / recall |
| `glyph-match/triplets` | 193 组 | 实集 | 排序（hard 0.5143）|
| `char-clustering` | 3 分片 | 可用 | 聚类 purity |
| `context-correction` | **1,681 槽位**（p4-p14，候选冻结）| 实集 | top1_gain / harmful_flip |
| `confusable-context` | **154 题**（人裁金标 + 冻结各臂）| 实集 | 形近对消歧 |
| `char-ocr` | **0**（空框架）| 框架 | — |

### 3.2 三个真缺口

**缺口 1：Step6 实集与 dev_set 几乎不重叠 —— 这是最要命的一个**

`context-correction` 在 p4-p14，dev_set 是 p11/21/24/26/33/42/47/60/70/137/141/151。
**只有 p11 的 29 个槽位重叠**；`confusable-context` 154 题里落在 dev_set 的只有 19 题。

后果：**A-D 四刀的效果，用现有测试集量不出来**。而 dev_set 上有的是：
- 整理本自动金标 1,619 条（`gold/v2_align`，A 刀之后可涨到 1,897）；
- **用户 273 条裁决**（独立真值，与整理本无关）。

所以 dev_set 现在**事实上就是** Step5/6 的主测试集，只是没被登记成一个分片。

**缺口 2：`char-ocr` 是空的**

换 OCR 引擎（PP-OCRv5/v6）没有验收集。但这个缺口**可以零成本补**：dev_set 的
1,897 条整理本金标 + 字块，直接就是 char-ocr 集。

**缺口 3：生僻字没有任何测试集**

L1/L2/L3 要量 top-10 命中率，而现在**一条金标都没有**。种子已经现成：用户 127 条
裁决里系统三路都没给出的 **14 条**，加 dev_set 里语料频次 ≤3 的 **29 条**。

### 3.3 要建的两个新分片

**`v2-dev-set`（主回归集）** —— 把 dev_set 登记成正式分片

```
v2-dev-set/
  items.jsonl        # 1933 字位，v2 id
  expected.json      # shape / reading / 来源(align|human) / 是否形近 / 语料频次
  frozen/            # 候选冻结：库 top5 + OCR top5 + 上下文 ranked
```

- **两路金标分层**：`align`（整理本自动，1,897 条，覆盖广但与 LM 同源）
  和 `human`（用户裁决，273 条，独立但只覆盖难例）。**报数必须分层**——
  拿 align 金标去验 context 通道是自证（LM 语料就是整理本）。
- 候选冻结：新算法进来时，先在冻结候选上跑（可比），再在实时候选上跑（真实）。

**`rare-char`（生僻字集）** —— 43 条起步（14 + 29），随人裁增长

```
rare-char/
  items.jsonl        # 字块 + 用户最终定的字 + 语料频次 + IDS + 是否 Unicode 有码
  expected.json      # gold char；无码字记 IDS
```

量三个数：**top-10 命中率**（L1/L2/L3 的 KPI）、**每条耗时**、
**无码率**（需要 IDS 描述而非选字的比例）。

## 4. 新算法进来时的纪律

引入 llm 策略、字体模板 kNN、IDS 护栏、部件模型，每一个都要过同一道关：

1. **先建集再动手**（handbook §3 P1）。没有验收集的算法不许接进生产路径。
2. **候选冻结**。比"算法 A vs B"时候选必须冻结，否则分不清是新算法强还是上游候选变了。
   `context-correction` 就是这么做的，照抄。
3. **报数必须成对**：gain 连 harmful_flip；精度连覆盖；准确率连分母。
4. **必须带基线**。至少三条：多数类、现行生产配置、以及"什么都不做"。
   字形层 64.3% < 瞎猜 76.0% 这个结论，只有带基线才看得出来。
5. **语料挖洞 + 打印挖了多少字**（`v2_align` 模块头的纪律）。Step6 的 LM 语料就是
   整理本，而 align 金标也从它来——不挖洞的数字一概作废，打印为 0 就是挖漏了。
6. **金标分层读**：`align` 与 `human` 分开报；`equal` 段与 `replace` 段分开报
   （equal 段恒等于当次转写，是自证，只测出必然 100%）。
7. **两路零同源证据**才能自动放行。字体模板、L3 部件模型与库匹配**同源**（都看图），
   它们之间互证不算数——这是 OCR×库 97.1% 那条老账的推论。

### 每刀的验收标准

| 刀 | 主指标 | 护栏（不许退） |
|---|---|---|
| A 整理本通道 | 人审率 7.9% → ≤2.5% | 自动放行错误率 ≤0.1%（双真值）|
| B LLM + 三方一致 | 人审率 → ≤1.5%；confusable 复现 ≥98% | harmful_flip ≤1.2%；IDS 护栏必须先上 |
| C 生僻字候选 | rare-char top-10 ≥80% | 不改变任何自动放行决定（只出候选）|
| D 读文定字 UI | 每条耗时中位 ≤3s | 裁决准确率不降（同批复裁抽样）|

## 5. 落地顺序

1. **先加 `client_ts`**（D 的一部分）——否则"每条耗时"永远没有基线，
   而这是 D 唯一的验收指标。
2. **建 `v2-dev-set` 分片**——A 刀的前后对比要靠它，且它同时补上 char-ocr 缺口。
3. A → B → C → D 按 `pipeline_review_2026-09-04.md` 的顺序做，每刀跑一次
   `scripts/survey_review_queue.py` + 上表的主指标。
4. 控制台质量看板加四个数：人审率 / 自动错误率 / 每条耗时 / 生僻字 top-10。
