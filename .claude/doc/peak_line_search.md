# 投影峰匹配找版框线（peak_line_search）

代码：`open_guji_cv/utils/peak_line_search.py`（核心算法）+
`scripts/find_border_lines.py`（CLI / 批量报告）+
`tests/test_peak_line_search.py`（合成图单测）。

跟 `border_detect.py`（LSD 检测线段 → 按共线性聚类 `cluster_lines`）是完全
不同的思路，两者目前**并存**，互不替换——`border_detect.py` 仍是
`open_guji_cv/detectors/borders.py` 用的生产算法，这份是从头设计的替代方案，
本轮只验证到 5 个样本页，还没有做全书回归，**没有接入生产管线**。

## 起因

用户想搞清楚"为什么版框上下边线一直比左右界行难找"，先让 LSD 直接探测
长直线（zero hits，横线信号被磨损/浓墨切得太碎），又试了拿生产代码的
`cluster_lines` 去拼这些碎段（能找到，但"按长度选最长簇"这个挑选规则
经常选错——真线经常排到几十名开外）。逐步倒退到最原始的信号——直接对
墨迹做逐行/逐列投影，从投影曲线本身找规律。

## 算法

### 1. 投影

竖直线（界行/左右边框）：逐列黑像素数 `mask.sum(axis=0)`。
水平线（上下边框）：逐行黑像素数 `mask.sum(axis=1)`。

### 2. 半高宽匹配度——不是滤波，是"这个点自己的峰有多宽"

最早尝试了两种思路，都不理想：

- **加权卷积**（中间 3 列正权重、两侧负权重的 9×9 核）：能压出一点信号，
  但效果不稳定，用户反馈"不太好"。
- **固定宽度的匹配滤波核**（37px 宽、零和、中心正两翼负）：跟真值格线
  对得上，但**区分度不够**——文字笔画偶然对齐也能打出接近真线的分数，
  而且核宽是猜的，磨损程度不同的页面需要不同的核宽，通用性差。

**最终方案**：对投影曲线上每个点 x，用它**自己的值**当基准，向左右各走，
走到跌破自身一半（`alpha=0.5`）的位置为止（容忍 `<hyst=3` 个点的小凹陷，
不算真跌出——笔画间的细缝不该打断峰）。两个边界之间的距离是"半高宽"。

```
匹配度 = 投影值 ÷ 半高宽
```

界行/边框：又高又窄，半高宽 4~9px，比值大（真实测试里普遍 200~500）。
正文列：投影值也不低，但半高宽 80~100px（正文列宽的量级），比值被拉得
很低（普遍个位数到十几）。**这个宽度是每个点现算的，不用猜"这条线该多宽"**
——这是相对固定核宽方案的关键优势。

调过一次参数（α 0.5→0.3，容忍度 3→4，让判定更"宽松"），结果**区分度反而
变差**：真线分数普遍跌 20%~77%，正文列驼峰只跌 10%~15%（宽的东西对阈值
放宽本来就不敏感），安全边际从 1.88× 掉到 1.16×。**结论：保留 α=0.5,
hyst=3**，除非以后有专门针对更破碎页面的理由。

### 3. 位置 + 角度联合搜索——一个真踩过的坑

版框线可能有微小倾斜（原稿本身、或裁切引入的残余倾斜）。单纯竖直/水平
投影会把斜线的峰"拖宽拖低"，用户提议"逐候选点搜索小角度"来救。

**第一版实现有 bug**：把峰的位置锁死在最初粗投影找到的 x₀ 上，只搜角度。
在 vol02/133 上，x=33、x=216 这两条线固定位置搜角度怎么都救不回来（最佳
倾角=0°，分数纹丝不动），一度被误判为"这两条线本来就弱，跟角度无关"。

用户看出问题："不应该只算这两个点，是这两个点周围一小段坐标都倾斜后计算，
最佳点可能移动，甚至要考虑移出页面以外"——峰的真实锚点会随倾角挪动，
锁死位置等于把最优解排除在搜索范围外。放开位置后：

- x=33 → 联合最优在位置 21、倾角 +0.84°，匹配度从 26.9 冲到 403.5
- x=216 → 联合最优在位置 206、倾角 +0.67°，匹配度从 24.4 冲到 404.1

两条线本来都不弱，是方法有缺口。原图叠加验证：新找到的斜线确实比旧的
竖直线更贴着真实墨迹走，不是凑出来的假峰（热力图上超过最高分一半的
格点只占 0.05%，是孤立尖峰）。

**位置搜索窗口不能任意宽**：宽度超过跟相邻真线的距离就会被更强的邻居
"劫持"（试过 ±260px 的宽窗口，两个候选都收敛到了别的候选自己的真线上）。
`find_vertical_lines` 用相邻候选的中点自动切窗口；手动调用
`joint_search_coarse_to_fine` 时窗口范围由调用方自己控制。

### 4. 性能优化（用户要求"先大步再小步"）

两处优化，實測 vol02/133 单条线联合搜索从 5~11s 降到 ~2s：

1. **只在局部极大值上算半高宽分数**——半高宽算法本身要沿曲线走，
   是这套方法里最贵的一步；不用扫窗口里每个位置，只在投影曲线自己的
   局部极大值（`radius=2` 内自己最大）上算，非峰值的点不可能是答案。
2. **角度先粗后细两段扫**：先粗扫一个较窄的范围（默认 ±2.9°，35 档）
   定位大致方向，再在附近精扫（默认 ±0.34°，25 档）。**踩过的坑**：
   最早想"粗扫用大范围（±16.7°）+ 粗步长"，结果因为真实的角度峰在
   slope 空间上相当窄（半高宽通常 &lt;0.01），粗步长 0.05 直接跳过了
   真正的峰，收敛到完全错误的角度/位置（分数从该有的 158.8 掉到 74）。
   **教训：粗扫范围可以窄，但步长必须细到不会跳过窄峰**——不能靠"先宽后
   窄"简单地想当然，两段的分辨率都要验证过河图才行。

### 5. 自动整页入口

`find_vertical_lines(mask, expected_count=N)`：先用整页粗投影 + 半高宽
全扫找候选峰（NMS 去重，`min_dist` 默认 60px——太小会把同一条线的相邻
局部峰重复收进来），再对每个候选做位置+角度联合精搜。`expected_count`
可选（跟 `border_detect.py` 的 `expected_cols` 用法一致）：候选数超过
预期时按分数只留最高的 N 条，比猜一个通用阈值稳（本轮 90 分位阈值 +
`min_dist=15` 曾经在 vol02/133 上收出 24 个候选，其中不少是文字笔画噪声）。

`find_horizontal_border(mask, side)`：只在页面顶/底 `band_frac`（默认
15%）窄带内找最强峰。

## 意外发现：vol02/133 底部边框，管线自己的检测偏了 41px

水平方向搜索时，底部区域最强响应根本不在 `border_detect.py` 生产算法
算出的 `inner_frame.bottom≈2363.9` 附近，而是在 **y≈2405**（差 41px，
匹配度 242.4）。原图叠加验证：管线声称的位置正好切在字身中间，真正的
版框线在字下面 40px 处清清楚楚一条横线。

这个发现最早是本轮调查最开始那张最原始的"逐行黑像素投影"图就看到的
异常尖峰（当时换算 y≈2406），当时只是标记疑点没深究；这次用严谨的
半高宽 + 位置角度联合搜索方法重新核实，两次结果几乎一致，不是巧合。
**这条线很可能是这页真正的版框下边，`border_detect.py` 在这一页上系统性
偏移了 41px**——跟本轮调查最初想解决的"浓墨粘连截断"问题很可能有关，
但这份文档止步于"发现"，还没有把这个修正接回生产管线（那需要在更多
页面上验证这个偏移是不是普遍现象，而不只是 vol02/133 这一页的巧合）。

### 已知局限一：抬头页顶部边框判断错——用户预判命中

vol01/33 是"抬头"页：部分列的正文比其他列起始得更高（敬语抬头的排版
惯例），这几列的顶端还画了一个小方框（把抬头字框起来）。这个小框的
黑色边线本身也会在顶部投影上打出一个强峰，跟真正贯穿全页 9 列的版框
顶边混在一起——算法找到的 y=212 大概率是"大多数**没有**抬头的列开始
排正文字"的位置，而不是版框顶边线（真值 y≈38，跟小框的位置更接近）。

这是用户在交代任务时就预判到的："我估计抬头的那个会出问题"——预判命中。
**当前版本没有处理这个情况**，顶部边框搜索窗口目前是"页面顶部 15% 高度"
一刀切，不区分抬头框和主边框。后续如果要修，方向是：先identify 哪些列
抬头（复用之前 `head_raise_rows` 的思路），把抬头列的顶部小框排除在
主边框搜索窗口外，或者干脆分开报告"主边框"和"抬头框"两条线。

### 已知局限二：职名页顶/底边框搜出退化结果（宽度=1px，卡在窗口边界）

vol01/90 的顶部/底部搜索都落在图像的绝对边界（y=0 或 y=h-1），宽度
退化成 1px。看原图：这一页顶部裁切之后**紧贴着正文字的顶端**，没有留出
明显的版框线/空白margin——大概率是 s3 裁剪步骤本身在这张职名页上把边框
一并裁掉了（职名页跟正文页的裁剪行为可能不一致，这类页面之前就有过
"钉桩然后微调"式的专项处理，参见 `char_clustering_design.md`）。也可能
这一页原始扫描就没留白边。**这不算是本算法的 bug**——投影本身找不到
真正的边框信号（因为输入图像里可能根本没有），退化结果是"没找到"的
一种（不太理想的）表达方式，比"假装找到了一条自信满满的假线"要好一些，
但更好的做法是显式判定"分数/宽度落在窗口边界 → 报告为未找到"而不是
返回一个看起来正常的 `LineMatch`。当前 `scripts/find_border_lines.py`
的报告页会把宽度 ≤2px 的结果标红提示，算是权宜之计。

## 用法

```bash
# 单页，只打印结果 + 存一张叠加图
PYTHONIOENCODING=utf-8 python scripts/find_border_lines.py page.png \
    --expected-cols 9 --out overlay.png

# 批量几页，出一份汇总报告（HTML，可发布成 Artifact）
PYTHONIOENCODING=utf-8 python scripts/find_border_lines.py \
    --pages vol02/133:9 vol02/135:9 vol01/33:9 vol01/90:9 vol01/171:9 \
    --root <s3裁剪产物根目录，跳过s4增强> --report report.html
```

**必须用跳过 s4 直线增强的产物**（`skip_steps=["enhance_lines"]`）——早前
对比过带增强 vs 不带增强的检测结果，enhance_lines 能把内边框位置挪动
最多 96.6px（vol01/33），这个量级足以让本算法的搜索窗口假设（跟相邻真线
中点切窗口）失效。
